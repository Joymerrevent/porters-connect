## 1. 課題（Problem Statement）

PORTERS Connect API は**レスポンスが XML 専用・OAuth が独自仕様・UTC 前提・削除 API なし・レート/サイズ制限あり・項目がテナント毎に動的**と癖が強く、連携開発のたびに各社が `fetch` + XML パースを手書きしている（再利用可能な TS/JS ラッパーは公式・非公式とも存在しない）。
結果、**実装コスト・バグ・保守負債**が連携案件ごとに発生し、ポーターズ社にも「利用者コード起因の問い合わせ」が回る。

## 2. 北極星とゴール（Goals）

**北極星: デファクト（第一想起）** — 「PORTERS Cloud API で開発するなら porters-connect を使うのが常識」になること。利用者“数”ではなく“第一想起”を成功と定義する。

ゴール（成果ベース）:

1. **連携実装の立ち上げを劇的に短縮**: 認証〜最初の型付き取得までを「ドキュメントを見ながら数十分」で到達できる。
2. **公認に値する品質**: ポーターズ社が「紹介してよい」と思える＝**上限内に自制する**・**機密情報を漏らさない**・サポート負荷を増やさない。
3. **契約前でも評価できる**: 実 API 契約が無くてもモックで動作確認・学習・テストができ、採用検討の入口に立てる。
4. **壊れにくく、壊れても安全**: フェイルセーフ（想定外でも被害を広げない）を既定動作にする。
5. **受託・社内開発の現場で実際に採用される**: ブログ流入 → 試用 → 実案件採用、の導線が成立する。

> **用語の変更（2026-09-12）**: 2 つ言い換えた。**どちらも要件の内容は変えていない。**
>
> - 目標2 と R-7 の「**良き API 市民**」（good API citizen の直訳で、日本語としては何を約束して
>   いるのか伝わらない）→「**上限内に自制する**」
> - 目標2 と R-11 の「**秘匿情報**」→「**機密情報**」。機密情報が標準的な語で、秘匿は「隠す」
>   という行為に重心がある（法務の「秘匿特権」など特定の文脈の語）
>
> 既存の ADR（[0010][adr10]・[0012][adr12]・[0025][adr25]・[0034][adr34]・[0047][adr47]・
> [0048][adr48] ほか）は旧称のまま参照している — 決定の記録なので書き換えない。

## 3. 非ゴール（Non-Goals）

- **第2層 MCP サーバー**: 価値は大きいが第1層安定後（別フェーズ）。v1 では設計余地だけ残す。
- **第3層 配布（Docker / npx 専用体験）・CLI**: 後続。
- **実行時 i18n（多言語ロケール切替）**: バックエンドが日本縛りのため過剰。公開サーフェスの英語化のみ行う。
- **削除機能**: API に存在しない。`delete()` を型レベルでも生やさない。
- **MVP 外リソース**（Recruiter / Contact / Activity / Contract / Sales / Opportunity / Phase の Write 等）: v0.2 以降で段階追加。
- **GUI・ホスティング型サービス・スクレイピング**: スコープ外。
- **PORTERS 公式 SDK の置換主張**: あくまで**非公式**ラッパー。

## 4. 利用者像（Personas）

- **P1 受託開発者 / フリーランス / 制作会社（主）**: 人材会社から API 連携を受託。短納期・型安全・自己解決できるエラーを重視。**国内・日本語**。
- **P2 人材会社の社内エンジニア（副）**: 自社サイト⇔PORTERS 連携を内製。継続保守する立場。
- **（将来）AI エージェント**: 第2層 MCP 経由。v1 では視野に入れるが対象外。

## 5. ユーザーストーリー（User Stories）

受託開発者（P1）:

- 受託開発者として、**`PortersClient` を host/appId/appSecret/scope で初期化**したい。XML や OAuth の独自仕様を意識せず使い始めるため。
- 受託開発者として、**`porters.candidate.search(条件)` / `get(id)` が型付きオブジェクトで返って**ほしい。XML パースを書かずに済むため。
- 受託開発者として、**作成/更新を型付き入力で行い、XML を自分で組み立てたくない**。`P_Id=-1`/更新の作法やネスト XML を隠してほしいため。
- 受託開発者として、**200 件超の取得を自動ページングで**取りたい。1 リクエスト 200 件制限を意識せず全件処理するため。
- 受託開発者として、**失敗時に「何が・なぜ・どう直すか」が分かる型付きエラー**がほしい。ポーターズに問い合わせず自己解決するため。
- 受託開発者として、**契約環境が無くてもモックで動かして学習・テスト**したい。採用可否を判断するため。

社内エンジニア（P2）:

- 社内エンジニアとして、**レート制限・リトライ・サイズ制限をライブラリが面倒を見て**ほしい。深夜バッチが API を痛めず安全に回るため。
- 社内エンジニアとして、**日時が ISO 8601（タイムゾーン明示）で曖昧さなく**返ってほしい。自分のタイムゾーン表示は自前で行うため。
- 社内エンジニアとして、**テナント固有のカスタム項目（`U_`/`A_`）も扱える**ようにしたい。自社のカスタム項目を読み書きするため。
- 社内エンジニアとして、**対応 PORTERS / API バージョンが明記**されていてほしい。アップデート追従を判断するため。

## 6. 要件（Requirements）

### Must-Have（P0）— これが無いと v1 として成立しない

- **R-1 認証（OAuth）**: `code_direct`（サーバ間）でのトークン取得、Access Token のキャッシュと**自動リフレッシュ**、Refresh も失効した場合は自動で `code_direct` 再取得（再認証が本当に必要なとき＝`code_direct` 自体が失敗したときのみ判別可能な `PortersAuthError`・ADR-0036）。初回の `code`（ブラウザ権限付与）は前提手順として**ドキュメント化**。トークンは差し替え可能なストア（既定インメモリ）。
  - 受入: 有効な資格情報で `search` が成功／Access Token 失効時に自動更新され処理継続／Refresh 失効時は自動で `code_direct` 再取得して処理継続し、`code_direct` 自体が失敗したときに判別可能な再認証エラー（`PortersAuthError`）を返す。
- **R-2 型付きクライアント**: `new PortersClient({ host, appId, appSecret, scopes, ... })`。公開 API は `src/index.ts` から明示 export。
- **R-3 リソース操作（MVP）**: Candidate / Job / Client / Process / Resume / Attachment の **Read（search/get）と Write（create/update）**、および必要なマスタ Read（Partition / User / Field / Option）。**delete は提供しない**。
  - 受入: 各リソースで型付き search/get/create/update が動作（モック XML で検証）。削除メソッドは型に存在しない。
- **R-4 XML の隠蔽**: レスポンス XML → 型付きオブジェクトへ内部変換。Write は型付き入力 → XML を内部生成。**XML を外に漏らさない**。Option/参照/User のネストを正規化（**Link/Image の正規化は v1 では未対応・deferred**＝ADR-0033 案F／roadmap 参照）。
- **R-5 検索条件の型付き表現**: `field` / `condition`（型別 suffix）/ `order` / `keywords` / `itemstate` / ページング（`start`/`count`）を型で表現。
- **R-6 自動ページング**: `Total`/`Count`/`Start` を用い、200 件刻みで全件・逐次取得するヘルパー（暴走防止の上限/イテレータ）。
- **R-7 レート上限の自制 & リトライ（フェイルセーフ）**: 1 分 Read 2000 / Write 500 を**自前スロットリング**で超えない（429 は返らない前提）。リトライ可能（Result Code `9`/`302`・ネットワーク）のみ指数バックオフで再試行、入力エラー（`100`系）は再試行しない。
  - 受入: 上限超で自動的に待機・分散する／一過性エラーは再試行し、確定的エラーは即座に判別可能エラーを返す。
- **R-8 リクエストサイズガード**: 全体長 ~15000 字を超える送信を**事前検知して警告/分割**（将来 16KB 化に追従可能に）。
- **R-9 構造化エラー（判別可能 union）**: 認証系とリソース系の**2 系統**を吸収。`category`（auth / permission / rateLimit / validation / network / transient / unknown ほか。**最終分類は ADR-0006 の 11 種**）・PORTERS の生コード・対処ヒントを持つ。**既定メッセージは英語**、ローカライズは利用側に委ねる。
  - 受入: 例外型/結果型から `category` と原因コードで分岐できる。
- **R-10 日時の表現（ISO 8601・タイムゾーン非変換）**: PORTERS の `yyyy/mm/dd HH:MM:SS`（UTC 扱い）/ `yyyy/mm/dd`（日付）を
  **ISO 8601 に正規化して入出力**する（DateTime は UTC 明示＝`...Z`、Date は日付のみで `Z` を付けない）。
  **JST 等の業務タイムゾーン変換は行わない（利用側の責務）**。Write でオフセット付き ISO を受けたら UTC に正規化して PORTERS 形式へ。`util/datetime` は「PORTERS 形式 ⇄ ISO の正規化」を担う。
  - 受入: 取得した DateTime が `...Z` の ISO で返る／オフセット付き ISO を渡しても UTC 化されて送信される／日付のみ項目は日付文字列で扱える。
- **R-11 機密情報を漏らさない**: App ID/Secret/トークンを**ログ・エラー・スナップショットに出さない**。設定は環境変数/引数から受け取り、リポジトリにコミットしない（`.env.example` のみ）。
- **R-12 差し替え可能なトランスポート（モック）**: HTTP 層を注入可能にし、**契約なしでもモック XML で全機能をテスト/評価**できる。ライブラリ自身のテストもこれで行う。
- **R-13 型安全の徹底**: 公開サーフェスに `any` を撒かない。リソース・スコープ・レスポンスを型で表現。
- **R-14 ランタイム/配布**: TypeScript(strict) / ESM / Node 22.12+ / MIT（CJS からは `require` 条件で同じ ESM 実体を読む・[ADR-0082][adr82]）。`X-P-ConnectAPI-Version: 2` を既定送信し、**対応 PORTERS / API バージョンを README・コードに明記**。
- **R-15 言語方針**: 公開サーフェス（型名・メソッド名・public JSDoc・エラー既定文）は英語、内部コメントは日本語可。**README/docs は日本語ファースト**。

### Nice-to-Have（P1）— あると強いが核は無くても回る

- **R-16 動的カスタム項目**: 標準 `P_` は同梱の静的型、テナント固有の `U_`/`A_` は**利用者がフィールド定義を宣言 → 型導出＋実行時検証**で型安全に扱う（ハイブリッド）。`Field Read` からの宣言生成は将来の opt-in dev ツール。方式は ADR-0004 で決定。
- **R-17 評価用サンドボックス**: 契約前の評価を狙った、すぐ動く offline クイックスタート/サンプル（モック前提）。GTM の評価可能性レバー。
- **R-18 自己解決を促すドキュメント**: 日本語の「よくあるエラーと対処」（Result Code・認証エラーの 2 系統対応表つき）。サポート肩代わり。

### Future Considerations（P2）— v1 では作らないが設計で潰さない

- 第2層 MCP（公開ツール `search_candidates` 等）。第1層を内部呼び出しするだけにできる API 設計にしておく。
- MVP 外リソースの全 R/W、CLI、Docker 配布、公開プレイグラウンド。
  （**CJS 出力は P2 から外れた** — 別実体は配らず `require` 条件で解決する形に決着・[ADR-0082][adr82]）

## 7. 成功指標（Success Metrics）※採用・普及の量に数値目標は置かない（[ADR-0084][adr84]）

市場が小さい（実需は数十〜百数十社規模の推測）ため、**量より“デファクトの兆候”をマイルストーンで**測る。
**採用・普及の量には数値目標を置かない**（[ADR-0084][adr84]）— 唯一の量的チャネルである npm の
ダウンロードは**ミラーと CI の取得が支配的**（publish 日に山が立ち、間の日はほぼ 0）で、実利用者が
数社に増えても数字が動かない。**ノイズに目標を置けば、達成・未達のどちらの判定も嘘になる。**

### 先行指標 — 自分で測れるので数値のまま

利用者がゼロでも測れて、しかも品質を直接動かすもの。

| 指標                         | 扱い                                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------------ |
| **Time-to-first-typed-call** | **数値**（暫定 30 分以内。**機械時間 5 秒は実測済み・読む時間は未計測**）            |
| **評価可能性**               | **YES/NO**。契約なしで評価できるか＝ CI の `pnpm sandbox` が緑なら YES（機械で出る） |
| **ドキュメント自己解決率**   | 定性。「よくあるエラー」で解決できる主要エラーの網羅                                 |

**Time-to-first-typed-call の測り方**（契約の有無で別物なので 2 経路）:

|            | 契約なしの経路                                                                                                                                | 契約ありの経路                                                                              |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 手順       | まっさらな Node プロジェクトで `npm i` →[契約なしでテストを書きたい][test-wo]に沿って `createMockTransport` で型付き `search` が 1 本通るまで | `npm i` →[前提][s-prereq] →[認証][s-auth] →[はじめての読み取り][s-read]で実データが返るまで |
| 測り方     | **人が 1 回通しで実行して時計で測る**（読む時間が支配的なので自動化しない）                                                                   | 同じ                                                                                        |
| いつ       | リリース前に 1 回                                                                                                                             | 契約取得後（[ライブ検証][lv]と同じ棚）                                                      |
| 結果の扱い | 実測値で暫定 30 分を置き換える。**超えたら入門の手順を削る**                                                                                  | 同じ                                                                                        |

**実測（2026-09-18・公開版 0.19.0・契約なしの経路）— 機械が動く時間だけ**:

| 段階                                            | 所要                                   |
| ----------------------------------------------- | -------------------------------------- |
| `npm i @joymerrevent/porters-connect`           | 2 秒                                   |
| TS ツールチェーン（`typescript` + `tsx`）の追加 | 2 秒（**既に TS プロジェクトなら 0**） |
| `tsc --noEmit`                                  | 1 秒                                   |
| 実行（型付き `search` が 1 件返る）             | 1 秒未満                               |
| **合計**                                        | **約 5 秒**（TS 導入を除けば約 3 秒）  |

あわせて分かったこと: [契約なしでテストを書きたい][test-wo]のスニペットは**公開版に対して無修正で動いた**
（公開パッケージで入門経路を通したのは初）。わざと壊した 2 行はコンパイルエラーになり、**型が効いている**
ことも確認した（消費者側 `module: nodenext` で解決）。

**読む時間は測っていない。** 読む量は[インストール][s-install] 1822 字 ＋ [当該ページ][test-wo]の
最初の型付き取得まで 547 字。**機械時間が 5 秒ということは、この指標のボトルネックは 100% 読む時間**なので、
**暫定 30 分は人が通しで歩いて測るまで据え置く**（機械時間で置き換えると嘘になる）。

### 遅行指標 — 0/1 のマイルストーン

**何をもって 1 とみなすか**と**どこを見るか**を決めてある（曖昧だと「兆候」が主観になるため）。

| マイルストーン   | 何をもって **1** とみなすか                                                   | どこを見るか                               |
| ---------------- | ----------------------------------------------------------------------------- | ------------------------------------------ |
| **実案件採用**   | 「実案件で使っている」と分かる連絡が 1 件（Issue / PR / 直接連絡 / 公開事例） | GitHub・問い合わせ                         |
| **流入→試用**    | 流入元に**ブログ等の外部ドメイン**が出る                                      | `gh api repos/…/traffic/popular/referrers` |
| **ベンダー言及** | ポーターズ社の公開物に本ライブラリへの言及が出る                              | 人が確認                                   |
| **品質シグナル** | **外部からの Issue / PR が 1 件**来る（Dependabot を除く）                    | GitHub                                     |

> ⚠️ **GitHub の traffic は直近 14 日ぶんしか残らない**（取得には push 権限が要る）。見に行かなければ
> 消えるので、**定期レビュー（`project-review`）でスナップショットに控える**手順にしてある。

## 8. オープン論点（Open Questions）

> 決着したものは**消さずに「（解決済み）」を付けて残す**（判断の経緯を保つ）。実機がないと確定しない項目は
> [live-verification][lv] へ移す。**2026-08-09 時点で本当に未決なのは 2 件**（成功指標の数値化タイミング・CJS 出力）。
> **2026-09-18 に両方とも決着し、未決は 0 件になった**（CJS は [ADR-0082][adr82]、成功指標は [ADR-0084][adr84]）。

- （解決済み）成功指標の**数値化のタイミング** — [ADR-0084][adr84] で決着（2026-09-18）。
  実測したら**ベースラインとみなせる実利用が 1 件も無く**（DL はミラー由来／star 1／外部の Issue・PR 0）、
  **置ける数値が無い**と分かった。採用・普及の量に数値目標は置かず、**0/1 のマイルストーン**で測る。
  自分で測れる先行指標（Time-to-first-typed-call・評価可能性）は数値のまま残す（§7）。
- （解決済み）**サンドボックス(R-17)** は **P1 のまま出荷**して決着（[ADR-0024][adr24] の `createMockTransport` ＋ `pnpm sandbox` を v0.1.0 に同梱）。P0 への引き上げは不要だった。
- （解決済み）**対応 PORTERS / API バージョン表記**は [ADR-0042][adr42] で確定＝**Connect API Version を契約の正**（`X-P-ConnectAPI-Version: 2` 前提）、製品 8.x/9.x は参考情報。
- （解決済み）v1 で **CJS 出力**まで出すか — [ADR-0082][adr82] で決着（2026-09-18）。**別実体は配らず**、
  `require` 条件を同じ ESM 実体に向ける（Node の `require(esm)`）。あわせて `engines.node` を `>=22.12.0` に上げた。
- （移送）**1 つの App トークンで複数 partition を叩けるか** は実機でしか確定しないため、[live-verification][lv] **LV-13** に移した（`tenant(id)`／F-3 が同一トークンのまま partition を差し替える実装＝この仮定の上に立つ）。設計は両対応なのでリリースはブロックしない。
- （解決済み）トークンストア・初回 code グラントの扱いは ADR-0007 で確定。
- （解決済み）**npm スコープ/組織** `@joymerrevent` / GitHub `Joymerrevent` は確定（`@joymerrevent/porters-connect` を 0.6.2 まで公開済み・README の「非公式」「契約必須」注記も整備済み）。

## 9. フェーズ計画（Timeline / Phasing）

実装は MVP リソース順に縦切りで進める（各段でモック XML テスト）。

1. **PoC**: OAuth（code_direct）＋ Candidate Read を型付きで実証（モック）。コア層（HTTP/XML/エラー/スロットリング/日時）の最小実装。
2. **MVP コア**: Candidate の Write、Job / Client / Process / Resume、Attachment（ファイル）。自動ページング・サイズガード・構造化エラーを通す。
3. **仕上げ**: 日本語 docs（よくあるエラー）・サンドボックス（R-17）・カスタム項目（R-16）・README（対応バージョン/非公式/契約必須）。

> 実 API 接続は契約環境が用意できてから PoC で検証。それまでは [docs/usage/reference][ref] の XML 例を fixture にする。
