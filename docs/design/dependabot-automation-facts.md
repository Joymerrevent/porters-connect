# Dependabot 自動化 — 設計の前に確かめた事実

この文書は**設計判断を含まない**。Dependabot 依存更新の自動化を設計し直すにあたり、
**確かめずに前提にしていたもの**を実測で潰した記録である。

## なぜこの文書があるか

[ADR-0065][adr65]（`update-branch` してから CI の緑を待つ）と [ADR-0066][adr66]
（`update-branch` をやめて develop の push CI に検証を移す）は、**どちらも実装後に前提が崩れた**。
崩れ方は同じで、**「`GITHUB_TOKEN` が CI を起動できる」を確かめずに前提にしていた**。

ADR-0065 の冒頭には「調査で確かめた事実」の表があったが、**そこに `GITHUB_TOKEN` の行が無かった**。
設計の前に事実を並べる手順自体はあったのに、並べる項目を取りこぼした。同じ失敗を繰り返さないため、
次の設計はこの文書を入口にする。

## 1. `GITHUB_TOKEN` の書き込みと CI の起動

**現れ方が 2 通りある。** 「起動しない」と一括りにすると設計を誤る。

| 書き込み                                       | 主体                  | run が作られるか       | 実行されるか                     | 実測                                             |
| ---------------------------------------------- | --------------------- | ---------------------- | -------------------------------- | ------------------------------------------------ |
| `push`（develop へマージ）                     | `github-actions[bot]` | **作られない（0 件）** | —                                | `068c080`：run 0 件・check-runs 0 件             |
| `push`（develop へマージ）                     | 人                    | 作られる（3〜4 件）    | 実行される                       | `2502c2b` 3 件 / `30f54a3` 4 件 / `f9ce172` 4 件 |
| `pull_request`（`update-branch` で head 更新） | `github-actions[bot]` | **作られる（5 件）**   | **`action_required` で承認待ち** | `383bf69` / `d02e800` とも 5 件                  |
| `push`（PR ブランチへ）                        | `dependabot[bot]`     | 作られる               | 実行される（ゲート無し）         | `e9cec71` 8 件 / `5d7e280` 6 件 / `21c3689` 6 件 |

**設計に効く点:**

- `GITHUB_TOKEN` でマージすると、**マージ後の状態を検証する CI がどこにも走らない**。
- `GITHUB_TOKEN` で `update-branch` すると、CI は**人の承認を待って止まる**。
- **dependabot 自身の push は正常**。PR 単独の CI は問題なく動く。

## 2. 承認ゲートは毎回かかる

「一度承認すれば以降は素通りするのでは」を検証し、**否定した**。2 回目の `update-branch`
（`d02e800`）でも人が手で承認しており、承認なしでは走らなかった。

**判定方法の注意（一度誤った）:** 承認された run は **conclusion が `success` に上書きされる**ため、
最終状態だけではゲートを通ったか判別できない。見るのは `created_at` と `run_started_at` の差。

| head                | run 作成 | 実際の起動         | 差                          |
| ------------------- | -------- | ------------------ | --------------------------- |
| `383bf69`（1 回目） | 05:29:03 | 06:16:36〜06:17:13 | **約 47 分**（承認まで）    |
| `d02e800`（2 回目） | 06:30:50 | 06:31:10〜06:31:44 | 20〜54 秒（承認直後の起動） |

## 3. dependabot の rebase は当てにできない

`.github/dependabot.yml` に `rebase-strategy` の指定は無い（既定 `auto`）。だが**実績は限定的**で、
base が動いても自動で rebase されるとは限らない。

| PR                                      | force-push（＝rebase）回数 |
| --------------------------------------- | -------------------------- |
| #222 / #221 / #220 / #191 / #190 / #188 | **0 回**                   |
| #175 / #174                             | 1 回                       |

**設計に効く点:** 「競合したら dependabot が作り直してくれる」を自動の回復手段として当てにできない。
`@dependabot rebase` を明示的に依頼する経路が要る。

## 4. 依存 PR の量と滞留

直近 100 PR のうち dependabot 発は **12 件**（約 4 週間分）。滞留は**多くが 0〜1 日**。

| PR          | 作成       | 滞留                 |
| ----------- | ---------- | -------------------- |
| #222        | 2026-09-04 | 1 日（マージ済）     |
| #221 / #220 | 2026-09-04 | **open・2 日経過**   |
| #191 / #190 | 2026-08-28 | 1 日                 |
| #188        | 2026-08-23 | 0 日                 |
| #175 / #174 | 2026-08-21 | 1 日                 |
| #173        | 2026-08-21 | 1 日（未マージ）     |
| #160        | 2026-08-14 | **6 日**（未マージ） |
| #154 / #153 | 2026-08-12 | 0 日                 |

**設計に効く点:** 週 3 件程度で、放置は例外的。**自動取り込みが省くのは「クリック 1 回」であって、
滞留の解消ではない**。ADR-0065 が挙げた価値は「毎回同じ深さで検査する」ことと
「やろうと思い出すコスト」で、取り込みの自動化はその一部でしかない。

## 5. 検証を自前で走らせる場合の所要時間

`ci` job の実測（`ubuntu-latest`）。**マージ後の状態をその場で検証する案の費用見積もり。**

| ケース                         | job 全体  | 内訳（2 秒以上）                                          |
| ------------------------------ | --------- | --------------------------------------------------------- |
| docs のみ（コード検査を skip） | **36 秒** | Lint 10 / Format 7 / pnpm setup 4                         |
| コード変更あり                 | **64 秒** | Lint 10 / Test 10 / Format 8 / pnpm setup 8 / Typecheck 5 |

`pnpm install --frozen-lockfile`（ロックファイル破損が出るステップ）は 2 秒未満（store キャッシュ有効）。

## 6. リポジトリ設定

| 項目                                     | 値                                    | 確認方法                                 |
| ---------------------------------------- | ------------------------------------- | ---------------------------------------- |
| `develop` の必須チェック                 | `ci` / `stryker`                      | `gh api .../branches/develop/protection` |
| `develop` の `strict`（base 鮮度の要求） | `false`                               | 同上                                     |
| 必須レビュー数                           | 0                                     | 同上                                     |
| develop への push で走るワークフロー     | `CI` / `CodeQL` / `Mutation` / `Test` | 各 `on.push.branches`                    |
| `ci.yml` の `workflow_dispatch`          | **無い**                              | `on:` に未定義                           |

## 未検証・未特定

設計では**これらを前提にしない**こと。必要なら先に確かめる。

- **承認ゲートの正体。** Settings → Actions → General のどの項目が効いているか未特定。
  public リポジトリでは REST API から読めなかった。**外せるのか、外すと何が緩むのかが不明。**
- **`workflow_dispatch` を `GITHUB_TOKEN` で叩いた場合に run が作られるか。** 未実測。
  `push` と同じ抑止がかかる可能性がある。
- **PAT / GitHub App を使った場合の実挙動とコスト。** 未実測。Scorecard への影響も未評価。
- **`pull_request` の `action_required` が dependabot PR 固有か、全 PR 共通か。** 未実測。

## この事実が設計に課す制約

決定ではなく、**満たさなければならない条件**として:

1. **`GITHUB_TOKEN` でマージするなら、検証は「CI が自動で走る」に依存できない。**
   同じ job の中で検証するか、別 identity を使うか、人がマージするかのいずれか。
2. **`update-branch` を `GITHUB_TOKEN` で行う設計は成立しない。** 承認が毎回要る。
3. **競合の自己回復を dependabot の自動 rebase に頼れない。**
4. **取り込みの自動化が省くのは 1 日あたり数分の手作業**。複雑さと引き合うかを設計時に問うこと。
