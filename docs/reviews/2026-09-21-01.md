### 1. API 忠実性 — 🟢 [RV-55][rv55]

**突き合わせたもの**: 0.20.0 の 2 実装を出典と 1 項目ずつ。

**Department**（`src/resources/department.ts`）は [reference][ref-dept] と完全に一致した:
6 項目の alias・Data Type（`P_Hidden` / `P_SortNo` は Number、登録日・更新日は System[DateTime]）、
`field` 省略時に PORTERS が `P_Id` しか返さない仕様に対して**カタログ全 6 項目を既定送信**
（[RV-1][rv1] の教訓）、`request_type` / `condition` / `get(id)` を**出さない**（出典が挙げないものは
公開しない）、スコープは `user_r`（`department_r` は存在しない）、Write API 無し。
UT の fixture は出典のサンプル（記事 43464258000793）そのもの。6 項目を一度に `field` に並べて
通るかは [LV-30][lv] として登録済み。

**時分型**（`src/util/time-of-day.ts`）は出典の規則（`09:00` → `1970/01/01 09:00`、
`26:00` → `1970/01/02 02:00`）と encode 側が一致し、`24:00` を 2 日目 `00:00` に置くのも出典どおり。
**気づいた経緯**: 「Read で取れた値を Write に戻せるか」を追って decode ⇄ encode の往復を見たところ、
[ADR-0086][adr86] 論点3「**両方向とも**検証する」に対して decode 側は基準日しか見ておらず、
1 日目の wire 時 24〜47・分秒 60 以上が通って**別の wire 値に往復する**ことを実測した。
**重要度を 🟢 にした根拠**: ライブラリ自身の Read 経路（`portersDateTimeToIso` → `Date.parse`）は
不正な時分を弾くので、Read 値をそのまま渡す限り届かない。届くのは手組みの ISO だけ。
**退けた解釈**: 「`Date.parse` が 1 日目の `24:00:00` を通すから Read 経路でも起きる」— 起きるが、
`"24:00"` と読むのは時計として正しく、再 encode は出典の正規形に落ちるので**害が無い**。

**もう 1 つ確かめたこと**: [ADR-0085][adr85]「値が要素名になる境界すべて」が実装で網羅されているか。
`src` で動的にタグを組む箇所は 8 つあり、呼び出し側の値が名前になるのは `encode.ts` の 2 つ
（Option の選択肢 alias・Write の項目 alias）だけで、どちらも `assertTagName` を通る。残る 6 つ
（`bulk-write.ts` の resource 名・`attachment.ts` の固定タグ・Image の 3 サブタグ・`buildWriteXml` の
resource 名）は**ライブラリの定数**。境界の数え漏れは無い。
