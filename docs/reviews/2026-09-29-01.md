### 1. API 忠実性 — 🟡 [RV-158][rv158]

**突き合わせたもの**: `reference/authentication-api/token.md`・`oauth.md`・`errors.md`、`reference/resource-api/README.md`・
`result-codes.md`・`write-format.md`・`field-data-types.md` の表と、`src/http/`・`src/auth/`・`src/xml/`・`src/accessor/` の
読み書きの経路を 1 行ずつ。一致を確かめたもの:

- **OAuth**: トークンは `X-porters-hrbc-oauth-token`（`http/requester.ts:34`）、`X-P-ConnectAPI-Version` も同じ場所で付ける。
  `code_direct` は `GET /v1/oauth?app_id&response_type=code_direct`（`auth/default-token-provider.ts:70-74`）で、
  `redirect_url` / `scope` を付けない（正典どおり）。ブラウザの URL は `scope` をカンマで区切る（`auth/auth-api.ts:109`）。
  期限はミリ秒を受け取った時刻に足す（`auth/exchange-token.ts:63-72`）。Refresh Token が 401（期限切れ）/ 107（無効）で
  拒否されたら `code_direct` からやり直す（`default-token-provider.ts:21` / `:95`）。
- **制限**: `MAX_REQUEST_LENGTH = 15000`・`READS_PER_MINUTE = 2000`・`WRITES_PER_MINUTE = 500`（`porters/request.ts`）。
  リクエストの長さは URL と本文の合計で測る（`requester.ts:75`）。スロットルは送る直前に数える（`:228`）。
  レート超過は 429 でなく切断という前提（ADR-0009 / 0010）なので、`Retry-After` を読まないのは正しい。
- **書き込み**: 新規は `P_Id` に `-1`（`accessor/data-writer.ts:40`）、利用者が渡した id は後から上書きする（`:87-88`）。
  応答はルートの `<Code>` を先に読み、`<Item>` ごとの `<Code>` / `<Id>` の欠けや崩れを成功と読まない（`xml/parse-write-result.ts`）。
- **フェーズの更新の再送**: `update` は冪等として再送する。フェーズを変える更新は「新しい Phase を追加」なので冪等でないように見えるが、
  1 回目が適用されていれば 2 回目は「同じ Phase で他項目のみ」になり上書きで済む（`write-format.md` の Phase の節）。**問題なしと判断**。

**気づいた経緯（RV-158）**: 同じ突き合わせで `write-format.md` の「データ型ごとの書式」を読むと、Number だけが「PORTERS が値を変える」
規則を持っていた。`encode-field.ts` は書式（`NaN`・指数表記）を止めているのに桁数は見ておらず、使い方の文書にも無かった。
**退けた解釈**: 「PORTERS の仕様なので、ライブラリの責任ではない」— 正典には書いてあるので事実は隠れていないが、
利用者が読む範囲に無い。ライブラリの存在理由（PORTERS の罠を隠す・知らせる）から外れるので指摘にした。
