## 観点別所見

> **指摘の詳細（概要・根拠・推奨・処置）は台帳の各 RV ファイルが正**。ここには
> **その回でしか分からないこと**（何を突き合わせて気づいたか・判断の背景・退行監視のための「問題なし」の記録）を残す。

固定の 8 観点を番号順で通す。

### 1. API 忠実性 — 🔴 [RV-23][rv23] ／ 🟡 [RV-26][rv26] ／ 🟢 [RV-28][rv28]

**気づいた経緯**: stakeholder の「どこまで完成しているか」に答えるため、
**reference の全 `P_` alias と全カタログを機械的に突き合わせた**。Client / Job / Resume / Process の差分は
`Reference` 型（Field Type 16 ＝ 値を持たない）と `P_Deleted` だけ＝正しい除外で、
**Candidate だけが値のある標準項目を落としていた**（[RV-23][rv23]）。この突合をしなければ人手では出なかった。

**重要度の判断**: [RV-23][rv23] を 🔴 にしたのは、落ちている 4 件に**メモ・住所詳細が含まれる**ため。
候補者のメモを型安全に扱えない ATS ラッパーは実用ブロッカーと見なした。
[RV-26][rv26] は F-2 の機能が半分しか届いていない状態、[RV-28][rv28] はガードの対称性の穴で、いずれも latent。

**良い点**: Candidate の alias 接頭辞が `Person` である罠（reference の要注意事項）は
`candidate.ts:55` で正しく扱われている。既定 field（ADR-0020）・User の 4 サブ展開・
System[Reference] の ID-only も wire 形と decode が一致している。

### 2. アーキテクチャ / ADR 遵守 — 🟡 [RV-25][rv25]

層分離は保たれている（XML は `xml/` に閉じ、`resources/` は組み立てだけ）。ADR-0044〜0051 の決定は
すべて実装に落ちている（`read-response.ts` の共有、`parseResourcePage(xml, resource)` の同定 2 条件）。

**気づいた経緯**: [ADR-0048][adr48]/[ADR-0049][adr49] が `host` を構築時に検証すると決めたので、
**同じ「設定の正しさ」を partition 側も守っているか**を確認したところ、無検証だと分かった（[RV-25][rv25]）。
決定が片側にしか適用されていない形で、ADR-0048 で塞いだのと同じ穴が残っている。

### 3. コーディング規約（ADR-0013） — 問題なし

`any` は実装コードに 0 件（`grep` 実測。ヒットはすべて英文コメント中の "any"）。
class は Error 派生 ＋ `PortersClient` のみ、内部協調子は factory 関数、関数は arrow、型は `type`。
`index.ts` はバレル、公開 API `src/index.ts` は明示 export でキュレーション、ファイル名は kebab-case。

### 4. 型安全 / 公開サーフェス — 🟢 [RV-30][rv30]

公開型は英語・JSDoc も英語で規約どおり。`ResourceDescriptor` や各 `*_DESCRIPTOR` が
`src/index.ts` に出ていない（in-repo 専用）のも意図どおり。

**気づいた経緯**: ビルド成果物 `dist/index.d.ts` の export リストを実際に読み、
公開ジェネリクスの制約型が名前で書けないことを確認した（[RV-30][rv30]）。`src/index.ts` を読むだけでは出ない。

### 5. エラーモデル — 問題なし（[RV-22][rv22] は契約待ちで `open` 継続）

基底 ＋ 系統別 4 サブクラス ＋ `category` 11 種、未知は `unknown` に倒す設計は維持。
[ADR-0044][adr44]/[ADR-0050][adr50] で HTTP ステータスが Resource / 認証の**両経路**で分類され、
`rateLimit` は 429 経由で produce される（RV-3 の予約値が到達可能になった）。
[RV-22][rv22] は安全側に倒した既知の副作用で、実 PORTERS では 429 が観測されない想定＝
[LV-9][lv] の確認待ち。**今回も状態変更なし**（再評価して `open` 継続と判断）。

### 6. テスト / 変異テスト厳密性 — 🟢 [RV-29][rv29]

563 件・カバレッジ perFile 100/98.9/100/100 で閾値（[ADR-0014][adr14]）を満たす。
fixture は実挙動に接地している（[ADR-0051][adr51] の実装時に「甘い canned body」6 件を掃除済み）。
フェイクサーバーが `src` の descriptor を直接使う（`test/fake/resources.ts`）ので、
**実装 ↔ フェイクのドリフトは構造的に起きない**。

**判断の背景**: 守られている境界（実装 ↔ フェイク）と、誰も見ていない境界
（reference ↔ カタログ）が同居していると分かったのが [RV-29][rv29]。
前者が構造で守られているぶん、後者の穴が見えにくくなっていた。

### 7. ドキュメント / DX — 🟡 [RV-24][rv24] ／ 🟢 [RV-27][rv27]

README には非公式明示・契約必須の注記・対応バージョン節がそろっており、md はリンク参照スタイル、
markdownlint も緑。[ADR-0035][adr35] が定めた「README は短い節＋ポインタ、深掘りは `docs/guide/<topic>.md`」の型も
oauth / multi-tenancy / bulk-write / error-handling で機能している。

**気づいた経緯**: ADR-0035 の型が F-1〜F-4 に適用されているかを 1 つずつ確認したところ、
**F-2 だけガイドが無く**（[RV-27][rv27]）、さらに型の外に **`defineFields` が丸ごと落ちている**
（[RV-24][rv24]）と分かった。後者は「実装済み」と数えられていたぶん、欠落が計画上も見えていなかった。

### 8. リリース準備 — 問題なし

`package.json` は `publishConfig.access: "public"`・`files: ["dist","CHANGELOG.md"]`・`exports`（types/import）・
`engines.node >= 20`・repository/bugs/homepage/keywords/author・MIT ＝ 12 版の公開実績どおり健全。
生成物（`dist/`・`coverage/`・`reports/`・`tmp/`）は git 追跡ゼロ（`git ls-files` 実測）。
CJS 出力は PRD §8 のオープン論点として**未決のまま**（ESM のみ）＝判断待ちで、欠陥ではない。

## 良かった点（strengths）

- **フェイルセーフの実装が積み上がっている**: 送信前サイズガード（URL+body 合算）・`host` 書式検証・
  Read 応答の envelope 同定・非冪等 write の再送抑止・例外は常に reject。いずれも「壊れたとき安全側に倒れる」形。
- **決定 ↔ 実装 ↔ 台帳の追跡性**: RV-13〜21 が ADR-0044〜0051 として起票 → accept → 実装 → リリースまで
  一直線に辿れる。ADR 51 本・proposed 0 件・実装待ち 0 件で、**決定の負債が無い**状態を維持している。
- **評価基盤が効いている**: フェイクサーバーが `src` の descriptor を共有するため、
  リソースを増やしても実装 ↔ フェイクのドリフトが構造的に発生しない（案B の追加コストを押し下げている）。
