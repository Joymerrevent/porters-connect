## 観点別所見

### 1. API 忠実性 — 🔴 RV-23 ／ 🟡 RV-26 ／ 🟢 RV-28

**RV-23**: [ADR-0019][adr19] は「**カタログが single source of truth**」と決め、Read 型も Write 入力型も
`FIELDS` から導出される。ゆえに**カタログの欠落はそのまま公開型の欠落**になる。
reference の全 `P_` alias とカタログを機械的に突き合わせたところ、Client / Job / Resume / Process の差分は
**`Reference` 型（Field Type 16 ＝ 参照表示専用で値を持たない）と `P_Deleted` だけ**＝正しく除外されている。
ところが **Candidate だけは値を持つ標準項目が 4 件落ちている** — `P_Memo`（メモ）・`P_Street`（住所詳細）・
`P_Fax`・`P_PhaseMemo`。Client には同じ 4 種がすべて載っており、**リソース間で非一貫**＝設計判断ではなく取りこぼし
（ADR-0019 にも部分実装の方針は無い）。影響は Read/Write 両方向で、`create({ P_Memo })` は型エラー、
既定 field 送信（[ADR-0020][adr20]）もカタログ由来なので **Read でも取りに行かない**。
候補者のメモが扱えない ATS ラッパーは実用ブロッカーなので 🔴。

**RV-26**: F-2 で `itemstate: "deleted" | "all"` を実装した（削除 API が無い PORTERS で削除済みを読む唯一の手段）。
しかし `P_Deleted`（0=未削除 / 1=削除済み）は全リソースのカタログに無い。reference は
「**Read の field としてのみ指定可能・Condition/Order/Write 不可**」と明記しており、
`itemstate: "all"` で読んだときに**どれが削除済みかを利用者が判別できない**＝機能が半分しか届いていない。
Data Type 欄が「ー」なので decode 形（`Number` 相当か文字列か）は仮定になる＝ LV 追加が要る。

**RV-28**: 送信前ガードは `keywords`（100 字）・`itemstate` の condition 制限・リクエスト長（~15000）・
Attachment 10MB と揃っているのに、**`count` の 1〜200 だけ検証されない**（`src/resources/query.ts`・
`src/resources/resource.ts:183`）。`count: 500` は不透明なサーバー応答に倒れる。ガードの対称性の穴。

**良い点**: Candidate の alias 接頭辞が `Person` である罠（reference の要注意事項）は
`candidate.ts:55` で正しく扱われている。既定 field（ADR-0020）・User の 4 サブ展開・
System[Reference] の ID-only も wire 形と decode が一致している。

### 2. アーキテクチャ / ADR 遵守 — 🟡 RV-25

層分離は保たれている（XML は `xml/` に閉じ、`resources/` は組み立てだけ）。ADR-0044〜0051 の決定は
すべて実装に落ちている（`read-response.ts` の共有、`parseResourcePage(xml, resource)` の同定 2 条件）。

一方 **RV-25**: [ADR-0048][adr48]/[ADR-0049][adr49] で `host` は「構築時に検証して誤設定なら繋ぐ前に落とす」と
決めたのに、**`partition` は無検証**で `src/client.ts:209` が `options.partition ?? 0` と**ライブラリが発明した既定値 0**を
全リクエストに載せる。`partition` は Read/Write 共通の**必須パラメータ**（[Resource API 概要][rapi]）で、
値は Partition Read で発見するもの＝ **0 という値の意味は reference のどこにも無い**。
`tenant(id)` だけを使う構成では client 既定が不要なので「必須化」は誤り。正しくは
**「一度も partition が束ねられていない呼び出し」を config エラーで落とす**（または 0 の意味を LV で確定させる）。
現状は設定漏れが「不透明なリソースエラー」として実行時に出る＝ ADR-0048 で塞いだのと同じ形の穴が残っている。

### 3. コーディング規約（ADR-0013） — 問題なし

`any` は実装コードに 0 件（`grep` 実測。ヒットはすべて英文コメント中の "any"）。
class は Error 派生 ＋ `PortersClient` のみ、内部協調子は factory 関数、関数は arrow、型は `type`。
`index.ts` はバレル、公開 API `src/index.ts` は明示 export でキュレーション、ファイル名は kebab-case。

### 4. 型安全 / 公開サーフェス — 🟢 RV-30

公開型は英語・JSDoc も英語で規約どおり。`ResourceDescriptor` や各 `*_DESCRIPTOR` が
`src/index.ts` に出ていない（in-repo 専用）のも意図どおり。

**RV-30**: `PortersClient<C extends DeclaredCatalogs>` / `TenantScope<C extends DeclaredCatalogs>` は公開型なのに、
制約の `DeclaredCatalogs` と、メンバ型に現れる `CustomFor` が **`src/index.ts` から export されていない**
（`dist/index.d.ts:724,740` に型は存在するが export リストに無い）。`typeof porters` で回避できるので実害は小さいが、
利用者がクライアントを引数に取るヘルパーの型を**名前で書けない**。2 行の追加で解消する。

### 5. エラーモデル — 問題なし（RV-22 は契約待ちで `open` 継続）

基底 ＋ 系統別 4 サブクラス ＋ `category` 11 種、未知は `unknown` に倒す設計は維持。
[ADR-0044][adr44]/[ADR-0050][adr50] で HTTP ステータスが Resource / 認証の**両経路**で分類され、
`rateLimit` は 429 経由で produce される（RV-3 の予約値が到達可能になった）。
RV-22（429 後に非冪等 `create` を再送しない）は**安全側に倒した既知の副作用**で、
実 PORTERS では 429 が観測されない想定＝ [LV-9][lv] の確認待ち。今回も状態変更なし。

### 6. テスト / 変異テスト厳密性 — 🟢 RV-29

563 件・カバレッジ perFile 100/98.9/100/100 で閾値（[ADR-0014][adr14]）を満たす。
fixture は実挙動に接地している（[ADR-0051][adr51] の実装時に「甘い canned body」6 件を掃除済み）。
フェイクサーバーが `src` の descriptor を直接使う（`test/fake/resources.ts`）ので、
**実装 ↔ フェイクのドリフトは構造的に起きない**。

**RV-29**: しかし **reference（`docs/reference/.../resources/*.md`）↔ カタログ**の突合は誰も見ていない。
RV-23（Candidate の 4 項目欠落）は 0.1.0 から今日まで 12 版・563 テストを**すべて素通りしてきた**
＝人の目だけが防波堤になっている。reference の表は機械抽出された Markdown なので、
「`Reference` 型と `P_Deleted` を除く全 `P_` alias がカタログに存在する」ことを検証するテストは書ける。
人の記憶でなく仕組みで守る＝フェイルセーフ。

### 7. ドキュメント / DX — 🟡 RV-24 ／ 🟢 RV-27

README には非公式明示・契約必須の注記・対応バージョン節がそろっており、md はリンク参照スタイル、
markdownlint も緑。[ADR-0035][adr35] が定めた「README は短い節＋ポインタ、深掘りは `docs/guide/<topic>.md`」の型も
oauth / multi-tenancy / bulk-write / error-handling で機能している。

**RV-24**: その型から **`defineFields` だけが完全に抜けている**。`src/index.ts` が export し、
[ADR-0023][adr23] で詳細設計まで済み、PRD の P1（R-16）として「実装済み」と数えられているのに、
**README に 0 箇所・guide に 0 箇所**（`error-handling.md` に例外契約の文脈で名前が出るだけ）。
ADR-0035 の Decision Drivers「**機能の存在は README で気づけること**」に正面から反する。
PORTERS の実テナントはカスタム項目を必ず持つので、**利用者が最初にぶつかる要求が最も見つけにくい**状態。

**RV-27**: 同じ型で F-1（oauth）・F-3（multi-tenancy）・F-4（bulk-write）にはガイドがあるのに、
**F-2（Read クエリ）だけ無い**。README の箇条書き（`README.md:189-198`）はあるが、
condition の Data Type 別演算子・削除済み Read の制約（90 日・3 項目）・order の対象型といった
実際に手が止まる部分は ADR-0038 を読むしかない。

### 8. リリース準備 — 問題なし

`package.json` は `publishConfig.access: "public"`・`files: ["dist","CHANGELOG.md"]`・`exports`（types/import）・
`engines.node >= 20`・repository/bugs/homepage/keywords/author・MIT ＝ 12 版の公開実績どおり健全。
生成物（`dist/`・`coverage/`・`reports/`・`tmp/`）は git 追跡ゼロ（`git ls-files` 実測）。
CJS 出力は PRD §8 のオープン論点として**未決のまま**（ESM のみ）＝判断待ちで、欠陥ではない。

## 良かった点（strengths）

- **フェイルセーフの実装が積み上がっている**: 送信前サイズガード（URL+body 合算）・`host` 書式検証・
  Read 応答の envelope 同定・非冪等 write の再送抑止・例外は常に reject。いずれも「壊れたとき安全側に倒れる」形。
- **決定 ↔ 実装 ↔ 台帳の追跡性**: RV-13〜21 が ADR-0044〜0051 として起票 → accept → 実装 → リリースまで
  一直線に辿れる。ADR 51 本・proposed 0 件・実装待ち 0 件で、**決定の負債が無い**状態を維持している。
- **評価基盤が効いている**: フェイクサーバーが `src` の descriptor を共有するため、
  リソースを増やしても実装 ↔ フェイクのドリフトが構造的に発生しない（案B の追加コストを押し下げている）。

## 次アクション候補

1. **RV-23 を最優先**（🔴・小さい）: Candidate に 4 項目を足す。カタログ 1 箇所の追加で Read/Write 型は自動追従。
   semver は **minor**（公開型に項目が増える）。同時に **RV-29**（突合テスト）を入れて再発を仕組みで止める。
2. **RV-24 → `docs/guide/custom-fields.md` を新設**（🟡・ADR-0035 の型どおり README に短い節＋ポインタ）。
   ついでに **RV-27** の `docs/guide/read-query.md` も同じ型で足せる。
3. **RV-25 / RV-26 は挙動変更＝ ADR が要る**。RV-25 は「partition 未束縛の呼び出しをどう扱うか」、
   RV-26 は「`P_Deleted` をどう型付けするか（＋ LV 追加）」。どちらも 1 本ずつの軽い ADR。
4. **リソース網羅（案B）とデータ型網羅（R-4 ＝ Link/Image）は方針判断が先**。
   [ADR-0033][adr33] は「案B は MCP 越しの需要に応じて機会的に」と決めており、
   **全リソース網羅を先にやるなら ADR-0033 を supersede する新しい ADR が要る**（方針の変更を記録に残す）。
