# RV-16 🟢 月次クォータを内蔵スロットルが守るかのような記述

- 重要度: 🟢 ／ 観点: ドキュメント
- 状態: fixed

## 概要

README が「レート制限：1 分あたり Read 2000 / Write 500、**月 15 万アクセス。内蔵スロットリングで分散。**」
と書いていたが、内蔵スロットル（`createThrottle`）は **1 分バケットのみ**で月次の概念を持たない。

## 根拠

- `README.md:343` / `CLAUDE.md`（PORTERS API 固有の注意点 6）— 月次も内蔵で守るかのような書き方。
- 実装は `src/http/throttle.ts:12-13,43-44` — `readPerMin` / `writePerMin` のみ。
- 出典 `docs/reference/resource-api/README.md:88` — 月次は**契約条件**であり
  API ドキュメント上の制限ではない旨。

## 影響

読者が「月次上限もライブラリが守る」と解釈しうる。
プロセスをまたぐ累積は永続化なしには原理的に守れないので、
**守れないものを守ると読ませている**のが問題。
利用者が自前の運用管理を省いた結果、契約上の上限を超える可能性がある。
記述だけの問題で実装変更は不要なため 🟢。

## 検出経緯

[ADR-0043][adr43] フェーズ4。**フェイクに月次クォータを実装した際に、
ライブラリ側に対応物が無いことが判明**した（[2026-08-09-01][run809]）。
正典を読み直してフェイクに写す作業が、doc の過大主張をあぶり出した形。

## 推奨

記述を実態に合わせる — 「**1 分あたりの上限は内蔵スロットルで自制**。
月次クォータ（約 15 万・契約条件）は**アプリ側の運用責務**」と書き分ける。
実装変更は不要（プロセス横断の累積管理はライブラリの責務ではない＝薄いラッパー方針）。
