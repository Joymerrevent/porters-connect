# RV-36 🟡 日時の変換だけが例外を投げ、それが `PortersError` でない（読み・書きの両方）

- 重要度: 🟡 ／ 観点: エラーモデル / フェイルセーフ
- 状態: open

## 概要

`Date` / `DateTime` / `Age` の変換だけが値を検査していて、しかも投げる例外が
**`PortersError` の系統から外れた素の `RangeError`** になっている。他の型は素通し。
これは**書き込みだけの話ではない** — 同じ変換は**読み取り**にも入っていて、そちら側は
**利用者が渡した値ではなく PORTERS が返した値**が引き金になる。

**これは方針が無いのではなく、方針に実装が従っていない状態である。**
[ADR-0006][adr6] と [ADR-0011][adr11]（どちらも accepted）は
「**型不一致はクラッシュさせず `validation` で surface（silent な誤変換をしない）**」と決めているのに、
`decode.ts` / `encode.ts` は**エラーモジュールを import していない**。詳細は「推奨」節。

併せて `docs/guide/custom-fields.md` の「**値レベルの検証はしません**」も、
読み側については ADR-0006 と矛盾している（後述）。

## 根拠

`src/xml/encode.ts` の `encodeField`（書き）と `src/xml/decode.ts` の `decodeField`（読み）を
各 Data Type で直接叩いた実測（2026-09-09・`develop` 51c6465）:

```text
[書き] Date     <- "not-a-date" => threw RangeError, isPortersError=false
[書き] DateTime <- "not-a-date" => threw RangeError, isPortersError=false
[書き] Number   <- "abc"        => ok: "abc"          ← 素通し
[書き] User     <- "abc"        => ok: "abc"          ← 素通し
[書き] Mail     <- "not-a-mail" => ok: "not-a-mail"   ← 素通し

[読み] Date     <- "ただの文字列"  => threw RangeError, isPortersError=false
[読み] DateTime <- "ただの文字列"  => threw RangeError, isPortersError=false
[読み] Date     <- "2026-09-09"   => threw RangeError, isPortersError=false
```

- 投げているのは `src/util/datetime.ts` の 4 関数（`throw new RangeError(...)` が計 5 箇所）。
  **`src/` で `PortersError` 派生でない throw はここだけ**。
- 経路は 2 つ。書きは `src/resources/resource.ts:479` の `buildWriteXml` → `encodeField`、
  読みは `decodeField`（`src/xml/decode.ts:277,286`）→ 各リソースの decode。
  どちらも `async` の内側なので届き方は **reject** で、[ADR-0046][adr46] の
  「`Promise` を返す公開メソッドは同期 throw しない」は**守られている**。問題は届き方ではなく**型**。
- [ADR-0006][adr6] は「エラーは判別可能な型に整理：基底 `PortersError` ＋ 系統別サブクラス ＋ `category`」
  と決めている。`RangeError` はそのどれでもない。
- `docs/guide/error-handling.md` のエラー一覧表に `RangeError` の行は**無い**
  （`grep -rn "RangeError" docs/` は 0 件）。ガイドが勧める
  `catch (e) { if (e instanceof PortersError) … }` の形は、この経路だけ取りこぼす。
- `Age` も同じ経路（`case "Date": case "Age":`）＝ 3 つ目の対象。

## 影響

**書き側**（利用者が渡した値が引き金）は軽い。送信前に止まるので誤った値は PORTERS に入らず、
壊れるのは利用者のエラーハンドリングだけ。`PortersError` で分岐しているコードでは、
日付の書き間違いだけが未知の例外として上位へ抜け、リトライ可否（`category`）も読めない。

**読み側のほうが重い**。引き金が**サーバーの応答**なので、利用者のコードが正しくても起きる。
`yyyy/mm/dd` でない値が 1 レコードでも混ざると、**そのページの読み取り全体が
`RangeError` で reject** する（decode はページ単位で走る）。現実に踏む経路は 2 つ:

1. **カスタム項目の宣言を取り違えた** — 実物がテキスト項目なのに `f.date()` と宣言すると、
   その項目に何か入っている全レコードの読み取りが落ちる。宣言の妥当性は誰も確かめていない
   （[ADR-0023][adr23] D5 が follow-up 送り）ので、取り違えたまま動かせてしまう。
2. **PORTERS 側の値が想定と違った** — LV 未確認の形（空文字以外の「未設定」表現など）が返ってきたとき、
   _寛容に読む_ のではなく**落ちる**。[gotchas][gotchas] は
   「未知 Alias に強い設計（寛容なパース・明確なエラー）」を求めているが、ここは
   寛容でも明確でもない。

**ライブラリの約束と実装が食い違っている**点は両側に共通する。ガイドの「値レベルの検証はしません」を
読んだ利用者は、日付だけ検証されることを知らない。

## 検出経緯

ロードマップの案D（`defineFields` 深掘り＝値レベルの実行時検証・テナント実在チェック・宣言生成）の
着手可否を評価する過程で、「値検証はまだ何も無い」という前提を確かめるために `encodeField` を
直接叩いたところ、**日付系だけ既に検証が効いていて、そこだけ例外の系統が違う**と分かった。
続けて読み側を叩いて、**同じ穴が decode 側にもあり、そちらはサーバー応答が引き金**だと分かった。

案D の「値レベルの実行時検証」は、**ゼロから足す話ではなく、既に決まっている方針に実装を
合わせる話**だと分かった。さらに検算（下記「#4 の判断材料」）で、**検証の範囲を他の型へ
広げる話でもない**ことが分かった — 日時が特別なのは検証があるからではなく、**変換があるから**で、
変換を持つ型は日時系だけである。直すべきは範囲ではなく**エラーの型**。

## 推奨

⚠️ **訂正（2026-09-10）**: 当初この節は「値レベル検証の ADR で新しく決める」と書いていたが、
**それは誤りだった**。既存 ADR を読み直したところ、**方針は 2 本の accepted な ADR で既に決まっている**。
本件は「決めること」ではなく **「決まっているのに実装されていないこと」**である。

### 既に決まっていること（accepted・実装されていない）

[ADR-0006][adr6]（accepted）:

> - 実在しない項目を使った → `PortersResourceError`（`category: "validation"`）で surface し、
>   `hint` に「この partition に存在しない/削除された可能性。Field Read で確認」を付ける（握り潰さない）
> - **宣言型と実データの食い違い**も `validation` で surface（**フィールド名付き・silent な誤変換はしない**）

[ADR-0011][adr11]（accepted）:

> - **フェイルセーフ**: 未知 Field/**型不一致はクラッシュさせず** [ADR-0006][adr6] の `validation` で
>   surface（**silent な誤変換をしない**）

**実装はどちらにも従っていない**。`src/xml/decode.ts` / `encode.ts` は
**エラーモジュールを import していない**（`grep -n "^import" src/xml/decode.ts src/xml/encode.ts`）。
`category: "validation"` を産むのは `src/errors/classify.ts` の**PORTERS 結果コード経路だけ**で、
型不一致から `validation` が出る経路は 1 本も無い。結果、冒頭の実測どおり:

| 実測された挙動            | ADR が要求する挙動           | 違反しているもの                         |
| ------------------------- | ---------------------------- | ---------------------------------------- |
| 型不一致 → 黙って `null`  | `validation` で surface      | **「silent な誤変換をしない」**          |
| 日時不一致 → `RangeError` | `validation` ＋ フィールド名 | 「クラッシュさせず」「フィールド名付き」 |

### 4 つの決めどころの現在地

| #   | 決めどころ                   | 状態                                                                                                                                                                                          |
| --- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 読みと書きを同じ扱いにするか | **読み側は決定済み**（`validation` で surface）。書き側は ADR-0006 が `defineFields` / `new PortersClient` の**設定**しか扱っておらず、**呼び出しごとの値**は書いていない → #4 に含めて要判断 |
| 2   | どのエラー型に寄せるか       | **決定済み** — `PortersResourceError` ＋ `category: "validation"` ＋ フィールド名 ＋ `hint`。`config` に寄せるか悩む必要は無かった                                                            |
| 3   | 読み側は落とすか寛容にするか | **決定済み** — 「クラッシュさせず `validation` で surface」＝ 型付きエラーで surface。**黙って `null` は明確に禁止**（当初「選びにくい」と書いたが、選べない）                                |
| 4   | 書き側の検証範囲             | **決定済み**（2026-09-10・stakeholder）— 案3＝**足さない**。「処置」節を参照                                                                                                                  |

当初この節は「#4 だけは ADR が必要」と見ていたが、**#4 は現状維持の決定になった**ため
（案3＝書き側に検証を足さない）、**新しい ADR は 1 本も要らない**。全体が
**accepted な決定に実装を合わせる作業**（[RV-32][rv32] と同じ形）に収まった。詳細は「処置」節。

なお ADR-0006 は同じ箇所で「起動前に検出したい場合は Field Read と突き合わせる**任意の事前検証**
（opt-in・将来の dev ツール）。既定では行わない」とも書いており、**そちらは [ADR-0069][adr69]**
（accepted）が担当する。本件（実行時に surface）と ADR-0069（事前に突合）は
**同じ問題への実行時／事前の両輪**であり、どちらか一方では埋まらない —
事前検証は opt-in で「既定では行わない」ものなので、**呼ばなかった利用者を守るのは本件のほう**である。

### #4 の判断材料（唯一の残り）

書き側（利用者が渡した値）を手前で検査するか。ADR-0006 の `config` 条項は
**構築時・宣言時**を対象にしており、呼び出しごとの値には触れていない。

> ⚠️ **訂正（2026-09-10）** — 本節の当初の記述には事実誤認があった。「案1（素通し）を採ると
> `"2026/09/09"` が~~黙って別の日付として送られる~~」と書いたが、**逆である**。実測:
>
> ```text
> 現状（検査＋変換あり）  ISO  "2026-09-09" => 送信 "2026/09/09"   ← 変換される
>                         P 形式 "2026/09/09" => RangeError         ← 弾かれる
> 素通しにした場合        ISO  "2026-09-09" => 送信 "2026-09-09"   ← ✗ PORTERS 形式でない
>                         P 形式 "2026/09/09" => 送信 "2026/09/09"  ← 通る
> ```
>
> 素通しで危ないのは **ISO 入力**のほうで、`"2026/09/09"` は素通しなら通る。
> ライブラリの契約は **ISO 8601 入力**（PRD R-10）なので、危ういのは**本線**である。
> 結論（案1 は採らない）は変わらないが、理由は下記に差し替える。

**この検算で分かった構造** — 日時の `RangeError` は**「値の検証」ではなく「変換の失敗」**である。
`encodeField` で**変換を伴う型は日時系だけ**（`Option` はタグに包むだけで失敗しえず、
`Image` は [ADR-0064][adr64] で既に検査済み、残りは全部 `scalar()` でそのまま出す）。
つまり「日時だけ検査が効いている」のは**揃えるべき非対称ではなく、変換のある型が日時だけ**という
当然の帰結であり、他の型に検査が無いのは**手抜きではなく、変換すべきものが無い**からである。

- **案1: 素通しに揃える**（日時の変換も外す） — ✗。ISO 入力（本線）が PORTERS 形式に
  変換されないまま送られる＝**silent なデータ破壊**。[ADR-0011][adr11] が読み側で
  パーサ自動変換を切ったのと同じ理由でここも譲れない。
- **案2: 日時系に揃えて他の型も検査する** — **「他の型」は一枚岩ではない**ので、まとめて
  賛否を決められない:
  - **明文の根拠があるもの** — `Number` は数値・ID 系（`User` / `System[Reference]` / `Link`）は
    数値・`Option` は配列・`Image` の mime 4 種。reference に書いてあるので検査しても発明にならない。
  - **明文の根拠が無いもの** — `Mail` / `Telephone` / `URL` の**書式**。reference はどれも
    「文字列」としか書いていない（`Telephone` に至っては「keyword 検索時はハイフン除去」という
    **検索側**の記述だけ）。ここを検査すると**ライブラリが規則を発明する**ことになり、
    ロードマップの但し書き（**契約前に厳しくしすぎない**）に正面から反する。
  - **原理的に検査できないもの** — 桁数（`P_Max` / `P_Min`）・必須・選択肢の実在。
    いずれも**テナント依存**で、Field Read / Option Read をしないと分からない
    （＝ [ADR-0069][adr69] の領分で、送信前ガードの仕事ではない）。
- **案3: 日時系は現状維持し、エラー型だけ `validation` に寄せる** — 検証範囲は増やさない。
  ガイドには「日時だけは**変換**するので形式を検査する」と正確に書く。
  **最小で、但し書きにも反しない。**

**案2 のうち「明文の根拠があるもの」だけは案3 と両立する**（検証範囲は増えるが発明はしない）。
ただし増えるのは**サーバーが確実に弾く値を 1 往復早く弾く**だけで、防いでいるのは
_silent_ な失敗ではない — 日時と違って、送ってしまっても result code で**大きな音がする**。
フェイルセーフが守りたいのは黙って壊れる側なので、**優先度は低い**。

### ガイドの記述も直す必要がある

`docs/guide/custom-fields.md` の「**値レベルの検証はしません**」は、
**読み側について ADR-0006 と矛盾している**（ADR-0006 は食い違いを `validation` で surface せよと言っている）。
実装を直すときに、3 つに書き分ける:

- **宣言と実データの食い違い**（読み）→ `validation` で surface する（黙って `null` にしない）
- **日時の書式**（書き）→ **変換するので**検査する。他の型は変換が無いので検査しない
  （非対称は意図したもの）
- **値の妥当性**（桁数・必須・選択肢の実在）→ PORTERS に委ねる。手前で厳しくすると、
  サーバーが受ける値を落として危険側に倒れる

## 処置

**方針は全 4 点が確定・実装は未着手**（2026-09-10・stakeholder）。**新しい ADR は起こさない。**

### 決まったこと

| #   | 決定                                                                         | 由来                                         |
| --- | ---------------------------------------------------------------------------- | -------------------------------------------- |
| 1   | 読みと書きで**クラスは分ける・`category` は揃える**（下表）                  | ADR-0006 の 2 軸設計（案C）                  |
| 2   | `category: "validation"` ＋ **フィールド名** ＋ `hint`                       | [ADR-0006][adr6]（既決）                     |
| 3   | 型付きエラーで surface する（**黙って `null` にしない**）                    | [ADR-0006][adr6] / [ADR-0011][adr11]（既決） |
| 4   | **案3 — 書き側に値検証を足さない**。日時の変換は維持し、エラーの型だけ揃える | 2026-09-10・stakeholder                      |

**#4 では「明文の根拠がある型」（`Number` は数値・ID 系は数値・`Option` は配列）も
`やらない`と決めた**（＝未実装ではなく**不要と判断した**）。理由は 2 つ:

- 防げるのは _silent_ な失敗ではない。送ってしまっても PORTERS の result code で**大きな音がする**ので、
  フェイルセーフが守りたい側ではない。
- 静的な Write 型（`WriteValueOfType.Number = number` 等）が**既にコンパイル時に止めている**。
  実行時に到達するのは cast 経由だけ。

日時が特別なのは検証があるからではなく **変換があるから**であり、変換を持つ型は日時系だけ
（「#4 の判断材料」の検算）。したがって**非対称は残るが、それは正しい非対称**である。
ガイドにもそう書く。

### エラーの型（#1・#2 の帰結）

| 引き金                                | クラス                 | category       | 根拠                                                                                    |
| ------------------------------------- | ---------------------- | -------------- | --------------------------------------------------------------------------------------- |
| **読み** — サーバー応答が宣言型と違う | `PortersResourceError` | `"validation"` | ADR-0006 が明文で指定（フィールド名 ＋ `hint` つき）                                    |
| **書き** — 利用者の値の書式が不正     | `PortersConfigError`   | `"validation"` | クラス＝「PORTERS 由来でない・使い方の誤り」／ category＝「入力・パラメータ・**書式**」 |

`category` を揃えるので利用者は `category === "validation"` で一様に分岐でき、
`instanceof` で**由来**（サーバー / 自分の値）を見分けられる。これは ADR-0006 案C の
「系統＝クラス、横断＝`category`」がそのまま効く形で、**新しい決定を持ち込んでいない**。

> **`config` ではなく `validation` を選んだ根拠** — ADR-0006 の category 定義は
> `config` を「設定/使い方の誤り（**`defineFields`・client オプション**。同期 throw）」と
> **明示的に絞っており**、`validation` を「入力・パラメータ・**書式**」と定義している。
> 呼び出しごとの値の書式は後者。SD-E が `PortersConfigError` と `config` を並べているのは
> 構築時・宣言時の話で、そこと衝突しない。

### なぜ ADR を起こさないか

- #1〜#3 は **accepted な決定（ADR-0006 / ADR-0011）に実装を合わせる**作業。
- #4 は **現状維持**の決定＝新しい挙動を持ち込まない。
- エラーの型も上記のとおり ADR-0006 の定義から**導かれる**もので、選択肢を新たに決めていない。

[RV-32][rv32] と同じ形（「挙動の決定を持ち込まないので ADR は起こしていない」）。

### 着手手順

1. `decode.ts` / `encode.ts` の日時変換の失敗を、上表のクラス ＋ `category: "validation"` に
   置き換える（フィールド名を載せるため、alias を変換関数まで渡す必要がある）
2. **読み側の型不一致（黙って `null`）も surface する** — `Option` ↔ テキストの取り違えが
   現状 `null` になる経路。ADR-0006 の「silent な誤変換をしない」はここが本体
3. `docs/guide/error-handling.md` のエラー一覧表に 2 行を足す
4. `docs/guide/custom-fields.md` の「値レベルの検証はしません」を書き分ける（下記）
5. `PortersConfigError` の JSDoc「thrown synchronously」に**呼び出し経路では reject で届く**旨を補う
   （[ADR-0046][adr46] と整合。同期 throw は構築時・`defineFields` のみ）
