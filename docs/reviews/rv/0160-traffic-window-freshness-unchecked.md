# RV-160 🟢 普及シグナルを控える手順が、GitHub が返した期間の最終日を確かめない

- 重要度: 🟢 ／ 観点: プロセス
- 状態: fixed

## 概要

レビューの手順は、GitHub の traffic API（views / referrers）の値をスナップショットに貼る。
2026-09-28 と 2026-09-29 の run では、API が返した日別の値が **09-23 で止まっていた**が、手順にはそれを確かめる段が無く、
止まった期間の合計がその日の値として記録されうる。

## 根拠

- 手順: `.claude/skills/project-review/SKILL.md` の「下調べ」は、`traffic/popular/referrers` と `traffic/views` を取って
  スナップショットに貼る、とだけ書く。返った期間の最終日を見る段は無い。
- 実測（2026-09-29 07 時台 JST・応答の `Date` は `Mon, 28 Sep 2026 22:19:08 GMT`）:
  `traffic/views` の日別は `2026-09-10`〜`2026-09-23` の 14 日（489 / 24）、`traffic/clones` の日別も `2026-09-23` が最後。
  09-24 以降も develop への push ごとに CI がリポジトリを clone しているので、clone が 0 件だったとは考えにくい。
  GitHub 側の集計が止まっているとみているが、GitHub の状態は確かめていない。
- [2026-09-28-01][run0928] は同じ値を「API が返した窓は 09-10〜09-23」「GitHub 側の集計の遅れとみられる・未確認」と書いた
  （気づいたのは、日別の値を並べて出したから）。

## 影響

[ADR-0084][adr84] が traffic を毎回控えるのは、**14 日で消える**値から「外部からの流入が始まった」ことに後から気づけるようにするため。
止まった期間の値を当日の値として記録すると、その間に流入があっても記録に残らず、記録上は「発火なし」に見える。
集計が戻れば同じ 14 日の窓で後から取り直せるので、取り返しがつかなくなるのは止まった状態が 14 日を超えたときだけ。🟢。

## 検出経緯

2026-09-28 の run 1 で API の窓が 09-23 で終わっていることに気づき、「集計の遅れ」として記録した。
翌日の run でも同じ窓が返り、clone の数も同じ日で止まっていたので、遅れではなく止まっていると判断した。

## 推奨

ADR 不要（手順の追記）。

- スキルの「下調べ」に 1 段足す: `traffic/views` の最後の日付を見て、今日より 2 日以上前ならスナップショットに
  「集計が止まっている（最終日 YYYY-MM-DD）」と書き、次の run で取り直す。
- 止まっている間の分は、集計が戻ってから 14 日以内に取り直す（09-24 以降の分なら 10-07 ごろまで）。

## 処置

推奨のとおり、スキルの手順に 1 段足した（2026-09-29・ADR 不要）。

- `.claude/skills/project-review/SKILL.md` の「下調べ」の普及シグナルの段に、返った期間の最終日を確かめる手順を足した。
  `gh api repos/Joymerrevent/porters-connect/traffic/views --jq '.views[-1].timestamp'` で最終日を出し、今日（UTC）より 2 日以上前なら
  スナップショットに「集計が止まっている（最終日 YYYY-MM-DD）」と書く。止まっている間の分は、集計が戻ってから 14 日以内の run で取り直す。
- `references/report-format.md` の普及シグナルの表の雛形を「直近 14 日」から「日別の期間 YYYY-MM-DD〜YYYY-MM-DD」に変え、
  最終日が古いときに表の下へ書くことを足した。

## 検証

- 足したコマンドを 2026-09-29 に実行し、`2026-09-23T00:00:00Z` が返ることを確かめた（その時点の UTC の日付は 2026-09-28。5 日前なので「止まっている」と判定される）。
