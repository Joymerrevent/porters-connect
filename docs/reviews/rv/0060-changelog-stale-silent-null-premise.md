# RV-60 🟢 0.21.0 の CHANGELOG と ADR-0087 が、0.15.0 で直した「黙って `null`」を現在の挙動として書いている

- 重要度: 🟢 ／ 観点: ドキュメント / API 忠実性
- 状態: open

## 概要

0.21.0 の CHANGELOG は破壊的変更の動機として「実物が Option の項目をテキストで読めば値が `null`
になり、**例外も警告も出ません**」と書く。だが同じ CHANGELOG の 0.15.0 節は「宣言型と実データの形が
食い違うと、`null` ではなく**エラーになります**」（[RV-36][rv36]）。**同じファイルの中で、同じ挙動を
逆に説明している**。出所は [ADR-0087][adr87] の Context で、[ADR-0069][adr69]（2026-09-09・RV-36 の
修正 2026-09-10 の前日）の実測表を「そのもの」として引いている。

## 根拠

- `CHANGELOG.md:23-24`（0.21.0）— 「実物が Option の項目をテキストで読めば値が `null` になり、例外も
  警告も出ません」。**現在形**。
- `CHANGELOG.md:622-625`（0.15.0）— 「実物が Option の項目を `f.singlelineText()` と宣言していた場合、
  **これまでは**読み取りが黙って `null` を返し … **いまは** `PortersResourceError`（`category:
"validation"`）で項目名つきに失敗します」。
- `src/xml/decode.ts:341` / `:358` — 形の食い違いは `throw mismatch(...)`（`validation`）。
  Option 項目（入れ子）をテキスト（スカラ）で読めば `:358` で throw する。
- [ADR-0087][adr87] `:68-73`「取り違えたときの倒れ方」— 「その結果は ADR-0069 が実測した表そのもので、
  Option の項目を `singlelineText()` で読めば**値が黙って `null` になる**。例外も警告も出ず」。
  同じ ADR の「信じている入力」表（`:262`）は「実データと形が食い違えば `validation` で surface
  （RV-36）」＝ **ADR の中でも Context と表が食い違っている**。
- [ADR-0069][adr69] `:4` Date 2026-09-09・`:26-34` の実測表。[RV-36][rv36] の処置は 2026-09-10。
  ADR-0069 の記述は**起票時点では正しい**（歴史的記録）。それを 12 日後の ADR-0087 が再検証せずに
  現在形で引いた。
- 正しく書けている例: `docs/usage/howto/handle-failures.md:300-311` — 「**以前は**黙って `null` に
  なっていました … いまは実装がそれに従います」。

## 影響

🟢。コードは正しく、困るのは読み手の理解だけ。ただし読み手は 2 種類いる:

- **利用者**（CHANGELOG）: 0.21.0 の節だけ読むと「宣言を取り違えても黙って `null`」と受け取り、
  存在しない silent 挙動に備えた防御コード（`?? ""` の類）を書くか、逆に 0.15.0 以降の
  `validation` エラーを「想定外」として握り潰す。破壊的変更の**理由**として書かれた文なので、
  移行を判断する人が最初に読む位置にある。
- **保守者**（ADR-0087）: 案B を採る理由の 1 つが「不正な状態そのものが消える」で、その不正な状態の
  倒れ方として silent `null` を挙げている。実際には RV-36 以降、Option ⇄ テキストの取り違えは
  **読み取り時に `validation` で落ちる**（見える）。案B の根拠は層の整合・トークン共有・型引数の
  単純化だけで十分に立つので**決定は変わらない**が、「黙って壊れるから」を主因に読んだ人が
  RV-36 の存在を知らずに同じ論を別の場所で繰り返す。実際、[RV-58][rv58] で分かったとおり、
  RV-36 後にも silent な経路（Number ⇄ テキスト）は残っており、**残っているのはそちら**。

## 検出経緯

観点 1 で `docs/usage/reference/gotchas.md` の書き換え（#365）「宣言との食い違いは `validation` で
知らせる」を `decode.ts` と突き合わせて正しいと確認した直後、同じ日に書かれた CHANGELOG 0.21.0 が
逆のことを言っているのに気づいた。`grep '黙って' docs CHANGELOG.md` で現在形のものを洗い、
ADR-0087 → ADR-0069 → RV-36 の日付を並べて経緯を特定した。

## 推奨

- (a) `CHANGELOG.md:23-24` の括弧内を事実に直す。0.21.0 の節は公開済みだが、CHANGELOG は
  [Keep a Changelog][kac] の慣行どおり**過去の節も訂正してよい**（version を変えない・誤記の訂正）。
  文案: 「（取り違えは読み取り時に `validation` エラーで見えるが、**どのテナントの宣言かを
  ライブラリは知らない**ので、正しい宣言に取り替える手掛かりが無い）」＝ 案B の実際の利点に寄せる。
- (b) [ADR-0087][adr87] の Context「取り違えたときの倒れ方」に**訂正の追記**を置く（決定の文面は
  書き換えない。同 ADR が実装時の訂正を「**訂正（実装時 2026-09-21）**」の形で既に 2 か所
  入れているので、その形に揃える）: Option ⇄ テキストは RV-36 で `validation`、残る silent は
  Number ⇄ テキスト（[RV-58][rv58]）。
- (c) 再発防止は仕組みにしにくい（自然文の時制）。代わりに、ADR が**別の ADR の実測表を引くときは
  日付と「その後の RV で変わっていないか」を 1 行添える**運用を ADR README の書き方に足すかどうか
  — 効果が薄ければ足さない。**ADR 不要**（文面の訂正）。
