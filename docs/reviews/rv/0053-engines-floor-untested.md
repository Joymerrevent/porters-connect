# RV-53 🟢 `engines` の下限 22.12 を CI が一度も走らせていない

- 重要度: 🟢 ／ 観点: テスト厳密性 / プロセス
- 状態: fixed

## 概要

`package.json` は `engines.node: ">=22.12.0"` を約束し、[ADR-0082][adr82] は
「22.12 は Node の `require(esm)` が既定で有効になる最小の版」という理由まで置いている。
だが CI のマトリクスは**メジャーだけを指定**していて、`22` は常にその時点の最新 22.x に
解決される。**約束した下限そのものは一度も実行されていない**。

## 根拠

`.github/workflows/test.yml:29` — `matrix: node: [22, 24, 26]`。
`actions/setup-node` に `22` を渡すと 22 系の最新（現在 22.2x）が入る。
`.node-version` も `22` の 1 行で、こちらも同じ。

同ファイルの冒頭コメント（`:1-8`）は
「**下限が 22.12 なのは** Node の `require(esm)` が既定で有効な最小の版だから（ADR-0082）」
「**下限・Active LTS・Current の 3 段**を保つ」と書いている。つまり
**意図は「下限を試す」**で、実装が「22 系の最新を試す」になっている。

なお現時点では**実害は無い**: `src` が使う最も新しいランタイム API は
`AbortSignal.timeout`（`src/http/fetch-transport.ts:58`・Node 17.3+）で、
22.12 より後に入った API の使用は grep で 0 件。

## 影響

**今は壊れていない。壊れても気づかない形になっている**のが指摘の中身（だから 🟢・latent）。

22.12 より後に追加された API を誰かが使った日に、CI は緑のまま
`engines` を信じた 22.12〜22.1x の利用者だけが実行時に落ちる。
落ち方は `TypeError: … is not a function` で、**ライブラリの不具合には見えない**。

このプロジェクトは同じ形の穴を繰り返し「仕組み」で塞いできた
（[RV-29][rv29] reference ↔ カタログ・[RV-42][rv42] 品質ゲート一覧・
[RV-44][rv44] coverage 除外）。ここも「コメントに書いた意図が実装で担保されていない」
同じ類型で、**下限を 1 つ足すだけで消える**。

## 検出経緯

観点 8（リリース準備）で [ADR-0082][adr82]（Node 下限を 22.12 に上げた破壊的変更）の
反映を確認していて、`engines` と CI マトリクスを並べて読んだ。
ワークフローのコメントが「下限」と明示しているのに指定が `22` なので、
**コメントと指定が同じことを言っていない**のが手がかり。
念のため「そもそも 22.12 以降の API を使っているか」も grep して、
現時点では latent と切り分けた。

## 推奨

`test.yml` のマトリクスに下限を**バージョンまで書いて**足す。挙動変更は無いので ADR は不要。

- (a) `node: ["22.12", 22, 24, 26]` — 下限を 1 段増やす。CI が 1 ジョブ増えるが、
  「3 段を保つ」という元の意図（下限 / Active LTS / Current）に**実装を合わせる**形。
- (b) `node: ["22.12", 24, 26]` — 22 系最新を下限に置き換える。ジョブ数は変わらない。
  22 系最新でしか出ない退行（Node 側の退行）は見えなくなるが、
  **ライブラリが約束しているのは下限**なので、どちらか 1 つなら下限を採るのが筋。

`.node-version`（ローカル / release ジョブ用）は開発版なので `22` のままでよい
（下限で開発する必要は無い）。**下限は「試す対象」であって「開発する版」ではない**という
切り分けを、ワークフローのコメントに 1 行足しておくと次に読む人が迷わない。

## 処置

**完了。**推奨の案a を採り、**ずれの検査も足した**（推奨を 1 つ超えている）。

1. マトリクスを `node: ["22.12.0", 22, 24, 26]` にした。`22`（系の最新）も残す —
   下限は「試す対象」であって開発する版ではないので、実際に使われる 22 系最新の退行も見たい。
   `.node-version`（ローカル / release）は `22` のまま。
   **パッチ版まで書く**のが要点で、`22.12` だとその系の最新に解決されてしまう。
2. `check:release` に `matrixCoversFloor` を足した。**マトリクスに書くだけだと、
   `engines` を上げたときに直し忘れて下限が未検査に戻る＝この指摘が再発する。**
   同スクリプトは既に `minNodeOf` で README バッジのドリフトを見ており、
   同じ「宣言 ↔ 実体」の検査として隣に置いた。

## 検証

`scripts/check-release-invariants.test.mjs` が固定しているもの:

- **メジャーだけの指定（`22`）は下限を含まないと判定する** — ここが検査の要点。
  通してしまうと素通りして、今と同じ状態に戻る。
- マイナーまで（`22.12`）でも下限の表記（`22.12.0`）と違えば通さない
  — 表記を 1 つに決め、エラー文が正解を示す。
- クォートの有無は問わない。
- マトリクス行が読めなければ「無い」扱い（**fail-safe** — 検査の空振りより、
  読めないことを報告して人に見てもらうほうがよい）。
- **`engines` を上げてマトリクスを直し忘れたら落ちる** — 再発の形そのものを固定した。
- `engines` が読めないときはマトリクスを見ない（先に `engines` を報告する）。

実測: `pnpm check:release` は
`✓ リリース不変条件 OK（version=0.19.0, baseline=0.19.0…）`。
マトリクスから下限を抜くと
`CI の Node マトリクスに engines の下限 "22.12.0" がありません` で落ちる。

品質ゲートは全 green（**1294 tests**）。
