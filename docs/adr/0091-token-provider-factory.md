# 91. トークンの取得だけを差し替え、キャッシュと更新の判断をライブラリに任せる入口を公開する

- Status: proposed
- Date: 2026-09-24
- Deciders: jun.shiromoto (Joymerrevent)

> 起票元は [RV-63][rv63]（2026-09-23）。RV-63 は「実例が 1 件出たら ADR を起票する」条件付きだったが、
> stakeholder が 2026-09-24 に**条件を待たずに進める**と決めた。ガイドの図と実装例を先に直す案（RV-63 推奨 (b)(c)）は
> 見送り、この ADR から始める。
>
> [ADR-0007][adr07] 案4（注入可能な認証ストラテジ）と [ADR-0012][adr12]（既定のキャッシュと更新）への**追加**で、
> どちらの決定も変えない。

## Context and Problem Statement

### いまの 2 つの入口

| 入口                           | 差し替えるもの                | 取得・キャッシュ・更新の判断 |
| ------------------------------ | ----------------------------- | ---------------------------- |
| `tokenStore`                   | トークンの**保存先**だけ      | ライブラリ（既定の方式）     |
| `auth`（独自 `TokenProvider`） | `getAccessToken` を**丸ごと** | **すべて利用者**             |

既定の方式（`src/auth/token-provider.ts` の `createDefaultTokenProvider`）の中身は、2 つに分かれている。

- **取得**: `code_direct` でコードを取り、Token API で交換する（`acquire` / `exchange`）。Refresh Token での更新（`renew`）
- **管理**: メモリのキャッシュ、期限の 60 秒前に取り直す判断（`refreshMarginMs`）、`forceRefresh`、
  同時呼び出しを 1 本にまとめる（`inflight`）、`tokenStore` への読み書き

この組み立てはライブラリの中に閉じていて、**取得だけを別の仕組みにし、管理はライブラリのものを使う**入口が無い。

### 取得を差し替えたい場面

PORTERS のトークンの取り方は `code_direct` の 1 通りなので、取得を差し替えるのは「**別のサービスが発行した
トークンを受け取る**」場面になる。例: 社内の中央サービスがトークンを一括で管理し、各アプリはそこから
受け取る。この場合、Refresh Token での更新は発行側が受け持ち、アプリに渡るのは Access Token とその期限だけになる。

### 自前で書くと間違えやすい

いまこの場面の利用者は、独自 `TokenProvider` で管理の部分まで書く。ガイド「認証とトークン」の
「トークンを自前で管理するとき」にある実装例は、キャッシュと `forceRefresh` を扱うが、**期限の判定**と
**同時呼び出しの 1 本化**が無い。期限切れのトークンを 401 が返るまで使い続け、同時に呼ばれると何本も取り直す。
ライブラリ自身が書いた例でも漏れた、という事実が、この部分を利用者に書かせるのは危ういことを示している。

### 問い

「取得だけを渡すと、管理はライブラリが受け持つ」入口を公開するか。公開するなら、利用者が渡す関数の形、
`tokenStore` との関係、`porters.auth` のメソッドの動きをどうするか。

## Decision Drivers

- **フェイルセーフ**: 期限の判定と同時呼び出しの扱いは、間違えても気づきにくい（動くが、無駄に取り直すか、
  期限切れで 1 回失敗する）。ライブラリが 1 か所で持つ。
- **非破壊**: `tokenStore` と独自 `TokenProvider` の 2 つの入口は変えない。
- **出典に無いものを発明しない**: PORTERS の取得経路は `code_direct` の 1 通り。別のサービスが何を返すかは
  利用者の世界なので、受け取る形は最小にする。
- **薄く**: 既定の方式の管理の部分を再利用し、新しい仕組みを増やさない。

## Considered Options

### 論点1: 入口を公開するか

- **案1a: 取得の関数を受け取って `TokenProvider` を返す関数を公開する** — 推奨
- 案1b: 公開しない（独自 `TokenProvider` を自分で書く形のまま。ガイドの実装例を直す）

### 論点2: 利用者が渡す関数の形

- **案2a: `acquire()` が Access Token と期限（任意）を返す。更新は発行側の仕事で、ライブラリは期限が近づいたら `acquire` を呼び直す** — 推奨
- 案2b: `acquire()` が Refresh Token まで含むトークン（`StoredTokens`）を返し、更新はライブラリが PORTERS の
  Token API で行う
- 案2c: `acquire` と `refresh` の 2 つの関数を受け取る

### 論点3: `tokenStore` を使うか

- **案3a: 使わない（プロセス内のキャッシュだけ）** — 推奨
- 案3b: 保存先を受け取り、再起動のときに読み戻す

### 論点4: `porters.auth` のメソッドはどう動くか

- **案4a: 独自 `TokenProvider` と同じ（`getToken` / `ensureAuthenticated` だけが動き、残る 4 つは `PortersConfigError`）** — 推奨
- 案4b: `clearTokens` も動く（キャッシュを捨てる）

## Decision Outcome

（proposed。以下は推奨で、決定は decider が行う。）

推奨: **案1a ＋ 案2a ＋ 案3a ＋ 案4a**。

```ts
import {
  PortersClient,
  createTokenProvider,
} from "@joymerrevent/porters-connect";

const auth = createTokenProvider({
  // 別のサービスからトークンを受け取る。期限（エポックミリ秒）は分かれば返す
  acquire: async () => {
    const { token, expiresAt } = await myTokenService.get();
    return { accessToken: token, expiresAt };
  },
});

const porters = new PortersClient({ hostname, auth });
```

### 論点1: 案1a を推す理由

- 管理の部分（期限の 60 秒前に取り直す・`forceRefresh` で取り直す・同時呼び出しを 1 本にまとめる）は、
  既定の方式がすでに持ち、テストされている。利用者が書き直すより、同じものを使えるほうが壊れにくい。
- 案1b でも用途は満たせるが、利用者全員が同じ管理を書き、同じ漏れ方をしうる（上の「自前で書くと間違えやすい」）。
- 入口が 3 つになる説明の負担は、ガイドで「保存先だけ変える／取得だけ変える／全部自前」の 3 行に並べれば済む。

### 論点2: 案2a を推す理由

- 取得を差し替える場面では、更新は発行側の仕事で、アプリに渡るのは Access Token と期限だけ（上の「取得を差し替えたい場面」）。
  案2b は Refresh Token と App Secret をアプリが持つ前提で、それなら既定の方式を使えばよい。
- **期限は任意**にする。発行側が期限を教えないこともある。期限が無ければ、ライブラリは 401 / 402 を受けて
  `forceRefresh` で呼び直す（既定の方式と同じく、失効の応答を受けたら 1 回だけ取り直す）。期限があれば、
  その 60 秒前に取り直す。
- 案2c は、更新の手段を持つ発行側でないと書けず、案2a で足りる場面に余分な形を増やす。

### 論点3: 案3a を推す理由

- トークンの正は発行側にある。アプリ側に写しを永続化すると、発行側が取り消したトークンを再起動後に使い続けうる。
- `tokenStore` の型（`StoredTokens`）は Refresh Token と 2 つの期限を必須にしていて、案2a の形とは合わない。
- 必要になれば、あとから保存先を受け取るオプションを足せる（非破壊）。

### 論点4: 案4a を推す理由

- 返すのはただの `TokenProvider` で、`auth` オプションに渡す。ライブラリから見ると独自 `TokenProvider` と
  区別が無く、特別扱いを増やさない。
- `authorizationUrl` / `exchangeAuthorizationCode` / `revokeUrl` は、発行側の仕事なのでライブラリは代行できない。
  `clearTokens` はキャッシュを捨てることはできるが、発行側のトークンは残るので「消した」と誤解させる。
  キャッシュを捨てたいときは `forceRefresh` で足りる。

### 実装の制約（基本設計として決めておくこと）

- **管理の部分は既定の方式と共有する**。期限の判断・`forceRefresh`・同時呼び出しの 1 本化を 2 か所に書かない。
  既定の方式は「`code_direct` と Refresh Token で取得する `acquire`」を渡した形として組み直す。既定の方式の動き
  （`tokenStore` への読み書き・Refresh Token での更新・`porters.auth` の 6 メソッド）は変えない。
- **期限の余裕は既定の方式と同じ 60 秒**を既定にし、オプションで変えられるようにする。
- **`acquire` の失敗はそのまま呼び出し側に届ける**。ライブラリは繰り返さない（既定の方式と同じ。取り直しは
  失効の応答を受けたときの 1 回だけ）。`acquire` が同期で throw しても reject で届く（Promise を返す公開メソッドは
  同期で throw しない、の約束）。
- **名前**: `createTokenProvider`（`createThrottle` / `createFetchTransport` / `createMockTransport` と同じ形）。
  オプションと戻り値の型の名前は実装で決める。

### Consequences

- Good: 別のサービスからトークンを受け取るアプリが、管理の部分を書かずに済む。期限切れのトークンを使い続ける・
  同時に何本も取り直す、という自前の実装で起きやすい失敗がライブラリの側で防がれる。
- Good: 既定の方式の管理の部分が 1 か所に集まり、2 つの入口で同じテストが効く。
- Good: 非破壊の追加で、minor で出せる。
- Bad: 認証の入口が 3 つになり、ガイドに使い分けの説明が要る（実装の PR で「認証とトークン」を書き直す。
  いまの「トークンを自前で管理するとき」の実装例も、そのときに直す）。
- Bad: 既定の方式を組み直すので、既定の方式の既存のテストで振る舞いが変わらないことを確かめる必要がある。
- Neutral: Refresh Token を持つ別経路の取得（案2b）は扱わない。必要になったら別の ADR にする。

## 信じている入力

| 値                            | 出どころ                     | 誰が書けるか   | 守り方                                                                                 | 取れなかったら                   | 誤っていたら                                                           |
| ----------------------------- | ---------------------------- | -------------- | -------------------------------------------------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------- |
| `acquire` が返す Access Token | 利用者の関数（別のサービス） | 利用者・発行側 | 空文字や文字列でない値は `PortersConfigError` で止める（送る前に分かる誤りは送らない） | `acquire` の失敗をそのまま届ける | PORTERS が 401 / 402 を返す → 1 回だけ取り直し、それでも駄目ならエラー |
| `acquire` が返す期限（任意）  | 利用者の関数（別のサービス） | 利用者・発行側 | 数値でなければ「期限なし」として扱う（取り直しは失効の応答を受けたときに倒す）         | 期限なしとして扱う               | 早すぎれば無駄に取り直すだけ。遅すぎれば 401 を受けて 1 回取り直す     |

期限を信用しすぎないのが要点で、期限が誤っていても、失効の応答を受けたときの取り直し（既存の仕組み）で回復する。

## Pros and Cons of the Options

### 案1a（公開する）／ 案1b（公開しない）

- 案1a — Good: 管理の部分を利用者が書かずに済む。Bad: 入口が 3 つになる。
- 案1b — Good: 入口が増えない。Bad: 利用者が管理を書き、ライブラリ自身の例でも漏れた部分が漏れうる。

### 案2a（Access Token と期限）／ 案2b（Refresh Token まで）／ 案2c（2 つの関数）

- 案2a — Good: 別のサービスから受け取る場面にそのまま合う。Bad: 更新の手段は発行側に任せきりになる。
- 案2b — Good: 更新までライブラリが持てる。Bad: アプリが Refresh Token と App Secret を持つ前提で、それなら既定の方式でよい。
- 案2c — Good: 更新の手段を細かく渡せる。Bad: 案2a で足りる場面に余分な形を増やす。

### 案3a（使わない）／ 案3b（保存先を受け取る）

- 案3a — Good: トークンの正が発行側の 1 か所に保たれる。Bad: 再起動のたびに取り直す。
- 案3b — Good: 再起動での取り直しを省ける。Bad: 発行側が取り消したトークンを使い続けうる。`StoredTokens` の形と合わない。

### 案4a（独自 `TokenProvider` と同じ）／ 案4b（`clearTokens` も動く）

- 案4a — Good: 特別扱いが無い。Bad: `clearTokens` が使えない。
- 案4b — Good: キャッシュを捨てる手段が増える。Bad: 発行側のトークンが残るのに「消した」と誤解させる。
