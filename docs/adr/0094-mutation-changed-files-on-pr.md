# 94. PR のミューテーションテストは変更したファイルだけにし、main への PR は必ずフル run にする

- Status: accepted
- Date: 2026-09-25
- Deciders: jun.shiromoto (Joymerrevent)

> 起票元は stakeholder の指摘（2026-09-25）: 「PR のたびにフルチェックで時間がかかる。リリースの PR だけ必ず
> フルチェックにして、それ以外は短縮できないか」。
>
> [ADR-0015][adr15] の実行戦略（2026-09-22 の訂正で「PR / push / nightly のすべてでフル run」）と、
> [ADR-0028][adr28] の訂正（2026-09-23）の「リリースの流れの PR（リリース PR・back-merge PR）は develop と
> 同じなら skip」を**改める**。`break` 100 の閾値、develop への push と nightly のフル run、`main` への push の
> skip（[ADR-0028][adr28] の注記）は据え置く。
>
> 議論の経緯: 起票時は「リリース PR（head が `release/`）を必ずフル run」とし、back-merge PR の skip は据え置いていた。
> stakeholder の指摘で、**リリースの流れかどうかは「`main` への PR かどうか」で見分ける**形に改めた。back-merge PR は
> 下の規則（`package.json` の `version` だけの変更は対象にしない）で自然に skip になる。
>
> **decider が案1a ＋ 案2a を選択し `accepted`（2026-09-25）。** 実装は accept 後・別 PR。

## Context and Problem Statement

### いまの形

`Mutation` ワークフロー（`.github/workflows/mutation.yml`）の `stryker` は必須チェックで、コードを含む PR では
**毎回フル run** する。CI の実測は 1 回 約 10〜11 分（2026-09-25 の PR #412 で 10 分台が 2 回）。

| いつ                            | いまの範囲                                  |
| ------------------------------- | ------------------------------------------- |
| 機能 PR（develop 向け）         | フル run（docs-only は skip）               |
| develop への push               | フル run                                    |
| リリース PR（release/* → main） | develop との違いが版番号と文書だけなら skip |
| back-merge PR（main → develop） | develop との違いが版番号と文書だけなら skip |
| main への push                  | develop との違いが版番号と文書だけなら skip |
| nightly                         | フル run                                    |

### PR をフル run にした理由（もとの問題）

[ADR-0015][adr15] は当初「PR は差分（incremental）」だった。Stryker の incremental は、前回の結果
（`reports/stryker-incremental.json`）を使い回す。**static mutant**（モジュール読み込み時に評価される定数。
リソースの項目表など）はテストごとの coverage を持たないため、「覆うテストが増えた」と判定されず、
その行を変えるか `--force` を掛けるまで前回の `Survived` が使い回される。`break` 100 と組み合わせると、
static の穴をテストで塞いだ PR が必ず落ちる。ゲートとして成り立たないので、2026-09-22 に PR もフル run にした。

### 起きていること

- 小さな変更の PR でも、マージできるまで毎回 10 分ほど待つ。PR を積み直す（force push・追いコミット）たびに
  やり直しになる（同じ ref の run は打ち切って新しく走る）。
- 機能 PR で検査したコードは、develop への push でもう一度フル run で検査している。

### 問い

機能 PR のミューテーションテストを、もとの問題（使い回した結果による誤判定）を再発させずに短くできるか。
その代わりに、どこで全体を担保するか。

## Decision Drivers

- **フェイルセーフ**: 短くするために、壊れた検査が静かに通る形にしない。判定に迷ったらフル run に倒す。
- **前回の結果を使い回さない**: もとの問題の原因は、使い回した結果が新しいテストを反映しないこと。
- **全体の担保はマージ後とリリースで持つ**: develop への push（マージ後の中身）と、リリース PR（公開する中身）。
- **ワークフローの `if` に判定を並べない**: 判定は `scripts/` の小さなスクリプトに置いてテストする（[ADR-0028][adr28] の訂正と同じ）。

## Considered Options

### 論点1: 機能 PR をどう短くするか

- **案1a: 変更したファイルのミュータントだけを、毎回ゼロから検査する**（`stryker run --mutate <ファイル>`・incremental は使わない）
- 案1b: incremental（`--incremental`）に戻す
- 案1c: 機能 PR ではミューテーションテストをやめ、develop への push・nightly・リリース PR だけにする
- 案1d: いまのまま（毎回フル run）

### 論点2: リリース PR をどうするか

- **案2a: `main` への PR は必ずフル run にする**（いまの「develop と同じなら skip」をやめ、ブランチ名で見分けない）
- 案2b: いまのまま（head が `release/` のものを見分け、develop と同じなら skip）

## Decision Outcome

採用: **案1a ＋ 案2a**（decider が 2026-09-25 に選択）。

### 決めること

**`main` 以外への PR（back-merge PR を含む）の対象ファイル**は、PR のマージ結果と base の差分から
次の規則で決める。**どれにも当てはまらない変更が 1 つでもあれば、フル run に倒す。**

| 変更されたもの                                                                                                               | 扱い                                                                 |
| ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `src/` の実装（`stryker.config.json` の `mutate` に入るファイル）                                                            | そのファイルを対象にする                                             |
| `src/` の隣のテスト（`x.test.ts`）                                                                                           | 隣の実装（`x.ts`）が `mutate` に入るなら対象にする。無ければフル run |
| `src/` の `mutate` の外（`index.ts`・`types.ts`・`src/types/`）                                                              | フル run（多くのファイルに効くため）                                 |
| `test/`（結合テスト・フェイクサーバー・フィクスチャ）                                                                        | フル run（どの実装を覆うか読めないため）                             |
| `package.json` の `version` だけの変更                                                                                       | 対象にしない（版番号はコードでない）                                 |
| 依存と設定（`package.json` の `version` 以外・`pnpm-lock.yaml`・`stryker.config.json`・`vitest.config.*`・`tsconfig*.json`） | フル run                                                             |
| コードでないもの（`**/*.md`・`docs/**`）                                                                                     | 対象にしない（[ADR-0028][adr28] の docs-only と同じ）                |
| `scripts/`・`.github/`                                                                                                       | 対象にしない（`src/` のミュータントを倒すテストを含まない）          |

- 対象が 0 件なら `stryker` は skip する（必須チェックの報告は保つ）。
- 対象があれば `stryker run --mutate <対象>` を実行する。テストは全部走らせ、閾値（`break` 100）はそのまま当てる。
- **incremental は使わない**。毎回ゼロから検査するので、前回の結果による誤判定（もとの問題）は起きない。
- 判定のスクリプトが失敗したら、フル run に倒す。

**それ以外**:

| いつ                                  | 範囲                                                                                              |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `main` への PR（リリース PR・hotfix） | **必ずフル run**（案2a）                                                                          |
| それ以外の PR（back-merge PR を含む） | 上の規則（変更したファイル、または フル run）。back-merge は版番号と文書だけなので対象 0 件＝skip |
| develop への push                     | フル run（据え置き。マージ後の中身を検査する唯一の run）                                          |
| main への push                        | develop との違いが版番号と文書だけなら skip（据え置き）                                           |
| nightly                               | フル run（据え置き）                                                                              |

### 論点ごとの理由

- **案1a**: もとの問題は「前回の結果の使い回し」で起きた。案1a は対象を絞るだけで、毎回ゼロから検査するので、
  static mutant の結果も毎回作り直される。手元の実測で、1 ファイルに絞ると約 25 秒だった（`src/util/datetime.ts`・
  2026-09-24）。CI ではインストールを含めて数分に収まる見込み。
- **案1b** はもとの問題がそのまま戻る。**案1c** は、PR の段階で検査が無くなり、テストの穴がマージ後にしか
  分からない。**案1d** は今回の問題（待ち時間）を解かない。
- **案2a**: 機能 PR を絞った分、公開する中身の全体を必ず 1 回フルで検査する場所が要る。develop への push でも
  フル run はしているが、失敗してもマージは止まらない。`main` への PR は必須チェックなので、ここでのフル run は
  公開を止められる。リリースは数日に 1 回で、約 11 分は許容できる。
  見分け方を「`main` への PR か」にするのは、git-flow で `main` に入る PR はリリースか hotfix で、どちらも公開する
  中身そのものだから。ブランチ名を見ないので、名前を付け間違えても検査が漏れる側に倒れない。back-merge PR の
  特別扱いも要らなくなり、ワークフローの分岐が 1 つ減る。

### 機能 PR で漏れるものと、それを拾う場所

変更したファイルに絞ると、**変えていないファイルのミュータントが、ほかの変更の影響で生き残るようになる**
場合は PR で見えない。例: 共有しているテストの補助関数を弱めた、隣でない場所のテストを消した。

- develop への push のフル run で見える（マージ後。必須ではないので、赤くなったことに人が気づく必要がある）。
- リリース PR のフル run で必ず止まる（必須チェック）。
- `test/` の変更と依存・設定の変更はフル run に倒すので、影響範囲の広い変更はこの漏れに入らない。

### Consequences

- Good: 実装とその隣のテストだけを変える PR（大半）は、待ち時間が 10 分台から数分になる見込み。
  もとの問題（使い回した結果による誤判定）は起きない。公開の前には必ずフル run が通る。
- Bad: 変えていないファイルへの影響は、PR では見えずマージ後に分かる。develop への push の失敗に気づく運用が要る。
- Bad: 判定のスクリプトとワークフローの分岐が増える（スクリプトはテストで押さえる）。
- Neutral: リリース PR（`main` への PR）は毎回約 11 分かかる（いまは skip されていた）。

## 信じている入力

| 値                      | 出どころ                           | 誰が書けるか | 守り方                                                       | 誤っていたら             |
| ----------------------- | ---------------------------------- | ------------ | ------------------------------------------------------------ | ------------------------ |
| PR の変更ファイルの一覧 | `git diff`（base とマージ結果）    | PR の作者    | 規則に当てはまらないものが 1 つでもあればフル run            | フル run（遅くなるだけ） |
| `mutate` の対象かどうか | `stryker.config.json` の `mutate`  | 保守者       | 判定は同じパターンを読んで使う（ワークフローに書き写さない） | 読めなければフル run     |
| 隣のテストと実装の対応  | ファイル名（`x.test.ts` ↔ `x.ts`） | 保守者       | 隣の実装が無ければフル run                                   | フル run                 |

## Pros and Cons of the Options

- 案1a — Good: 速い。使い回さないので誤判定しない。Bad: 変えていないファイルへの影響は PR で見えない。判定が増える。
- 案1b — Good: 速い。Bad: もとの問題が戻る。
- 案1c — Good: いちばん速い。Bad: テストの穴がマージ後にしか分からない。
- 案1d — Good: 漏れが無い。Bad: 待ち時間が解けない。
- 案2a — Good: 公開する中身を必ずフルで検査する。ブランチ名に頼らない。Bad: リリース PR に約 11 分かかる。
- 案2b — Good: リリースが速い。Bad: 機能 PR を絞ると、公開の前に必須のフル run が無くなる。ブランチ名で見分ける。
