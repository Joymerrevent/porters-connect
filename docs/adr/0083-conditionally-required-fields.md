# 83. 条件付き必須（`※`）は型で止めず、無条件必須（`●`）だけを `create` の必須にする

- Status: accepted
- Date: 2026-09-18
- Deciders: jun.shiromoto (Joymerrevent)

## Context and Problem Statement

PORTERS のリソース表は「新規必須」列に 2 種類のマークを付ける。

| マーク | 意味             | 例                                                                                     |
| ------ | ---------------- | -------------------------------------------------------------------------------------- |
| `●`    | 無条件に必須     | `Sales.P_Owner`                                                                        |
| `※`    | **条件付き**必須 | `Sales.P_Client` / `P_Recruiter` / `P_Job` / `P_Contract` / `P_Candidate` / `P_Resume` |

[ADR-0019][adr19] の案W2 は「`create` は**新規必須の項目を型で必須**にする」と決めたが、
**`●` と `※` を区別していない**。実装は `●` だけを `REQUIRED_ON_CREATE` に入れており
（`src/resources/sales.ts`）、理由はコードのコメントと[書き込みの制約ガイド][limits]にある。
けれども**決定としては記録されていない**。

これが効くのは公開型 `SalesCreateInput` の形で、**変えれば破壊的変更**になる。
`1.0.0` の前に確定させたい。

問い: **`※` の項目を、公開の入力型で必須にするか。しないなら、その規則は何か。**

Sales の `※` が表しているのは**依存の連鎖**で、平らな必須リストでは表せない（[出典][limits]）。

```text
Sales.P_Job -> Sales.P_Recruiter -> Sales.P_Client <- Sales.P_Contract
（A -> B は「A は B の下位リソース」）
```

- 下位を指定するなら、その**上位も同時に**指定する。`P_Job` を出すなら `P_Recruiter` と `P_Client` も要る。
- クリアは**逆向き**（上位をクリアするなら下位も一緒に）。
- `P_Candidate` と `P_Resume` は**新規登録時に両方**。更新で片方だけ指定した場合は、
  指定した値と**更新前のもう一方の値**で検査される。

**つまり「6 つのうちどれが要るか」は、送ろうとしている組み合わせと、更新なら
サーバー側の現在値で決まる。** 呼び出し時点の型だけでは決まらない部分がある。

## Decision Drivers

- **フェイルセーフ**＝壊れたときに安全側へ倒れる。ここでの安全側は後述のとおり**非対称**。
- **公開型は `1.0.0` の契約**。緩い → 厳しい は破壊的変更なので、迷ったら**緩い側から始める**。
- **出典に無いものを発明しない**（[ADR-0002][adr2]）。`※` の正確な条件は**ドキュメント由来で未検証**
  （[LV-5][lv] は `●` の列だけを「確定」にしている）。
- **薄く・堅く**（CLAUDE.md）。第1層にビジネスロジックを持ち込まない。

### 安全側がどちら向きか（この決定の要）

**手前で弾く**のと**サーバーに弾かせる**のとでは、失敗したときの回復可能性が違う。

| 弾く場所           | 利用者から見た結果                                    | 回避できるか                         |
| ------------------ | ----------------------------------------------------- | ------------------------------------ |
| クライアント（型） | **コンパイルが通らない**                              | **できない**（ライブラリの修正待ち） |
| サーバー           | 型付きエラー（`PortersResourceError` ＋ Result Code） | できる（値を直して再送）             |

**規則の見立てが誤っていた場合、厳しすぎる側の誤りは利用者が回避できない。**
緩すぎる側の誤りは往復 1 回と型付きエラーで済む。`※` の条件が未検証である以上、
ここでの「安全側」は**緩い側**になる。

## Considered Options

- 案A: **`●` だけを型の必須にする**（現状の明文化）。`※` はサーバーに委ね、ガイドに規則を書く。
- 案B: **`※` も一律で必須にする**（6 項目とも `SalesCreateInput` の必須キーにする）。
- 案C: **依存の連鎖を型で表す**（取りうる組み合わせの union で、`P_Job` 単独指定などを弾く）。
- 案D: **送信前の実行時ガードで検査する**（型は緩いまま、`create` の中で連鎖を検査して throw）。

## Decision Outcome

採用: **案A** — **`●`（無条件必須）だけを型の必須にし、`※`（条件付き必須）はサーバーに委ねる**。
規則はリソース横断で 1 つ: **`REQUIRED_ON_CREATE` に入れてよいのは出典の「新規必須」列が `●` の項目だけ**。

理由は上の非対称性に尽きる。`※` の条件は[出典][limits]の散文から起こしたもので**実機未確認**であり、
その未確認の規則を公開型に焼き付けると、**誤っていたときに利用者が回避できない**。
案A なら誤りの代償は往復 1 回と型付きエラーで、`1.0.0` 後に**緩い → 厳しい**へ動かす道も残る
（逆向きは破壊的変更になるので塞がる）。

案B は明確に誤りである。`P_Client` だけを指定する呼び出しは**出典の規則で正当**なのに弾いてしまう。

案C は Sales の `create` に限れば書ける（連鎖 5 状態 × Candidate/Resume のペア 2 状態）。
だが**更新の「更新前の値と突き合わせる」条件は型に載らない**（サーバー状態に依存する）ので、
`create` だけ型で締めて `update` は委ねる形になり、**同じ項目の規則が 2 か所で違う説明**になる。
未確認の規則に対してその複雑さを払う段階ではない。

案D は型を壊さずに検査を足せるが、**弾く場所がクライアントである点は案C と同じ**で、
誤ったときに回避できない。加えて[送信前ガード][adr46]は現状「長さ」「形式」といった
**送信内容だけで閉じる検査**に限っており、リソース間の意味的な規則を持ち込むと第1層が厚くなる。

> **決定の実質は「現状維持」だが、記録が要る理由**: いまの形は 2 つの accepted な決定
> （[ADR-0019][adr19] W2 ＋ [ADR-0061][adr61] 論点4 の「サーバー状態に依存する条件は委ねる」）から
> **導かれてはいる**が、どちらも `※` を名指ししていない。公開型の形を決めているのが
> **コードのコメントだけ**という状態を `1.0.0` に持ち込まないための起票。

### Consequences

- Good: 公開型が**出典の `●` 列と 1:1** になる。判断の余地が入らず、リソースが増えても同じ規則で決まる。
- Good: 未確認の規則を契約に焼き付けない。実機で条件が判明したら、**その時点で**締めるか決められる。
- Bad: **`P_Job` だけを渡すコードはコンパイルが通り、実行時に PORTERS が弾く**。
  往復 1 回と、利用者が受け取るエラーの解釈が要る。
- Bad: 型だけ見ても依存の連鎖は分からない。**ガイドを読ませることに依存する**
  （[書き込みの制約][limits]に表と図を置いてある）。
- Neutral: `※` を持つリソースは Sales だけではない。同じ規則が Client / Recruiter / Job などの
  `※` にも及ぶ（それらは現状も `●` だけを必須にしている＝挙動は変わらない）。

## 信じている入力

| 値                                | 出どころ                                       | 誰が書けるか | 守り方                                                            | 取れなかったら                     | 誤っていたら                                   |
| --------------------------------- | ---------------------------------------------- | ------------ | ----------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------- |
| 「新規必須」列の `●` / `※` の区別 | PORTERS のリソース表（`docs/usage/reference`） | PORTERS 側   | **仕組み**（カタログの `REQUIRED_ON_CREATE` と reference の突合） | 列が読めない＝必須リストを作らない | 必須の取りこぼし → 実行時に Result Code で判明 |
| `※` の依存連鎖の内容              | PORTERS の Write 記事（散文）                  | PORTERS 側   | **散文のみ**（ガイドに書き写す・型では強制しない）                | 規則が書けない＝委ねる側に倒す     | **委ねているので実害なし**（サーバーが正）     |
| 利用者が渡す参照 ID の実在        | 利用者のコード                                 | 利用者       | **検査しない**（[限界][limits]に明記）                            | —                                  | サーバーが Result Code で返す                  |

**この決定は「厳しくするのはいつでもできる／緩くするのは破壊的変更」という非対称に賭けている。**
賭けが外れる形は「PORTERS が実は 6 項目すべてを無条件に要求していた」だが、
その場合でも**利用者にはサーバーのエラーが届く**（黙って壊れない）。
`※` の条件は [LV-5][lv] の隣に置く実機確認事項のままにする。

## Pros and Cons of the Options

### 案A（`●` だけを必須・推奨）

- Good: 出典の列と 1:1。規則が 1 つで、リソース横断で同じ。
- Good: 誤ったときの代償が小さく、後から締められる。
- Bad: 依存の誤りは実行時まで分からない。

### 案B（`※` も一律必須）

- Good: 「必須」という言葉に忠実に見える。
- Bad: **正当な呼び出しを弾く**（`P_Client` だけの指定）。出典の規則と矛盾する。
- Bad: 利用者に回避手段が無い。

### 案C（依存を型で表す）

- Good: `P_Job` 単独指定のような誤りをコンパイル時に捕まえられる。
- Bad: `update` の条件（更新前の値との突き合わせ）は型に載らず、`create` だけ厳しくなる。
- Bad: union が大きくなり、型エラーの読みにくさを利用者が払う。
- Bad: **未確認の規則**を公開型に焼き付ける。

### 案D（送信前の実行時ガード）

- Good: 型を複雑にせずに誤りを早く返せる。
- Bad: 弾く場所はクライアントのまま＝誤っていたら回避できない。
- Bad: 送信内容だけで閉じない検査を第1層に持ち込む（[ADR-0046][adr46] のガードの性格と違う）。
