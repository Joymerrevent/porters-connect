# 106. 結果の分からない `create` の案内を広げ、表に無い Result Code を分類する

- Status: proposed
- Date: 2026-09-26
- Deciders: jun.shiromoto (Joymerrevent)

> 起票元はレビュー台帳の [RV-123][rv123] と [RV-114][rv114]。どちらも Low で、動きは安全側に倒れている。
> RV-123 は [ADR-0103][adr103] が決めた「登録された可能性あり」の案内の範囲を広げるか、RV-114 は [ADR-0006][adr6] の
> コードの対応表に無いコードを分類するかを問う。どちらも accepted な決定の範囲を変えるので、この ADR で決める
> （2 つを 1 本にまとめたのは decider の指示。どちらもエラーの分類と案内の見直し）。

## Context and Problem Statement

### 論点 1: 送った後の `create` の、再試行しない失敗（RV-123）

[ADR-0103][adr103] は、送信済みの非冪等な書き込み（`create`）が**再試行できる失敗**（通信の失敗・Code `302` など）で終わったとき、
`retryable: false` と「登録された可能性あり。重複を確かめてから再実行を」という hint で届けると決めた
（`src/http/requester.ts` の `recoveryFor` と `asUnknownOutcome`）。

ただ、**再試行しない失敗のなかにも、登録まで進んだかが分からないもの**がある。

| 失敗                                                      | いまの届き方                                  | 登録まで進んだか                             |
| --------------------------------------------------------- | --------------------------------------------- | -------------------------------------------- |
| Code `1000`（処理失敗）                                   | `category: "server"`・hint なし               | 分からない（「処理失敗」としか言わない）     |
| 表に無い Code                                             | `category: "unknown"`・hint なし              | 分からない                                   |
| HTTP 200 で本文が読めない（`unparseable write response`） | `category: "unknown"`・中間装置を疑う hint    | 分からない（何が答えたかが分からない）       |
| Code `8`・`100`〜・`301`・`400`・`403` など               | `validation` / `conflict` / `permission` など | 進んでいない（PORTERS が理由を返して断った） |
| HTTP 3xx / 4xx（PORTERS の本文なし）                      | `unknown` / `config` / `permission`           | 進んでいない見込み（API の手前で止まった）   |

どれも自動では再送しないので、重複は作らない（安全側）。欠けているのは、利用者が「登録されたかもしれない」と
気づく手がかりだけ。問いは、**送った後の `create` が、PORTERS が「処理しなかった」と言っていない失敗で終わったとき、
再試行できるかどうかにかかわらず、同じ案内を付けるか**。

### 論点 2: ADR-0006 の表に無い Result Code（RV-114）

reference の 2 つの表（[result-codes.md][rc]・[errors.md][autherr]）には、[ADR-0006][adr6] の対応表に無いコードが 3 つある。
いまはどれも「上記以外」＝ `unknown`（再試行しない）に落ちる。

| API            | Code  | reference の意味         | 近いコードの分類                                        |
| -------------- | ----- | ------------------------ | ------------------------------------------------------- |
| Resource       | `5`   | ユーザー ID 無効         | `401` / `402`（トークンの問題）は `auth`                |
| Authentication | `113` | 登録アプリのサイトが無い | `104`（app_id が無効）・`105`（secret が無効）は `auth` |
| Authentication | `-1`  | キャンセル               | —（ブラウザの同意画面で断った場合とみられる）           |

表と実装のずれは、`src/errors/*-error.test.ts` が reference の表を読んで検出する（分類していないコードを明示的に並べる。#453 で足す。RV-114 の処置）。
問いは、**この 3 つを分類するか**。

## Decision Drivers

- **取り消せない重複に気づけること**（フェイルセーフ）。削除 API が無いので、気づくのが遅れるほど直しにくい。
- **分からないことを分かったように言わない**。「進んでいない」と PORTERS が言っている失敗に「登録された可能性あり」を付けない。
- **既にある案内を失わない**。中間装置を疑う hint などは、それ自体が手がかり。
- **分類は reference の意味に基づける**。意味の分からないコードは `unknown` に倒す（ADR-0006 のフェイルセーフ）。

## Considered Options

論点 1:

- **案1A: 範囲を広げる**。送信済みの `create` が、`category` が `server` か `unknown` の失敗で終わり、PORTERS の本文を読んだか
  （`code` がある）、HTTP 2xx で本文が読めなかったときは、再試行できるかにかかわらず「登録された可能性あり」の hint を付ける。
  元の hint があれば、その後ろに続ける。
- 案1B: 今の範囲（再試行できる失敗だけ）のままにする。RV-123 は対応しないで閉じる。
- 案1C: 案内の文ではなく、エラーに `mayHaveApplied` のような公開のプロパティを足す。

論点 2:

- **案2A: `5` と `113` を `auth` にし、`-1` は `unknown` のままにする**。
- 案2B: 3 つとも `unknown` のままにする。RV-114 は、表と突き合わせるテストを足したところで閉じる。
- 案2C: 3 つとも分類する（`-1` は `permission`）。

## Decision Outcome

**未決（proposed）**。推奨は **案1A と 案2A**。

### 推奨の理由

- **案1A**: 利用者が重複に気づく手がかりを、「分からない」失敗すべてにそろえる。PORTERS が理由を返して断った失敗
  （`validation` など）と、API の手前で止まった失敗（PORTERS の本文が無い 3xx / 4xx）には付けないので、
  「分からないことを分かったように言わない」も守れる。中間装置の hint は消さずに続けるので、手がかりは減らない。
  公開の型は変わらない（hint の文が増えるだけ）。
- **案1C を推さない理由**: 公開 API が増え、`retryable` との関係（どちらを見ればよいか）を利用者に説明し直すことになる。
  案1A で足りない場面が出てから考えればよい。
- **案2A**: `5` と `113` は、近いコードと同じ種類（トークン・アプリの登録の問題）で、reference の意味から分類できる。
  `auth` にしても再試行の動きは変わらない（自動の取り直しは Resource の `401` / `402` だけが引き金。`src/http/requester.ts`）。
  `-1` は意味が状況で変わりうる（同意画面でのキャンセルか、それ以外か、reference に説明が無い）ので、`unknown` に残す。

### Consequences（案1A・案2A を採った場合）

- Good: 送った後の `create` の「分からない」失敗すべてで、重複を確かめる案内が出る。表と実装のずれが、テストで見える。
- Bad: hint が長くなる場合がある（元の hint ＋ 登録の可能性）。`5` / `113` の `category` が `unknown` から `auth` に変わるので、
  `category` で振り分けている利用者には振る舞いの変化になる（再試行はどちらもしない）。
- Neutral: `retryable` はどちらの案でも `false` のまま。ADR-0006 の表の決定は、この ADR が accepted になったら行を足した形に改める
  （ADR-0006 の本文は書き換えず、この ADR への参照を足す）。

## 信じている入力

| 値                         | 出どころ                 | 誰が書けるか      | 守り方                                             | 取れなかったら                     | 誤っていたら                                                |
| -------------------------- | ------------------------ | ----------------- | -------------------------------------------------- | ---------------------------------- | ----------------------------------------------------------- |
| 応答の Result Code         | PORTERS                  | PORTERS           | 仕組み: 数字だけを受ける                           | 読めない応答（`unknown`）          | 表に無いコードは `unknown`。表とのずれはテストが検出する    |
| 応答が PORTERS の本文か    | 応答の本文と HTTP status | PORTERS・中間装置 | 仕組み: 読めたか・`code` があるか・status で分ける | 読めなければ「分からない」側に倒す | 中間装置の本文を PORTERS と読まないよう、既存の検査に任せる |
| コードの意味（5・113・-1） | reference                | PORTERS           | 散文: reference の表                               | —                                  | 実機で違う意味と分かったら分類を見直す（LV に記録）         |

## Pros and Cons of the Options

### 案1A

- Good: 重複に気づく手がかりがそろう。公開の型は変わらない。
- Bad: 「分からない」の判定（`category` と、本文を読めたか）をライブラリが持つ。判定の条件が増える。

### 案1B

- Good: 変更が無い。自動では再送しないので、安全側は保たれている。
- Bad: `1000` や読めない応答のとき、利用者が重複を疑うきっかけが無い。

### 案1C

- Good: 機械的に判定できる。
- Bad: 公開 API が増え、`retryable` との使い分けを説明し直す必要がある。

### 案2A

- Good: reference の意味どおりに分類でき、`-1` のように意味の分からないものは安全側に残る。
- Bad: `category` の値が変わる（利用者から見た振る舞いの変化）。

### 案2B

- Good: 変更が無い。
- Bad: 意味が分かっているコードまで `unknown` になり、利用者の手がかりが弱い。

### 案2C

- Good: 表に無いコードが無くなる。
- Bad: `-1` の意味を推測で決めることになる。
