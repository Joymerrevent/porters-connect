# 54. スナップショットと台帳の役割分担（内容重複の解消）

- Status: proposed
- Date: 2026-08-16
- Deciders: jun.shiromoto (Joymerrevent)

> [ADR-0052][adr52] 合意事項 9 が「**スナップショットは変更しない。台帳とスナップショットの内容重複は
> 別の論点で、本 ADR では扱わない**」として明示的に残した論点を決める。
> stakeholder から「スナップショットに何を見つけたかの RV は残してよい。RV の詳しい内容は
> `docs/reviews/rv/*.md` にまとめるのがよい」との提案があった（2026-08-16）。
> 決定は decider が行う（自己 accept しない）。実施は accept 後の別 PR。

## Context and Problem Statement

`/project-review` は 2 種類の成果物を残す — **台帳**（`findings.md` ＋ `rv/NNNN-*.md`・現在地）と
**各回のスナップショット**（`YYYY-MM-DD-NN.md`・その時の写真）。
[ADR-0052][adr52] で台帳を 1 件 1 ファイルに分割したことで、**同じ内容が 2 箇所にある**状態が顕在化した。

実測（2026-08-16）:

- `2026-08-16-01.md` は 238 行で、うち**観点別所見 100 行の大半が `rv/*.md` の概要・根拠・推奨と同じ内容**。
- 原因は**様式の指示そのもの**にあった。[report-format][fmt] は観点別所見について
  「root cause、根拠 `file:line`、docs/reference の該当、推奨を散文で」と指示しており、
  これは**台帳の中身そのもの**。直後に「台帳の要約ではなく『なぜ』を残す」と但し書きがあるが、
  前半と後半が矛盾していた。
- 一方、2026-06 の 5 本はもともと**観点ごとの状態記述が主**で、指摘への言及は 1 行程度＝
  実質的に望ましい形になっていた。**ルールを明文化すれば守れる**ことを示している。

重要な非対称性がある。[ADR-0052][adr52] / [ADR-0053][adr53] で扱った索引のドリフトは
「**現在形の主張が実態とズレて嘘になる**」問題だったが、スナップショットの記述は
**日付付きの過去形**なので、時間が経っても嘘にならない（「2026-08-16 時点で RV-23 は open だった」は永久に真）。
つまりここで解くべきは**正しさの問題ではなく、重複による保守コストと可読性の問題**。

決めるべきは「**どちらに何を書くか**」と「**既存のスナップショットを遡って整理するか**」。

### 先行して判明した落とし穴（実施順序に効く）

[ADR-0052][adr52] の実施中、**台帳が snapshot の上位集合だと確認しないまま snapshot を削る**という
手順を踏みかけた。実際には逆で、初期の台帳は 1 件 8 行の圧縮形式だったため
**詳細はスナップショット側にしか無かった**（RV-1 は台帳 641 字に対しスナップショット 6913 字）。
先に削っていたら**情報を失っていた**。この順序は本 ADR の決定に必ず含める必要がある。

## Decision Drivers

- **同じことを 2 箇所に書かない**（更新のたびに両方直す手間・どちらが正か分からなくなる）
- **失ってはいけない情報を先に保全する**（削る前に台帳へ回収する）
- **スナップショットは点景**（[report-format][fmt]「同日に複数回回しても追記せず連番で別ファイル」＝
  後から書き換えない運用）。この原則との折り合いをつける
- **退行検知**（「問題なし」の記録・良かった点はスナップショットにしか残らない）
- **部分読み込みのしやすさ**（AI が 1 件だけ読める＝[ADR-0052][adr52] と同じ動機）

## Considered Options

### 軸1: 何をどちらに書くか

- **案1a: 役割分担を明文化する** — 指摘の詳細（概要・根拠・影響・推奨・処置・検証）は**台帳が正**。
  スナップショットは「**その回に何を見つけたか**」（ID・重要度・一行要約・リンク）と
  「**そこでしか分からないこと**」（ゲートの実測値・気づいた経緯・判断の背景・その回だけの調査結果・
  良かった点・次アクション）を残す。
- **案1b: 現状維持** — 様式は変えず、重複を許容する。
- **案1c: スナップショットから指摘の記述を全廃** — ID の一覧とゲート結果だけにする。

### 軸2: 既存 9 本をどうするか

- **案2a: 遡って整理する**（新様式に揃える）
- **案2b: 今後の回だけ新様式にする**（既存は触らない＝点景の原則を優先）

## Decision Outcome

> **未決（proposed）**。以下は起票者の推奨であり、決定は decider が行う。

**推奨: 案1a ＋ 案2a**。

理由:

- **案1a**: 重複の原因が様式の指示にあったので、そこを直せば止まる（2026-06 の 5 本が実例）。
  案1c は行き過ぎで、**「なぜ気づいたか」「なぜその重要度にしたか」といった
  その回固有の判断が失われる**（これは台帳にも書くが、run をまたぐ視点＝
  「フェイクがエラー経路 3 つをまとめて露出させた」のような集約的観察は台帳の 1 件には収まらない）。
  案1b は保守コストを放置する。
- **案2a**: 新様式を決めておきながら**最新のスナップショットが旧様式のまま残る**と、
  次に書く人が「見本」として旧様式を読む。実際 `2026-08-16-01.md` が一番ルールから外れていた。
  点景の原則との折り合いは、**書き換えた事実を冒頭に注記する**ことで付ける
  （黙って直さない＝経緯を残す）。
- ただし**過去形の記述は腐らない**ので、案2b（既存は触らない）も十分に筋が通る。
  9 本すべてを触る手間と、当時の記録をそのまま保つ価値をどう見るかの判断になる。

### 実施時の合意事項（accept 後の別 PR）

1. **順序を守る — 「回収してから削る」**。スナップショットの記述を削る前に、
   **その内容が対応する `rv/*.md` に入っていることを確認**する。入っていなければ**先に台帳へ回収**する。
   逆順にすると情報を失う（[ADR-0052][adr52] 実施中に実際に踏みかけた）。
2. **様式を先に直す**（[report-format][fmt] / [SKILL.md][skill]）。観点別所見の指示から
   「root cause、根拠 `file:line`、推奨を散文で」を外し、**台帳へリンクして台帳に無いことだけ書く**に改める。
   これを直さないと次の run で同じ重複が再生産される。
3. **サマリ表**: ID は `rv/` の本体へリンクし、**状態は「その run 時点」**である旨を明記する
   （現在の状態は索引が正）。
4. **散文中の `RV-N` はリンクにしない**。`RV-1〜12` や `RV-13/14/15` のような範囲表記が多く、
   逐一リンク化すると読みにくい。リンクは**サマリ表の ID 列と観点別所見の見出し**に限る。
5. **独自構成のスナップショットは無理に揃えない**（`2026-06-17-01` の 3 run タイムライン、
   `2026-06-22-03` の横断監査 A 群/B 群）。観点別所見を持たないので、リンク付けと注記に留める。
6. **書き換えたスナップショットには冒頭に注記**を入れる（いつ・なぜ整理したか・内容は削除ではなく台帳へ集約された旨）。
7. **`検証`（fixed の根拠）はスナップショットに残さない** — [ADR-0052][adr52] の 7 節構成で
   台帳に受け皿ができたため。fixed 検証の run は「何を確認したか」の要約とリンクに留める。
8. **semver 影響なし**（`docs/` は tarball 非同梱）。

### Consequences

- Good: 同じことを 2 箇所に書かなくなる／台帳が「詳細の正」として一意に定まる／
  スナップショットが短くなり、その回固有の情報が埋もれない／次に書く人が読む見本が新様式になる。
- Bad: 既存 9 本を触る手間（案2a）。**点景を後から書き換える**ことになり、
  「スナップショットは不変」という単純な原則が「不変。ただし様式改訂時は注記のうえ整理する」に複雑化する。
- Neutral: 過去形の記述は腐らないので、本件は**正しさではなく重複の問題**という位置づけを維持する
  （索引のドリフトと同じ緊急度では扱わない）。

## Pros and Cons of the Options

### 案1a: 役割分担を明文化（推奨）

- Good: 重複の原因（様式の指示）を直接断つ。2026-06 の 5 本という「守れている実例」がある。
  その回固有の判断（なぜ気づいたか・なぜその重要度か）は残る。
- Bad: 「台帳に無いことだけ書く」の線引きに毎回判断が要る（機械的には決まらない）。

### 案1b: 現状維持

- Good: 何もしなくてよい。スナップショット単体で完結して読める。
- Bad: 更新のたび 2 箇所を直す。どちらが正か曖昧なまま増え続ける。

### 案1c: 指摘の記述を全廃

- Good: 重複がゼロになり、線引きの判断も不要。
- Bad: run をまたぐ集約的な観察（「フェイクがエラー経路 3 つをまとめて露出させた」）や
  重要度の判断根拠が失われる。**削りすぎ**。

### 案2a: 既存 9 本を遡って整理（推奨）

- Good: 見本が新様式に揃う。最も重複の多い最新の 1 本が直る。
- Bad: 点景を書き換える。手間が 9 本ぶん。

### 案2b: 今後の回だけ

- Good: 当時の記録をそのまま保てる。手間ゼロ。原則が単純なまま。
- Bad: 最新のスナップショットが旧様式の見本として残り続ける。
