# 68. 公開 API リファレンスの作り方

- Status: accepted
- Date: 2026-09-09（accepted: 2026-09-09）
- Deciders: jun.shiromoto (Joymerrevent)

> `1.0.0` の完成条件 **V2「リファレンス完成」**（[roadmap][rm]）の中身を決める。
> [ADR-0035][adr35] は**使い方（guide）**の構造を決めたが、**網羅的な API リファレンス**は対象外だった。

## Context and Problem Statement

現在あるドキュメントは 2 種類で、**どちらも「網羅」を保証していない**。

| 何            | 対象                     | 網羅性                                              |
| ------------- | ------------------------ | --------------------------------------------------- |
| README        | 存在に気づき最短で動かす | 意図的に絞っている（[ADR-0035][adr35] 案A）         |
| `docs/guide/` | 機能ごとの使い方 7 本    | トピック単位。**公開 API の全記号を覆ってはいない** |

一方、公開 API は `src/index.ts` でキュレーションしており、**JSDoc は英語で整備済み**（CLAUDE.md の
規約: 公開サーフェスの JSDoc は英語）。つまり**リファレンスの素材は既にコードにある**が、
それを読む手段が「ソースを開く」しかない。

利用者が「`t.candidate.search()` は何を受けて何を返すか」「`ImageWriteValue` の形は」を調べるとき、
現状は型定義を追うことになる。**世の中の TS ライブラリが持っている形の API リファレンス**を用意したい。

決めるのは 3 点。

1. **生成するか、手で書くか**
2. **どの形式で、どこに置くか**（リポジトリ内 / 静的サイト / npm ページ）
3. **陳腐化をどう防ぐか**（このリポジトリの既存の型＝「人の注意でなく仕組みで守る」に合わせる）

## Decision Drivers

- **陳腐化しないこと** — ドキュメントの穴は過去に実害が出ている（[RV-24][rv24] / [RV-27][rv27]）。
  **公開 API を変えたらリファレンスも必ず変わる**を仕組みで担保したい。
- **差分が読めること** — このリポジトリは「索引と本文の一致を CI で検査」「reference ↔ カタログ突合」など、
  **ズレを機械が見つける**形を積み重ねている。同じ形に載せたい。
- **1 人メンテの帯域** — 静的サイトのビルド・デプロイ・テーマ保守を抱え込みたくない。
- **日本語ファースト**（CLAUDE.md）と、**公開 API の JSDoc は英語**という既存規約の両立。
- **依存を増やしすぎない** — 開発依存であっても、供給網は増える。

## Considered Options

- 案A: **TypeDoc → HTML を生成し、GitHub Pages で公開**
- 案B: **TypeDoc + `typedoc-plugin-markdown` → Markdown を `docs/api/` に生成してコミット**（推奨）
- 案C: **api-extractor + api-documenter**（`.api.md` の API レポート ＋ Markdown 生成）
- 案D: **手書きのリファレンス**（`docs/reference-api.md` 等）
- 案E: **作らない**（README ＋ guide のままとし、型定義を正とする）

いずれも「素材はコードの JSDoc」という点は同じで、違うのは**出力先・網羅の担保・保守コスト**。

| ---------------------------------- | -------------- | ------------------------------------------------------------ |
| `typedoc`                          | 0.28.20        | peer は TypeScript `5.0.x`〜`6.0.x`。本リポジトリは `^6.0.3` |
| `typedoc-plugin-markdown`          | 4.13.0         | TypeDoc の出力を Markdown 化                                 |
| `@microsoft/api-extractor`         | 7.59.1         | `.api.md`（API レポート）を生成・差分検査に使える            |
| `@microsoft/api-documenter`        | 7.30.14        | api-extractor の出力から Markdown を生成                     |
| `vitepress` / `@astrojs/starlight` | 1.6.4 / 0.42.0 | 静的サイト側の器（生成物を載せる先）                         |

> ⚠️ **TypeDoc の peer は TypeScript 6.0.x まで**。本リポジトリが TS 6.1 以降へ上げると
> **TypeDoc の追従を待つ**ことになる。案A / 案B が抱える唯一の運用リスク。

## 案A と「Markdown → サイト」は**同じゴールへの 2 経路**（積み重ねではない）

議論で出た指摘: **静的サイトが Markdown を入力に取るなら、HTML を生成する必要は無いのでは。**
そのとおりで、この 2 つは順に積むものではなく**どちらか一方を選ぶ**関係にある。

| 経路                             | 誰が見た目を持つか                    | サイト生成器 | 出力                      |
| -------------------------------- | ------------------------------------- | ------------ | ------------------------- |
| 案A: TypeDoc → **HTML**          | **TypeDoc**（検索・ナビ込みの完成品） | **不要**     | そのままホストできる HTML |
| 案B ＋ サイト: Markdown → 生成器 | **こちら**（テーマ・ナビ・検索）      | 必要         | 生成器が出す HTML         |

つまり **HTML 生成の唯一の存在意義は「サイト生成器を保守しなくて済む」こと**。
逆に言えば、サイトを立てるなら案A の HTML は**要らない**。

### このリポジトリでは案A が弱い理由が 2 つある

1. **GitHub 上で読めない**。Markdown はリポジトリのファイルビューでそのまま読めるが、
   **HTML はソースが表示されるだけ**でレンダリングされない。つまり案A は
   **必ず Pages 等のデプロイとセット**になり、「まずコミットだけしておく」ができない。
   案B は**サイトを立てなくても、その日から価値がある**（GitHub で読める・差分が PR に出る）。
2. **既存ドキュメントが全部 Markdown**。README ＋ `docs/guide/` 7 本（日本語）は Markdown で、
   将来サイト化するなら**リファレンスと同じサイトに載せたい**（ナビと検索が 1 つになる）。
   案A の HTML は TypeDoc が完結して出すので、**ガイドと統合できない**（別サイトが 2 つ建つ）。

サイト化する場合の接続部品も揃っている（2026-09-09 実測）: `typedoc-vitepress-theme` 1.1.4 ／
`docusaurus-plugin-typedoc` 1.4.3。**TypeDoc の Markdown を既存ガイドと同じサイトに載せる道**は用意されている。

> **まとめ**: 案A を選ぶ理由は「サイト生成器を持ちたくない、かつ公開サイトは欲しい」ときだけ。
> 本リポジトリは既存ドキュメントが Markdown なので、**Markdown で出しておけば「サイトを作らない」
> 「後で作る」の両方に開いている**。案A は候補として残すが、優先度は低い。

## 案の可逆性（後から乗り換えられるか）

**どの案を採っても「後から HTML サイトを足す」ことはできる**。理由は、**案B も案C も最終出力が
Markdown** だから — 静的サイト（VitePress / Starlight / Docusaurus）は Markdown を入力に取る。
つまり「まず Markdown で始めて、必要になったらサイト化する」は**どの案からでも通る道**。

ただし**乗り換えのコストは案によって違う**。

| 出発点                              | 後から HTML サイトを足す                                  | 生成器の数     | 備考                                                                                                         |
| ----------------------------------- | --------------------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------ |
| **案B**（TypeDoc → Markdown）       | Markdown をサイトに載せる（`typedoc-vitepress-theme` 等） | **1 つのまま** | TypeDoc は HTML も出せるので案A へ切り替えも可能。ただし上記のとおり、**サイトを立てるなら HTML 出力は不要** |
| **案C**（api-extractor → Markdown） | api-documenter の Markdown をサイトに載せる               | **1 つのまま** | ただし出力は api-documenter のもの。**「TypeDoc の HTML」が欲しい場合は TypeDoc を追加**＝生成器 2 つ        |

**案C から「TypeDoc の HTML」を足すのは、実質的に生成器を 2 つ抱えること**になる（api-extractor 系と
TypeDoc が同じ公開 API を別々に読む）。同じものを 2 経路で生成すると、**片方だけ古くなる**状態が作れてしまう
＝このリポジトリが避けてきた形。案C を採るなら、サイト化も api-documenter の出力で通すのが筋。

### 案は排他ではない — 関心事が 2 つある

整理すると、ここには**別々の 2 つの関心事**が混ざっている。

1. **読み物としてのリファレンス** — TypeDoc / api-documenter が担う
2. **公開サーフェスの変更検出** — api-extractor の `.api.md`（API レポート）が担う

api-extractor の強みは (2) で、`1.0.0` の「公開 API の凍結」と相性が良い。よって現実的な組み合わせは:

- **案B で (1) を満たし、必要になったら api-extractor の API レポートだけ (2) として足す**（推奨の道）
- **案C で (1)(2) をまとめて引き受ける**（初期コストは高い。`api-extractor.json`・`.d.ts` ロールアップ・
  `.api.md` のレビュー運用が要る）

**どちらも後戻りできる**ので、この論点は「取り返しがつくか」ではなく「**いま払うコストと、
出力の体裁のどちらを取るか**」で決めてよい。

いずれも現役。`npm view <pkg> deprecated` はすべて空（非推奨の宣言なし）。

## 案B / 案C を実測した（2026-09-09）

議論で出た問い「`.api.md` は自分でコードごとに仕様を書くのか」に答えるため、**実際に生成した**。
答えは **100% 生成物**（手書きしない。ファイル冒頭に `Do not edit this file.` と入る）。

**やったこと**: `dist/index.d.ts`（0.14.0 のビルド成果物）を入力に、`@microsoft/api-extractor` 7.59.1 を
`--local` で実行。リポジトリは汚さず、作業ディレクトリの外に自己完結の最小プロジェクトを作って走らせた。

**得られたもの**: `porters-connect.api.md` **838 行**。実装は含まず、公開されている型と署名だけが並ぶ。

```ts
// @public
export type ImageWriteValue = {
  FileName: string;
  ContentType: ImageContentType;
  Content: string;
};
```

用途は**読み物ではなく変更検出**。コミットしておき、CI で再生成して差分が出たら落とす
＝ `pnpm check:index`（索引と本文の一致）や reference ↔ カタログ突合と同じ形。
読み物としてのリファレンスは、これとは別に api-documenter が `.api.json` から生成する。

### 実測で分かった導入コスト 3 つ

**「手書きしない」＝「タダで手に入る」ではない**。本リポジトリに適用すると、着手前に決めることが 3 つある。

| #   | 何が起きるか             | 件数       | 中身                                                                                                                                                                                                                                                                                                   |
| --- | ------------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | `ae-missing-release-tag` | **158 件** | 公開記号すべてに `@public` / `@beta` / `@alpha` / `@internal` のいずれかを要求される。JSDoc は整備済みだが**タグだけが無い**。全部に付けるか、警告を抑止するかの判断が要る                                                                                                                             |
| 2   | `ae-forgotten-export`    | **57 件**  | 公開型が**未公開の内部型を参照している**という指摘（例: `export type Activity = ReadRecord<typeof FIELDS$9>` の `ReadRecord`）。`src/index.ts` を明示 export で**キュレーションする**方針（CLAUDE.md）と、api-extractor の「エントリポイントから辿れるものは全部 export しろ」という前提が噛み合わない |
| 3   | 同梱 TypeScript が古い   | —          | `Analysis will use the bundled TypeScript version 5.9.3` ／ `The target project appears to use TypeScript 6.0.3 which is newer than the bundled compiler engine`。**TypeDoc の peer 制約と同種の問題が api-extractor 側にもある**（しかも同梱コンパイラなので、5.9.3 が 6.0.3 のコードを解析する）     |

（ほかに `ae-unresolved-link` が 1 件。TSDoc のリンク解決漏れで、軽微。）

### 案B — TypeDoc + `typedoc-plugin-markdown`（実測）

**やったこと**: `src/index.ts` を入力に、`typedoc` + `typedoc-plugin-markdown` を実行（出力先は
リポジトリ外）。案C と違い、**入力はソースそのもの**（`.d.ts` ではない）。

**得られたもの**: **182 ファイル / 合計 9,509 行**の Markdown。`README.md` と `globals.md` が索引になり、
**1 記号 = 1 ファイル**。結果は `0 errors / 58 warnings`。

**中身は「読み物」になっている** — JSDoc の本文がそのまま説明として載り、ソース行へのリンクが付く。
たとえば `ImageWriteValue` のページには、書き込み値の説明・読み値との非対称・`VERIFY(live)`（LV-22）まで、
コードに書いた英語 JSDoc がそのまま出る。**`.api.md`（署名だけ・838 行）とは目的が違う**ことが実物で分かる。

### 案C の読み物側 — api-documenter も実測した

当初この節は**案B の読み物と案C の台帳（`.api.md`）を比べていた**が、それは不公平な比較だった。
案C にも読み物側（api-documenter）があるので、`docModel` を有効にして `.api.json` を出し、
`api-documenter markdown` を走らせた。**172 ファイル / 4,854 行**。

**読み物どうしで比べると、決定的な差が 1 つ出た。**

|                            | 案B（TypeDoc → Markdown）            | 案C（api-documenter → Markdown） |
| -------------------------- | ------------------------------------ | -------------------------------- |
| 入力                       | `src/index.ts`（ソース）             | `.api.json`（`.d.ts` 経由）      |
| 出力                       | 182 ファイル / **9,509 行**          | 172 ファイル / **4,854 行**      |
| **JSDoc の Markdown 記法** | **そのまま描画される**               | **エスケープされて壊れる**       |
| ソース行へのリンク         | **あり**（SHA 埋め込みに注意・後述） | **なし**                         |
| 警告                       | 58 件（内部型の参照）                | 参照解決の警告が数件             |

**エスケープの問題**が効く。本リポジトリの JSDoc は `**required**` のように**強調を多用**している
（ドキュメント全体の書き方がそうなっている）。api-documenter はコメントを TSDoc の平文として扱うため、
これを `\*\*required\*\*` と**エスケープして出力**する。実測で **60 箇所**が壊れた。
`<!-- -->` や `\~15000` のような残骸も混ざる。

同じ記号を並べると差は明らか（入力の JSDoc は同一）:

- **TypeDoc**: `All three are **required**` … 太字として描画される
- **api-documenter**: `All three are \*\*required\*\*` … 記号がそのまま見える

つまり **api-documenter を読み物として使うなら、JSDoc から Markdown 記法を抜く**か、
**壊れた表示を受け入れる**かになる。前者は「保守者が読めること」を優先して整えてきた
コメントの質を下げる方向で、本リポジトリの方針と合わない。

（`.api.md` の台帳としての価値は別。署名だけ 838 行で、**変更検出**という目的には過不足がない。）

### 訂正 — 「内部型の参照」は api-extractor 固有ではなかった

当初「これらは api-extractor 固有のコスト」と書いたが、**実測したら TypeDoc でも同じ問題が出た**。

| 指摘                             | api-extractor                      | TypeDoc                                                                     | 性質                                                    |
| -------------------------------- | ---------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------- |
| リリースタグが無い               | **158 件**                         | **0 件**（要求しない）                                                      | **api-extractor 固有**                                  |
| 公開型が未 export の内部型を参照 | **57 件**（`ae-forgotten-export`） | **58 件**（`... is referenced by X but not included in the documentation`） | **両方で出る＝ツールの癖ではなく、この公開 API の性質** |

例: `export type ActivityPage = ResourcePage<typeof FIELDS>` の `ResourcePage` や `FIELDS` は
公開していない。だから**どちらのツールでも「参照先が辿れない」と言われる**。

これは**発見であって不具合ではない**。`src/index.ts` を明示 export でキュレーションする方針
（CLAUDE.md）の**副作用が、初めて数字で見えた**ということ。ツール選択とは別に、
**`1.0.0` の「公開 API の凍結」を考えるなら、この 57〜58 箇所をどう扱うかは避けて通れない**。

### 案B に固有の注意 — 生成物にコミット SHA が埋まる

TypeDoc のソースリンクは既定で**その時点のコミット SHA**を指す
（`.../blob/0f2c0f1de…/src/xml/encode.ts#L55`）。**生成物をコミットする案B では、
コミットのたびに 182 ファイル全部のリンクが変わる**＝差分がノイズになる。

回避はできる（`gitRevision` をブランチ／タグに固定する、または `disableSources` でリンクを出さない）が、
**採用するなら設定を決めてから**入れる必要がある。実測しなければ気づけなかった点。

## TypeScript の版制約をどう見るか（2026-09-09 実測）

案B を採る場合の唯一の運用リスクとして挙げた「TypeDoc の peer は TS `5.0.x`〜`6.0.x`」について、
**どれくらい気にすべきか**を確かめた。

**現状は適合している。** 実際にインストールされている TypeScript は **6.0.3** で、peer の `6.0.x` に入る。
引っかかるのは**宣言レンジのほう**で、`^6.0.3` は将来の `6.1.x` 以降も許すため、**TS を上げた時点で
範囲外になりうる**（`.npmrc` に `strict-peer-dependencies` の設定は無く、pnpm の既定に従う）。
なお現時点では typedoc をまだ依存に入れていないので、この制約は**まだ効いていない**。

**それでも「気にしなくてよい」と判断できる理由が 3 つある。**

1. **影響範囲がドキュメント生成だけ**。ライブラリのビルド（tsup）・型検査（tsc）・テスト・公開物には
   一切関係しない。壊れても**利用者に届くものは何も変わらない**。
2. **静かに壊れない**。TS を上げるのは Dependabot の PR なので、ドキュメント再生成のゲートが
   その PR の CI で落ちる＝**気づく**。リリース後に発覚する類の問題ではない（fail-safe 側）。
3. **案C はこの軸でもっと悪い**。api-extractor は TypeScript を**同梱**しており、
   実測では**今日すでに**「bundled 5.9.3 / target 6.0.3」の警告が出ている。
   つまり版追従の問題は案B を避ける理由にならない。

**起こりうる実害は 1 つだけ**: TypeDoc が新しい TS minor に対応するまで、TS の更新を保留することになる。
TypeDoc のリリース間隔は実測で**おおむね月 1 回**（0.28.15〜0.28.20 が 2025-11〜2026-07）。

> ⚠️ 対処として「ドキュメントのゲートを警告に落とす」ことは**しない**。それは fail-open で、
> 「生成が壊れたまま気づかない」状態を作る。素直に**待つ**か、TS の更新を保留するのが安全側。

## Decision Outcome

**決定（accepted・2026-09-09）: 案B — TypeDoc + `typedoc-plugin-markdown` で Markdown を生成し、
リポジトリにコミットする。CI で再生成して差分が出たら落とす。**

決め手は**実測**だった（上記「案B / 案C を実測した」）。

- **読み物として JSDoc がそのまま活きる**。api-documenter は Markdown 記法をエスケープし、
  実測で **60 箇所**が壊れた。本リポジトリの JSDoc は強調を多用しているので影響が大きい。
- **ソース行へのリンクが付く**（api-documenter には無い）。
- **リリースタグ 158 件の前工程が要らない**（案C 固有のコスト）。
- TypeScript の版制約は**ドキュメント生成にしか影響せず**、壊れても CI で気づく（上記の評価）。

案B を推す理由:

- **生成物をリポジトリに置く**ので、公開 API を変えると**リファレンスの差分が PR に出る**。
  レビューで「この変更は利用者に何が見えるか」が読める＝このリポジトリが繰り返し使っている型。
- **陳腐化を仕組みで防げる**: CI で再生成して `git diff --exit-code`（`pnpm check:index` と同じ発想）。
  生成し忘れると**落ちる**ので、人の注意に頼らない。
- **静的サイトを抱えない**。GitHub 上で Markdown がそのまま読め、リンクは既存 docs と同じ相対リンク。
  サイトが要るようになったら、Markdown を VitePress / Starlight に載せるのは後からできる（案A へ移行可能）。
- 手書き（案D）は質は上がるが、**公開 API の記号数に比例して陳腐化する**。このライブラリは
  `src/index.ts` の export が多く、1 人メンテでは追随しきれない。

案C（api-extractor）は**公開サーフェスの変更検出**が強力で、`1.0.0` の「公開 API 凍結」と相性が良い。
ただし本 ADR の目的は**読み物としてのリファレンス**なので、**別の関心事**として切り分ける。
`.api.md` を台帳として足すかどうかは、公開 API 凍結を考えるときに別 ADR で判断する。

### 実装時に決めること（本決定を変えない範囲）

実装は**別 PR**。着手時に次の 4 点を確定する。

1. **ソースリンクの扱い** — 既定ではリンクにコミット SHA が埋まり、**毎コミットで 182 ファイルが変わる**。
   `gitRevision` をブランチ／タグに固定するか、`disableSources` で出さないかを決める。**放置しない**。
2. **出力先** — `docs/api/` を想定（既存 `docs/guide/` と並ぶ位置）。
3. **CI ゲート** — 再生成して `git diff --exit-code`。生成漏れは落とす（`pnpm check:index` と同じ形）。
4. **内部型の参照 57〜58 箇所** — 公開型が未 export の内部型を参照している件。**これは案B 固有ではなく
   公開 API そのものの性質**（案C でも同数出た）なので、本 ADR では扱わない。`1.0.0` の公開 API 凍結を
   考えるときに別途決める。当面は警告のまま生成する。

### 実装時に決めたこと（2026-09-10・実測つき）

**決定1: `gitRevision: "main"` に固定する**（`disableSources` は採らない）。

churn を実測したところ、**問題は SHA だけ**で、行番号は思っていたほど動かなかった。

| 設定                   | ソースリンク | コメント 1 行の追加で変わるファイル   |
| ---------------------- | ------------ | ------------------------------------- |
| 既定（SHA 埋め込み）   | 402 本       | **175 / 176**（＝中身が同じでも全部） |
| `gitRevision: "main"`  | 402 本       | **2 / 176**（定義位置が動いた分だけ） |
| `disableSources: true` | 0 本         | 0 / 176                               |

SHA をブランチ名に替えるだけで churn は 175 → 2 に落ちる。残る 2 ファイルは
**記号の定義位置が実際に動いた**ぶんなので、消すべき差分ではない。
`disableSources` は churn を 0 にできるが、**「ソース行へのリンクが付く」は案B を選んだ決め手の 1 つ**
だったので、それを捨ててまで 2 ファイルを削る理由が無い。

> **`sourceLinkTemplate` で `#L{line}` を外す案も試したが無意味だった** — 行番号は URL だけでなく
> **リンクの表示テキスト**（`[src/client.ts:140](…)`）にも入るため、churn は 2 ファイルのまま変わらない。
>
> `main` を選んだのは、リファレンスを読むのは**公開版の読者**だから。develop で追加した記号の
> リンクはリリースまで解決しないが、その間に読むのは開発者だけなので許容する。

**決定2: 出力先は `docs/api/`**（想定どおり）。入口は `docs/api/index.md`（`entryFileName`）。

**決定3: ゲートは `pnpm check:api`**（`scripts/check-api-reference.mjs`）。ADR は
`git diff --exit-code` と書いていたが、**一時ディレクトリへ生成して中身を突き合わせる**形にした。
素の `git diff` は作業ツリーが汚れていると誤検知し、検査のために `docs/api` を書き換えてしまう
（検査に副作用がある）。検出したい事象は同じで、`pnpm docs:api` と同じ `typedoc.json` を使うので
設定が片方だけ変わることもない。**落ちることを実測で確認済み**（宣言側の JSDoc を 1 行変えると
`functions/defineFields.md` を名指しして落ちる）。

**決定4: 内部型の 58 件は警告のまま**（ADR の指示どおり）。`treatWarningsAsErrors: false` と
`validation.notExported: true` で「出すが落とさない」にした。0 件にするかは公開 API 凍結の議題。

**副産物として V2 の達成を確認した**: `dist/index.d.ts` の export 節にある **177 記号すべてに
リファレンスのページがある**（176 ページ ＋ 索引）。TypeDoc は entry point から到達できる記号を
すべて出すので、これは偶然ではなく**構造的に保たれる**（記号を足せばページが増え、
足し忘れれば `check:api` が落ちる）。

> **注意**: `src/index.ts` の**再 export 行に書いたコメントはリファレンスに出ない**（実測）。
> TypeDoc は宣言側の JSDoc を読むため。`src/index.ts` のキュレーション用コメントは
> **保守者向け**であって利用者向けではない、という前提で書くこと。

### Consequences

- Good: 公開 API の変更が**リファレンスの差分として PR に現れる**。CI が生成漏れを落とす。
- Good: 静的サイトの運用コストが 0。後からサイト化する道も残る。
- Bad: **生成物をコミットする**ため差分が大きくなる（`dist` を置くのとは違い、読み物なので許容範囲か要判断）。
- Bad: TypeDoc の TS 対応に版が縛られる（上記の peer 制約）。
- Neutral: JSDoc が**そのまま利用者向けの文章になる**＝英語のまま出る。日本語ファースト方針との整合は
  「guide は日本語・リファレンスは英語（コード由来）」で切り分ける想定（要確認）。

## 信じている入力

該当なし — 本決定は**ビルド時に自分のソースから生成する**話で、外部 API・LLM・第三者が書ける文書からの
入力を受け取らない。生成元は同一リポジトリの TypeScript と JSDoc であり、CI の再生成差分検査が
「生成物と入力のズレ」を検出する。

## Pros and Cons of the Options

### 案A TypeDoc → HTML ＋ GitHub Pages

- Good: 見た目が整い、検索・相互リンクが効く。利用者に URL 1 本を出せる。
- Bad: デプロイ経路とテーマの保守を抱える。**差分が PR に出ない**（生成物がリポジトリに無い）。

### 案B TypeDoc → Markdown をコミット（推奨）

- Good: 差分が PR に出る。CI で生成漏れを落とせる。サイトは不要。後から案A へ移行できる。
- Bad: 生成物の差分が大きい。Markdown の表現力は HTML に劣る。

### 案C api-extractor + api-documenter

- Good: `.api.md` の API レポートで**公開サーフェスの変更を検出**できる（凍結宣言と相性が良い）。
  レポート自体は**完全な生成物**で手書きしない（上記「案C を実測した」）。
- Bad: 設定が重く、目的（読み物）に対して過剰。2 つのツールを抱える。
- Bad: **着手前にリリースタグ 158 件**の方針決めが要る（案B には無いコスト）。
  内部型の export（57 件）は**案B でも 58 件出る**ので、案C 固有のコストではない（上記「訂正」）。

### 案D 手書き

- Good: 読み物として最良。順序・強調を設計できる。
- Bad: **必ず陳腐化する**。公開 API の記号数に対して 1 人では追随できない。

### 案E 作らない

- Good: コスト 0。型定義は IDE で読める。
- Bad: 「リファレンスの完成」を `1.0.0` の条件にした以上、**条件を満たさない**。
