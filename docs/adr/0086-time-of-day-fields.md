# 86. DateTime の時分型は宣言で区別し、`HH:mm` で入出力する

- Status: proposed
- Date: 2026-09-20
- Deciders: jun.shiromoto (Joymerrevent)

> 2026-09-20 の出典再取得（[#347][pr347]）で見つかった **PORTERS 9.3.0（2026/08/04）の項目タイプ「時分型」**
> への対応方針。ライブラリは今この型を**知らない**。Field Type が年月日時分型と同じ `12` で API からは
> 区別できないため、「どう扱うか」の前に「**誰がどこで区別するか**」を決めないと実装に入れない。
> **0.x のブロッカーではない**（時分型項目を使わないテナントには影響が無い）が、管理者が項目を
> 足した瞬間に**既存連携が Code 103 で落ちる**型の変更なので、方針だけ先に決める。
>
> 本 ADR は公開サーフェス（宣言のしかた・値の型・condition）を決める。内部のラベルの持ち方は
> 論点5 に方向だけ書き、詳細は実装 PR に委ねる。

## Context and Problem Statement

### 正典の形

出典は [Data Type: DateTime（時分型）の追加][src-announce]（2026/08/04・PORTERS 9.3.0）と、
それを受けて改訂された [Field Type & Data Type List][src-fdt]（2026-07-28）／[Read API - Parameter][src-param]
（2026-07-28）。要約は [field-data-types][ref-fdt] の「時分型」節。

| 場面                | 出典の記述                                                                                                                                                                                                                                                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 何か                | 「時刻（時分）のみを保持する項目です。PORTERS の画面では **00:00〜47:59** の範囲で入力できます。**Field Type は年月日時分型と同じ「12（DateTime）」**」                                                                                                                                                                       |
| 保存                | 「データベース上は **1970/01/01 を基準日**とした年月日時分として保存されます（24:00〜47:59 は 1970/01/02）」。例: 09:00 → `1970/01/01 09:00`、26:00 → `1970/01/02 02:00`                                                                                                                                                      |
| Read                | 「年月日時分型と同じ `[yyyy/mm/dd HH:MM:SS]` の書式で出力されます。例: `<Job.U_XXX>1970/01/01 09:00:00</Job.U_XXX>`」「**HH:MM のみの書式では出力されません**」「**タイムゾーンによる変換は行われません**」                                                                                                                   |
| Write               | 「`[1970/01/01 HH:MM:SS]`（00:00〜23:59）」「`[1970/01/02 HH:MM:SS]`（24:00〜47:59 に相当）」「基準日以外の年月日を指定した場合はバリデーションエラーとなり、**Code 103** が返ります（HTTP ステータスは 200）」                                                                                                               |
| Search（condition） | 「基準日を付けた書式で指定します」。例: `condition=Job.U_XXX:ge=1970/01/01 15:00:00,Job.U_XXX:le=1970/01/02 02:00:00`。「不正な書式を指定した場合は **Code 100** が返り検索は実行されません（HTTP ステータスは 200）」「order には年月日時分型と同様の仕様で指定できます」                                                    |
| 判別                | 「時分型項目は、Field - Read では年月日時分型と同じ Field Type = 12 として取得されます。**現在、API のレスポンスから対象の項目が時分型かどうかを判別する手段は提供されていません**」「PORTERS のカスタマイズ画面（項目&詳細）で対象の項目が時分型であることをご確認のうえ、項目のエイリアスを指定して個別に対応してください」 |
| 既存連携への影響    | 「既存の連携プログラムが当該項目を年月日時分型と同様に扱い、任意の日時（例：2026/07/09 09:00:00）を書き込むと、**Code 103 エラーが発生します**」                                                                                                                                                                              |
| ヘッダ              | 「時分型項目の利用にあたり、HTTP Header（X-P-ConnectAPI-Version）の指定は不要です」                                                                                                                                                                                                                                           |

**PORTERS 側に 3 つの事実がある**: ① 型の体系（Field Type / Data Type）は増えていない＝**Data Type は 17 のまま**
（[field-data-types][ref-fdt]）。② 標準項目（`P_*`）に時分型は無く、**テナントのカスタム項目（`U_` / `A_`）
としてしか現れない**（9.3.0 で「作成できる項目タイプ」として足されたもの。Link / Image と同じ位置づけ＝
[ADR-0064][adr64]）。③ **API からは判別できない**ので、ライブラリが自動で正しく扱う道は無い。

### ライブラリの現状（2026-09-20・実装を読んだ結果）

ライブラリは FT-12 を `DateTime` として ISO 8601（UTC・`Z` 付き）に正規化する（[ADR-0011][adr11]・
[PRD R-10][prd]）。変換は `src/util/datetime.ts` の 2 関数で、**タイムゾーン演算をしない書式変換**である:

- Read: `portersDateTimeToIso("1970/01/01 09:00:00")` → `"1970-01-01T09:00:00Z"`。**値は欠けない**が、
  「UTC の日時」というラベルが付いて届く（時分型は UTC ではないし日時でもない）。
- Write / condition: `isoToPortersDateTime` は `Date.parse` → UTC の各要素で組み立てる。
  `"1970-01-01T09:00:00Z"` なら `1970/01/01 09:00:00` に戻り**通る**。しかし `"1970-01-01T09:00:00+09:00"`
  は `1970/01/01 00:00:00` になり、**黙って 9 時間ずれる**（Code は返らない＝気づけない）。
  `"2026-07-09T09:00:00Z"` のような普通の日時は PORTERS が Code 103 で拒否する（これは surface される）。

つまり**今の倒れ方は「値が通るか黙ってずれるか」**で、ずれる側がフェイルセーフに反する。
しかも 26:00 のような値を書くには `1970/01/02 02:00` の規則を利用者が自分で組む必要がある。

問い: **時分型を、① 誰がどこで区別し、② どんな値で入出力し、③ 誤って年月日時分型として扱ったとき
どう倒れ、④ condition / order でどう書けるようにするか。**

## Decision Drivers

- **フェイルセーフ** — 黙ってずれる経路を無くす。PORTERS が Code 100 / 103 で拒む値は**送信前に**
  `PortersConfigError` で止める（[ADR-0046][adr46] の経路）。
- **PORTERS の事実に忠実** — Data Type の列挙を発明しない（[ADR-0016][adr16]・D3 の 17/17 検査）。
  判別できないものを「判別できる」ことにしない。
- **1970 規則を利用者に見せない** — 「26:00 は 1970/01/02 02:00」を各利用者が実装するのは、
  ライブラリが XML を外に漏らさないのと同じ理由で避ける。
- **既存の語彙の再利用** — 宣言は `defineFields` の builder（[ADR-0023][adr23]・[ADR-0064][adr64]）、
  型の食い違いは `validation` で surface（[RV-36][rv36]）。
- **公開サーフェスは必要な分だけ**。

## 論点1: 誰がどこで区別するか

- **案1a: `defineFields` の builder に `f.time()` を足し、利用者が宣言で明示する** — 推奨
- 案1b: `f.dateTime({ timeOnly: true })` のようにオプション引数で示す
- 案1c: 何も足さない。利用者が `dateTime()` のまま `1970-01-01T09:00:00Z` を自分で組む（現状）
- 案1d: 実行時に値を見て推定する（読んだ値の年が 1970 なら時分型として扱う）

**推奨は案1a。** 区別できるのはテナント管理者だけで（出典「カスタマイズ画面で確認」）、その知識を
ライブラリに渡す場所は**宣言**しかない。時分型はカスタム項目にしか現れないので、宣言必須
（[ADR-0074][adr74]）の 1 ルールにそのまま乗る＝「時分型は `f.time()` で宣言する」。Link / Image と同じ
経路（[ADR-0064][adr64] 案5a）で、新しい入口は増えない。

案1b は同じことをオプションで書くだけで、型の導出（宣言 → 値の型）が `dataType` リテラル 1 本で
回っている現状（`CatalogOf<R>` は `R[K]["dataType"]`）にオプション引数を通すと分岐が増える。
`f.age()` が `f.date()` の別メソッドであるのと同じく、**値の形が違うなら別メソッド**にする。

案1c は現状維持＝「黙ってずれる」経路を残す。案1d は**値から型を推定**する形で、年月日時分型に
1970/01/01 の値が正規に入る場合（システム移行のダミー日付など）を時分型と誤読する。読みで型が
揺れるのは RV-36 で塞いだ方向と逆。**どちらも採らない。**

## 論点2: 値の型（利用者が読む形・渡す形）

- **案2a: `"HH:mm"` の文字列（`00:00`〜`47:59`）。PORTERS の画面表記そのもの** — 推奨
- 案2b: ISO 日時 `"1970-01-01T09:00:00Z"`（現状の FT-12 と同じ）
- 案2c: 0 時からの分の整数（`540` / `1560`）
- 案2d: `{ hours: number; minutes: number }`

**推奨は案2a。** 管理者が画面で見る値（`09:00` / `26:00`）と利用者のコードの値が一致し、1970 規則は
ライブラリの内側に閉じる。**ISO 8601 の時刻ではない**（ISO の `hh` は 24 まで）ので、
[PRD R-10][prd]「日時は ISO 8601」の外に置く — 時分型は**日時ではなく時刻**で、UTC でもない
（出典「タイムゾーンによる変換は行われません」）。R-10 の対象外であることを [概念: 日時は UTC][concept-dt] に
書く。

- Read: `1970/01/01 09:00:00` → `"09:00"`、`1970/01/02 02:00:00` → `"26:00"`。**秒が `00` でなければ
  `"HH:mm:ss"` で保持する**（画面は時分だけだが、出典は秒付きの書式を出すと言うだけで「常に 00」とは
  言っていない。黙って落とさない）。
- Write / condition: `"HH:mm"` または `"HH:mm:ss"`。`HH` は `00`〜`47`、`mm` / `ss` は `00`〜`59`。
  それ以外は**送信前に** `PortersConfigError`（`category: "validation"`・項目名付き — [ADR-0006][adr6]）。
  `24:00` 以上は基準日を `1970/01/02` にして `HH - 24` を書く。

案2b は 1970 規則を利用者に押し付け、オフセット付きで渡したときのずれも残る（現状の問題そのもの）。
案2c は読み書きに換算が要り、`26:00` が `1560` になる対応を利用者が覚えることになる。案2d は
文字列 1 本で足りるところに構造を足すだけ。

## 論点3: 誤った宣言・未対応のときの倒れ方

区別を宣言に委ねる以上、**宣言が間違う**ことは前提に置く。2 方向ある。

| 実際の項目   | 宣言         | Read                                           | Write                                                                                |
| ------------ | ------------ | ---------------------------------------------- | ------------------------------------------------------------------------------------ |
| 時分型       | `dateTime()` | 通る（`1970-01-01T09:00:00Z`）。**気づけない** | `Z` 付きなら通る／オフセット付きは**黙ってずれる**／普通の日時は Code 103（surface） |
| 年月日時分型 | `time()`     | 基準日以外の日付が来る＝**検出できる**         | `HH:mm` は常に 1970 基準の値になる → PORTERS は受け付ける（**気づけない**）          |

- **案3a: 読みで基準日を検証する** — 推奨。`time()` と宣言した項目に `1970/01/01` / `1970/01/02` 以外の
  日付が来たら、[RV-36][rv36] と同じ形で `PortersResourceError`（`category: "validation"`・項目名・
  「`dateTime()` で宣言し直す」ヒント）にする。黙って `"HH:mm"` に潰さない。
- **案3b: `generateFieldDecls` が FT-12 の行に注記を出す** — 推奨（3a と併用）。宣言生成
  （[ADR-0069][adr69]）は Field Read から `12` → `f.dateTime()` を出すしかない（判別不能）。そこに
  `// FT-12: 時分型なら f.time() に直す（Field Read では区別できない）` を添える。宣言が生まれる唯一の
  場所に置く注意書きなので、ガイドの注意書きより届く。
- 案3c: `dateTime()` の Write / condition で 1970/01/01・02 の値を弾く（時分型の疑い）
- 案3d: `dateTime()` の Write でオフセット付き ISO を弾く（`Z` だけ受ける）
- 案3e: 何もしない（ガイドの注意書きだけ）

**推奨は案3a ＋ 案3b。** 「時分型を `dateTime()` と誤宣言した」側（表の 1 行目）は**ライブラリからは
原理的に見分けられない**（正規の DateTime と同じ形が来る）ので、検出できる 2 行目を確実に検出し、
1 行目は宣言の入口（3b）とガイドで潰す。案3c は年月日時分型に 1970 の値が正規に入る場合を弾いてしまい、
案3d は [ADR-0011][adr11] / R-10 の「オフセット付き ISO を UTC に換算して受ける」契約を壊す。どちらも
**正しい使い方を巻き添えにする**ので採らない。案3e は現状。

`verifyFields` / `assertFieldsMatch`（[ADR-0069][adr69]）は Field Type を突き合わせるので、`time()` も
`dateTime()` も `12` に写して**一致と判定する**。判別できないものを突合で嘘をつかないために、
`time()` は Field Type `12` と一致で正しい（案1a の帰結）。突合が時分型の誤宣言を検出しないことは
ADR-0069 のガイドに明記する。

## 論点4: condition / order

- **案4a: `TimeCondition`（`gt` / `ge` / `eq` / `le` / `lt`、値は `"HH:mm"`）を足し、送信時に基準日を付ける。
  order は年月日時分型と同じく可** — 推奨
- 案4b: condition には使えないことにする（`never`）

**推奨は案4a。** 出典は condition・order とも「年月日時分型と同様」と言い、例まで載せている。使えるものを
塞ぐ理由が無い。値の検証は Write と同じ（書式・範囲を送信前に）。不正な書式は PORTERS が Code 100 で
**検索を実行しない**ので、送信前に止めることで「0 件だった」と「検索されなかった」の取り違えを防ぐ
（[ADR-0051][adr51] と同じ関心）。

## 論点5: 内部のラベル — Data Type を増やさない

- **案5a: `DataType` の列挙は 17 のまま。時分型は**宣言の変種**として、カタログの型ラベルにライブラリ内部の
  値（例 `"Time"`）を 1 つ足す（`DataType` とは別の union）** — 推奨
- 案5b: `DataType` に `"Time"` を足す
- 案5c: `FieldDef` に修飾子（`{ dataType: "DateTime"; timeOnly: true }`）を持たせ、カタログにも修飾子を運ぶ

**推奨は案5a。** `DataType` は「PORTERS が定義する値の形」で（[ADR-0016][adr16]）、D3 の検査は
reference の 17 と `LIBRARY_DATA_TYPES` の集合が**両方向で一致する**ことを見ている
（`test/integration/reference-catalog.test.ts`）。案5b はこの検査を緩めるか、PORTERS に無い Data Type を
発明するかのどちらかになる。一方で decode / encode / condition / order の分岐は**カタログの型ラベル
1 本**（`Record<alias, DataType | null>`）で回っている（`DecodedValueOf` / `WriteValueOfType` /
`ConditionOf` の表）ので、ラベルを 1 つ増やすのがいちばん素直で、案5c の「修飾子を全経路に運ぶ」より
小さい。`DataType | null` を参照する箇所は `src/` に **28**（2026-09-20・grep 実測）で、
機械的な置き換えの範囲。Field Type の対応表（`src/resources/field-type.ts`）では `"Time"` → `12`
（逆引きは `DateTime` のまま＝ Field Read から生成される宣言は `dateTime()`）。

型の名前・置き場所（`CatalogType` のような union を切るか）は詳細設計で、実装 PR が決める。

## Decision Outcome

（proposed — 論点ごとの推奨は上記。decider の選択で確定する）

推奨をまとめると: **`f.time()` で宣言し、`"HH:mm"`（00:00〜47:59）で読み書きし、condition も同じ値で
書ける。1970 基準日はライブラリの内側に閉じる。`time()` 項目に基準日以外が来たら validation エラー、
宣言生成は FT-12 に注記を出す。`DataType` は 17 のまま。**

### Consequences

- Good: 「26:00」を 1970/01/02 に写す規則を利用者が持たなくてよい。オフセット付き ISO で黙ってずれる経路が
  時分型については構造的に無くなる。Code 100 / 103 になる値を送信前に止められる。
- Bad: **宣言しない限り救えない**（API から判別できないので、ライブラリに自動の道は無い）。
  `"HH:mm"` は ISO ではないので、日時をすべて ISO で扱う（R-10）の**例外を 1 つ持つ**
  — ただし時分型は日時ではない、という整理で例外を正当化する。内部ラベルが 1 つ増え、Data Type と
  1:1 でなくなる（`"Time"` → FT-12）。
- Neutral: 時分型を持たないテナントには何も変わらない。標準項目（`P_*`）に時分型は無いので、
  静的カタログは触らない。秒が `00` 以外で返る実例があるかは実機で確かめる（実装時に LV を起票）。

## 信じている入力

## Pros and Cons of the Options

### 案1a: `f.time()`（推奨）

- Good: 区別の知識を持つ人（管理者）から開発者へ、宣言 1 行で渡る。Link / Image と同じ経路。
- Bad: 宣言を忘れる／間違えると救えない（API の制約で、どの案でも同じ）。

### 案1c: 何もしない

- Good: 変更ゼロ。
- Bad: オフセット付き ISO で黙ってずれる。26:00 の規則を利用者が持つ。

### 案1d: 値から推定

- Good: 宣言不要。
- Bad: 正規の 1970 日時を誤読する。読みで型が揺れる。

### 案2a: `"HH:mm"`（推奨）

- Good: 画面表記と一致。1970 規則が内側に閉じる。
- Bad: ISO ではない（R-10 の例外）。

### 案2b: ISO 日時

- Good: 既存の型のまま。
- Bad: 現状の問題を全部残す。

### 案5a: 内部ラベルを 1 つ足す（推奨）

- Good: D3 の 17/17 検査を守る。分岐が表 1 本で済む。
- Bad: `DataType | null` の参照 28 箇所を広げる。ラベルと Data Type が 1:1 でなくなる。

### 案5b: `DataType` に足す

- Good: 置き換えが要らない。
- Bad: PORTERS に無い Data Type を発明する（[ADR-0016][adr16] に反する）。D3 検査を緩める。
