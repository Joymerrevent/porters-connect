## Context and Problem Statement

`defineFields` が今見ているのは**綴りの形だけ**である。alias が `U_` / `A_` で始まること、
リソースキーが既知であること — この 2 つを同期で検査して、通ったら branded にして終わり
（[ADR-0023][0023] D4）。**宣言した項目がテナントに実在するか**、**宣言した Data Type が実物と
一致するか**は、ライブラリの中の誰も確かめていない。

### 食い違うと何が起きるか（実測・2026-09-09）

`decodeField` を直接叩いた結果。左が「実物の型 / 宣言した型」:

| 実物 / 宣言                   | 結果                                              |
| ----------------------------- | ------------------------------------------------- |
| Option / `f.singlelineText()` | **`null`**（選択肢が黙って消える）                |
| テキスト / `f.option()`       | **`null`**（値が黙って消える）                    |
| テキスト / `f.date()`         | `RangeError` で**そのページの読み取り全体が失敗** |
| Number / `f.singlelineText()` | `"123"`（文字列として読める＝実害は小さい）       |

**上 2 行が問題の核**である。例外も警告も出ず、値が `null` になる。利用者から見ると
「その項目は空だった」と区別が付かない。これは**気づけない壊れ方**＝このプロジェクトが
フェイルセーフで避けたい側そのものである。3 行目は落ちるので気づけるが、
飛ぶのが `PortersError` ですらない（[RV-36][rv36]）。

### 食い違いは「あり得る事故」ではなく、PORTERS 自身が警告している状況

`docs/reference/gotchas.md` の「データモデル・Alias」節は、出典記事からこう転記している:

- **Alias は環境・テナント依存**。本番と開発用テスト環境で項目・選択肢の Alias がズレると連携が壊れる
- **PORTERS 側で項目が変更・削除される**とアプリが壊れ得る。未知 Alias に強い設計（寛容なパース・明確なエラー）

つまり「宣言を書いた時点では合っていたが、後からズレる」は**運用上の既定路線**である。
にもかかわらず、ライブラリはズレを検出する手段を持っていない。

### 生成側 — 翻訳表を持っているのに、利用者に手でやらせている

現在の手順は `docs/guide/custom-fields.md` の「テナントの項目を調べる」節にある:

```ts
for await (const f of t.field.searchAll({ resource: "candidate" })) {
  console.log(f.P_Alias, f.P_Name, f.P_Type); // 例: U_score, 適性スコア, 3
}
```

`P_Type` は数値なので、利用者は [Field Type / Data Type][fdt] の表を引いて `3 → f.number()` と
**手で翻訳**することになる。ところが**その翻訳表はライブラリが既に持っている** —
`test/fake/master-read.ts:57` の `FIELD_TYPE_VALUE` が Data Type → Value の対応を全 17 型ぶん持ち、
フェイクの Field Read 応答を組み立てている。**公開していないだけ**である。

### 問い

**テナントの Field カタログを読んで、(a) 宣言との食い違いを報告し、(b) 宣言の雛形を生成する機能を、
どこに・どんな形で置くか。食い違いをどう届けるか。読めないリソース・宣言できない型・
未知の型をどう扱うか。**

## 先に塞ぐ必要がある穴（本 ADR の前提・[RV-37][rv37]）

**Process が Field Read で読めない。** `defineFields` は `process` のカスタム項目を受け付ける
（`CustomFieldResource` は 11 件）のに、Field Read の `ResourceType`（`src/resources/field.ts` の
`RESOURCE_VALUE`）は**10 件で Process だけ欠けている**。reference は Process = Value 7 と明記し、
Field List 記事へのリンクも持っているので、これは判断ではなく書き落としである
（同じ事実の対応表が `src/resources/resource-list.ts` にもあり、そちらは 11 件で正しい）。

本 ADR の突合・生成は Field Read を土台にするので、**このまま作ると Process だけ穴が開く**。
[RV-37][rv37] の処置は論点6 で扱う。

## Decision Drivers

- **黙って壊れる側を可視化する** — 上表の `null` 落ちを、利用者が**気づける形**にする。
- **検出しても落とさない** — テナント側で項目が 1 つ消えただけでアプリが起動しなくなるのは、
  安全側ではなく**可用性を落とす**。落とすかどうかは利用者が決められる形にする。
- **契約なしで動く**（[ADR-0004][0004]） — 突合・生成は opt-in。使わない利用者には無変更。
  フェイクの Field Read が実装済みなので、**開発・テストは契約前に完結する**。
- **薄さ** — 依存ゼロ。ファイルシステムを触らない。CLI を抱えない。
- **ドリフト不能** — Field Type Value ↔ Data Type の対応表を 2 箇所に持たない
  （同じ失敗を `RESOURCE_VALUE` / `RESOURCE_VALUES` で一度やっている＝[RV-37][rv37]）。
- **型安全** — 生成物は**静的に型が付く形**であること。ランタイムのオブジェクトを返すだけでは
  [ADR-0004][0004] の目的（宣言 → 型導出）を満たさない。

## Considered Options

### 論点1: 関数の粒度

- **案1a: `verifyFields` と `generateFieldDecls` の 2 本**を独立に実装する。
- **案1b: 読み取りプリミティブ 1 本 ＋ その上の 2 本**（推奨）。
  `readCustomCatalog(t, resource)` が「テナントのカスタム項目 alias → Data Type」を返し、
  突合と生成はどちらもその結果を加工するだけにする。
- **案1c: 生成だけ出す**。突合は「生成し直して既存の宣言ファイルと `git diff`」に委ねる。

案1c は魅力的に見えるが**成立しない**。生成物はソース文字列であり、比較したいのは
`DefinedFields`（実行時の値）である。整形・並び順・コメントの差が差分に混ざるので、
「項目が 1 つ消えた」を機械が判定できない。CI に載せるなら構造の比較が要る。

### 論点2: 置き場所

- **案2a: 本体の公開 API**（`src/index.ts` から export）。
- **案2b: サブパス export**（`@joymerrevent/porters-connect/fields-dev` など）＝本体に載せない。
- **案2c: CLI**（`npx porters-fields generate`）。
- **案2d: 案2a ＋ 案2c**。

案2c 単独は薄さに反する（引数解析・認証情報の受け取り・出力先の面倒を抱える）。
案2b は tsup のエントリと `package.json` の `exports` を増やす必要があり、**現状サブパスは 0 本**。
ESM でツリーシェイクが効くので、本体に置いても使わない利用者のバンドルには入らない。

### 論点3: Field Type Value ↔ Data Type 表の正典

- **案3a: `src/` に 1 枚の表を置き、順・逆とも導出する**（推奨）。
  行は `{ value, dataType, 宣言可否 }` の 3 列。フェイクもこの表から引く。
- **案3b: `src/` に順方向、`test/fake` に逆方向**（今と同じ二重管理）。

この対応は**単射ではない**ことに注意が要る。Option は 3 サブタイプ（5 Checkbox / 6 Radio /
7 Dropdown）が同じ Data Type に畳まれ、System 系 4 つは Value 11 を共有し、
14 Currency の Data Type は Number、16 Reference は**そもそも Data Type を持たない**。
したがって逆方向（Data Type → Value）は「代表値を選ぶ」判断を含む。フェイクは既にその判断をしていて
（Option→7・System→11）、[LV-12][lv] に「実物の Value は未確認」として登録済み。
案3a はその判断を 1 箇所に集める。

### 論点4: 宣言できない型・未知の Value

Field Read が返しうる `P_Type` のうち、`CustomDataType`（[ADR-0023][0023] D3）に写せないもの:

| `P_Type` | 何                    | なぜ写せないか                                                   |
| -------- | --------------------- | ---------------------------------------------------------------- |
| 11       | System 系 4 種        | システム管理＝標準項目の領域。宣言の対象外                       |
| 16       | Reference             | **Data Type を持たない**（参照表示専用・項目自体が値を持たない） |
| 未知     | 将来 PORTERS が足す型 | 対応表に無い                                                     |

- **案4a: 落とさず、報告に残す**（推奨）。生成ではコメントとして出力に残し、
  突合では「宣言対象外」の別枠に置く。
- **案4b: 未知の Value に出会ったら throw**。
- **案4c: 黙って捨てる** — ✗。**未知の型が増えたことに誰も気づけなくなる**。fail-open そのもの。

案4b は「新しい型が 1 つ増えただけで既存の生成・突合が全部止まる」ので、
テナント側の変更に対して脆い。案4a は「知らない型があった」という事実を運ぶだけで止まらない。

### 論点5: 突合結果の届け方

- **案5a: レポートを返す**（throw しない）。呼び出し側が読んで判断する。
- **案5b: 不一致で throw**。
- **案5c: 案5a ＋ 「これだけは見逃せない」を投げる薄い assert ヘルパー**（推奨）。

レポートに載せる区分は 4 つになる:

| 区分           | 意味                                 | 深刻度                               |
| -------------- | ------------------------------------ | ------------------------------------ |
| `missing`      | 宣言したがテナントに無い             | **高**（読み書きの要求に載る）       |
| `typeMismatch` | 実在するが Data Type が違う          | **最高**（黙って `null` になる側）   |
| `undeclared`   | テナントにあるが宣言していない       | 低（素通しで動く＝現状どおり）       |
| `unverifiable` | そのリソースのカタログを読めなかった | **中**（無いのか、読めないのかが別） |

`unverifiable` を `missing` と混ぜないことが要点である。読めなかったリソースの宣言を
「実在しない」と報告すると**偽の警報**になり、警報全体が信用されなくなる。
Field Read が権限（`field_r`）不足で失敗した場合・Process のように**そもそも選択できない**場合
（論点6）が、ここに落ちる。

案5b を既定にしない理由は Decision Drivers のとおり。ただし**起動時に落としたい**利用者は必ずいる
（本番で黙って `null` を読むより、起動時に落ちるほうがよい運用）ので、案5c は
「既定は報告・落としたければ 1 行」にする。

### 論点6: Process をどうするか（[RV-37][rv37] との関係）

- **案6a: RV-37 を先に直し、対応表を 1 つに統合してから本 ADR を実装する**（推奨）。
- **案6b: 本 ADR では Process を `unverifiable` として報告に出し、RV-37 は別途**。
- **案6c: Process を対象外と決める** — ✗。reference が Value 7 と Field List 記事の両方を持つ以上、
  非対応にする根拠が無く、`1.0.0` の V1（非対応セルは ADR 番号必須）を満たせない。

案6a を推す理由は、本 ADR の突合が**「11 リソース中 10 だけ確かめられる」**状態で出ると、
`unverifiable` が 1 件常に立ち続けることになり、区分の意味が薄れるため。
RV-37 の処置は小さい（参照は計 4 箇所）。

### 論点7: alias の表記ゆれ（[LV-12][lv]）

Field Read の `P_Alias` が接頭辞つき（`Person.U_score`）で返るか bare（`U_score`）かは**未確認**。
フェイクは接頭辞つきを返している。

- **案7a: 両対応**（`.` があれば最後の要素を取る）＋ `VERIFY(live)` を残す（推奨）。
- **案7b: 接頭辞つき前提**。外れたら全項目が `U_` 判定を外れて**丸ごと消える**。

案7b の外れ方が悪い。接頭辞つきを期待して bare が来ると、剥がす処理が空振りするだけなので
実は動く — が、逆（bare を期待して接頭辞つきが来る）だと `ALIAS_PATTERN`（`/^[UA]_/`）に
1 件も当たらず、**カタログが空**として報告される。「テナントにカスタム項目が 1 つも無い」と
「読めていない」の区別が付かない典型なので、両対応にして
**Candidate の接頭辞が `Person` である**こと（reference の要注意事項）も同じ処理で吸収する。

## Decision Outcome

採用: **論点1=案1b ／ 論点2=案2a ／ 論点3=案3a ／ 論点4=案4a ／
論点5=案5c ／ 論点6=案6a ／ 論点7=案7a**。decider が 2026-09-10 に推奨案どおり選択。

決定の骨子を 1 つの形にすると:

```ts
// 1) 読み取りプリミティブ（論点1・案1b）
const catalog = await readCustomCatalog(porters.tenant(1), "candidate");
// -> { U_score: "Number", U_source: "Option" } ＋ 写せなかった項目の記録

// 2) 突合（論点5・案5c）
const report = await verifyFields(porters.tenant(1), myFields);
report.typeMismatch; // [{ resource: "candidate", alias: "U_source",
//    declared: "SinglelineText", actual: "Option" }]
assertFieldsMatch(report); // 落としたい人だけこの 1 行

// 3) 生成（論点1・案1b）
const src = await generateFieldDecls(porters.tenant(1), ["candidate", "job"]);
// -> defineFields({ … }) の TypeScript ソース文字列。ファイルは利用者が書く
```

選んだ理由:

- **一番助かるのが `typeMismatch`** であり、それは今まさに黙って `null` を返している経路
  （冒頭の実測表）。突合を出す価値はここに集中している。
- **生成はソース文字列を返すだけ**にすることで、ライブラリがファイルシステムを触らずに済み
  （薄さ）、かつ生成物は**静的に型が付く**（`defineFields` を通るので型導出はそのまま効く）。
  ランタイムのカタログを返す形は型が付かず、[ADR-0004][0004] の目的を外す。
- **対応表を 1 枚にする**（案3a）ことで、[RV-37][rv37] で踏んだ「同じ事実が 2 箇所にあり
  片方だけ古い」を繰り返さない。フェイクがその表を使うので、**表が間違っていると
  既存のフェイク経由テストが落ちる**＝人の注意に頼らない検査になる。
- **落とさないのを既定にする**（案5a/5c）のは、このプロジェクトのフェイルセーフの読み方
  （「壊れたときに安全側へ倒れる」）に沿う。テナントの項目変更でアプリが起動しなくなるのは
  安全側ではない。落としたい運用のために `assertFieldsMatch` を別に置く＝
  **許可と沈黙を分ける**（[ADR-0047][0047] と同じ形）。

### accept 時に併せて決めたこと

**`active` の既定は突合と生成で分ける**（2026-09-10）。Field Read の `active` は
`-1` 全件 / `0` 未使用 / `1` 使用中。

| 用途 | 既定 | 理由                                                                                    |
| ---- | ---- | --------------------------------------------------------------------------------------- |
| 突合 | `-1` | `1` にすると、**使われていないが宣言されている項目**を `missing` と誤報する（偽の警報） |
| 生成 | `1`  | 未使用の項目まで雛形に並べても宣言する動機が無い。実用は「使用中だけ」                  |

これは好みではなく**正しさの問題**なので、実装時送りにせずここで固定する。突合の既定を
`1` にした瞬間に、区分表（論点5）の `missing` が信用できなくなる — 偽の警報が混ざった警報は
読まれなくなり、[RV-37][rv37] の `unverifiable` を分けた意味も消える。
どちらも呼び出し側から上書きできるようにはする。

### 実装時に決めること（本決定を変えない範囲）

1. **`unverifiable` の粒度** — 「権限が無い」「そもそも選択できない」「通信で落ちた」を
   区別して持つか、1 つにまとめるか。区別すると型が増える。**`missing` と混ぜない**ことだけが
   本決定（論点5）で、内訳の粒度は実装で決めてよい。
2. **`undeclared` を既定で出すか** — 出すとテナントによっては数十件並ぶ（標準項目は除外するので
   `U_`/`A_` だけだが、それでも多い）。既定は件数だけ、詳細はオプション、という形もありうる。
3. **生成の出力に `P_Name` を載せるか** — 項目の日本語名をコメントで添えると読みやすいが、
   生成物に**テナントの業務語彙**が入る。生成物をリポジトリにコミットする利用者にとっては
   情報の持ち出しになりうるので、**既定 off** に倒す方向で検討する。

### Consequences

- **Good**: 今まさに黙って `null` を返している経路（冒頭の実測表）が、利用者から**見える**ようになる。
  宣言を手で書き写す作業（ガイドの「テナントの項目を調べる」節）が消える。
  Field Type Value ↔ Data Type の対応表が 1 枚になり、フェイクが同じ表を使うので**ドリフトが検査で落ちる**。
  突合・生成とも opt-in なので、使わない利用者には無変更。
- **Bad**: 公開 API に記号が 3 つ（＋ assert で 4 つ）増え、V2 のリファレンスにもそのぶん載る。
  「dev ツールなのに本体の API に見える」（案2a の代償）。逆引きの代表値を選ぶ判断
  （Option→7 / System→11）が `test/` から `src/` へ出てくる。
- **Neutral**: [LV-12][lv] の**影響範囲が広がる**。`P_Alias` の表記は今はフェイクの都合だが、
  実装後は**利用者に見せる生成物の正しさ**がそこに乗る（両対応にして被害は抑えるが、
  実機確認の価値は上がる）。着手前に [RV-37][rv37] を塞ぐ必要がある＝本 ADR の実装は
  **2 PR に分かれる**（RV-37 の是正 → 本体）。

## 信じている入力

この決定は**テナントの Field Read 応答を信じて型を組み立てる**ので、ここが実質すべてである。

| 値                      | 出どころ           | 誰が書けるか                     | 守り方                                                                    | 取れなかったら                                               | 誤っていたら                                                           |
| ----------------------- | ------------------ | -------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------- |
| `P_Alias`（項目の名前） | PORTERS Field Read | **テナント管理者**（画面で命名） | 仕組み: `U_`/`A_` 接頭辞で絞る ＋ 接頭辞の剥がし（論点7・案7a）           | **`unverifiable`**（空のカタログ＝「項目が無い」と読まない） | 生成物が壊れた識別子を含みうる → **生成時に識別子として妥当か検査**    |
| `P_Type`（項目の型）    | PORTERS Field Read | テナント管理者（項目の型設定）   | 仕組み: 対応表（論点3・案3a）に無い Value は**写さず記録**（論点4・案4a） | その項目だけ「型不明」として残す                             | 突合が誤った `typeMismatch` を出す → **報告のみで落とさない**（案5a）  |
| リソースの Value        | 同梱の対応表（人） | 保守者のみ                       | 仕組み: 網羅テスト（[RV-37][rv37] の推奨）＋ reference との突合           | 該当なし（静的）                                             | Field Read が 400／別リソースの項目を読む → **[LV-12][lv] で実機確認** |
| 権限（`field_r`）       | 契約・アプリ設定   | 契約者                           | 仕組み: 失敗を `unverifiable` に落とす（`missing` にしない）              | **`unverifiable`**                                           | 部分的に読めて部分的に読めない → リソース単位で区分を持つ              |

**「取れなかった」と「0 件」を混ぜない**のが本表の要点である。カタログが空で返ってきたとき、
それを「このリソースにカスタム項目は無い」と読むと、権限不足も接頭辞の読み違い（論点7）も
**すべて「宣言が全部余計」という偽の警報**に化ける。

## Pros and Cons of the Options

### 案1b（プリミティブ ＋ 2 本）

- Good: 突合と生成が同じ 1 本の読み取りを共有する＝ Field Read の癖（接頭辞・未知の型・
  ページング）に対する処理が 1 箇所に集まる。利用者が独自の使い方をしたいときの逃げ道にもなる。
- Bad: 公開する記号が 3 つに増える（V2 のリファレンスにも 3 つ載る）。

### 案2a（本体の公開 API）

- Good: サブパス・ビルドエントリ・CLI のどれも増やさない。ESM のツリーシェイクで
  使わない利用者のバンドルには入らない。
- Bad: 「dev ツールなのに本体の API に見える」。JSDoc で用途を書く程度の防御しかない。

### 案3a（対応表 1 枚）

- Good: ドリフト不能。フェイクが同じ表を使うので、表の誤りが既存テストで落ちる。
- Bad: 逆引きの「代表値を選ぶ」判断（Option→7 / System→11）が `src/` に出てくる。
  今はフェイク側の都合として `test/` に隠れているものが、公開側の関心事になる。

### 案5c（レポート ＋ assert）

- Good: 既定は落とさない（可用性）。落としたい運用は 1 行で選べる（明示）。
- Bad: API が 2 つになる。「どちらを使うべきか」をドキュメントで導く必要がある。

### 案4a（未知を記録して落とさない）

- Good: PORTERS が型を足しても止まらない。足されたこと自体は報告に出るので気づける。
- Bad: 「知らない型があるが動いている」状態が常態化しうる。報告を誰も読まなければ意味がない。
