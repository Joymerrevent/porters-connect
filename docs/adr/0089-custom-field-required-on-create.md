# 89. カスタム項目を、宣言で明示したときだけ `create` の必須にする

- Status: proposed
- Date: 2026-09-23
- Deciders: jun.shiromoto (Joymerrevent)

> 起票元は [RV-62][rv62]（2026-09-23）。使い方ドキュメントの校閲中に stakeholder が
> 「PORTERS の項目では必須を設定できるのだから、カスタム項目の宣言でも必須を表せるようにしてほしい」と提案した。
>
> [ADR-0023][adr23] D7 の「カスタムは `requiredOnCreate` に入らない（常に任意）」を**部分的に改める**提案。
> accepted になったら、ADR-0023 には「D7 の『常に任意』は ADR-0089 で改めた」の一行を足す（本文は書き換えない）。

## Context and Problem Statement

### いまの形

- **宣言したカスタム項目は、`create` の入力型でつねに任意**（[ADR-0023][adr23] D7）。`f.number()` などの
  ビルダーには必須を表す書き方が無い。
- **標準項目は、出典の「新規必須」列の `●` を型の必須に写している**（[ADR-0019][adr19] W2・[ADR-0083][adr83]）。
  `create` の入力型 `CreateInput<F, Req>` の `Req`（必須キー）は、各リソースの `REQUIRED_ON_CREATE` から来る
  （`src/resources/resource.ts:92`）。`REQUIRED_ON_CREATE` は**型だけ**で使われ、実行時の検査はしない。
- **PORTERS 側では、テナント管理者がカスタム項目を入力必須にできる**。その状態は Field Read の
  `Field.P_Required`（`0` = 通常 / `1` = 入力必須）で読める
  （[Field の項目][ref-field]）。ライブラリは Field マスタの型としては `P_Required` を持っている
  （`src/resources/field.ts:39`）が、**宣言の生成と突合の道具（[ADR-0069][adr69]）はどこでも読んでいない**
  （`readCustomCatalog` が持ち帰るのは alias・Data Type・項目名だけ。`src/fields/tenant-catalog.ts`）。

つまり、テナントが必須にしている項目を `create` で渡し忘れても、型は何も言わない。標準項目の `●` なら
コンパイルで止まるのに、カスタム項目は実行時まで分からない。

### 実行時にどうなるかは、まだ分からない

**PORTERS の Write API が `P_Required=1` の項目の欠落を弾くかどうかは、出典に書かれておらず、実機でも
確かめていない**（[live-verification][lv] にも項目が無い）。弾くなら Result Code で分かり、弾かないなら
空のまま登録される＝気づけない。どちらの場合でも、型で止められれば「実行するまで分からない」は無くなる。

### 問い

カスタム項目を `create` の必須として宣言できるようにするか。できるようにするなら、どう書き、
`generateFieldDecls` / `verifyFields` はテナントの `P_Required` をどう扱うか。

## Decision Drivers

- **フェイルセーフ**: 渡し忘れを実行時でなくコンパイル時に止める。ただし、誤って厳しくしたときに利用者が
  抜け出せなくなる形は避ける（[ADR-0083][adr83] の非対称性の議論）。
- **型はコンパイル時に決まる**（[ADR-0004][adr04]）。実行時に読んだ `P_Required` から型は作れない。
- **非破壊**: いまの宣言（`f.number()`）とそれを使うコードは、そのままの意味で通り続けること。
  `TenantScope<typeof fields>` のような型の書き方も変えさせない。
- **出典に無いものを発明しない**: `P_Required` は出典にある。「API が強制するか」は出典に無いので前提にしない。
- **薄く**: 第1層に「必須かどうかを実行時に検査する」ロジックを足さない（標準項目の `●` も型だけ）。

## Considered Options

### 論点1: 宣言で必須を表せるようにするか

- **案1a: 宣言で明示したときだけ必須にする（opt-in）** — 推奨
- 案1b: 現状維持（カスタム項目はつねに任意。欠落は PORTERS の判定に委ねる）
- 案1c: `create` の直前に Field Read で `P_Required` を読み、欠落を実行時に弾く

### 論点2: 書き方

- **案2a: ビルダーの引数** `f.number({ required: true })` — 推奨
- 案2b: メソッドチェーン `f.number().required()`
- 案2c: リソースごとの別キー `candidate: (f) => ({ … }), required: { candidate: ["U_score"] }`

### 論点3: `generateFieldDecls` がテナントの `P_Required` をどう写すか

- **案3a: `P_Required=1` の項目に `{ required: true }` を出す（既定で写す）** — 推奨
- 案3b: 既定では出さず、オプション（例 `copyRequired: true`）を付けたときだけ出す
- 案3c: 写さない（必須は人が手で書く）

### 論点4: `verifyFields` が必須の食い違いをどう扱うか

- **案4a: 新しい区分で報告し、`ok` は変えない（`assertFieldsMatch` も止めない）** — 推奨
- 案4b: 報告し、`ok` を倒す（`assertFieldsMatch` が止める）
- 案4c: 報告しない

## Decision Outcome

（proposed。以下は推奨で、決定は decider が行う。）

推奨: **案1a ＋ 案2a ＋ 案3a ＋ 案4a**。

### 論点1: 案1a（opt-in）を推す理由

- **[ADR-0083][adr83] の非対称性が、ここでは当てはまらない**。ADR-0083 が「厳しすぎる側の誤りは利用者が回避
  できない」としたのは、必須を決めるのが**ライブラリ**だったから（直すにはライブラリの修正を待つしかない）。
  カスタム項目の必須を決めるのは**利用者自身の宣言**で、厳しすぎれば `{ required: true }` を消せば済む。
  誤りの代償が「宣言を 1 行直す」なので、型で止める側に倒してよい。
- **案1b は、渡し忘れを実行時まで持ち越す**。API が `P_Required` を強制しない場合は、気づかないまま空で
  登録される。
- **案1c は第1層を厚くし、しかも標準項目と規則が割れる**。`create` のたびに Field Read を挟む
  （往復とスコープ `field_r` が増える）か、キャッシュを持つことになる。標準項目の `●` は型だけで止めて
  いるのに、カスタム項目だけ実行時に止めると「どこで止まるか」の説明が 2 通りになる。
  [ADR-0083][adr83] が案D（送信前の実行時ガード）を退けた理由とも同じ。

必須にするのは **`create` / `createMany` の入力型だけ**で、`update` / `updateMany` は従来どおり任意
（更新は部分的に送るもので、標準項目の `●` も `update` では任意）。実行時の検査はしない（型だけ。
`REQUIRED_ON_CREATE` と同じ）。

### 論点2: 案2a（ビルダーの引数）を推す理由

- 宣言の値 `FieldDef` は `{ dataType }` のただのオブジェクトで、案2a なら `{ dataType, required }` に
  増えるだけで済む。案2b はビルダーの戻り値にメソッドを生やすことになり、宣言の値が「データ」でなくなる。
- 渡し方をメソッドチェーンでなく引数にするのは、[ADR-0087][adr87]（`tenant(id, { fields })`）と同じ選び方。
  あとで別の指定（例: 桁数）を足すときも、同じ引数に並べられる。
- 案2c は項目の宣言と必須の指定が離れ、alias を 2 回書く（綴りのずれが起きうる）。

### 論点3: 案3a（既定で写す）を推す理由

- `generateFieldDecls` は「テナントの実際の設定を宣言の形にする」道具で、`P_Required` もテナントの設定。
  既定で写すのが素直で、写さないなら生成物がテナントの設定と食い違って始まる。
- 生成物は人が読んでコミットするソースで、厳しすぎると思えば消せる（論点1 と同じ理由で、誤りの代償が小さい）。
- 案3b は、知らなければ使われない。案3c は、テナントの設定をコードに書き写す手作業を利用者に残す。

### 論点4: 案4a（報告だけ）を推す理由

`verifyFields` の `ok` を倒すのは、いまは「読み書きが壊れる」ずれだけ（`missing` / `typeMismatch` /
`unverifiable`。[ADR-0069][adr69]）。必須の食い違いはどちら向きでも読み書きを壊さない。

| 食い違い                                             | 何が起きるか                                                                                   |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 宣言は必須・テナントは任意                           | 型が PORTERS より厳しい。利用者が選んだ厳しさかもしれない（業務上は必須、など）                |
| 宣言は任意・テナントは必須（生成後に管理者が変えた） | 今日と同じ（型は止めず、PORTERS の判定に委ねる）。宣言を直せば止められる、と知らせる価値がある |

どちらも「知らせる」価値はあるが「起動を止める」ほどではない。`undeclared`（テナントにあるが宣言していない）
と同じ扱いにする。区分の名前は実装で決める（例 `requiredMismatch`）。

### 実装の制約（基本設計として決めておくこと）

- **宣言の実行時の値にも必須を残す**。`verifyFields(scope, fields)` が比べるため。ただし、リソースに合流させる
  項目表（alias → Data Type）の形は変えない（読み書きの経路は必須を知らなくてよい）。
- **型の書き方を変えさせない**。`TenantScope<typeof fields>`・`DefinedFields`・`DeclaredCatalogs` を使っている
  コードは、そのまま通ること。必須の情報は `defineFields` の戻り値の型に載せ、利用者に新しい型引数を書かせない。
- **`readCustomCatalog` の戻り値に必須を足す**（`TenantCustomCatalog` に alias → 必須かどうか）。
  既存のプロパティは変えない（足すだけ）。
- **ライブ検証に項目を足す**: 「Write API は `P_Required=1` の項目の欠落を弾くか」。`pnpm check:lv` は
  コードの `VERIFY(live)` と台帳を両方向で突き合わせるので、**実装の PR で**コードの印と一緒に足す。

### Consequences

- Good: テナントが必須にしている項目の渡し忘れが、標準項目の `●` と同じくコンパイルで止まる。
  テナントごとに必須が違う SaaS では、「どのテナントで何が必須か」が宣言に現れる。
- Good: 既定は変わらない（`required` を書かなければ今日と同じ）。非破壊の追加で、minor で出せる。
- Good: `generateFieldDecls` の出力がテナントの設定により近くなる。`verifyFields` で、生成後に管理者が必須を
  変えたことに気づける。
- Bad: `generateFieldDecls` をやり直すと、`P_Required=1` の項目を渡していなかった `create` がコンパイルエラーに
  なる。生成物を入れ替えたときに初めて気づく形で、型を締める方向の変化（ただし原因は宣言にあり、利用者が
  選べる）。
- Bad: 公開型が少し増える（ビルダーの引数の型、`TenantCustomCatalog` の必須、`verifyFields` の新しい区分）。
- Neutral: API が `P_Required` を強制するかどうかは、この決定の前提にしない。強制するなら型は
  「PORTERS より手前で止める」、強制しないなら「PORTERS が止めない欠落を止める」になり、どちらでも価値がある。
  ガイドの「必須かどうかは PORTERS の判定に委ねる」の文は、実機で確かめたら書き直す。

## 信じている入力

| 値                                     | 出どころ                                         | 誰が書けるか                 | 守り方                                                                                                                    | 取れなかったら                                                                                | 誤っていたら                                                                               |
| -------------------------------------- | ------------------------------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 宣言の `required`                      | 利用者のコード（`f.number({ required: true })`） | 利用者                       | 型（`true` だけを受ける）。値は `defineFields` が他の宣言と一緒に検査する                                                 | 書かなければ任意（今日と同じ）                                                                | 厳しすぎ → `create` がコンパイルで止まる → 宣言を直す。緩すぎ → 今日と同じ                 |
| `Field.P_Required`（`0` / `1`）        | PORTERS の Field Read                            | テナント管理者（PORTERS 側） | `generateFieldDecls` の出力（人が読んでコミットする）と `verifyFields` の報告だけに使う。型や実行時の検査には直接使わない | 読めない・欠けている → 生成では `required` を出さない（任意側）。突合では食い違いを報告しない | 生成物が厳しすぎ・緩すぎになる → 人が直せる。`verifyFields` が次の突合で食い違いを報告する |
| Write API が `P_Required` を強制するか | 出典に無い（実機未確認）                         | PORTERS 側                   | **前提にしない**。ライブ検証の項目にする                                                                                  | —                                                                                             | ガイドの記述だけが影響を受ける（型の振る舞いは変わらない）                                 |

`P_Required` が `0` / `1` 以外の値で来たときは、**任意として扱う**（厳しくする側に倒さない。生成物が
コンパイルを通らなくなると、利用者は理由の分からないエラーを受け取る）。

## Pros and Cons of the Options

### 案1a（opt-in）

- Good: 渡し忘れをコンパイルで止められる。既定が変わらない。誤ったときの代償が「宣言を 1 行直す」で小さい。
- Bad: 宣言の型の仕組みが少し増える。

### 案1b（現状維持）

- Good: 何も増えない。
- Bad: 渡し忘れが実行時まで分からない。API が強制しない場合は気づけない。

### 案1c（実行時に `P_Required` を読んで弾く）

- Good: 宣言を書かなくてもテナントの設定どおりに止まる。
- Bad: `create` ごとに往復かキャッシュが要り、`field_r` のスコープも要る。第1層が厚くなる。
  標準項目（型だけ）と止まる場所が割れる。弾く場所がクライアントで、誤っても利用者が回避できない。

### 案2a（引数）／ 案2b（チェーン）／ 案2c（別キー）

- 案2a — Good: 宣言の値がデータのまま。後から指定を足せる。Bad: 引数のオブジェクトを書く分だけ長い。
- 案2b — Good: 読んだときに英語として自然。Bad: 宣言の値にメソッドが生える。指定を足すたびにメソッドが増える。
- 案2c — Good: 項目の宣言が今と同じ形のまま。Bad: alias を 2 回書く。宣言と必須が離れる。

### 案3a（既定で写す）／ 案3b（オプション）／ 案3c（写さない）

- 案3a — Good: 生成物がテナントの設定どおり。Bad: 生成し直すと既存の `create` が止まることがある。
- 案3b — Good: 生成し直しても既存のコードが止まらない。Bad: 知らなければ使われず、生成物が設定と食い違う。
- 案3c — Good: 生成物が今と同じ。Bad: 必須を手で書き写す作業が残る。

### 案4a（報告だけ）／ 案4b（`ok` を倒す）／ 案4c（報告しない）

- 案4a — Good: 知らせつつ、起動は止めない（読み書きは壊れないので）。Bad: 報告を読まない人には届かない。
- 案4b — Good: 必ず気づく。Bad: 利用者が意図して厳しくした宣言でも起動が止まる。
- 案4c — Good: 何も増えない。Bad: 生成後に管理者が必須を変えても気づけない。
