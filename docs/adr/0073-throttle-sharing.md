# 73. スロットルの共有単位（client ごとをやめ、注入できるようにする）

- Status: accepted
- Date: 2026-09-13
- Deciders: jun.shiromoto (Joymerrevent)

> [RV-43][rv43] の処置。1 分あたりの上限を自制するバケットが **`PortersClient` ごと**に作られる
> ため、テナント別に client を立てると 1 プロセス内で自制が分裂する。しかもドキュメントが
> その形を勧めていた。**既定を安全側に寄せる**のと、**プロセスを跨いで協調できる継ぎ目を開ける**
> のを、まとめて決める。
>
> **decider が 4 論点すべて推奨案どおり選択し `accepted`（2026-09-13）**（既定でプロセス内共有 ／
> 共有の単位はホスト ／ `Throttle` を注入可能にする ／ テスト専用のリセット API は公開しない）。
> 実装は別 PR。

## Context and Problem Statement

`createThrottle()` は `PortersClient` のコンストラクタの中で呼ばれ、`createThrottle` 自体は
モジュールスコープに状態を持たない。つまり**バケットは client ごと**で、プロセス内で束ねる
仕掛けが無い（`src/client.ts` / `src/http/throttle.ts`）。

既定 `safety` は 0.9 なので 1 client あたり Read 1800 / Write 450 /分。**N client なら N 倍**出る。
PORTERS から見えるのは合計なので、[PRD R-7][prd]（1 分 Read 2000 / Write 500 を自前スロットリングで
超えない）が成立しない。

これは机上の話ではない。**ドキュメントが client を分ける形を勧めている**:

- `docs/usage/howto/multi-tenant.md` — partition ごとに別トークンで運用したいとき
- `docs/usage/howto/custom-fields.md` — テナントで項目構成が違うとき

[ADR-0010][0010] は「**単一プロセス前提**のため多インスタンス/分散では厳密な上限保証は弱い」と
書いている。弱いと認めているのは**プロセスを跨ぐ**場合であって、**1 プロセス内で分裂すること**は
想定に入っていない。つまりこれは 0010 の決定の穴であって、決定の変更ではない。

超過しても PORTERS は判別可能なコードを返さず接続を切る（[ADR-0044][0044]）。表に出るのは
`PortersNetworkError`（`retryable: true`）なので、**リトライでさらに叩く**。原因が「client を
分けたこと」だと気づく手がかりがどこにも無い。

### 問い

**スロットルを何の単位で共有し、利用者に何を差し替えさせるか。**

## Decision Drivers

- **上限内に自制する**（[PRD R-7][prd]・目標2「公認に値する品質」）— このライブラリが公認され得る
  条件そのもの
- **フェイルセーフ** — 既定が安全側に倒れること。利用者が正しく設定しないと守られない形にしない
- **黙って壊れないこと** — 分裂しているかどうかが、利用者から見えるか
- **継ぎ目は 1 つの型で開ける**（`transport` / `auth` / `tokenStore` と同じ作法）
- **テストを汚さない** — グローバル可変状態はテスト間で漏れる。このリポジトリが最も嫌う形

## Considered Options

### 論点1: 既定を共有にするか

- **案1a: 既定でプロセス内共有にする**（推奨）。同じ宛先の client は同じバケットを使う。
- **案1b: 既定は今のまま（client ごと）で、注入だけ足す** — 知っている人しか直らない。
  **黙って壊れる側が既定のまま**残るので、RV-43 の中心（気づけないこと）が解けない。
- **案1c: 何もせず、ドキュメントに書くだけ** — 仕組みで守らない。このリポジトリが繰り返し
  避けてきた形。

### 論点2: 共有の単位

**正典はレート上限が何単位か（App / 契約 / ホスト）を明示していない**（下記「信じている入力」）。
確定しないなら、**広く共有する＝叩きすぎない**側へ倒すのがフェイルセーフ。

- **案2a: ホスト（アクセスポイント）ごと**（推奨）。ホストは契約ごとに払い出されるので、
  実質「契約ごと」に近い。同じ PORTERS を向く client は自動的に束ねられる。
- **案2b: ホスト ＋ App ID ごと** — 上限が App 単位なら正確。ただし**同じ App で複数 client を
  立てる**のが今回の問題そのものなので、キーに App を足しても分裂は防げる一方、**未確認の仮定に
  依存**する。
- **案2c: プロセス全体で 1 つ** — 別ホスト（別契約・ローカルのフェイク）まで巻き込む。
  開発時にフェイクサーバーを叩くと本番向けのバケットを消費する、という筋の悪さがある。

### 論点3: 差し替えの形

- **案3a: `Throttle` の実装を注入できるようにする**（推奨）。`PortersClientOptions.throttle` を
  足し、`Throttle` 型と `createThrottle` を公開する。
  - 明示的に渡せば共有・分離・無効化のすべてが利用者の手に入る。
  - **プロセスを跨ぐ協調**（Redis 等で実装した `Throttle`）が書けるようになる。これは
    [ADR-0010][0010] が「弱い」と認めたまま置いた点で、継ぎ目を開けるだけで利用側が塞げる。
- **案3b: 設定値だけ渡せるようにする**（`readPerMin` / `writePerMin` / `safety`）。
  上限は調整できるが、**共有はできない**（インスタンスを渡せないため）。跨プロセスも無理。
- **案3c: 何も公開しない**（既定の共有だけ入れる）。単純だが、テストで無効化する手段も、
  分散で協調する手段も無い。

### 論点4: テストへの影響（グローバル可変状態）

案1a はプロセス内にレジストリを持つことになる。**テスト間で漏れる**のがこのリポジトリの
最も嫌う形なので、扱いを決めておく。

- **案4a: キーがホストなので、テストは別ホスト名を使えば干渉しない**（推奨）。加えて案3a の
  注入があるので、干渉が問題になるテストは自前のバケットを渡して切り離せる。
- **案4b: リセット関数を公開する**（`__resetThrottles()` 相当）— テスト専用 API が公開
  サーフェスに残る。**公開 API はキュレーションする**方針（CLAUDE.md）に反する。
- **案4c: 共有をやめる** — 論点1 に戻る。

## Decision Outcome

採用: **論点1=案1a ／ 論点2=案2a ／ 論点3=案3a ／ 論点4=案4a**。

選んだ理由:

- **既定が守らないなら守っていない**（案1a）。RV-43 の中心は「ドキュメントが勧めた形に従うと
  壊れる」ことなので、利用者側の行動を要求する解（案1b・1c）では解けない。
- **未確認の仮定には広く倒す**（案2a）。上限が何単位かは正典が言っていない。分からないときは
  **叩きすぎない側**が安全側。ホストは契約ごとなので、実用上ほぼ「契約ごと」になる。
- **継ぎ目を開けると、0010 の積み残しも利用側で塞げる**（案3a）。跨プロセス協調は
  ライブラリの責務にしない（月次の累積管理と同じ線引き）が、**書けるようにはしておく**。
  `transport` / `auth` / `tokenStore` と同じ作法で、新しい概念を増やさない。
- **テスト専用 API は公開しない**（案4a）。注入があれば足りる。

### 公開サーフェスへの追加（semver minor）

- `PortersClientOptions.throttle?: Throttle`
- `Throttle` 型 ／ `createThrottle`（既定実装・オプション付き）

いずれも**追加のみ**で、既存の呼び出しは変わらない。ただし**既定の挙動は変わる**（複数 client が
同じホストを向くとき、合計が上限内に収まる＝以前より遅くなりうる）。これは意図した変更で、
CHANGELOG に明記する。

### Consequences

- **Good**: ドキュメントが勧める形に従っても上限を超えない。テナント別 client の代償が消えるので、
  [カスタム項目をテナント単位で持つ][rv43] という別の要望の動機もかなり減る。
  跨プロセス協調の道が開く（[ADR-0010][0010] の積み残し）。
- **Bad**: プロセス内にレジストリという可変状態が増える。既定の挙動が変わる（速度が落ちる場面が
  ある）。公開サーフェスが 3 つ増え、`Throttle` の契約を semver で守る対象になる。
- **Neutral**: [ADR-0010][0010] を supersede **しない**。方式（token bucket・安全率・操作別）は
  そのままで、**共有単位だけ**を決める部分改定。

## 信じている入力

- **レート上限が何単位か（App / 契約 / ホスト）は、正典に書かれていない。**
  `docs/usage/reference/resource-api/README.md` と `gotchas.md` は「1 分あたり Read 2000 /
  Write 500・超過すると強制切断され得る」とだけ言う。**案2a はここを「ホスト ≒ 契約」と仮定して
  いる。** 契約後に確かめる項目として `docs/live-verification.md` に 1 件足す（accept 後・実装 PR で）。
  仮定が外れた場合の倒れ方は安全側（広く共有＝叩きすぎない）なので、外れても超過はしない。
- それ以外の入力（`src` の現状・[ADR-0010][0010] / [ADR-0044][0044] の記述）は同一リポジトリで、
  CI で再現できる。

## Pros and Cons of the Options

### 案1a（既定でプロセス内共有）

- Good: 利用者が何もしなくても上限を守る。ドキュメントの記述が真になる。
- Bad: グローバルなレジストリを持つ。既定の挙動が変わる。

### 案1b（注入だけ足す）

- Good: 既存挙動を変えない。実装が小さい。
- Bad: **知らない人は分裂したまま**。RV-43 の「気づけない」が残るので、処置として弱い。

### 案2a（ホストごと）

- Good: 未確認の仮定に対して安全側。実装が単純（キーが 1 つ）。
- Bad: 同一ホストで別 App を扱うと、必要以上に絞る可能性がある（実在するかは未確認）。

### 案3a（`Throttle` を注入可能にする）

- Good: 共有・分離・無効化・**跨プロセス協調**がすべて利用側の手に入る。既存の継ぎ目と同じ作法。
- Bad: 公開サーフェスが増える。`Throttle` の契約を semver で守ることになる。

### 案3b（設定値だけ）

- Good: 公開する型が増えない。
- Bad: **共有できない**ので今回の問題を解けない。跨プロセスも無理。
