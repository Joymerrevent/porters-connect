# 67. Dependabot 自動化をやめ、スキルの対話実行に戻す（ADR-0065 / 0066 の supersede）

- Status: accepted
- Date: 2026-09-06（accepted: 2026-09-06）
- Deciders: jun.shiromoto (Joymerrevent)

> [ADR-0065][adr65] は依存更新の判定と取り込みを GitHub Actions に載せると決め、[ADR-0066][adr66] は
> その取り込み手順を改訂した。実装して本番で動かした結果、**取り込み側は `GITHUB_TOKEN` の制約で
> 成立しない**ことが分かり、回避策を重ねるほど複雑になった。得られるものの大きさに対して
> 割に合わないと判断し、**自動化そのものを畳む**。判定も取り込みも `.claude/skills/dependabot-merge`
> の対話実行に戻す。**この 2 本を本 ADR が supersede する。**

## Context and Problem Statement

実装と本番実行で確かめた事実は [設計前提の調査][facts] にまとめてある。設計判断に効くのは 4 点:

1. **`GITHUB_TOKEN` の書き込みは CI を起動できない。** しかも現れ方が 2 通りある —
   `push`（マージ）では run が**作られず**、`pull_request`（`update-branch`）では作られるが
   **`action_required` で承認待ち**になる。
2. **承認ゲートは毎回かかる。** 「一度承認すれば以降は素通り」を検証して否定した。
3. **dependabot の自動 rebase は当てにできない**（8 件中 2 件のみ）。競合の自己回復を任せられない。
4. **依存 PR は週 3 件程度で、滞留は多くが 0〜1 日。** 例外は 6 日が 1 件。

1〜3 から、`GITHUB_TOKEN` のままでは「マージ後の状態を検証する」手段が無い。回避するには
別 identity（PAT / GitHub App）を持つか、マージした job の中で検証を自前に走らせるかになる。

4 が効く。**自動取り込みが省いているのは 1 日あたり数分のクリック**であって、滞留の解消ではない。
[ADR-0065][adr65] が挙げた価値のうち「**毎回同じ深さで検査する**」「やろうと思い出すコスト」は
判定側にあり、取り込みの自動化はその一部でしかない。

## Decision Drivers

- **得られるものと複雑さが引き合うか。** 秘密情報の追加や検証の二重管理は、恒久的な保守コスト。
- **フェイルセーフ。** 「検証が走らないのに成功に見える」形を残さない。
- **同じ真実を 2 箇所に置かない。** 判定の基準をワークフローとスキルの両方が持つと、片方だけ古くなる。
- **人の関与を減らすこと自体は目的ではない。** 目的は「毎回同じ深さで検査すること」。

## Considered Options

- 案A: 続ける。別 identity（PAT / GitHub App）を導入して `GITHUB_TOKEN` の制約を回避する
- 案B: 続ける。マージした job の中で検証を自前に走らせる
- 案C: **判定だけ残す。** 取り込みは人が GitHub の UI で押す
- 案D: **やめる。** 判定も取り込みもスキルの対話実行に戻す — 採用

## Decision Outcome

採用: **案D**。ワークフロー 2 本と付随するシェル 4 本を削除し、
`.claude/skills/dependabot-merge` の対話実行に一本化する。

**案C（判定だけ残す）は最後まで有力だった。** 判定側は実測で動いており、追跡 Issue に
判定表を出すところまで確認できている。それでも採らないのは、**判定の基準が 2 箇所に増える**ため。
ワークフローのプロンプトとスキルの `SKILL.md` が同じ判断基準を持ち、雛形を共有する構成は、
片方だけ更新されて食い違う典型の形になる。週 3 件・滞留 0〜1 日の対象に対して、その保守を
恒久的に抱える価値は無いと判断した。

案A は秘密情報を増やし、develop へ push できるトークンを常設することになる。Scorecard と
権限分離で積み上げてきた方針と逆行する。案B は `ci.yml` と検証内容が二重管理になる。
どちらも「取り込みのクリック 1 回」のための代償として大きい。

### Consequences

- Good: **保守対象が減る。** ワークフロー 2 本・シェル 4 本・雛形の機械可読行が不要になる。
- Good: **`GITHUB_TOKEN` の制約から解放される。** 人がマージすれば CI は普通に走る。
- Good: 判断基準が `SKILL.md` の 1 箇所に戻る。
- Bad: **依存更新の検査は「人が思い出して起動する」に戻る。** ADR-0065 が解こうとした問題は残る。
  滞留が長期化するようなら、判定だけを別の軽い形（例: 定期的に Issue を立てるだけ）で
  再導入する余地はある。
- Bad: 実装と本番実行に費やした時間は回収できない。ただし [設計前提の調査][facts] として
  残る事実には、次に同種の自動化を考えるときの価値がある。
- Neutral: `dependabot.yml`（cooldown・グループ・target-branch）は**変更しない**。
  依存更新 PR が作られる仕組み自体はこれまでどおり。

## 信じている入力

**該当なし。** 自動で動くものを無くす決定なので、このリポジトリが新たに信じることになる
外部入力は増えない。むしろ [ADR-0065][adr65] の表に挙げた 11 件がすべて不要になる。

## Pros and Cons of the Options

### 案A: 別 identity を導入して続ける

- Good: `update-branch` もマージ後 CI も両方解決する。設計を大きく変えずに済む。
- Bad: 秘密情報が増える。**develop へ push できるトークンが常設**され、漏れたときの被害が大きい。
- Bad: PAT は個人に紐づき、GitHub App は導入と保守のコストがある。

### 案B: マージ job の中で自前に検証

- Good: 秘密情報を増やさない。検証する場所と判断する場所が一致する。所要は 36〜64 秒と安い。
- Bad: `ci.yml` と検証内容が**二重管理**になる。片方だけ更新されて食い違う。

### 案C: 判定だけ残す

- Good: 実測で動いている部分を活かせる。取り込みは人が押すので検証は正常に働く。
- Bad: **判定基準がワークフローとスキルの 2 箇所に増える。** 雛形の共有で緩和はできるが、
  プロンプトと `SKILL.md` の乖離は残る。
- Bad: 週 3 件の対象に対して、ワークフロー 1 本＋シェル 3 本の保守が恒久的に残る。

### 案D: やめる（採用）

- Good: 保守対象が最小。判断基準が 1 箇所。
- Bad: 起動が人の記憶に戻る。

- `.github/dependabot.yml` は変更しない。
