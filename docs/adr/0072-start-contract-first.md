# 72. 入門を「契約済みの読者」から始める（`start/` の並べ直し）

- Status: accepted
- Date: 2026-09-12
- Deciders: jun.shiromoto (Joymerrevent)

> [ADR-0070][0070] は 4 層（入門 → 考え方 → 目的別 → リファレンス）を決め、入門 5 本の
> **1 本目を「契約なしで動かす」から始めた**。だが実際の読者は**すでに PORTERS と契約している人**で、
> 最短で自分のアプリを繋ぎたい。本 ADR は 0070 の**入門（`start/`）の並びと目次の節順だけ**を改める
> （4 層の構成・各層の役割・検査①〜④は変えない）。
>
> **decider が 6 論点すべて推奨案どおり選択し `accepted`（2026-09-12）**（入門を 6 本に割る ／
> `install.md` は「インストールと、クライアントの構築」／ 見出しの通し番号を外す ／
> モックとフェイクサーバーは目的別へ ／ 目次は 入門 → 目的別 → 考え方 → リファレンス ／
> README の導線を差し替え）。実装は別 PR。

## Context and Problem Statement

現在の入門は 5 本で、1 本目が `createMockTransport` から始まる。

```text
start/
  install.md       1. インストールと、最初の 1 回 ← 契約なし・モックで動かす
  authenticate.md  2. 認証を通す
  first-read.md    3. はじめての読み取り
  first-write.md   4. はじめての書き込み
  going-live.md    5. 本番に出す前に
```

このライブラリの利用には **PORTERS 契約 ＋ Connect API オプション契約**が要る（README の
`> [!IMPORTANT]`）。つまり**読者はほぼ全員、契約済みで来る**。「契約なしで動かす」は、
その人たちにとって**本題ではない**。

### 実測してわかった 3 つのずれ（2026-09-12）

**1. README と入門で立ち位置が矛盾している。**
README の「最短で動かす」は**本物の client**（`PORTERS_HOST` / `PORTERS_APP_ID` /
`PORTERS_APP_SECRET`）で始まる。ところがそこから飛ぶ `start/install.md` は**モック**で始まる。
入口が二枚舌になっている。

**2. モック節は二重メンテになっている。**
`start/install.md` の「契約なしで動かしてみる」と `howto/test-without-contract.md` は、
**同じ `createMockTransport` ＋ 同じ Candidate XML**を載せている。片方を直してももう片方は残る
（[ADR-0070][0070] が README で直したのと同じ構図）。

**3. 契約済みの読者の「最初の壁」は install ではない。**
無人運用の `code_direct` は、**事前に一度ブラウザで権限付与済みであること**が前提
（`howto/authenticate.md` 冒頭の 2 フェーズ表）。したがって契約済みの人でも、コードを書く前に

- API アプリの登録（Redirect URL を決める）
- ホスト名・App ID・App Secret の受け取り
- 対象 Company DB での権限付与
- 付与するスコープの決定

が要る。**これらは今 2 ページ目にコードと混ざって埋まっている。** 最初に当たる壁が、
最初のページに無い。

### 目次の節順も、動線と逆になっている

`docs/usage/index.md` は **入門 → 考え方 → 目的別 → リファレンス**の順に並ぶ。
「早く繋いで、あとで深く理解したい」読者にとって、**考え方（PORTERS 固有の前提）が
目的別 HOWTO の手前にある**のは 1 段遠回りになる。

### 問い

**入門をどう並べ替え、モックとフェイクサーバーをどこへ置き、目次の節順をどうするか。**

## Decision Drivers

- **主たる読者は契約済み**で、自分のアプリを PORTERS に繋ぎたい人
  （CLAUDE.md の最優先目標＝収益化より**多くの実利用者に使われること**）
- **最初の成功体験が「本物に繋がった」であること** — モックが返す値は成功体験にならない
- **二重メンテを作らない**（[ADR-0070][0070] が README で消したものを、入門に作り直さない）
- **1 ページ 1 責務**（同 ADR が accept 時に「`start/` を 5 本に割る」と決めた理由と同じ）
- **既存の検査が空振りしないこと**（[ADR-0070][0070] 論点4 の検査①〜④・[ADR-0071][0071] 論点2 の番人）
- 「契約なしで動かす」を**捨てない** — 権限付与を待つ間・CI・テストでは実際に要る

## Considered Options

### 論点1: 入門の並び

- **案1a: 6 本に割る**（推奨）

  ```text
  start/
    prerequisites.md  始める前に（PORTERS 側で用意するもの）  ← コードなし
    install.md        インストールと、クライアントの構築
    authenticate.md   認証を通して、疎通を確認する
    first-read.md     はじめての読み取り
    first-write.md    はじめての書き込み
    going-live.md     本番に出す前に
  ```

  境界は「**PORTERS の画面でやること＝ 1 本目／ライブラリのコードが関わること＝ 3 本目**」。
  権限付与は画面での承諾を含むが、URL を組み立てるのはライブラリなので `authenticate.md` 側。

- **案1b: 5 本のまま中身だけ入れ替える** — `install.md` に「用意するもの」を同居させる。
  ファイル追加が無く最も安いが、**1 ページ 2 責務**になる（契約・登録の話と `npm i` の話）。
- **案1c: モック節を削るだけ** — 順序は現状維持。最小。ずれ 3（最初の壁が 2 ページ目にある）が残る。

### 論点2: `install.md` の厚み

案1a では「用意するもの」と「認証」を前後のページに出すので、`install.md` に何を残すかを決める。

- **案2a: 「インストールと、クライアントの構築」**（推奨）。`npm i` ／ Node 20+・ESM ／
  型定義同梱で `@types` 不要 ／ `PortersClient` の構築（env 3 値）／ `host` は**ホスト名だけ**・
  `https://` を付けると**構築時に落ちる** ／ **ここではまだ何も呼べない**の明示。50〜70 行。
- **案2b: `npm i` だけ**（構築は `authenticate.md` へ）。ページが 20 行級になり、
  **薄すぎるページ**ができる。設定の話（`host` の検査）の置き場所も失う。

### 論点3: 見出しの通し番号

現在は `# 1. インストールと、最初の 1 回` のように**見出しに番号が埋まっている**。

- **案3a: 番号を外す**（推奨）。順序は目次の表と `前提` / `次に読む` の鎖（検査②）が守る。
  番号は**検査の外にある二重管理**で、ずれても誰も気づかない。
- **案3b: 6 本ぶんに振り直す**。今回は直るが、**次に増減したらまた全ページ**を触る。

### 論点4: モックとフェイクサーバーの行き先

- **案4a: 両方 `howto/test-without-contract.md` へ**（推奨）。`start/install.md` の
  「もっと本物に近づけたいとき」（`pnpm fake:serve`）も一緒に降ろす。これは**clone した
  開発者向け**で、npm で入れた利用者の環境には存在しないもの＝入門に置く理由がいちばん薄い。
  入門からは「契約待ち・CI なら」の 1 行リンクだけ残す。
- **案4b: モックだけ移し、フェイクサーバーは入門に残す** — 「パッケージには入っていない」という
  注記つきのものが入門に残り続ける。

### 論点5: 目次（`docs/usage/index.md`）の節順

- **案5a: 入門 → 目的別 → 考え方 → リファレンス**（推奨）。「早く繋ぐ → あとで深く」に素直。
  考え方へは入門・HOWTO の本文から既にリンクが張られているので、下げても迷子にならない。
  **節のリード文は現行のまま**（「ここを読んでおくと目的別の手順が短く読める」）にする。
  「詰まったら読む」に書き換えると、**実際にはいちばん効く節**が事故ってから読むものになる。
- **案5b: 現状維持**（入門 → 考え方 → 目的別 → リファレンス＝[ADR-0070][0070] のまま）。

### 論点6: README の「契約が無くても試せます」

- **案6a: 格下げし、「前提」を格上げする**（推奨）。現在 README は
  「**契約が無くても試せます** — インストールと、最初の 1 回は、契約もネットワークも無しで
  動かすところから始まります」で**入門への導線そのもの**になっている。ここを
  「契約・アプリ登録・権限付与の 3 点」を先に見せる形に差し替え、モックは目的別への 1 行にする。
- **案6b: 現状維持** — README の導線だけが旧構成を指したまま残る。

## Decision Outcome

採用: **論点1=案1a ／ 論点2=案2a ／ 論点3=案3a ／ 論点4=案4a ／ 論点5=案5a ／ 論点6=案6a**。

選んだ理由:

- **読者は契約済みで来る**（案1a）。最初のページが「用意するもの」なら、**最初に当たる壁が
  最初のページにある**。いまは壁（アプリ登録・権限付与）が 2 ページ目にコードと混ざっている。
- **最初の成功体験を「本物に繋がった」にする**（案1a・案2a）。`authenticate.md` の終わりで
  `porters.partition.search()` が自分の Company DB を返す — これが「繋がった」の証拠になる。
  モックが返す `山田 太郎` は、何の証拠にもならない。
- **番号は二重管理**（案3a）。順序の正は鎖（検査②）で、番号はその写しでしかない。
  写しを人が保つ形は、このリポジトリが繰り返し避けてきた形。
- **モックは捨てない、降ろす**（案4a）。権限付与を待つ間・CI・テストでは実際に要るので、
  **目的から引ける場所**（`howto/test-without-contract.md`）に一本化する。
  同じ内容が 2 箇所にある状態が消えるので、二重メンテも同時に解ける。

### 検査への影響（先に確かめた・2026-09-12）

[ADR-0071][0071] が「移設という作業そのものが、移設を検出すべき検査を無効化する」と記録したので、
**今回も先に確かめた**。結論は**4 つとも素通り**で、番人の追加は要らない。

| 検査                              | 影響                                                                                                                                                                                                               |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ①目次と実ファイルの 1:1           | `docs/usage/index.md` の表に 1 行足すだけ。足し忘れれば**落ちる**（＝正しく働く）                                                                                                                                  |
| ②入門の鎖                         | `prerequisites.md` が新しい入口。`前提` 行は**リンクなしの平文でも通る**（`start` 外を指すものは鎖に数えない）                                                                                                     |
| ③公開 API が入門/目的別から辿れる | `GUIDE_GLOBS` が `docs/usage/start/**` を含むので、ページ追加は自動で対象に入る                                                                                                                                    |
| ④コード例の型検査                 | 番人はグロブ単位（`start/**` が 1 件でも拾えれば通る）＝**コード無しの `prerequisites.md` でも問題ない**。マークダウン側は現在 91 ブロック（`start/` は 17）で、モック例が 1 つ減っても下限 `MIN_BLOCKS=40` に遠い |

### Consequences

- **Good**: 契約済みの読者が、最初のページで**自分がやるべき準備**に出会う。最初の成功体験が
  「本物に繋がった」になる。モックの二重メンテが消える。目次が「早く繋ぐ → あとで深く」に並ぶ。
- **Bad**: `start/` が 5 → 6 本に増える。入門全 6 ページの見出しと `前提` / `次に読む` を書き換える
  （鎖は検査②が守るが、書き換え自体は手作業）。README の導線 2 行と、
  `howto/test-without-contract.md` への内容移動が要る。
- **Neutral**: [ADR-0070][0070] を supersede **しない**。4 層・各層の役割・検査①〜④はそのままで、
  本 ADR は論点1 で決めた `start/` の中身と論点5 相当の節順だけを改める**部分改定**。
  「契約なしで動かす」は消えず、目的別へ移る。

## 信じている入力

該当なし — 本決定は**自分たちが書く文章の並べ方**の話で、外部 API・LLM・第三者が書ける文書からの
入力を受け取らない。上記「検査への影響」の根拠は同一リポジトリのスクリプト
（`scripts/check-doc-index.mjs` / `scripts/check-doc-examples.mjs` / `scripts/check-api-mentions.mjs`）
であり、CI で再実行できる。

## Pros and Cons of the Options

### 案1a（6 本に割る）

- Good: 1 ページ 1 責務が保てる。最初の壁が最初のページに来る。ページ追加は検査を素通りする（実測）。
- Bad: ページ数が増える。入門の見出し・鎖を全ページ書き換える。

### 案1b（5 本のまま）

- Good: ファイル追加が無い。リンクの張り替えが最小。
- Bad: `install.md` が「契約・アプリ登録」と「`npm i`」の 2 責務になる。
  [ADR-0070][0070] が README で直した「入門と概念の同居」を小さく作り直すことになる。

### 案1c（モック節を削るだけ）

- Good: 一日で終わる。
- Bad: **今回の不満の中心**（契約済みの人の最初の壁が 2 ページ目にある）が残る。

### 案3a（見出しの番号を外す）

- Good: 増減のたびの振り直しが消える。順序の正が鎖（検査②）1 つになる。
- Bad: ページ単体を開いた読者に「入門の何番目か」が見えない（目次と `前提` / `次に読む` で補う）。

### 案4a（モックもフェイクサーバーも目的別へ）

- Good: 二重メンテが消える。npm 利用者の環境に無いもの（`fake:serve`）が入門から消える。
- Bad: `howto/test-without-contract.md` が厚くなる（現在 157 行 ＋ 移設分）。

### 案5a（目次を 入門 → 目的別 → 考え方 → リファレンス に）

- Good: 「早く繋ぐ → あとで深く」の動線どおりに並ぶ。
- Bad: [ADR-0070][0070] が置いた「考え方を先に読ませる」意図が弱まる（リード文で補う）。
