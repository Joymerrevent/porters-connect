# 52. レビュー指摘台帳の構成（単一ファイル vs 1 件 1 ファイル）

- Status: proposed
- Date: 2026-08-16
- Deciders: jun.shiromoto (Joymerrevent)

> stakeholder 提案（2026-08-16）: 「**RV を ADR のように 1 件 1 ファイルへ分離してはどうか**（`docs/reviews/rv/*.md`）。
> その方が AI が読みやすい」。分割そのものより **index（一覧）をどう保つか**が本 ADR の実質的な論点。
> 決定は decider が行う（自己 accept しない）。実施は accept 後の別 PR。

## Context and Problem Statement

`/project-review` は 2 種類の成果物を残す（[report-format][fmt]）— **横断台帳** `docs/reviews/findings.md`（RV-N・
ID 不変・エントリを消さず状態と処置を更新する「生きた」文書）と、**各回のスナップショット** `YYYY-MM-DD-NN.md`（点景）。
この台帳が単一ファイルで、回を重ねるごとに伸び続けている。

実測（develop 時点）:

- **386 行 / 22 件**。さらに 2026-08-16 のレビュー（別ブランチで作業中）で 8 件増えて **521 行 / 30 件**になる。
- **1 件あたりが伸びている**: 初期の RV-1〜12 は一律 **8 行**だったが、RV-13 以降は根拠を `file:line` で示し
  処置に「何をどう直したか」を残す運用が定着し、**RV-17 が 37 行・RV-20 が 33 行・RV-21 が 32 行・RV-19 が 29 行**。
  この密度は意図したもの（[SKILL.md][skill]「再現・追跡できない指摘は価値が低い」）なので、**今後も縮まない**。

読み手のコスト構造がこれで変わる。**1 件を参照したいときに 500 行超を読む**ことになり、
人にとっても AI にとっても無駄が大きい（AI の場合はコンテキストを直接消費する）。RV-50 まで行けば 1000 行を超える。
一方 ADR は当初から **1 判断 1 ファイル**（[ADR-0001][0001]）で 51 本を運用できており、同じ規模でも破綻していない。

問うべきは「**台帳を 1 件 1 ファイルに分割するか**」と、分割するなら「**一覧（index）をどう保つか**」。
後者が本質で、**index と本体で状態がズレると台帳の信頼性そのものが失われる**（「index は open だが本体は fixed」）。
「処置が追えること」が台帳の存在理由なので、これはフェイルセーフの問題として扱う。

## Decision Drivers

- **処置が追えること**（台帳の存在理由・[live-verification][lv] と同じ思想）。状態の正が 1 つに定まること
- **人の記憶でなく仕組みで守る**（`CLAUDE.md` の運用哲学）。二重管理は必ずズレる前提で設計する
- **部分読み込みのしやすさ**（AI が 1 件だけ読める＝コンテキスト効率）と**差分の局所性**（1 件の更新が 1 ファイルの diff）
- **移行コストと既存リンクの保全**（台帳は ADR 11 本・スナップショット・roadmap 等から参照されている）
- **既存運用との一貫**（ADR の 1 判断 1 ファイル・`NNNN-kebab-title.md`）
- **スケール**（件数が 2〜3 倍になっても同じ運用が成り立つか）

## Considered Options

- **案A: 現状維持** — 単一 `findings.md` のまま。
- **案B: 分割 ＋ 全項目 index** — `docs/reviews/rv/NNNN-*.md` に分割し、`findings.md` は現行のサマリ表
  （ID / 重要度 / 観点 / 状態）を人手で維持する。
- **案C: 分割 ＋ 生成 index ＋ CI 検査** — index を `rv/*.md` から生成し、生成物とコミット内容の一致を CI で検査する。
- **案D: 分割 ＋ 状態を持たない index** — index には **ID・タイトル・リンクだけ**を置き、
  **重要度・状態の正は各ファイルだけが持つ**。集計は `grep` で行う。
- **案E: 分割せず `fixed` をアーカイブ** — `findings.md` は open のみとし、`fixed` は `findings-archive.md` へ移す。

## Decision Outcome

> **未決（proposed）**。以下は起票者の推奨であり、決定は decider が行う。

**推奨: 案D**（分割 ＋ 状態を持たない index）。

理由（Decision Drivers に照らす）:

- **状態のズレが原理的に起きない**。案B は index に状態を持つので二重管理になり、更新頻度が低い
  （数週間に一度の run ＋ 随時の処置）ぶん**ズレても気づきにくい**。案D は index に状態を書かないので、
  **状態の正は常に各 RV ファイル 1 箇所**。二重管理の対象を「存在（ID とタイトル）」だけに絞る
  ＝ ズレても「新しい RV が index に無い」という**無害で目立つ形**にしか出ない。
- **仕組みで守るが、道具は最小**。案C は正攻法（このリポジトリには `scripts/check-release-invariants.mjs` の前例がある）だが、
  スクリプト＋そのテスト（[ADR-0014][0014] の方針でテストが要る）＋ CI ジョブが増える。
  **30 件規模には過剰**で、案D で足りる。件数が増えて index の維持が負担になったら、
  **案D → 案C は index の作り方を変えるだけ**で移行できる（ファイル構成は同じ）。
- **分割そのものの利得**: 1 件だけ読める（AI のコンテキスト効率）／1 件の更新が 1 ファイルの diff になる／
  1 件が長くなっても他に影響しない（RV-17 の 37 行のような密度を萎縮させずに済む）／ADR と運用が揃う。
- **移行コストが低いことを実測で確認済み**: 台帳を参照している **24 ファイル**（ADR 11 本・スナップショット・
  `roadmap.md`・`live-verification.md`・`design/fake-server-plan.md`・スキル）は**すべてファイル単位のリンク**で、
  **`findings.md#rv-13` のようなアンカー参照は 0 件**。`findings.md` を index として**同じパスに残せば、
  既存リンクは 1 本も壊れない**。
- 案A（現状維持）を退ける理由は上記の伸び方。案E は 1 ファイルの利点を保ったまま肥大化だけ抑える良い対案だが、
  **状態が変わるたびにファイル間を移動する**＝ diff が大きく、`git log --follow` でも経緯が追いにくい。
  「エントリを消さない」原則の**見かけ上の違反**にも見え、台帳の信頼性の説明が一段面倒になる。

### 実施時の合意事項（accept 後の別 PR）

1. **配置**: `docs/reviews/rv/NNNN-kebab-title.md`。**番号は ADR と同じ 4 桁ゼロ埋め**（`0023-…`）で、
   数字は RV-N の N。ID は不変・ファイルは削除しない（現行原則を継承）。
2. **index はパスを変えない**: `docs/reviews/findings.md` のまま。中身を「一覧＋運用の説明」に置き換える。
   既存 24 ファイルのリンクを触らない＝移行の副作用をゼロにする。
3. **1 ファイルの様式**: メタは箇条書き、本文は見出し（37 行を 1 行 1 フィールドで持つのは無理がある）。

   ```markdown
   # RV-23 🔴 Candidate の静的カタログが標準項目 4 件を欠く

   - 重要度: 🔴 High ／ 観点: API 忠実性 / 型安全
   - 状態: open
   - 検出: 2026-08-16（2026-08-16-01）

   ## 概要 / ## 根拠 / ## 検出経緯 / ## 推奨 / ## 処置
   ```

4. **状態行の書式を固定する**: `- 状態: open` のように**行頭から機械可読**にする
   （集計は `grep -l "^- 状態: open" docs/reviews/rv/*.md`）。将来 案C へ移るときの入力にもなる。
5. **移行はスクリプトで機械分割**する（`## RV-N …` 見出しで規則的に切れる）。手作業の転記はミスが出るため行わない。
   分割後に全 30 件を目視確認し、`pnpm lint:md` / `format:check` を通す。
6. **スキルを同じ PR で更新する**（[SKILL.md][skill] の「`docs/reviews/findings.md`（生きた台帳）を更新」と
   [report-format][fmt] の様式）。**これを忘れると次回の `/project-review` で単一ファイル運用に戻る**
   ＝ 決定が実装に定着しない。
7. **スナップショット（`YYYY-MM-DD-NN.md`）は変更しない**。台帳とスナップショットの内容重複は別の論点で、本 ADR では扱わない。
8. **semver 影響なし**（`docs/` は tarball 非同梱）。

### Consequences

- Good: 1 件だけ読める／差分が局所化する／件数が増えても破綻しない／ADR と運用が揃う／
  **状態の正が 1 箇所に定まる**（index に状態を持たないため）。
- Bad: ファイルが 30 個増える（ADR が 51 本あるので運用の違和感は小さい）。
  **一覧で状態が見えなくなる**ため、「今 open は何件か」は `grep` か各ファイルを開く必要がある
  （`roadmap.md` の「open N 件」は現在も手動更新なので、そこは変わらない）。
- Neutral: index と本体の二重管理は「存在」だけ残る（新規 RV の index 追記漏れはありうるが、無害で目立つ）。
  将来 案C（生成＋検査）へ移る余地を残す。

## Pros and Cons of the Options

### 案A: 現状維持（単一 `findings.md`）

- Good: 一覧性が最も高い（1 ファイルを開けば全部見える）。`grep` が 1 ファイルで済む。移行コストゼロ。
- Bad: 1 件を読むのに全体を読む。件数 × 密度で伸び続ける（30 件で 521 行、50 件なら 1000 行超）。
  1 件の更新が巨大ファイルの diff になる。AI のコンテキストを無駄に消費する。

### 案B: 分割 ＋ 全項目 index（人手更新）

- Good: 分割の利得を得つつ、一覧で重要度・状態まで見える（現行の見え方を保てる）。
- Bad: **状態が 2 箇所にある＝必ずズレる**。更新頻度が低いのでズレに気づきにくく、
  「処置が追える」という台帳の存在理由を損なう。人の注意に依存する＝フェイルセーフとして弱い。

### 案C: 分割 ＋ 生成 index ＋ CI 検査

- Good: 一覧の見え方を保ちつつ、ズレを**仕組みで**防ぐ。この repo の哲学に最も忠実。
- Bad: スクリプト＋テスト＋ CI ジョブが増える（30 件規模には過剰）。index の様式を変えるたびに生成器も直す。

### 案D: 分割 ＋ 状態を持たない index（推奨）

- Good: 状態の正が 1 箇所。道具が増えない。分割の利得を全部得る。案C へ後から移行できる。
- Bad: 一覧で状態が見えない（`grep` が要る）。「open だけ一覧したい」が 1 手増える。

### 案E: 分割せず `fixed` をアーカイブ

- Good: 1 ファイルの一覧性を保ったまま、現役の台帳を短く保てる。移行が軽い。
- Bad: 状態変化のたびにファイル間移動＝ diff が大きく経緯が追いにくい。
  1 件あたりの肥大化（37 行）には効かない。「エントリを消さない」原則の説明が面倒になる。
