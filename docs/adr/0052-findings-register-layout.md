# 52. レビュー指摘台帳の構成（単一ファイル vs 1 件 1 ファイル）

- Status: accepted
- Date: 2026-08-16
- Deciders: jun.shiromoto (Joymerrevent)

> **案C（改）で `accepted`（2026-08-16）**: `docs/reviews/rv/NNNN-*.md` へ**1 件 1 ファイルに分割**し、
> index（`docs/reviews/findings.md`）は**状態を含む一覧を保つ**。ズレは**人の注意ではなく検査で弾く**
> （`pnpm check:findings` を CI の常時実行ブロックに置く）。実施は本 ADR とは別 PR。
> 起票時の推奨は案D（状態を持たない index）だったが、**議論中の実測で案C のコスト見積もりが過大と判明**し、
> 「一覧で状態が見える」利点をほぼ同じコストで取れるため案C（改）を採る。経緯は下記「議論中に得た実測」。

## Context and Problem Statement

`/project-review` は 2 種類の成果物を残す（[report-format][fmt]）— **横断台帳** `docs/reviews/findings.md`（RV-N・
ID 不変・エントリを消さず状態と処置を更新する「生きた」文書）と、**各回のスナップショット** `YYYY-MM-DD-NN.md`（点景）。
この台帳が単一ファイルで、回を重ねるごとに伸び続けている。

実測（develop 時点）:

- **386 行 / 22 件**。さらに 2026-08-16 のレビュー（別ブランチで作業中）で 8 件増えて **521 行 / 30 件**になる。
- **1 件あたりが伸びている**: 初期の RV-1〜12 は一律 **8 行**だったが、RV-13 以降は根拠を `file:line` で示し
  処置に「何をどう直したか」を残す運用が定着し、**RV-17 が 37 行・RV-20 が 33 行・RV-21 が 32 行・RV-19 が 29 行**。
  この密度は意図したもの（[SKILL.md][skill]「再現・追跡できない指摘は価値が低い」）なので、**今後も縮まない**。

読み手のコスト構造がこれで変わる。**1 件を参照したいときに 500 行超を読む**ことになり、
人にとっても AI にとっても無駄が大きい（AI の場合はコンテキストを直接消費する）。RV-50 まで行けば 1000 行を超える。
一方 ADR は当初から **1 判断 1 ファイル**（[ADR-0001][0001]）で 51 本を運用できており、同じ規模でも破綻していない。

問うべきは「**台帳を 1 件 1 ファイルに分割するか**」と、分割するなら「**一覧（index）をどう保つか**」。
後者が本質で、**index と本体で状態がズレると台帳の信頼性そのものが失われる**（「index は open だが本体は fixed」）。
「処置が追えること」が台帳の存在理由なので、これはフェイルセーフの問題として扱う。

### 議論中に得た実測（2026-08-16・決定の根拠）

「ADR の index はどう管理しているのか」という問いから、**先行事例として ADR の index を実測**した。
`docs/adr/README.md` は状態を **3 箇所**で持っている（一覧テーブルの「ステータス」列／論点バックログの散文／
各 ADR 本文の `- Status:`）。自動化・検査は一切なく、すべて手動。**結果は二分した**:

- **一覧テーブルは健全**。ADR 51 本すべてで本文 `Status:` と突合したところ、不一致は 0037 の 1 件のみで、
  それも本文 `superseded by [[0039]]` ↔ テーブル `superseded` という**省略の差**＝実質ドリフトなし。
- **散文の側は腐っていた**。「実装はこれから」と書いたまま放置された記述が **5 件**
  （ADR-0038 は 0.4.0 で公開済みなのに「実装は別 PR」、ADR-0017 / 0018 / 0021 は「コード反映は別 PR」、
  ADR-0051 は実装・公開済みなのに【accept 済み・実装待ち】節に残置）。

この差は**構造の差**と読める。テーブルは 1 行 1 件・列固定・値が enum で、**エントリを足す編集と同じ手の動きで更新でき、
ズレていれば目で見て分かる**。散文は「いつ実装されたか」という別軸の状態を自由文で持ち、更新の契機が編集動線から外れる。

さらに、この突合そのものが **6 行のシェル**で書けた。ここから起票時の
「案C はスクリプト＋テスト＋ CI ジョブが増えるので 30 件規模には過剰」という見積もりは**過大**だったと分かった
（比較ロジック自体は数行で、既存の `check:release` と同じ形に収まる）。

## Decision Drivers

- **処置が追えること**（台帳の存在理由・[live-verification][lv] と同じ思想）。状態の正が 1 つに定まること
- **人の記憶でなく仕組みで守る**（`CLAUDE.md` の運用哲学）。二重管理は必ずズレる前提で設計する
- **部分読み込みのしやすさ**（AI が 1 件だけ読める＝コンテキスト効率）と**差分の局所性**（1 件の更新が 1 ファイルの diff）
- **移行コストと既存リンクの保全**（台帳は ADR 11 本・スナップショット・roadmap 等から参照されている）
- **既存運用との一貫**（ADR の 1 判断 1 ファイル・`NNNN-kebab-title.md`）
- **スケール**（件数が 2〜3 倍になっても同じ運用が成り立つか）

## Considered Options

- **案A: 現状維持** — 単一 `findings.md` のまま。
- **案B: 分割 ＋ 全項目 index（人手のみ）** — `docs/reviews/rv/NNNN-*.md` に分割し、`findings.md` は現行のサマリ表
  （ID / 重要度 / 観点 / 状態）を人手で維持する。検査なし。
- **案C: 分割 ＋ 全項目 index ＋ 検査** — 案B に、index と各ファイルの一致を検査する仕組みを足す。
  - **案C（改）**: 検査を **`scripts/` の小さなチェッカー ＋ CI の常時実行ステップ**として実装する
    （既存 `check:release` と同じ形）。起票時に想定した「生成器＋テスト＋専用 CI ジョブ」より軽い。
- **案D: 分割 ＋ 状態を持たない index** — index には ID・タイトル・リンクだけを置き、
  重要度・状態の正は各ファイルだけが持つ。集計は `grep`。
- **案E: 分割せず `fixed` をアーカイブ** — `findings.md` は open のみとし、`fixed` は `findings-archive.md` へ移す。

## Decision Outcome

**採用: 案C（改）**。`docs/reviews/rv/NNNN-kebab-title.md` へ 1 件 1 ファイルに分割し、
`docs/reviews/findings.md` は **ID / 重要度 / 観点 / 状態 / 概要 ＋ リンク**を持つ index として維持する。
index と各ファイルのズレは **`pnpm check:findings`** が検出し、**CI で落とす**。

理由（Decision Drivers に照らす）:

- **「一覧で状態が見える」は運用上の実利がある**。`/project-review` は毎回「**前回の open を再評価する**」ところから
  始まり（[SKILL.md][skill]「open 指摘の再評価が今回の仕事の半分」）、[roadmap][rm] も「open N 件」を掲げる。
  案D はこの入口を `grep` に置き換えるが、**台帳を開いた人が状態を見られない**のは日常の摩擦として無視できない。
- **ズレを人の注意に委ねない**。案B との差は検査の有無だけで、**検査が無いと腐る**ことは上記の実測が示している
  （ADR index の散文 5 件）。逆に、**機械的に突合できる形（テーブル＋固定書式）なら生き残る**ことも同じ実測が示した。
  案C（改）は「見える形（テーブル）」と「守る仕組み（検査）」を両方取る。
- **コストが想定より小さい**。比較ロジックは数行で、既存 [`check:release`][ci] と同じ「`scripts/` の小さな `.mjs` ＋
  `pnpm` スクリプト ＋ CI の常時実行ステップ」に収まる。**新しい仕組みの発明は不要**（前例の横展開）。
- **分割そのものの利得**（案B〜D 共通）: 1 件だけ読める（AI のコンテキスト効率）／1 件の更新が 1 ファイルの diff になる／
  1 件が長くなっても他に影響しない（RV-17 の 37 行のような密度を萎縮させずに済む）／ADR と運用が揃う。
- **移行コストが低いことを実測で確認済み**: 台帳を参照している **24 ファイル**（ADR 11 本・スナップショット・
  `roadmap.md`・`live-verification.md`・`design/fake-server-plan.md`・スキル）は**すべてファイル単位のリンク**で、
  **`findings.md#rv-13` のようなアンカー参照は 0 件**。`findings.md` を index として**同じパスに残せば、
  既存リンクは 1 本も壊れない**。

退けた案:

- **案A（現状維持）**: 上記の伸び方（1 件あたり 8 行 → 37 行）で、1 件を読むのに全体を読む構造が固定化する。
- **案B（検査なし）**: 実測した ADR index の散文と同じ経路で腐る。フェイルセーフとして弱い。
- **案D（状態を持たない index）**: ズレは原理的に起きないが、**一覧で状態が見えない**代償が大きい。
  案C（改）のコストが案D とほぼ変わらないと分かった時点で、案D を選ぶ理由が消えた。
  なお案C の検査が将来重荷になったら、**index から状態列を落とすだけで案D へ後退できる**（ファイル構成は同じ）。
- **案E（アーカイブ）**: 1 ファイルの一覧性を保つ良い対案だが、状態変化のたびにファイル間移動＝ diff が大きく
  経緯が追いにくい。1 件あたりの肥大化（37 行）にも効かない。

### 実施時の合意事項（accept 後の別 PR）

1. **配置**: `docs/reviews/rv/NNNN-kebab-title.md`。**番号は ADR と同じ 4 桁ゼロ埋め**（`0023-…`）で、
   数字は RV-N の N。ID は不変・ファイルは削除しない（現行原則を継承）。
2. **index はパスを変えない**: `docs/reviews/findings.md` のまま。中身は「運用の説明 ＋ 一覧テーブル
   （ID / 重要度 / 観点 / 状態 / 概要 ＋ 各ファイルへのリンク）」にする。
   既存 24 ファイルのリンクを触らない＝移行の副作用をゼロにする。
3. **1 ファイルの様式**: メタは箇条書き、本文は見出し（37 行を 1 行 1 フィールドで持つのは無理がある）。

   ```markdown
   # RV-23 🔴 Candidate の静的カタログが標準項目 4 件を欠く

   - 重要度: 🔴 High ／ 観点: API 忠実性 / 型安全
   - 状態: open
   - 検出: 2026-08-16（2026-08-16-01）

   ## 概要 / ## 根拠 / ## 検出経緯 / ## 推奨 / ## 処置
   ```

4. **メタ行を機械可読に固定する**: `- 状態: open` のように**行頭から決め打ち**で書く。
   これが検査の入力になる（重要度・観点も同様に固定書式）。
5. **検査 `pnpm check:findings`**: `scripts/check-findings-index.mjs` を追加し、
   **(a)** index の各行と `rv/*.md` が 1 対 1 で対応する（**取りこぼし・幽霊行の両方**を検出）、
   **(b)** 重要度 / 観点 / 状態が一致する、**(c)** 状態が既定の語彙（open / fixed / wontfix / deferred）である、
   を検査する。ズレたら非ゼロ終了。既存 [`check:release`][ci] と同じ形（`scripts/` の `.mjs` ＋ `pnpm` スクリプト）とし、
   同じく `scripts/check-findings-index.test.mjs` でテストする（`scripts/` は coverage 計測対象外＝
   [ADR-0014][0014] の 100% 閾値は掛からないが、テストは前例に倣って付ける）。
6. **CI は「常時実行ブロック」に置く**。[ADR-0028][0028] のパスフィルタにより **docs-only の変更では
   typecheck / test / build が skip される**が、台帳の更新はまさに docs-only PR で起きる。
   よって `Format check` / `Lint` / `Release invariants` と同じ**常時実行の位置**に
   `Findings index` ステップを足す（`if: steps.changes.outputs.code == 'true'` を**付けない**）。
   ここを間違えると**検査が一度も走らない**＝決定が形だけになる。
7. **移行はスクリプトで機械分割**する（`## RV-N …` 見出しで規則的に切れる）。手作業の転記はミスが出るため行わない。
   分割後に全 30 件を目視確認し、`pnpm lint:md` / `format:check` / `check:findings` を通す。
8. **スキルを同じ PR で更新する**（[SKILL.md][skill] の「`docs/reviews/findings.md`（生きた台帳）を更新」と
   [report-format][fmt] の様式）。**これを忘れると次回の `/project-review` で単一ファイル運用に戻る**
   ＝ 決定が実装に定着しない。併せて「新規 RV は index にも 1 行足す（`check:findings` が守る）」を明記する。
9. **スナップショット（`YYYY-MM-DD-NN.md`）は変更しない**。台帳とスナップショットの内容重複は別の論点で、本 ADR では扱わない。
10. **semver 影響なし**（`docs/` は tarball 非同梱）。

### Consequences

- Good: 1 件だけ読める／差分が局所化する／件数が増えても破綻しない／ADR と運用が揃う／
  **一覧で状態が見える運用を維持**したまま、**ズレを仕組みで弾ける**（人の注意に依存しない）。
- Bad: 検査スクリプト＋そのテスト＋ CI ステップが増える（前例の横展開なので発明は無いが、保守対象ではある）。
  ファイルが 30 個増える（ADR が 51 本あるので運用の違和感は小さい）。
  **メタ行の書式が検査に縛られる**（自由に書き換えられない＝様式変更時は検査も直す）。
- Neutral: index は依然として二重管理だが、**ズレたら CI が落ちる**ので「気づけない」状態ではなくなる。
  重荷になったら index の状態列を落として案D へ後退できる。

## Pros and Cons of the Options

### 案A: 現状維持（単一 `findings.md`）

- Good: 一覧性が最も高い（1 ファイルを開けば全部見える）。`grep` が 1 ファイルで済む。移行コストゼロ。
- Bad: 1 件を読むのに全体を読む。件数 × 密度で伸び続ける（30 件で 521 行、50 件なら 1000 行超）。
  1 件の更新が巨大ファイルの diff になる。AI のコンテキストを無駄に消費する。

### 案B: 分割 ＋ 全項目 index（人手のみ・検査なし）

- Good: 分割の利得を得つつ、一覧で重要度・状態まで見える。追加の道具が要らない。
- Bad: **状態が 2 箇所にあり、検査が無い**。更新頻度が低いのでズレに気づきにくい。
  ADR index の散文 5 件が**まさにこの経路で腐った**（実測）。

### 案C（改）: 分割 ＋ 全項目 index ＋ 検査（採用）

- Good: 一覧の見え方を保ちつつ、ズレを**仕組みで**防ぐ。この repo の哲学に忠実で、`check:release` の前例に乗る。
- Bad: 保守対象（スクリプト・テスト・CI ステップ・書式の固定）が増える。
  CI の配置を誤ると（パスフィルタ配下に置くと）検査が走らず、形だけになる。

### 案D: 分割 ＋ 状態を持たない index

- Good: 状態の正が 1 箇所。道具が増えない。分割の利得を全部得る。
- Bad: 一覧で状態が見えない（`grep` が要る）。レビューの入口（前回 open の再評価）と roadmap の「open N 件」で
  毎回 1 手増える。**案C（改）とコスト差が小さいと分かった時点で選ぶ理由が薄れた**。

### 案E: 分割せず `fixed` をアーカイブ

- Good: 1 ファイルの一覧性を保ったまま、現役の台帳を短く保てる。移行が軽い。
- Bad: 状態変化のたびにファイル間移動＝ diff が大きく経緯が追いにくい。
  1 件あたりの肥大化（37 行）には効かない。「エントリを消さない」原則の説明が面倒になる。

## More Information

- 現行の運用と様式: [SKILL.md][skill]／[report-format][fmt]。**両方とも本決定に合わせて更新が要る**（実施時の合意事項 8）。
- 検査の前例: [`scripts/check-release-invariants.mjs`][ci]（`pnpm check:release`・CI の常時実行ステップ・
  同ディレクトリにテスト）。本決定の `check:findings` はこれと同じ形に揃える。
- CI のパスフィルタ: [ADR-0028][0028]。docs-only 変更で重い検査が skip される仕様なので、
  **`check:findings` は skip 対象に入れない**（実施時の合意事項 6）。
- 台帳の思想的な親: [live-verification][lv]（LV-N・行を消さず状態を更新する）。**LV は本 ADR の対象外**
  （13 件・1 ファイルで収まっており、同じ問題は起きていない）。同じ問題が出たら本 ADR を先例にできる。
- 1 判断 1 ファイルの先例: [ADR-0001][0001]。ドキュメント構成をプロセス決定として ADR 化した先例:
  [ADR-0035][0035]（README と `docs/guide` の役割分担）。
- 実測の出典: `docs/reviews/findings.md`（develop・386 行 / 22 件）、参照元 24 ファイル・アンカー参照 0 件
  （`grep -rn "findings\.md#"`）、ADR index の突合（本文 `Status:` ↔ 一覧テーブル・51 本）。
  **ADR index の散文で見つかった陳腐化 5 件は本 ADR とは別に是正する**（決定の対象ではなく、実測の副産物）。
