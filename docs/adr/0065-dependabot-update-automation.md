# 65. Dependabot 依存更新の判定と取り込みを自動化する

- Status: accepted
- Date: 2026-09-05（accepted: 2026-09-05）
- Deciders: jun.shiromoto (Joymerrevent)

> 依存更新 PR の検査は**毎回同じ手順**で、しかも**間違えても静かに通る**種類の作業。
> `.claude/skills/dependabot-merge` はその手順を固定したが、**人が起動しないと動かない**。
> 起動を仕組みへ移し、判断材料を毎回同じ深さで揃える。**通す/止める の決定は人に残す。**

## Context and Problem Statement

[ADR-0025][adr25] 以降、リリースと back-merge は自動化してきた（[ADR-0029][adr29] / [ADR-0062][adr62]）が、
**依存更新の取り込みだけが人の記憶に残っている**。スキルは手順を固定したものの起動は手動で、実測では
3 件（#220 / #221 / #222）が滞留していた。cooldown を満たし CI も緑なのに滞留するのは、**検査そのものの
コストではなく「やろうと思い出すコスト」**が原因である。

決めるべきことは 8 つある。**論点1〜3 が起動と実行の形、論点4 が認証、論点5 が出力、論点6 が取り込み手順、論点7 がモデル、論点8 が費用の抑制。**

## Decision Drivers

- **フェイルセーフ** — 壊れたときに安全側へ倒す。**静かに通る**形を作らない。
- **人の記憶に置かない** — 起動も出力形式も仕組みで守る（[ADR-0039][adr39] / [ADR-0052][adr52] と同じ規律）。
- **決定は人に残す** — 依存 PR は develop 向けで npm 公開を起動しない＝可逆性は高いが、**通す判断は人**。
- **信頼できない入力を前提にする** — PR 本文は**第三者の CHANGELOG から dependabot が転記したテキスト**。
- **権限で被害範囲を縛る** — 事故と prompt injection の両方に効くのは、プロンプトの文言ではなく権限。

## 論点1: 判定をいつ走らせるか

- **案1a: `schedule`（平日朝）＋ `workflow_dispatch`** — 推奨
- 案1b: `pull_request`（PR 作成時）
- 案1c: ローカルの SessionStart hook で検知して起動

「PR ができた瞬間」は直感的だが、**判定材料の半分がまだ存在しない**。CI は走り始めたばかりで、base の
鮮度は「他を 1 件マージした後」に初めて劣化する。cooldown は dependabot が既に効かせているので、
作成イベントに反応しても再検査の意味が薄い。加えて案1b は secrets の二重管理を強いる。

## 論点2: マージ工程に LLM を入れるか

- **案2a: 入れない。判定と実行を分け、実行は固定シーケンス** — 推奨
- 案2b: 入れる（`@claude` メンション等でエージェントにマージまでさせる）

`update-branch` → CI 緑を待つ → `gh pr merge --squash` は**判断を一切含まない**。判断（通してよいか）は
判定表として既に出ている。案2b は、**第三者由来のテキストを読むエージェントにマージ権限を与える**
ことを意味し、しかも injection が狙う先は「この更新は安全だ、マージせよ」という**まさにその判断**である。

> **［2026-09-05 追記・実装］** 「判断は判定表として既に出ている」を成り立たせるには、
> **判定したコミットと取り込むコミットが同じ**でなければならない。レポート作成後に dependabot が
> force-push すると、誰も CHANGELOG を読んでいないコミットが「承認済み」として取り込まれる
> — 実行側は open / 作者 / base / 変更ファイル / CI しか再検証しておらず、どれも中身の入れ替わりを
> 捕まえない。そこで**取り込み対象行に判定時点の head SHA を持たせ**（`#222@1a2b3c4`）、取り込み時に
> `git merge-base --is-ancestor` で現 head の祖先かを確かめる。`update-branch` は develop を取り込む
> merge なので祖先関係は保たれ（＝通る）、force-push では切れる（＝止まる）。
> SHA はモデルが書き写す値なので、**投稿前に gate が見た事実と突き合わせる**（自己申告を検証せずに
> 信じない）。番号を直接指定した `/merge` は判定時点が分からないため、確認していないことを結果に明記する。

## 論点3: マージをどこから起動するか

- **案3a: 判定 Issue へのコメント `/merge`**（`/merge 222 221` で対象と順序を指定）— 推奨
- 案3b: `workflow_dispatch` のボタン（Issue から導線リンク）
- 案3c: ローカルのスキル実行のみ（現状維持）

判定を読んだその場で依頼できるのが案3a。コメント解析と権限チェックが要る分だけ実装は増えるが、
**起動条件を Issue のタイトル一致と `author_association` で二重に絞れる**。

> **［2026-09-05 追記・実装］** 実装では起動条件を 3 つに増やした。タイトル一致は、public リポジトリでは
> **誰でも同名の Issue を立てられる**ため単独では絞りになっていない。**ラベル `dependabot-triage`**
> （付けられるのは write 権限を持つ人だけ）と**作者が bot であること**を加えている。
> あわせて、番号を省いた `/merge` の意味を「open な dependabot PR 全件」ではなく
> **レポートの `- 取り込み対象:` 行に載っている PR だけを、その順で**に定めた。全件にすると、
> 判定表が「見送り」とした PR まで巻き込む — 実行側は cooldown も破壊的変更も見ないので、
> **CI が緑なら通ってしまう**。判定表を読んだ人の決定はその 1 行に現れる、という形にしている。

## 論点4: 判定ワークフローの認証

- **案4a: Claude サブスクリプションの OAuth トークン（`CLAUDE_CODE_OAUTH_TOKEN`）** — 推奨
- 案4b: API キー（`ANTHROPIC_API_KEY`）
- 案4c: OIDC / Workload Identity Federation

案4a は API 課金が発生しない。トークンは**発行した個人のサブスクに紐づく**ため、複数リポジトリや
組織で共有する段階になったら案4b へ切り替える（公式もそう案内している）。案4c はサブスクリプションでは
使えず、Console のサービスアカウントが要る。

## 論点5: レポート形式をどう固定するか

- **案5a: 雛形ファイルを単一の正とし、投稿後に機械検証する** — 推奨
- 案5b: GitHub の `.github/ISSUE_TEMPLATE/`
- 案5c: プロンプトに「この形式で書け」と書くだけ

形が毎回変わると、読む側は差分ではなく全文を読み直すことになり、結局読まれなくなる。案5b は
**API 経由の作成に効かない**ので、置いても案5c と同じ状態になる。案5c はモデルの記憶に依存し、
崩れても静かに通る。

**検証は投稿の前に行う。** 後に回すと崩れたレポートが一度 Issue に出てしまう。また投稿自体も
判断を含まないのでシェルが行い、Claude はレポートを書くところまでを担当する。こうすると
Claude が途中で失敗してもレポートさえ書けていれば投稿でき、`gh issue` の権限も渡さずに済む。

> **［2026-09-05 追記・実装］** 「Claude に Issue の権限を渡さない」は**プロンプトの文言では実現できない**。
> `Bash(gh api:*)` の許可と job の `issues: write` が揃うと、`gh issue` を禁じても API 経路は開いたままで、
> 第三者由来のテキスト（PR 本文）を読む主体が書き込める状態になる。実装では**判定 job（`issues: read`）と
> 投稿 job（`issues: write`）に分割**し、レポート本文だけを job 出力で渡している。
> 検証範囲も広げた: 見出しの構造だけでなく、**次回の実行要否に使う機械可読行**（検査時刻・判定の指紋・
> 取り込み対象）まで投稿前に検証する。**検証しない行は、読めなくなったときに静かに機能を失う**
> （検査時刻が読めなくなれば論点8 の 3 日ルールが無言で無効化される）。行の形の定義は
> `.github/scripts/dependabot-report-format.sh` に 1 箇所置き、読む側と検証する側で共有する。

## 論点6: base が古い PR を `update-branch` するか

- **案6a: 続ける。ただし理由を「CI に検証させるため」に置き換える** — 推奨
- 案6b: やめる（GitHub が要求していないので不要と割り切る）

スキルの現行記述「branch protection が base の鮮度を要求する／1 件マージすると残りは
`Base branch was modified` で弾かれる」は、**現在このリポジトリでは成り立たない**（`strict: false`）。
だが結論は変わらない。**GitHub が止めてくれないからこそ**、更新しないと「develop を取り込んだ後の
ロックファイル」に対して CI が一度も走らないまま develop に入る。ロックファイルは機械的に解決すると
**静かに壊れる**ので、ここは CI に検証させる必要がある。

## 論点7: 判定に使うモデルをどう選び、固定するか

- **案7a: 階層だけ固定し、版は浮動にする（`--model opus` ＝ 最新の Opus）** — 推奨
- 案7b: 版まで固定する（`--model claude-opus-5`）
- 案7c: モデルを指定せず Claude Code の既定に追随する
- 案7d: Sonnet など下位の階層に落とす

この自動化が人手に対して価値を出すのは、**長い CHANGELOG の中の 1 行の破壊的変更を見落とさない**
という一点である。cooldown や CI の突き合わせは既にスクリプト側（`triage.sh`）が決定的にやっており、
モデルに委ねているのは読解と判断だけ。**能力が効くのは、まさに自動化が対価を得ている部分**なので、
ここを削るのは費用対効果の計算として筋が悪い。

案7d（階層を落とす）については、費用が認証の選択（論点4）に依存する。**案4a（サブスクリプション）
では消費するのは契約の利用枠**で、階層を落としても支払いは変わらない。案4b（API キー）に切り替えた
場合のみ差が出る。

| モデル    | 1 回あたりの推計 | 備考          |
| --------- | ---------------- | ------------- |
| Opus 5    | $0.47〜$0.65     | 現行          |
| Sonnet 5  | $0.19〜$0.26     | 約 2.5 分の 1 |
| Haiku 4.5 | $0.09〜$0.13     | 約 5 分の 1   |

（最終コンテキスト約 37,000 トークン・10 ターン・プロンプトキャッシュ有効を前提とした推計。
`count_tokens` による実測ではない。入力の 43% は dependabot の PR 本文が占める。）

**固定したいのは能力の下限であって、特定の版ではない。** 案7c を採らないのは、既定に追随すると
**階層ごと下がりうる**（既定が下位モデルになれば黙って従う）ためで、そこは明示して防ぐ。
`opus` エイリアスなら階層は保証されるので、この懸念は生じない。

**案7b（版まで固定）を採らないのは、腐るからである。** モデル ID の更新を促す仕組みが本リポジトリに
無い — dependabot は依存パッケージを見るがモデル ID は見ないので、古くなっても誰も気づかない。
やがて提供終了で黙って壊れるか、劣った版に留まり続ける。**更新されない固定は、固定ではなく放置**である。
案7b が守る「どの版が判定したかの再現性」は Actions の実行ログで追えるので、腐敗のリスクと
引き換えにするほどの価値は無い。

なお `--fallback-model` で過負荷時の下位階層への自動退避も設定できるが、**採らない**。黙って階層が
下がるのは案7c と同じ問題であり、判定は日次で再実行されるのだから、失敗して次の回に回るほうが
安全側に倒れる。

**同じ理由で `--effort` も明示的に固定する。** モデルだけ固定して effort を既定任せにするのは
一貫していない。effort の既定は**モデルごとに違いうる**（`high` が既定だが Opus 4.7 だけ `xhigh`）
ため、既定値が変われば挙動も黙って変わる。`high` を選ぶ根拠もモデル選択と同じで、公式ドキュメントは
`low` を「知性を要さないタスクに限る」、`medium` を「多少の知性を犠牲にできる作業向け」としており、
どちらもこの用途の説明に当てはまらない。

費用を下げる必要が生じた場合の順序は **論点8 の抑止 → `--effort` を下げる → 階層を落とす**。
ただし費用の主因は入力側（1 回あたり推計で入力 約 $0.35 に対し出力 $0.13〜$0.30）なので、
出力側にしか効かない effort の効き幅は限定的である。

## 論点8: 同じ判定を繰り返さない仕組みを入れるか

- **案8a: 前回のレポートから状況が変わっていなければ起動しない（指紋 ＋ 鮮度）** — 推奨
- 案8b: 抑止しない。毎回判定する
- 案8c: 実行間隔を週次にして回数自体を減らす

ワークフローは **PR が残っている限り毎営業日走る**ため、数日滞留すると同じ判定を毎朝やり直すことになる。
費用の主因はエージェントループが再送する会話全体（累計入力は最終コンテキストの約 7 倍）なので、
ここが月額に直結する。

指紋の作り方に落とし穴がある。**`triage-facts.txt` をそのままハッシュしてはいけない** — 本文に
「（9 日前）」のような経過日数が入っており、何も変わっていなくても毎日値が変わって抑止が効かない。
拾うのは判定が変わりうる要素だけ（PR の集合と head SHA / 各チェックの結論 / base の鮮度 /
cooldown 未達の警告が付いたパッケージ）。

ただし **cooldown の熟成は時間依存で、指紋だけでは捉えきれない**（major の 14 日境界は `triage.sh` の
7 日警告には現れない）。そこで「前回から 3 日以上経っていれば指紋が同じでも再判定する」を併用する。
**取りこぼすくらいなら余分に走らせる**＝安全側に倒す。

案8c は回数を確実に減らすが、**新しく来た PR に気づくのが最大 1 週間遅れる**。滞留を減らすのが目的の
自動化で、気づきを遅らせるのは本末転倒である。

## Decision Outcome

**決定（accepted・2026-09-05）：推奨どおり全採用 — 案1a / 案2a / 案3a / 案4a / 案5a / 案6a / 案7a / 案8a。**

まとめると: 判定は **`schedule`（平日朝）で走らせ**、前回から状況が変わっていなければ**起動しない**
（指紋 ＋ 3 日の鮮度）。使うモデルは **`opus` エイリアスで階層だけ固定し版は浮動**、`--effort high` は
明示。認証は**サブスクリプションの OAuth トークン**。出力は**雛形を単一の正とし、投稿の前に機械検証**
してからシェルが追跡 Issue に反映する。マージは**判定 Issue への `/merge` コメント**で起動し、
**その工程に LLM を入れない**。取り込みは 1 件ずつ **`update-branch` してから CI の緑を待つ**。

### Consequences

**良くなること**

- 依存更新が**滞留しなくなる**。起動が人の記憶から外れる。
- 判定材料が**毎回同じ深さ**で揃う。破壊的変更・major・`engines` の読み取りという、人手で最も漏れやすい
  部分が自動化の対象になる。
- マージ経路に LLM が無いので、**prompt injection でマージが誘発される経路が存在しない**。
- レポートの形が固定されるので、**前回との差分**として読める。

**引き受けるコスト・制約**

- **ワークフローが `main` に載るまで動かない。** `schedule` も `issue_comment` も既定ブランチ限定。
  git-flow 上、有効化はリリースを経由する。
- **public リポジトリでは 60 日停滞で `schedule` が無言停止する。** 気づけない壊れ方なので、
  ワークフローにコメントで明記する。
- **判断材料を取得できなかった朝は、定期実行が赤くなる。** 当初の実装は `gh api` の失敗を
  「open な PR は 0 件」と読んでいたため、API が落ちている間は判定が緑のまま静かに止まり、
  この自動化が防ごうとしている滞留がそのまま起きていた（実装後のレビューで検出）。
  取得の失敗は job を落として知らせる方に倒したので、**一時的な API 障害でも通知が出る**。
  赤は仕様であって事故ではない。頻発するようなら再試行を挟む判断が要る。
- **トークンは個人のサブスクに紐づく。** 共有段階になったら案4b へ切り替える判断が要る。
- **判定は Claude が書く。** 形式は機械検証できるが、**内容の正しさは検証できない**。だから
  マージの決定を人に残す設計にしている。
- **`SKILL.md` の base 鮮度に関する記述は事実と食い違っていた**（`strict: false` なので
  「base が古いと GitHub が弾く」は成り立たない）。この変更で論点6 の結論に合わせて修正済み。
  未了として残さないため、事実と処置をここに残す。
- **モデルの版は浮動なので、新しい Opus が出れば自動で乗り換わる。** 判定の挙動が変わる可能性は
  残るが、階層は下がらない。どの版が判定したかは Actions の実行ログで追う（論点7）。
- **重複実行の抑止はゼロにはできない。** 3 日ルールがあるため滞留が長いほど効果は頭打ちになる。
  cooldown の熟成を取りこぼさないための意図的な下限である（論点8）。

## Pros and Cons of the Options

### 案1a `schedule` ＋ `workflow_dispatch`（推奨）

- 良い: 判定材料が揃った頃に走る。secrets の制約を受けない。PR が 0 件なら LLM を起動しないので課金されない。
- 悪い: PR 作成から最大 1 日ずれる。既定ブランチにしか置けない。

### 案1b `pull_request`

- 良い: PR ができた瞬間に反応する。
- 悪い: CI 未完了で判定材料が揃わない。base の鮮度が意味を持たない。**secrets を読めず**、
  Dependabot secrets 側に鍵を二重管理することになる。

### 案2a マージに LLM を入れない（推奨）

- 良い: injection の経路が存在しない。API 課金も発生しない。決定的で再現する。
- 悪い: 判定表に無い例外的な状況（想定外のファイル変更など）には**止まることしかできない**。

### 案2b マージまでエージェントにやらせる

- 良い: 1 往復で終わる。
- 悪い: 第三者由来テキストを読む主体にマージ権限を与える。`contents: write` が要る。
  サブスクリプション認証だと**共同作業者が個人の枠を消費する**形になり、規約のアカウント共有に近づく。

### 案5a 雛形＋機械検証（推奨）

- 良い: 対話実行（`SKILL.md` §4）と自動実行が**同じ雛形**を参照するので食い違わない。崩れたら job が落ちる。
- 悪い: 雛形と検証の two-step を保守する必要がある。列を足すときは雛形側を直す規律が要る。

### 案5b `ISSUE_TEMPLATE`

- 良い: GitHub 標準の仕組みで、追加実装が要らない。
- 悪い: **API 経由の作成に効かない**ので、この用途では何も強制できない。人間向けの新規作成ピッカーも汚す。

### 案6a `update-branch` を続ける（推奨）

- 良い: マージ後のロックファイルに対して CI が走る。壊れた lock が静かに入るのを防ぐ。
- 悪い: 1 件ごとに CI の再実行を待つため、3 件で 10〜30 分かかる。

### 案6b `update-branch` をやめる

- 良い: 速い。GitHub も止めない。
- 悪い: **develop を取り込んだ後の状態を誰も検証していない**まま取り込むことになる。
  ロックファイルの壊れ方は静かなので、次に誰かが `pnpm install` するまで気づけない。

### 案7a 階層だけ固定・版は浮動（推奨）

- 良い: 能力の下限が保証される（階層は下がらない）。版の改善に自動で乗れる。**腐らない** —
  更新を促す仕組みが無くても古くならない。
- 悪い: どの版が判定したかが設定ファイルからは分からない（実行ログで追う）。新しい版で挙動が
  変わる可能性は残る。

### 案7b 版まで固定

- 良い: 何が判定したかが設定から一目で分かる。挙動が変わらない。
- 悪い: **更新を促す仕組みが無いので腐る。** dependabot はモデル ID を見ない。提供終了で黙って
  壊れるか、劣った版に留まり続ける。更新されない固定は放置と変わらない。

### 案7c モデルを指定しない

- 良い: 保守が要らない。
- 悪い: **階層ごと下がりうる。** 既定が下位モデルになれば黙って従う。変化に気づけない形の変更であり、
  フェイルセーフに反する。

### 案7d 下位の階層に落とす

- 良い: API 課金に切り替えた場合、費用が Sonnet で約 2.5 分の 1 になる。
- 悪い: **この自動化が対価を得ている当の部分**（長い CHANGELOG から破壊的変更を拾う）を削ることになる。
  案4a のままなら支払いは変わらないので、そもそも得るものが無い。

### 案8a 指紋 ＋ 鮮度で抑止（推奨）

- 良い: 滞留時の無駄な再判定が消える。`::notice::` に理由が残るので、抑止されたことが後から追える。
- 悪い: 指紋の構成要素を保守する必要がある。`triage.sh` の出力形式を変えると指紋の作り方も見直しが要る。

### 案8b 抑止しない

- 良い: 実装が単純。取りこぼしの可能性がない。
- 悪い: 滞留日数にそのまま比例して費用が増える。同じ内容の Issue 更新が毎朝走る。

## More Information

- 実装は別 PR（本 ADR とは分ける。[ADR-0001][adr01] の運用）。
- スキル本体は `.claude/skills/dependabot-merge/`。本 ADR で決めた形式の正は同ディレクトリの
  `templates/report.md` に置き、`SKILL.md` §4 と定期実行の両方がこれを参照する。
- 論点6 に伴い、`SKILL.md` の「branch protection が base の鮮度を要求する」旨の記述は**事実と
  食い違っている**ので修正が要る。
- **モデルを工程ごとに使い分ける案は採らなかった。** 判定ワークフローで Claude が触るのは
  「SKILL.md と事実ファイルを読む → 各 PR 本文から破壊的変更を探す → レポートを組み立てる →
  追跡 Issue を更新する」で、CHANGELOG の読解だけではない。しかし**文脈の大半（入力の 43%）を
  占めるのが PR 本文**であり、そこを安いモデルに任せて要約させると、高いモデルは**落とされた情報を
  復元できない**。工程を分けるなら「安いモデルに回す」ではなく「**LLM から外す**」方が筋が良い
  （論点2 と同じ考え方）。**この方針でレポートの検証と Issue の upsert はシェルへ移した**ので、
  Claude の担当は「SKILL.md と事実を読む → PR 本文から破壊的変更を探す → レポートを書く」に絞られる。
- **PR 本文の切り詰めは効果が小さい。** 実測では dependabot の `Commits` ブロックは PR 本文の 24%
  （最終コンテキスト全体の 10%）に留まり、残りは Changelog / Release notes ＝**落としてはいけない部分**
  だった。入力削減の手としては割に合わない。
