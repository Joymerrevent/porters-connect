# 71. 利用者向けドキュメントを `docs/usage/` の 1 箇所にまとめる

- Status: proposed
- Date: 2026-09-12
- Deciders: jun.shiromoto (Joymerrevent)

> [ADR-0070][0070] は 4 層（入門 → 考え方 → 目的別 → リファレンス）を決めたが、**置き場所は
> `docs/` 直下のまま**にした。結果として利用者向けと開発者向けが同じ階層に 14 項目並んでいる。
> 本 ADR は 0070 の**ディレクトリ構成だけ**を改める（層の分け方・各層の役割は変えない）。

## Context and Problem Statement

`docs/` 直下は現在こうなっている。

```text
docs/
  index.md  start/  concepts/  howto/  reference/  api/     ← 利用者向け（ADR-0070 の 4 層）
  adr/  design/  reviews/  history/                         ← 開発者向け
  roadmap.md  live-verification.md  fake-server-runbook.md  release-runbook.md
```

**読者の種類が違うものが、同じ深さに並んでいる。** 目次（`docs/index.md`）は「この下は開発者向け」と
節で区切って導線を作っているが、**ファイルの並びはその区別を表していない**。困るのは 2 つの場面。

1. **サイト化のとき**（[ADR-0070][0070] 論点5 で「目次ファイル 1 枚だけ用意し、必要になったら
   そこから設定を起こす」と決めた）。載せる範囲を `docs/**` から**列挙で除外**して指定することになり、
   generator の設定に「これは載せない」という一覧が生まれる。パスで表せるなら設定は 1 行で済む。
2. **リポジトリを開いた人の第一印象。** 14 項目のうちどれを読めばよいかが、名前からは分からない。

### 移設コスト（2026-09-12 実測）

| 対象         | 指している md | コード・設定             | 備考                                                 |
| ------------ | ------------- | ------------------------ | ---------------------------------------------------- |
| `start/`     | 1             | 2                        |                                                      |
| `concepts/`  | 10            | 3                        |                                                      |
| `howto/`     | 30            | 1                        |                                                      |
| `reference/` | 75            | **36 ファイル・51 箇所** | `src` の実装コメントが「API 事実の正典」として名指し |
| `api/`       | 7             | 4                        | ほかに設定 6 箇所（下記）                            |

`docs/api` を名指ししている設定・スクリプトは **7 箇所**: `typedoc.json` の `out`、
`scripts/check-api-reference.mjs` の `COMMITTED`、`scripts/check-doc-links.mjs` の `SKIP_PREFIXES`、
`.markdownlint-cli2.jsonc` の `ignores`、`.prettierignore`、`lint-staged.config.mjs`、
および `ci.yml` / `check-doc-examples.mjs` のコメント。

### 移設すると、検査が 2 つ静かに空振りする（実測）

`docs/start` を `docs/usage/start` へ仮移動して各ゲートを回した結果:

| 検査                            | 挙動                                                                                                    |
| ------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 検査①（目次と実ファイルの 1:1） | **落ちる**（目次側が古いと気づく）                                                                      |
| リンク検査（`check:links`）     | **落ちる**（相対リンクが解決しない）                                                                    |
| **検査②（入門の鎖）**           | **沈黙**。`docs/start` が無い＝対象ゼロで緑                                                             |
| **検査④（コード例の型検査）**   | **95 → 78 ブロックに縮んで緑**。移した 17 ブロックが対象外になるが、下限 `MIN_BLOCKS=40` には掛からない |

**移設という作業そのものが、移設を検出すべき検査を無効化する。** 定数を直し忘れても誰も気づかない。
これは本 ADR がいちばん重く見る事実で、実装の一部として**番人の追加**を含める必要がある。

## Decision Drivers

- **サイト化の単位がパス 1 本で表せること**（0070 論点5 の前提を壊さない）
- **読者の種類がディレクトリに現れること**
- **移設コストが、得るものに見合うこと** — 特に `src` のコメント 51 箇所を触る価値があるか
- **検査が空振りしないこと**（このリポジトリで最も重い壊れ方＝静かに通る）
- 過去の名前と衝突しないこと（`docs/guide/` は [#259][pr259] で退役済み）

## Considered Options

- 案A: **3 層だけ**（`start` / `concepts` / `howto`）を `docs/usage/` へ。`reference` と `api` は据え置き
- 案B: **4 層すべて**を `docs/usage/` へ（`reference` と `api` も含む）
- 案C: **読者で二分** — `docs/usage/` と `docs/internal/`（`adr` `design` `reviews` なども移す）
- 案D: 何もしない（目次の節区切りで足りるとみなす）

名前の候補は `usage`（[ADR-0070][0070] のタイトルと揃う）／`manual`。`guide` は退役済みのため除外。

## Decision Outcome

採用: **案B**、名前は **`usage`**。

```text
docs/
  README.md           ← リポジトリを開いた人の入口（利用者は usage/ へ、開発者はこの下へ）
  usage/
    index.md          ← 利用者向けの目次（4 層の入口）
    start/  concepts/  howto/  reference/  api/
  adr/  design/  reviews/  history/
  roadmap.md  live-verification.md  fake-server-runbook.md  release-runbook.md
```

理由: **4 層は「読者が読むもの」という 1 つの塊**であり、`reference` と `api` を外に残すと
「引くものだけ別の場所」という説明が必要になる。サイト化のときに載せる範囲が `docs/usage/**` の
1 行で表せることが、最大の利得。案A はコストは小さいが利得も半分で、`reference` を外に残す理由が
「移すのが面倒だから」になる — それは構成の理由として弱い。

案C は docs 直下がいちばんきれいになるが、`adr` のパスは**過去の PR 本文・コミットメッセージ・
外部から参照される可能性のある URL**に焼き付いており、得るものに対して失うものが大きい。
案D は上記 2 場面の問題が残る。

### 決めたこと（2 論点）

**論点1: `docs/index.md` は `docs/usage/index.md` へ移す**（案1b）。

「利用者向けは `usage/` で完結する」を徹底する。目次が `usage/` の外にあると、4 層をまとめた
意味が半分になり、サイト化のときに「目次だけ別扱い」という例外が生まれる。代わりに
**`docs/README.md` を新設**し、リポジトリを開いた人を「読む人は `usage/`、作る人はこの下」と
振り分ける。入口が 2 枚に増えるのは承知のうえで、**役割が違う 2 枚**なので混乱は生まない。

目次を動かすと影響するのは実測で 5 箇所（2026-09-12）— `README.md` の本文とラベル定義の 2 箇所、
`docs/start/going-live.md` の 1 箇所、`scripts/check-doc-index.mjs` の `indexPath`、
`scripts/check-doc-links.mjs` の `SENTINELS`。**このうち `SENTINELS` は移動を検出して落ちる**ので、
目次の移動だけは黙って通らない。

**論点2: 空振りした検査に番人を足す**（案2a）。

`check-doc-index.mjs`（検査①②）と `check-doc-examples.mjs`（検査④）に、
`check-doc-links.mjs` の `SENTINELS` と同じ規律を入れる — **「必ず実在するはずの対象」を宣言し、
見つからなければ落とす**。今回の実測で空振りした 2 つがこれで塞がる。検査④には下限
（`MIN_BLOCKS=40`）があるが、**95 → 78 に縮んでも発火しなかった**ので、下限だけでは足りない。

番人は移設と同じ PR に入れる。**移設の前に入れておくと、移設中に赤くなって移設が完了できない**ため、
順序は「移設 → 同じ PR で番人」になる。

| ------------------------------------------------------------------------------------------------ | -------------------------- | ------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------- |
| 検査が持つディレクトリ定数（`USER_DOC_DIRS` / `START_DIR` / `MARKDOWN_ROOTS` / `SKIP_PREFIXES`） | コード中の定数（人が書く） | このリポジトリに書ける人 | **今は無い**（`check-doc-links.mjs` の `SENTINELS` だけが例外）   | **静かに対象ゼロ**。実測で検査②が沈黙・検査④が 17 ブロック縮んだ         | 気づけない。緑のまま検査だけ消える → 論点2 で塞ぐ             |
| 生成物の出力先（`typedoc.json` の `out` と `check-api-reference.mjs` の `COMMITTED`）            | 設定 2 箇所（二重管理）    | 同上                     | 再生成差分ゲート（`check:api`）。ただし**両方が同じ値である前提** | 片方だけ直すと、生成先と検査先がずれて**常に差分ありで落ちる**（安全側） | 落ちるので気づける                                            |

| `src` のコメントが指す `docs/reference` のパス                                                   | 実装コメント 51 箇所       | 同上                     | **無い**（散文なので機械が見ていない）                            | —                                                                        | **誤ったまま残る**。リンクではないので `check:links` も見ない |

最後の行が案B の主要な負債である。移設と同時に一括置換するが、**置換漏れを検出する仕組みは無い**。

## Pros and Cons of the Options

### 案A（3 層だけ）

- Good: 触るのは md 41 ファイルと検査 3 本。`src` に一切触れない
- Bad: `reference` と `api` が外に残り、「4 層」という説明とディレクトリが食い違う。サイト化のとき
  載せる範囲が 2 本になる

### 案B（4 層すべて・採用）

- Good: サイト化の範囲が `docs/usage/**` の 1 行。4 層の説明とディレクトリが一致する
- Bad: `src` のコメント 51 箇所と設定 7 箇所を触る。ドキュメント移設の PR が `src` を含むため、
  差分が「何の変更か」を一目で言いにくくなる
- Neutral: `docs/api` は生成物なので、移設後に `pnpm docs:api` で作り直せば内容の検証は不要

### 案C（読者で二分）

- Good: docs 直下が 2 つのドアになる
- Bad: `adr` の参照が md だけで 52 ファイル。外部 URL にも影響しうる

### 案D（何もしない）

- Good: コストゼロ
- Bad: サイト化のときに除外リストが生まれる。今の違和感は残る

## More Information

- 改める対象: [ADR-0070][0070]（4 層の構成）。**層の分け方・各層の役割・検査①〜④は変えない**。
  変えるのはディレクトリの位置だけなので supersede ではなく**部分改訂**として扱う
- 名前の経緯: `docs/guide/` は [#259][pr259] で `howto/` ＋ `concepts/` へ移設して退役した。
  同じ名前を別の意味で復活させない
- **記録側（ADR・台帳・roadmap）の扱い**: リンクは書き換え、**決定の文面は書き換えない**。
  [#259][pr259] の移設で採った方針（「リンクは主張ではなく指し先なので、動くままにしておくほうが
  記録の値打ちが保てる」）をそのまま踏襲する
- 実装は本 ADR の accept 後、**別 PR**で行う（ADR と実装を分ける運用）
