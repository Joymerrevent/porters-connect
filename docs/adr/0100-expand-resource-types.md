# 100. リソースの公開の型は、各リソースのファイルでメソッドを書き出す

- Status: proposed
- Date: 2026-09-25
- Deciders: jun.shiromoto (Joymerrevent)

> 起票元は stakeholder との議論（2026-09-25）。マスタの公開の型を、データ系と同じく共通の型（`MasterResource<Q, T>`）の
> 別名で書こうとしたところ、API リファレンスからメソッドの説明が消えることが分かった。調べると、データ系は以前から同じ
> 状態だった。stakeholder は「共通の型でまとめると、リソースごとにメソッドが変わったとき足かせになる。どんなメソッドを
> 持つかはリソースごとの責任」として、**データ系・マスタとも、共通の型をやめて各リソースで書き出す**と決めた。

## Context and Problem Statement

### いまの形（2026-09-25 時点）

| 対象               | 公開の型の書き方                                                                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| データ系 12 種     | 共通の型 `DataResource<F, Req, R, Unsupported, Bound>`（117 行・公開していない）の別名。例: `CandidateResource<C, CR> = DataResource<…>` |
| マスタ 4 種        | 各マスタのファイルで `search` / `searchAll`（User は `current` も）を書き出している                                                      |
| Attachment・Option | 各ファイルで書き出している（形がほかと違うため）                                                                                         |

### API リファレンスでの見え方

- `DataResource` を公開していないので、typedoc はその中身を展開しない。**データ系 12 種のリファレンスのページには、
  型の引数（`C` / `CR`）しか載らず、`search` / `get` / `create` などのメソッドの説明が無い**。
- マスタのページには、書き出したメソッドの引数・戻り値・説明が載っている。

### 共通の型でまとめることの利点と足かせ

- 利点: メソッドの形（引数・戻り値・説明）の定義が 1 か所で、共通の約束を変えるときに 1 か所を直せば済む。
- 足かせ: どのメソッドを持つかが共通の型で決まる。リソースごとにメソッドが違うときは、型の引数（受けないクエリの
  キー `Unsupported`・束ねる項目 `Bound`）や `Omit` / `&` で表すことになり、そのリソースのファイルを読んでも何を
  持つかが分からない。今もマスタ（User の `current`、Option に `searchAll` が無い）・Phase（`of` で束ねる）・
  Attachment（本体の切り替え）で違いがある。

### 問い

リソースの公開の型を、共通の型の別名で書くか、各リソースのファイルでメソッドを書き出すか。

## Decision Drivers

- **責務**: どんなメソッドを持つかは、リソースごとの責任。そのリソースのファイルを読めば分かる。
- **API リファレンス**: 利用者がリファレンスで各リソースのメソッドの説明を読める。
- **型は今までどおり項目の一覧から導く**（[ADR-0019][adr19]）: レコード・クエリ・入力の型は共通の部品のまま。
- **共通の約束の変更を漏らさない**: 書き出すと同じ形が 12 か所に並ぶので、揃っていることを仕組みで確かめる。

## Considered Options

- **案A: データ系・マスタとも、各リソースのファイルでメソッドを書き出す。共通の型（`DataResource` / `MasterResource`）は
  公開の型には使わない**（stakeholder の決定）
- 案B: マスタだけ書き出し、データ系は `DataResource` の別名のまま（リファレンスの穴は残る）
- 案C: `DataResource` / `MasterResource` を公開の型にし、各リソースはその別名で書く（リファレンスには共通の型のページが
  できる）

## Decision Outcome

**未決（proposed）**。stakeholder は案A を選んだ（2026-09-25）。以下は案A で書いた場合の形。

### 決めること（案A）

- 各リソースの公開の型（`CandidateResource` / `PartitionResource` など）は、そのリソースのファイルで、持つメソッドを
  1 つずつ書き出す（引数・戻り値・JSDoc の説明）。
- 書き出すのはメソッドの一覧と形だけ。**メソッドの引数や戻り値に使う型は、今までどおり共通の部品から導く**
  （`SearchQuery<F, R>` / `ReadRecord<F>` / `CreateInput<F, Req>` / `Expand<R>` など。[ADR-0019][adr19]）。
- 受けないクエリのキー（Phase の `keywords` / `itemstate`）や束ねる項目（Phase の `Resource`）は、型の引数ではなく、
  そのリソースの型の書き出しの中で直接表す。
- `DataResource` / `MasterResource` は公開の型には使わない。factory（`createDataResource` / `createMasterResource`）が
  返す実装の型としてだけ残すか、無くすかは実装で決める。
- **揃っていることを型のテストで確かめる**: データ系 12 種の公開の型が、同じメソッドを同じ形で持つことを型のテストで
  固定する（違いを持たせるリソースは、テストの中で明示的に除く）。共通の約束を変えたときに 1 つ直し忘れると、テストが落ちる。

### 案A を採る理由

- どのメソッドを持つかがリソースのファイルで読め、リソースごとの違いを型の引数や `Omit` で表さずに済む。
- 利用者は API リファレンスで、各リソースのメソッドの説明を読める（データ系の既存の穴が塞がる）。
- 同じ形が並ぶ保守の手間は、型のテストで「揃っていること」を確かめれば、直し漏れを止められる。
- **案B** はデータ系のリファレンスの穴を残し、マスタとデータ系で書き方が食い違う。
- **案C** は、リソースごとの違いを共通の型の引数で表す足かせが残る。共通の型の引数（`F` / `Req` / `R` / `Unsupported` /
  `Bound`）が公開の約束になり、後から変えると破壊的変更になる。

### Consequences

- Good: 各リソースのファイルで、そのリソースが持つメソッドが読める。API リファレンスに全リソースのメソッドの説明が載る。
- Good: リソースごとの違いを、そのリソースの型の中で直接書ける。
- Bad: データ系で同じ形の書き出しが 12 か所に並ぶ（1 リソースあたり約 120 行・合計約 1,400 行）。共通の約束を変えると
  12 か所を直す。直し漏れは型のテストで止める。
- Neutral: 公開 API（型の中身）は変わらない。リファレンスの見え方が変わる。

## Pros and Cons of the Options

- 案A — Good: 責務がリソースのファイルに揃う。リファレンスが埋まる。Bad: 同じ形の書き出しが 12 か所。
- 案B — Good: データ系の手間が増えない。Bad: リファレンスの穴が残る。書き方が食い違う。
- 案C — Good: 定義が 1 か所。リファレンスに共通の型のページができる。Bad: 違いを型の引数で表す足かせが残る。
  共通の型の引数が公開の約束になる。

## More Information

- 実装（accepted 後・別 PR）: データ系 12 種の公開の型の書き出し、マスタは現状の書き出しのまま、
  `DataResource` / `MasterResource` の扱い、揃っていることを確かめる型のテスト、API リファレンスの生成し直し。
- 順番: [ADR-0096][adr96]（`field` で戻り値の型を絞る）の実装の**後**に行う。ADR-0096 は `search` / `searchAll` / `get` /
  `getMany` の型を変えるので、共通の型 1 か所で変えてから書き出せば、変更は 1 回で済む（先に書き出すと 12 か所になる）。
