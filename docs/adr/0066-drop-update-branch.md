# 66. dependabot PR の base 更新をやめ、検証を develop の CI に移す（ADR-0065 論点6 の改訂）

- Status: proposed
- Date: 2026-09-06
- Deciders: jun.shiromoto (Joymerrevent)

> [ADR-0065][adr65] 論点6 は「`update-branch` を続ける。理由は**更新後の状態を CI に検証させるため**」と
> 決めた。初回の本番実行で、その **CI が走らない**ことが分かった。目的を果たせない手順を残すか、
> 検証の場所を移すかを決める。**本 ADR は論点6 の結論だけを改訂**し、他の 7 論点は変えない。

## Context and Problem Statement

[ADR-0065][adr65] 論点6 の理由づけはこうだった — GitHub は base の鮮度を要求しない（`strict: false`）が、
**更新しないと「develop を取り込んだ後のロックファイル」に対して CI が一度も走らないまま develop に入る**。
ロックファイルは機械的に解決すると静かに壊れるので、そこは CI に検証させる。

2026-09-06、追跡 Issue への `/merge` で**取り込み側を初めて本番実行**したところ、この前提が崩れた。

| 事実                                                                    | 確認方法                                                              |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `update-branch` は成功し head が変わる                                  | #222 の head が `e9cec71` → `383bf69`                                 |
| 更新後の CI 5 本が**すべて `action_required`（ジョブ 0 件＝承認待ち）** | `gh run list`（`CI` / `Test` / `Mutation` / `Commitlint` / `CodeQL`） |
| 起動主体は `GITHUB_TOKEN`                                               | run の `actor` = `triggering_actor` = `github-actions[bot]`           |
| **このリポジトリで初発**                                                | 直近 100 実行のうち `action_required` はこの 5 本だけ                 |
| 元の head では普通に走っていた                                          | `dependabot[bot]` が push した `e9cec71` は 8 件すべて success        |
| **人が承認すれば完走して緑になる**                                      | 承認後 `success×8` / `mergeable_state=clean`                          |
| 承認しない間、取り込みは安全に止まる                                    | `wait_green` が 25 分待って中断。**0 件マージ**・残りは未着手         |

つまり **`update-branch` を `GITHUB_TOKEN` で行うと、その直後の CI が承認ゲートに入る**。承認しない限り
check-runs は 0 件のままで、「証拠ゼロを緑と見なさない」設計により取り込みは必ず中断する。

結果として論点6 は**二重に目的を外している**。

1. **検証されない** — 更新後の状態に CI が走らないので、そもそも検証の機会が生まれない。
2. **1 回の承認で終わらない** — `/merge` を押した人が、その後さらに CI の承認を求められる。
   「判定表を読んで 1 回承認したら、あとは機械が順に取り込む」という設計意図（論点3）が崩れる。

なお承認を要求している設定そのものは、public リポジトリでは REST API から読めなかった。
**「`GITHUB_TOKEN` 起因の run がゲートに入る」までは実測だが、どの設定が効いているかは未確定**である。

## Decision Drivers

- **フェイルセーフ** — ロックファイルが壊れたまま**気づかれずに**進む形を作らない。
- **1 回の承認で完了する** — 人の関与を「通してよいかの判断」1 点に集約する（[ADR-0065][adr65] 論点3）。
- **承認ゲートを緩めない** — fork PR からの実行を止める防御を兼ねている。ここを外すと被害範囲が広がる。
- **検証の機会を失わない** — 「検証しない」に倒すのではなく、**検証の場所を移す**ことで解く。

## Considered Options

- 案A: リポジトリ設定で承認ゲートを外す
- 案B: `update-branch` をやめ、**develop への push で走る CI** に検証させる — 推奨
- 案C: `update-branch` を別トークン（PAT / GitHub App）で行う
- 案D: ワークフローが自分の run を承認する（`actions: write`）

## Decision Outcome

採用: **案B**。

`update-branch` を行わず、CI が緑な PR をそのまま取り込む。**ロックファイルの検証は、マージ後に
develop への push で走る `ci` が担う**（`ci.yml` は `push: branches: [main, develop]` を持ち、実績もある）。

論点6 の**精神は保たれる** — 「GitHub が止めてくれないからこそ CI に検証させる」は変わらず、
検証の時点が**マージ前からマージ直後へ**移るだけである。develop は開発統合ブランチで、`main` へは
release を経由するため、壊れたロックファイルが利用者に届く経路は無い。

案A を採らないのは、承認ゲートが fork PR の防御を兼ねているため。**この 1 つの不便のために、
関係のない防御まで緩めるのは割に合わない。** 案C は秘密情報の管理が増え、`GITHUB_TOKEN` で足りる
という [ADR-0065][adr65] 論点4 の方針とも逆行する。案D はゲートの意味を消す。

### Consequences

- Good: **`/merge` が 1 回の承認で完了する。** 承認ゲートに触らずに解ける。
- Good: 実装が減る（`update-branch` の呼び出し・`sleep 15`・失敗時の分岐が不要になる）。
  取り込みの所要時間も短くなる（1 件あたり CI 再実行の待ちが消える）。
- Bad: **壊れたロックファイルが develop に一度入る。** 検出はマージ直後の CI なので、
  気づくまでに数分の窓がある。直すには revert か追いのコミットが要る。
- Bad: 複数 PR を続けて取り込むとき、2 件目以降は「1 件目を取り込んだ後の develop」に対する
  CI を**通していない状態**でマージされる。競合の検出はマージ時の GitHub 側に委ねる。
- Neutral: base が古いまま取り込むので、PR の CI が保証するのは「**その PR 単独での緑**」だけになる。
  これは `strict: false` の下で人が手でマージするときと同じ条件で、**新たなリスクではない**。
- Neutral: 承認ゲートの設定が将来変わって `GITHUB_TOKEN` 起因の run が走るようになっても、
  本 ADR の決定は有効なまま（`update-branch` が不要という結論は変わらない）。

## Pros and Cons of the Options

### 案A: 承認ゲートを外す

- Good: 実装を変えずに済む。論点6 の結論もそのまま。
- Bad: **fork PR からの実行を止める防御まで緩む。** 依存更新の利便のために、関係のない攻撃面を開く。
- Bad: どの設定が効いているかが未確定なので、**何を緩めたのか正確に言えないまま**変更することになる。

### 案B: `update-branch` をやめる（採用）

- Good: 承認ゲートに触らない。1 回の承認で完了する。実装が減る。
- Bad: 検証がマージ後になる。壊れたロックファイルが develop に一度入りうる。
- Neutral: `strict: false` の下で人が手でマージする条件と同じ。

### 案C: 別トークン（PAT / GitHub App）

- Good: `update-branch` 後の CI が走る。論点6 の結論を保てる。
- Bad: 秘密情報が増える。PAT は個人に紐づき、GitHub App は導入コストがある。
- Bad: [ADR-0065][adr65] 論点4 で「`GITHUB_TOKEN` で足りる」とした方針と逆行する。

### 案D: 自分の run を承認する

- Good: 設定も実装方針も変えずに通る。
- Bad: **ゲートの意味が消える。** `actions: write` を持つ job が、自分が作った run を承認する形になる。
