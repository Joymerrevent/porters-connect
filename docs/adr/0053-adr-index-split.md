# 53. ADR 索引を運用ドキュメントから分離し、実装状態を検査可能にする

- Status: accepted
- Date: 2026-08-16
- Deciders: jun.shiromoto (Joymerrevent)

> **案1a ＋ 案2a ＋ 案3a で `accepted`（2026-08-16）**: `README.md` を運用（＋論点バックログ＋導線）に絞り、
> **`index.md` を一覧テーブルだけの純粋なファイル**として新設する。腐りの中心だった**状態別 3 節は廃止**し、
> 「実装済みか・どの版で出たか」は**索引の `実装` 列 ＋ ADR 本文の `- Implemented:`** という突合可能な形へ移す。
> 検査は [ADR-0052][adr52] の `check:findings` と**1 本に統合**する。実施は本 ADR とは別 PR。
>
> 起票の発端は stakeholder 提案（2026-08-16）「**`docs/adr/README.md` は README と索引を分ける運用が良いのでは**」。
> [ADR-0052][adr52] で `docs/reviews/` に同じ形を決めた直後の提案で論点は共通するが、
> **分割だけでは今回腐った部分は直らない**ため、分離に加えて散文の廃止と実装状態の検査可能化までを本 ADR で決めた。

## Context and Problem Statement

`docs/adr/README.md`（208 行）は、性質も変更頻度も違うものが 1 ファイルに同居している。実測:

| 部分                                            | 行数     | 変更頻度               | 2026-08-16 の実測            |
| ----------------------------------------------- | -------- | ---------------------- | ---------------------------- |
| ADR とは・運用ルール・フェーズ凡例              | 23 行    | **ほぼ不変**（年単位） | 健全                         |
| 一覧テーブル                                    | 57 行    | **ADR ごと**           | 健全（51 本すべて一致）      |
| 論点バックログ（未起票）                        | 22 行    | ときどき               | 1 件が陳腐化                 |
| 【議論中】【accept 済み・実装待ち】【実装済み】 | 35 行    | **ADR ごと**           | **4 件が陳腐化＝腐りの中心** |
| 決定済み ＋ リンク定義                          | 約 58 行 | ADR ごと               | 健全                         |

問題は 2 つある。

**(1) 変更頻度の違うものが混ざっている。** 年単位で変わらない運用ルール 23 行が、ADR を 1 本足すたび diff に巻き込まれる。
逆に索引を読みたいだけの読み手（人・AI）は、運用の説明と論点バックログを読み飛ばす必要がある。

**(2) 腐る部分がある。** [ADR-0052][adr52] の決定根拠として本ファイルを実測したところ、
**一覧テーブルは 51 本すべて健全**（不一致は 0037 の表記省略のみ）だった一方、
**状態を散文で言い換えた 3 節は 5 件中 4 件が陳腐化**していた（ADR-0038 は 0.4.0 で公開済みなのに「実装は別 PR」、
0017 / 0018 / 0021 は「コード反映は別 PR」、0051 は実装済みなのに【accept 済み・実装待ち】節に残置。
5 件目は 0052 の起票時に是正済み）。

この 3 節の中身を分解すると、**2 種類が混ざっている**ことが分かる:

- **テーブルの `ステータス` 列の言い換え**（proposed / accepted）＝ **完全な重複**。
- **「実装済みか・どの版で出たか」という別軸**＝ テーブルに無い情報。だから散文に溜まった。

つまり**ファイルを 2 つに割っても、この 3 節がどちらかに残る限り同じ腐り方をする**。
分離と同時に「重複を消し、足りない軸を検査可能な形で持つ」ところまで決める必要がある。

## Decision Drivers

- **人の記憶でなく仕組みで守る**（`CLAUDE.md`）。[ADR-0052][adr52] で
  「機械的に突合できる形なら生き残り、検査の無い散文は腐る」という**同一リポジトリ内の実測**を得ている
- **変更頻度でファイルを分ける**（安定した規約と、毎回変わる索引を混ぜない）
- **部分読み込みのしやすさ**（索引だけ読める＝ AI のコンテキスト効率）
- **発見性**（GitHub は `docs/adr/` を開いたとき `README.md` を自動表示する）
- **移行コストと既存リンクの保全**（`[adr]` として 5 ファイルから参照されている）
- **[ADR-0052][adr52] との一貫**（同じ検査系統に乗せられるか）

## Considered Options

3 つの軸で決める。

### 軸1: どちらを `README.md` にするか

- **案1a: README ＝ 運用 ＋ 導線**（`index.md` に一覧テーブル）
- **案1b: README ＝ 一覧**（`conventions.md` 等に運用を退避）
- **案1c: 分けない**（現状維持）

### 軸2: 状態別 3 節と「実装状態」の扱い

- **案2a: 3 節を廃止し、実装軸を列にする** — 索引に `実装` 列（**版番号**）を足し、
  各 ADR 本文に `- Implemented: 0.4.0`（該当しなければ記載なし）を置いて突合可能にする
- **案2b: 3 節を廃止し、実装軸は三値**（`実装済み` / `未` / `—`）で持つ。版番号は追わない
- **案2c: 3 節を廃止するだけ**（実装軸は索引に持たず、roadmap の担当にする）
- **案2d: 3 節を残す**（現状維持）

### 軸3: 検査の実装

- **案3a: [ADR-0052][adr52] の `check:findings` と 1 本に統合**し、対象（index パス・エントリ群・列定義）を
  引数化した汎用チェッカーにする
- **案3b: 別スクリプト**（`check:adr-index`）として独立させる
- **案3c: 検査しない**（人手のみ）

## Decision Outcome

**採用: 案1a ＋ 案2a ＋ 案3a**（decider 判断・2026-08-16。起票時の推奨どおり）。

```text
docs/adr/
├── README.md     # 運用（ADR とは・ルール・フェーズ凡例）＋ 論点バックログ（未起票）＋ index への導線
├── index.md      # 一覧テーブルのみ ＝ 機械検査の対象
└── NNNN-*.md     # 各 ADR（`- Implemented:` を任意で追加）
```

理由:

- **案1a**: 索引を「テーブルだけの純粋なファイル」にしておくと、**検査の契約が明確**になり、散文が再び侵入しにくい。
  README を運用側に残せば **`[adr]` の 5 リンク（roadmap / basic-design / requirements / README / CONTRIBUTING）は
  張り替え不要**で、`docs/adr/` を開いた人はまず README を見る＝ 発見性も保てる（先頭に索引への導線を置く）。
  案1b は「ディレクトリを開いたら一覧が見える」利点があるが、索引ファイルに運用の説明が同居しないだけで
  結局 README に散文が戻りやすい。案1c は上記 (1)(2) を放置する。
- **案2a**: 3 節の重複部分を消し、残る「実装軸」を**索引の列 ＋ 本文のフィールド**という**突合可能な形**にする。
  版番号まで持つのは、ライブラリとして「**どの決定がどの版で世に出たか**」が単体で有用だから
  （[CHANGELOG][changelog] を辿らずに追える）。三値の案2b より情報量が多く、コスト差は小さい
  （直近分は [roadmap][rm] が既に版を記録している）。案2c は roadmap との二重管理になり、
  ADR を見ただけでは実装状態が分からない。案2d は腐りの原因を残す。
  - **すべての ADR が実装軸を持つわけではない**（プロセス系＝[ADR-0001][adr1] /
    [ADR-0013][adr13] / [ADR-0025][adr25] 等）。
    よって `- Implemented:` は**任意**とし、索引の当該列は `—`。検査は**双方向の一致**だけを見る
    （片方にあって片方に無ければ落とす）＝「記載漏れ」ではなく「食い違い」を検出する。
  - **backfill は既知分のみ**とする。[roadmap][rm] が記録している 0034→0.3.0 / 0038→0.4.0 / 0040→0.5.0 /
    0041→0.6.0 / 0044〜0050→0.7.0 / 0051→0.8.0 は確実。0.1.0 以前に積まれた決定は
    版の特定に [CHANGELOG][changelog] の考古学が要るため**空欄のまま**でよい（検査は一致だけを見るので通る）。
- **案3a**: 索引の突合ロジックは対象が違うだけで同型（エントリ群 ↔ 索引テーブルの列一致・1 対 1 対応・語彙検査）。
  1 本に一般化すれば保守対象が増えない。**[ADR-0052][adr52] の実装より前に本 ADR を決める**と、
  最初から汎用に書けて二度手間を避けられる。

### 実施時の合意事項（accept 後の別 PR）

1. **`docs/adr/index.md` を新設**し、一覧テーブルとそのリンク定義だけを置く。**散文を入れない**。
2. **`README.md` は運用に絞る** — ADR とは / 運用ルール / フェーズ凡例 / 論点バックログ（未起票）/
   **冒頭に索引への導線**。状態別 3 節（【議論中】【accept 済み・実装待ち】【実装済み】）は**削除**する。
3. **索引テーブルの列**: `# / タイトル / フェーズ / ステータス / 実装`。`実装` は版番号（`0.4.0`）または `—`。
4. **ADR 本文のヘッダに `- Implemented: X.Y.Z` を任意で追加**する（`Status` / `Date` / `Deciders` の下）。
   [`0000-template.md`][tpl] にも任意項目として追記する。
5. **検査を `check:findings` と統合**し、`scripts/check-doc-index.mjs`（仮）＋ `pnpm check:index` に一般化する。
   対象は 2 つ（`docs/adr/index.md` ↔ `docs/adr/NNNN-*.md` ／ `docs/reviews/findings.md` ↔ `docs/reviews/rv/*.md`）。
   **CI は常時実行ブロック**に置く（[ADR-0028][adr28] のパスフィルタ配下だと docs-only 変更で走らない
   ＝ [ADR-0052][adr52] 合意事項 6 と同じ理由）。
6. **`[adr]` の既存リンク 5 本は張り替えない**（README が入口のまま）。
   ただし「決定の**索引**」を指す意図が明確な箇所（[roadmap][rm]・[findings][fnd]）は `index.md` へ向け直すか、
   実施時に個別判断する。
7. **論点バックログの陳腐化 1 件**（【基本設計】のページング・検索条件が「実装は別 PR」のまま）は移設時に是正する。
8. 実施順序: **[ADR-0052][adr52] の移行 PR と本 ADR の実施 PR は分ける**が、
   **検査スクリプトは先に着手するほうで汎用形として作る**（後発は対象定義を足すだけにする）。
9. **semver 影響なし**（`docs/` は tarball 非同梱）。

### Consequences

- Good: 運用ルールが ADR 追加の diff に巻き込まれなくなる／索引だけ読める／
  **腐りの中心だった散文 3 節が消え、残る実装軸は CI が守る**／`docs/reviews/` と構造・検査が揃う。
- Bad: ファイルが 1 つ増え、`docs/adr/` を開いた人が一覧を見るのに 1 クリック増える。
  ADR 本文に新しい任意フィールドが増える（テンプレートと運用ルールの更新が要る）。
  `- Implemented:` の記入は人手＝**記入漏れは検出できない**（食い違いのみ検出）。
- Neutral: backfill は既知分のみなので、古い ADR の `実装` 列は当面 `—` が並ぶ。
  必要になったら CHANGELOG から埋められる（検査は妨げない）。

## Pros and Cons of the Options

### 軸1

- **案1a（README ＝ 運用・推奨）**: Good = 索引が純粋になり検査契約が明確／既存リンク張り替え不要／
  ディレクトリを開くと運用と導線が見える。Bad = 一覧まで 1 クリック増える。
- **案1b（README ＝ 一覧）**: Good = 開いてすぐ一覧が見える（発見性が最大）。
  Bad = 索引ファイルが README という「何でも書ける場所」になり、散文が戻りやすい／運用の退避先の名前を決める必要。
- **案1c（分けない）**: Good = 移行ゼロ。Bad = 変更頻度の混在も腐りも放置。

### 軸2

- **案2a（版番号・推奨）**: Good = 実装軸が検査可能になり、どの版で出たかが ADR から辿れる。
  Bad = 記入の手間／古い ADR の backfill は諦める前提が要る。
- **案2b（三値）**: Good = 記入が軽い。Bad = 「どの版か」が失われ、結局 CHANGELOG か roadmap を見に行く。
- **案2c（列を持たない）**: Good = 索引が最小。Bad = 実装状態が roadmap 頼みになり、ADR 単体で完結しない。
- **案2d（現状維持）**: Good = 何もしなくてよい。Bad = 4 件が腐った経路をそのまま残す。

### 軸3

- **案3a（統合・推奨）**: Good = 保守対象 1 本／2 つの索引が同じ規律で守られる。
  Bad = 汎用化のぶん設定（列定義）がやや抽象になる。
- **案3b（別スクリプト）**: Good = 各々が単純。Bad = ほぼ同型のコードが 2 本になり、片方だけ直す事故が起きる。
- **案3c（検査しない）**: Good = 道具が増えない。Bad = [ADR-0052][adr52] で退けた案B と同じ経路で腐る。
