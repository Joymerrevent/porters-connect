# 90. 利用者の TypeScript の下限を 5.4 とし、古い版では明示のエラーに倒し、CI で下限の版を走らせる

- Status: proposed
- Date: 2026-09-24
- Deciders: jun.shiromoto (Joymerrevent)

> 起票元は [ADR-0089][adr89] の実装（[#388][pr388]）。同梱の型定義が `NoInfer`（TypeScript 5.4 で追加）を
> 使うようになり、古い TypeScript では**黙って誤った型**になることを確かめた（下記）。stakeholder は
> 2026-09-24 に「下限を README に書く」（[#390][pr390]）と「CI の検査を先に入れる」を選んだ。本 ADR は、
> その下限を**仕組みで守る**形を決める。

## Context and Problem Statement

### いまの形

- 利用者の実行環境の下限は **Node.js だけ**を `engines` に書き（[ADR-0082][adr82]）、CI の Node マトリクスが
  下限の版そのものを走らせ、`pnpm check:release` が `engines` と CI のずれを弾く（[RV-53][rv53]）。
- **TypeScript の下限はどこにも無かった**。開発は TypeScript 6.0 で行い、型定義は `tsup` が生成する。
  利用者がどの版で型を読むかは検査していない。`check:cjs` は利用者として型をコンパイルするが、
  使うのはリポジトリの TypeScript（6.0）だけ。

### 古い TypeScript で起きること（2026-09-24 に確かめた）

ビルドした型定義に対して、`{ required: true }` を付けた項目 `U_a` と付けていない項目 `U_b` を宣言し、
`create({ P_Owner: 1, U_a: 1 })` をコンパイルした。

| TypeScript    | `skipLibCheck: false`                                  | `skipLibCheck: true`                        |
| ------------- | ------------------------------------------------------ | ------------------------------------------- |
| 5.4.5         | 期待どおり                                             | 期待どおり                                  |
| 5.3.3 / 5.0.4 | `NoInfer` が見つからないエラー ＋ `U_b` まで必須になる | **エラーが出ないまま `U_b` まで必須になる** |

`skipLibCheck: true` はよく使われる設定で、そのとき利用者は**理由の分からない型エラー**（宣言していない必須）を
受け取る。壊れ方が「黙って誤る」側にある。

### `exports` の版の条件で、古い版を別の型定義に向けられる

TypeScript は `exports` の条件に `types@<5.4` のような**版の範囲**を書ける。試したところ
（`moduleResolution: bundler`）、5.3.3 / 5.0.4 は `types@<5.4` の型定義を読み、5.4.5 は通常の `types` を読んだ。

### 問い

TypeScript の下限をどこに書き、下限より古い版ではどう振る舞わせ、CI で何を検査するか。

## Decision Drivers

- **フェイルセーフ**: 下限より古い版では、黙って誤った型にせず、**何が足りないかが読めるエラー**にする。
- **約束した版を走らせて初めて約束になる**（[RV-53][rv53]）: 下限を書いたら、その版そのものを CI で走らせる。
- **一箇所で持つ**: 下限の値を複数の場所に写すなら、ずれを機械で弾く（`check:release` と同じ形）。
- **薄く**: 利用者のインストールを失敗させない（パッケージマネージャの挙動に依存する仕組みは避ける）。

## Considered Options

### 論点1: 下限より古い版で何が起きるようにするか

- **案1a: `exports` に `types@<5.4` の条件を足し、「5.4 以上が要る」と読める型定義に向ける** — 推奨
- 案1b: 何もしない（README の記載だけ。古い版では今の「黙って誤る」まま）

### 論点2: 下限をどこに機械で読める形で置くか

- **案2a: `exports` の `types@<X` 条件そのものを正とし、README・導入のページ・CI の版はそれと突き合わせる** — 推奨
- 案2b: `peerDependencies` に `"typescript": ">=5.4"`（`optional`）を置く
- 案2c: 機械で読める場所を持たない（README と CI にそれぞれ書く）

### 論点3: CI で何を検査するか

- **案3a: ビルドした型定義に対して、下限の版（パッチまで固定）と開発で使う版の 2 つで、利用者のコードをコンパイルする** — 推奨
- 案3b: 開発で使う版だけ（今の `check:cjs` と同じ）

## Decision Outcome

（proposed。以下は推奨で、決定は decider が行う。）

推奨: **案1a ＋ 案2a ＋ 案3a**。

### 論点1: 案1a を推す理由

案1b では、下限より古い利用者は「宣言していない項目まで必須になる」という、ライブラリの不具合にしか見えない
エラーを受け取る。案1a なら、`import` した時点で「このパッケージは TypeScript 5.4 以上が要る」という型のエラーに
なり、原因がそのまま読める。**壊れたときに、何が壊れたかが見える側に倒す**。

- 向け先の型定義（例 `dist/requires-typescript-5.4.d.ts`）は、公開 API の名前ごとに「5.4 以上が要る」と読める型を
  置く小さなファイルにする。中身の形は実装で決める。
- `import` 条件と `require` 条件の両方に足す。`moduleResolution: node`（`exports` を読まない古い解決）では
  `typesVersions` で同じ向け先にする。どの解決方式で効くかは実装の PR で確かめ、効かない方式があれば
  README に書く。

### 論点2: 案2a を推す理由

- 下限より古い版を別の型定義に向ける条件は、**下限の値そのもの**を持っている。これを正にすれば、下限の値は
  1 箇所で済む。README・導入のページ・CI の版は、`pnpm check:release` がこの値と突き合わせる（[RV-53][rv53] で
  `engines` と CI の Node マトリクスを突き合わせているのと同じ形）。
- 案2b は、パッケージマネージャによって「警告だけ」「インストールを止める」「何もしない」が分かれ、
  利用者のインストールを失敗させうる。任意の peer の版の食い違いをどう扱うかを 3 つのマネージャで確かめ続ける
  手間にも見合わない。
- 案2c は、下限を上げたときに片方だけ直す事故を防げない。

### 論点3: 案3a を推す理由

- 下限の版（例 `5.4.5`）を**パッチまで固定**して走らせる。`5.4` の系の最新を走らせると、約束した版そのものは
  一度も走らない（[RV-53][rv53] と同じ理由）。
- 開発で使う版（6.0）でも同じコードをコンパイルし、新しい版での退行も見る。
- コンパイルする利用者のコードは、公開 API の代表的な使い方（クライアントの構築・`tenant(id, { fields })`・
  読み書き・`{ required: true }`）と、**型エラーになるべきところ**（`@ts-expect-error`）を含める。
  エラーになるべき行がエラーにならなかったら落ちる＝型が緩んだことにも気づける。
- あわせて、**下限より古い版（例 5.3）で、案1a の明示のエラーが出ること**も確かめる。仕組みが黙って
  外れたとき（条件の書き間違いなど）に気づくため。
- `check:cjs` と同じく `dist` を見る検査なので、`pnpm build` の後に走らせる（`pnpm check` には束ねない）。
  使う TypeScript は `pnpm dlx --package=typescript@<版>` で取る（開発依存に古い版を入れない）。

### Consequences

- Good: 下限より古い利用者は、原因が読めるエラーを受け取る。黙って誤った型にならない。
- Good: 下限を上げる・下げるときは `exports` の条件を直せば、README と CI のずれを `check:release` が教える。
- Good: 型定義が下限の版で読めなくなる変更（新しい TypeScript の機能を使う）を、CI が PR の時点で止める。
- Bad: CI の時間が少し増える（TypeScript を 3 版取得してコンパイルする。数十秒の見込み）。
- Bad: `exports` が少し複雑になる。解決方式ごとに効き方を確かめる手間がある。
- Neutral: 下限を上げること自体は、利用者から見ると破壊的変更になりうる。上げるときは CHANGELOG に書き、
  semver の判断をする（Node の下限と同じ扱い。[ADR-0082][adr82]）。

## Pros and Cons of the Options

### 案1a（古い版を明示のエラーに向ける）／ 案1b（何もしない）

- 案1a — Good: 原因が読めるエラーになる。Bad: `exports` が少し複雑になり、解決方式ごとに確かめる手間がある。
- 案1b — Good: 何も増えない。Bad: 古い版の利用者が、原因の分からない型エラーを受け取る。

### 案2a（`exports` の条件を正にする）／ 案2b（`peerDependencies`）／ 案2c（持たない）

- 案2a — Good: 下限の値が 1 箇所。Bad: 値を読み出す処理を `check:release` に足す。
- 案2b — Good: パッケージマネージャが知らせることがある。Bad: マネージャごとに挙動が違い、インストールを失敗させうる。
- 案2c — Good: 何も増えない。Bad: ずれを防げない。

### 案3a（下限の版と開発の版でコンパイル）／ 案3b（開発の版だけ）

- 案3a — Good: 約束した版で読めることを毎回確かめる。Bad: CI の時間が少し増える。
- 案3b — Good: 速い。Bad: 今回の `NoInfer` のような変更を見逃す（今回も PR の時点では気づかなかった）。
