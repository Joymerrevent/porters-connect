# 105. 検索の条件とキーワードの値に区切り文字があれば、送る前に拒否する

- Status: accepted
- Date: 2026-09-26
- Deciders: jun.shiromoto (Joymerrevent)

> 起票元は `src` 全体のレビュー（2026-09-26）の [RV-68][rv68]。[ADR-0038][adr38] SD-8 は「値の中のエンコードは
> URLSearchParams に任せる」と決めたが、URLSearchParams は区切りのカンマと値の中のカンマを同じ `%2C` にするので、
> PORTERS 側では区別できないと分かった。SD-8 の前提を改めるので、この ADR で決める。
>
> **decider が案A を選択し `accepted`（2026-09-26）。** 実装は accept 後・別 PR。

## Context and Problem Statement

### 区切り文字（reference）

| パラメータ                                       | 区切り                                                             |
| ------------------------------------------------ | ------------------------------------------------------------------ |
| `condition`                                      | 条件どうしはカンマ（AND）。1 つの条件は `[Alias]:[suffix]=[value]` |
| `condition` の Option / Link / Id の `or`・`and` | 値どうしはコロン                                                   |
| `keywords`                                       | キーワードどうしはカンマ（AND）                                    |

reference（[Read の README][readref]）は、値の中に区切り文字を入れる方法（エスケープ）を書いていない。

### 何が起きるか

実測（[RV-68][rv68]）: `condition: { P_Name: { part: "山田,Person.P_Owner:eq=5" } }` は
`Person.P_Name:part=山田,Person.P_Owner:eq=5` として送られた。値の途中から、2 つ目の条件として読まれる。

- 利用者の入力をそのまま条件に使うと、検索結果が黙って変わる。
- 削除済みを読むとき（`itemstate` が `deleted` / `all`）の「条件に使える項目の制限」（ADR-0038 SD-4）も、この形なら通ってしまう。
- `keywords` の要素の中のカンマは、キーワードが 1 つ増えたことになる。
- Option / Link / Id の値の中のコロンは、値が 1 つ増えたことになる。

### 問い

区切り文字を含む値を、どう扱うか。

## Decision Drivers

- **検索の意味を黙って変えない**（フェイルセーフ）。
- **原典に無いものを発明しない**: PORTERS が認めるエスケープの方法は書かれていない。
- **正しい値を拒否しない**: 日時の値（`yyyy/mm/dd HH:MM:SS`）はコロンを含むので、テキストや日時の値のコロンは拒否できない。

## Considered Options

- **案A: 区切りとして読まれる文字を含む値を、送る前に `PortersConfigError` で拒否する**。
- 案B: 独自にエスケープする（例: `\,` や `%252C`）。
- 案C: 今のまま送り、文書に注意を書く。

## Decision Outcome

採用: **案A**（decider が 2026-09-26 に選択）。

- 案B は、PORTERS が解釈する保証の無いエスケープを発明することになる。解釈されなければ、別の意味の検索が黙って走る。
- 案C は、利用者の入力を条件に使う場面で、検索結果が黙って変わる形を残す。
- 案A は、今は「黙って誤った検索」になる値を、送る前のエラーに変える。正しく書かれた検索には影響しない。

### 決めること（案A）

| 値                                                            | 拒否する文字            |
| ------------------------------------------------------------- | ----------------------- |
| `condition` のすべての値（テキスト・数・日時・一覧）          | カンマ `,`              |
| `condition` の一覧の要素（Option / Link / Id の `or`・`and`） | カンマ `,` とコロン `:` |
| `keywords` の要素                                             | カンマ `,`              |

- テキストと日時の値の中のコロンは拒否しない（日時の値がコロンを含み、PORTERS は最初の `:` で alias と suffix を区切るとみられる）。
  値の中のコロンを PORTERS がどう読むかは、[live-verification][lv] に登録して実機で確かめる。
- エラーは `PortersConfigError`（`category: "config"`）。hint で、区切り文字を含む値では検索できないことと、
  代わりの手段（区切り文字を含まない部分で検索し、結果を手元で絞る）を案内する。
- ほかの送信前の検査（keywords の 100 文字など）と同じく、`search` / `searchAll` は同期 throw せず reject で届ける（[ADR-0046][adr46]）。

### Consequences

- Good: 検索の意味が黙って変わらない。削除済みを読むときの項目の制限を、値の細工で越えられなくなる。
- Bad: カンマを含む値（例: 「株式会社A,B」）で部分一致の検索ができなくなる。今もその検索は正しく動いていないので、失うものは無い。
- Neutral: 今は通っている呼び出しがエラーになるので、利用者から見ると動きが変わる。誤った検索を止める修正として扱い、CHANGELOG に書く。

## 信じている入力

| 値                       | 出どころ  | 誰が書けるか                 | 守り方                     | 取れなかったら | 誤っていたら                            |
| ------------------------ | --------- | ---------------------------- | -------------------------- | -------------- | --------------------------------------- |
| 条件の値                 | 利用者    | 利用者（その先の入力を含む） | 仕組み: 送る前に文字を検査 | —              | 区切り文字があれば `PortersConfigError` |
| キーワード               | 利用者    | 利用者（その先の入力を含む） | 仕組み: 送る前に文字を検査 | —              | 同上                                    |
| PORTERS の区切りの読み方 | reference | PORTERS                      | 散文: reference の説明     | —              | 値の中のコロンの扱いを LV で確かめる    |

## Pros and Cons of the Options

### 案A

- Good: 黙って誤った検索を送らない。原典に無いものを発明しない。
- Bad: 区切り文字を含む値では検索できない。

### 案B

- Good: 区切り文字を含む値でも検索できる（PORTERS が解釈すれば）。
- Bad: 解釈される保証が無い。外れれば黙って誤った検索になる。

### 案C

- Good: 変更が無い。
- Bad: 黙って誤った検索になる形が残る。
