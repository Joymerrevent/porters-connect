# 70. 使い方ドキュメントの構成（説明サイトの元になる原稿）

- Status: proposed
- Date: 2026-09-10
- Deciders: jun.shiromoto (Joymerrevent)

> `1.0.0` の完成条件 **V2** の本体。[ADR-0035][0035] は「README は最短で動かす入口・機能ごとの手順は
> `docs/guide/<topic>.md`」と決めたが、**読者の目的から引ける構成にはなっていない**。
> [ADR-0068][0068] が作ったのは **API 記号のリファレンス**で、V2 が求めていたものではなかった
> （経緯は [roadmap][rm] の V2 注記）。**説明サイトの元になる原稿**をどう組むかを決める。

## Context and Problem Statement

V2 の文言は当初「公開 API が 1 つ残らず**リファレンス**に載っている」だった。これは
**API 記号の一覧**とも**使い方のドキュメント**とも読める。実際に前者として実装され
（[ADR-0068][0068]）、後者が意図だったと判明して V2 の定義が差し替えられた（2026-09-10・stakeholder）。

求められているのは <https://jestjs.io/ja/> や <https://nextjs.org/docs> のような**説明サイトの
元になる原稿**である。**サイトの構築は対象外**（原稿までで、後から載せられる形にする —
[ADR-0068][0068] が「サイトが要るようになったら Markdown を VitePress / Starlight に載せるのは
後からできる」と書いた想定どおり）。

### 参照した 2 サイトの構成（2026-09-10 実測）

どちらも同じ原則で並んでいた。

| 節                           | 中身                                               |
| ---------------------------- | -------------------------------------------------- |
| **Getting Started**          | 順序のあるチュートリアル。導入 → 中核概念 → 配備   |
| **Guides**                   | 目的別。データ／開発／性能／配備／高度な型／テスト |
| **API Reference**            | 網羅。種類ごと（関数・設定・CLI …）                |
| **Architecture / Community** | 内部・貢献                                         |

**進み方は「概念 → 実践のガイド → 詳細なリファレンス」**で、ページは**機能ではなく目的**で束ねられている。

### このリポジトリの現状（実測）

| 2 サイトの節    | このリポジトリ                                                                 |
| --------------- | ------------------------------------------------------------------------------ |
| Getting Started | **無い**。README（497 行）が入口・概念・操作一覧を兼ねる                       |
| Guides          | `docs/guide/` 7 本・計 1,473 行。ただし**機能単位**                            |
| API Reference   | `docs/api`（176 頁・[ADR-0068][0068]）／`docs/reference`（PORTERS API の事実） |
| Architecture    | `docs/adr` `docs/design`（内部向け）                                           |

**`docs/` に索引が無い**（直下の `.md` は runbook 3 本と roadmap だけ）。つまりサイトの目次に
なるものが文字どおり存在せず、入口は README しかない。

既存 7 本の見出しを並べると、**API の面に沿って書かれている**ことが見える:

- `read-query.md` — `field` / `expand` / `image` / `condition` / `order` / `keywords` / `itemstate` / `count`
- `custom-fields.md` — 宣言できる型 / 検証されること / どこまで検証するか
- `write-constraints.md` — 送信前に弾くもの / PORTERS に委ねるもの

内容は薄くない（むしろ濃い）。問題は**引き方**である。「候補者を名前で探したい」人は、
まず `read-query.md` を選び、次に「それは `condition` という節だ」と当てなければならない。
**目的からの入口が無い。**

### 既存 7 本は本当に古いのか（2026-09-10 実測）

「内容が古い・間違っているかもしれないので書き直したほうがよいのでは」という指摘を受けて測った。
**古いのは事実だが、局所的で、しかも機械で見つかる種類だった。**

最終更新を破壊的変更と突き合わせると、**3 本が 0.10.0（`PortersClient` から `partition` を外した
破壊的変更・2026-08-22）より前**で止まっている:

| ガイド                 | 最終更新   | 0.10.0 より前か |
| ---------------------- | ---------- | --------------- |
| `oauth.md`             | 2026-07-01 | **前**          |
| `bulk-write.md`        | 2026-08-21 | **前**          |
| `multi-tenancy.md`     | 2026-08-21 | **前**          |
| `write-constraints.md` | 2026-09-09 | 後              |
| `read-query.md`        | 2026-09-09 | 後              |
| `custom-fields.md`     | 2026-09-10 | 後              |
| `error-handling.md`    | 2026-09-10 | 後              |

実際に壊れているものが**コンパイラで確認できた**。`multi-tenancy.md` と `custom-fields.md` に
載っている次の形は、いま型エラーになる:

```ts
new PortersClient({ host, appId, appSecret, partition, tokenStore });
// error TS2353: Object literal may only specify known properties,
// and 'partition' does not exist in type 'PortersClientOptions<EmptyCatalog>'
```

**19 日間ずっと壊れていた**（0.10.0 は 2026-08-22）。そして注目すべきは、`custom-fields.md` は
**2026-09-10 に更新されているのに壊れたまま**だということ — 別の節を直しても、
**離れた場所の古い例は誰も見ない**。

根本原因ははっきりしている。**ドキュメント内のコードは 1 行も検査されていない**:

| どこ                | TypeScript コードブロック | 検査 |
| ------------------- | ------------------------- | ---- |
| `docs/guide/` 7 本  | 47                        | なし |
| `README.md`         | 11                        | なし |
| `src/**/*.test.ts`  | （53 ファイル）           | あり |
| `test/integration/` | （12 ファイル）           | あり |

**58 個のコード例が、型が変わっても何も言わない。**

### README が抱え込んでいるもの

`## リソースと操作` が **133 行**、`## クイックスタート` が 45 行。ほかに
読み取り値の表現・書き込み・添付・エラー・PORTERS 固有の注意。**入門と概念とリファレンスが
1 ファイルに同居**している。[ADR-0035][0035] は「README は存在に気づき最短で動かす入口」と
決めたが、実際にはそれを大きく超えている。

### 問い

**入門（順に読む）・考え方・目的別 HOWTO をどう並べ、既存の README / `docs/guide` 7 本を
どう組み替えるか。そして V2 の「完成」を何で測るか。**

## Decision Drivers

- **目的から引ける** — 「〜したい」で目次を引けること。これが今いちばん欠けている。
- **順に読める** — 初めての人が上から読めば動かせる道筋があること。
- **後からサイトに載せられる** — ディレクトリと目次が site generator の構造にそのまま対応すること。
  ただし**今はサイトを作らない**。
- **穴が無いことを検査できる** — V2 は `1.0.0` の条件なので、「完成した」を機械で言えること
  （D1〜D5・V1 と同じ形＝[roadmap][rm]）。
- **書いたものを腐らせない** — 1 人メンテ。二重メンテを増やさない。
- **日本語ファースト**（CLAUDE.md）。英語は後追い。

## Considered Options

### 論点1: 章立て（IA）

- **案1a: 2 サイトに倣って 4 層**（推奨）

  ```text
  docs/
    index.md          ← 目次（サイトの入口になる）
    start/            入門：順に読む
      1 install.md        インストールと最初の 1 回（契約なし・フェイクで動かす）
      2 authenticate.md   認証を通す
      3 first-read.md     はじめての読み取り
      4 first-write.md    はじめての書き込み
      5 going-live.md     本番に出す前に（partition・レート・エラー・監視）
    concepts/         考え方：PORTERS 固有の前提（読み物・API 面ではない）
      partition.md        Partition（Company DB）とテナント
      aliases.md          alias と Data Type（P_ / U_ / A_）
      datetime.md         日時は UTC・ISO 8601 で入出力する
      no-delete.md        削除 API が無いということ
      limits.md           長さ・件数・レートの上限
    howto/            目的別：「〜したい」
      search-records.md   条件で探したい
      bulk-write.md       200 件超をまとめて書きたい
      attachments.md      添付ファイルを扱いたい
      custom-fields.md    テナント固有項目を型付きで扱いたい
      multi-tenant.md     複数テナントを 1 プロセスで扱いたい
      sync-batch.md       毎日同期するバッチを書きたい
      handle-failures.md  失敗したときに落とす／続ける
      test-without-contract.md テストを書きたい（フェイクサーバー）
    reference/        （既存）PORTERS API の事実
    api/              （既存）公開 API の記号リファレンス
  ```

- **案1b: 3 層**（入門／HOWTO／リファレンス）— 「考え方」を HOWTO の各ページに溶かす。
  ファイルは減るが、Partition や alias の説明が**複数ページに重複**する。
- **案1c: 現状維持＋目次だけ足す** — `docs/index.md` を作って 7 本を並べる。最小。
  順序と目的別の入口は手に入らない。

### 論点2: 既存 7 本をどうするか

- **案2a: 目的別へ移し、必要なら割る**（推奨）。`read-query.md` は「探したい」（HOWTO）と
  「クエリの各要素」（リファレンス的）に**割れる**。前者は `howto/search-records.md`、
  後者はそのまま残して HOWTO から参照する。
- **案2b: そのまま `howto/` に移すだけ**（名前を変える）。安いが、機能単位の見出しが残る。
- **案2c: 全部書き直す** — 「古いかもしれない」を根拠に捨てる案。**実測すると割に合わない**（上記）:
  壊れていたのは **2 箇所・原因は 1 つ**（`partition` の削除）で、内容そのものは濃い。
  そして**書き直しても検査が無ければ同じ速度で腐る** — `custom-fields.md` は今日更新されたのに
  壊れた例が残った、というのがその証拠。**捨てることは腐敗を止めない。**

### 論点3: README の役割と [ADR-0035][0035] の扱い

- **案3a: README を入口に絞り、[ADR-0035][0035] を supersede**（推奨）。
  README は「これは何か・入れ方・30 行で動く例・目次への導線」まで。
  `## リソースと操作`（133 行）は `docs/api` と HOWTO へ移す。
- **案3b: [ADR-0035][0035] を拡張**（supersede しない）。0035 の「README は最短で動かす入口」は
  そのまま有効で、`docs/guide` の中身の並べ方を足すだけと見る。
- **案3c: README は現状維持** — サイトを作るとき README とサイトで**二重メンテ**になる。

### 論点4: V2 の「完成」を何で測るか

散文で「充実した」と書くと検査できない。候補:

- **案4a: 3 つの機械的な検査**（推奨）
  1. **目次との 1:1** — `docs/index.md` に載っているページが実在し、実在するページが載っている
     （`pnpm check:index` と同じ形の突合＝既存スクリプトに対象を足すだけ）
  2. **入門の順序が通る** — `start/` の各ページに「前提」と「次に読む」があり、鎖が切れていない
  3. **公開メソッドが HOWTO から辿れる** — `docs/api` の各記号ページに対し、
     **少なくとも 1 本の HOWTO / 入門ページから言及がある**（＝「載っているが誰も使い方を書いていない」を防ぐ）
  4. **コード例がコンパイルする** — ドキュメント内の TypeScript ブロック（現在 58 個）を抽出して
     `tsc` に通す。**これが今いちばん効く**（上記の実測: 2 例が 19 日間壊れていた）。
     部分断片は `// @check: skip` のような目印で明示的に除外し、**除外したことが見える**ようにする
- **案4b: 1 と 2 だけ**（3・4 は重い）。「使い方が書かれていない公開 API」も「動かない例」も検出できない。
- **案4c: チェックリストを roadmap に置いて人が見る** — 陳腐化する（このリポジトリが繰り返し避けてきた形）。

### 論点5: サイト化への備えをどこまでやるか

- **案5a: 目次ファイル 1 枚だけ**（推奨）。`docs/index.md` を人が読める目次にし、
  site generator が要るようになったらそこから設定を起こす。frontmatter は入れない。
- **案5b: frontmatter（`title` / `sidebar_position`）を今から入れる** — 特定の generator に
  早く縛られる。GitHub 上の見た目も汚れる。
- **案5c: 何もしない** — 目次が無いままなので、サイト化のとき IA を一から起こすことになる。

### 論点6: 英語版

- **案6a: 日本語のみ。英語は別 ADR**（推奨・CLAUDE.md の日本語ファーストどおり）。
- **案6b: 章立てだけ英語も用意** — 中身が無い枠が残る。

## Decision Outcome

**未決（`proposed`）。** 推奨は **論点1=案1a ／ 論点2=案2a ／ 論点3=案3a ／ 論点4=案4a ／
論点5=案5a ／ 論点6=案6a**。

推す理由:

- **いちばん効くのは「考え方」節**（案1a）。このライブラリの難所は API の形ではなく
  **PORTERS 固有の前提**（Partition・alias と Data Type・UTC・削除が無い・上限）で、
  いま各ガイドに散っている。1 箇所に置けば HOWTO が短くなり、重複も消える。
- **既存 1,473 行は資産**（案2a）。濃さは足りていて、足りないのは並べ方。捨てずに組み替える。
- **README を絞る**（案3a）のは、サイトを作る日に**二重メンテの発生源になる**のが README だから。
  先に絞っておけば、サイト化は「`docs/` を載せる」だけで済む。
- **V2 は検査できる形にする**（案4a）。検査 3（公開メソッドが HOWTO から辿れる）は
  「リファレンスには載っているが使い方を誰も書いていない」という**まさに今回起きたずれ**を、
  検査 4（コード例がコンパイルする）は**19 日間壊れていた例**を機械で捕まえる。
  D1〜D5 / V1 と同じ「両方向の突合」の形。
- **「古いから書き直す」は解にならない**（案2a を案2c より推す理由）。腐敗の原因は書き方ではなく
  **検査が無いこと**で、それは検査 4 で塞ぐ。1,473 行を捨てても検査が無ければ同じ速度で腐る。

決め切れていない点（accept 時に決めたい）:

1. **`start/` を 5 本に割るか、1 本の長いページにするか** — Jest の「はじめましょう」は 1 本で長い。
   分けると「次に読む」の鎖の保守が要る。
2. **`howto/sync-batch.md` を入れるか** — 実務シナリオ（毎日同期）は価値が高いが、
   **ライブラリの範囲を超える**（スケジューラ・冪等性・差分検出）。どこで切るか。
3. **リソース別の操作一覧**（README の 133 行）の行き先 — `docs/api` に任せるか、
   `howto/` の下に「リソース別」を作るか。

## 信じている入力

該当なし — 本決定は**自分たちが書く文章の並べ方**の話で、外部 API・LLM・第三者が書ける文書からの
入力を受け取らない。検査（論点4）の入力は同一リポジトリの Markdown と `docs/api` の生成物であり、
どちらも CI で再生成・突合できる。

## Pros and Cons of the Options

### 案1a（4 層：入門／考え方／目的別／リファレンス）

- Good: 2 サイトで実証された並び。目的から引ける。「考え方」が重複を吸収する。
- Bad: ディレクトリが 3 つ増え、ページ数が 7 → 18 前後になる（書く量が増える）。

### 案1c（目次だけ足す）

- Good: 一日で終わる。
- Bad: **今回の不満（順に読めない・目的から引けない）が残る**。V2 を満たさない。

### 案2a（移して割る）

- Good: 既存の濃さを保ちつつ、HOWTO とリファレンスの役割を分ける。移す過程で**全ページを読み直す**ので、
  古い記述はそこで見つかる（検査 4 が入れば、見落としても機械が止める）。
- Bad: リンクの張り替えが広範（README・ガイド間・ADR からの参照）。

### 案2c（全部書き直す）

- Good: 文体と粒度が揃う。古い記述を持ち越さない。
- Bad: **腐敗を止めない**（検査が無ければ新しい原稿も同じ速度で古くなる）。1,473 行の濃い内容を
  捨てる。書き直しの間、ドキュメントが二重に存在する期間ができる。

### 案3a（README を絞り 0035 を supersede）

- Good: 二重メンテの発生源を先に消す。サイト化が「`docs/` を載せる」だけになる。
- Bad: README が短くなると、npm ページで見える情報が減る（リンクで補う必要）。

### 案4a（3 つの機械的な検査）

- Good: 「完成」を人の感想でなく検査で言える。検査 3 が今回のずれを再発させない。
- Bad: 検査 3 の実装が要る（`docs/api` の記号名と HOWTO の言及を突合するスクリプト）。
