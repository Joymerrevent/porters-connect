# 84. 成功指標をどう測るか（数値目標を置くか、マイルストーンだけにするか）

- Status: proposed
- Date: 2026-09-18
- Deciders: jun.shiromoto (Joymerrevent)

> [PRD §8][prd] に **2026-08-09 から残っていた最後の未決**（「成功指標の数値化のタイミング」）の起票。
> `1.0.0` の完成条件 V3（判断待ちが 0 になるまで進めない）の最後の 1 件。**決定は decider 待ち。**

## Context and Problem Statement

[PRD §7][prd] は「**数値目標はベースライン取得後に設定**」と書き、[§8][prd] は
「ベースライン＝最初の実利用が出てから設定する想定で良いか」を未決のまま残している。

**まず前提を測り直した**（2026-09-18・実測）。**ベースラインとみなせる実利用は、まだ 1 件も観測できない。**

| 指標                  | 実測                                                                                                                             | 出どころ         |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| npm ダウンロード      | 06-01〜09-18 で合計 3547。ただし**山は publish 日に立つ**（09-06=156 / 09-09=141 / 09-13=269 / 09-16=172）。**非公開日は 0〜26** | npm registry API |
| GitHub                | star **1** / fork 0 / watch 0                                                                                                    | GitHub API       |
| 外部からの Issue / PR | **0 件**（PR 100 本は所有者と Dependabot のみ）                                                                                  | GitHub API       |

**ダウンロードの形はミラーと CI の取得と一致していて、人間の継続利用の形ではない。**
publish のたびに山が立ち、間の日はほぼ 0 — 利用者が増えたときに出るはずの「publish と無関係な定常」が無い。

ここから問題が 1 つ出る。**「ベースライン取得後に数値化」のまま置くと、この未決は永久に閉じない。**
公開から 3 か月半で発火条件が来ていないし、来る時期も読めない。そして V3 は「判断待ちが 0 件」を
求めているので、**`1.0.0` がこの 1 件で止まる**。

問い: **「いつ数値化するか」ではなく、この未決をどう閉じるか。そもそも数値目標を置くのか。**

## Decision Drivers

- **市場が小さい**（実需は数十〜百数十社の推測・[PRD §7][prd]）。**1 社刻みの世界で「率」や「量」の
  目標を置いても、意味のある差が出ない。**
- **信頼できる量的シグナルが無い**（上の実測）。npm のダウンロードは**ミラーが支配的**で、
  利用者が数人に増えても同じ形のまま埋もれる。star は人気の代理であって利用ではない。
- **フェイルセーフ**＝壊れたときに安全側へ倒れる。**ノイズに目標を置くと、誤ったシグナルで舵を切る。**
  指標が無いほうが安全側に倒れる場面がある。
- **「後でやる」を残さない**。本プロジェクトは、期限も発火条件も無い「後で」が実際に腐る
  （2026-09-18 のロードマップ棚卸しで、7 箇所の「未リリース」表記が数版ぶん古いまま見つかった）。
- 最優先目標は**収益化より実利用者に使われること**（CLAUDE.md）。指標はその判断を助けるためにある。

## Considered Options

- 案A: **発火条件つきで確定** — 「数値目標はベースライン取得後に置く」を決定として確定し、
  **何をもってベースラインとみなすか**を検査できる形で書く（未決 → 条件待ち）。
- 案B: **いま数値目標を置く** — ダウンロード数・star 数などに目標値を設定する。
- 案C: **数値目標は置かず、0/1 のマイルストーンだけで評価する**と決める。
- 案D: **計測の土台を先に作る** — 週次でダウンロード・star を記録する仕組みを入れ、貯まってから決める。

## Decision Outcome

**未決（`proposed`）。** 推奨は**案C**、ただし下の 2 つの限定つき。

**案C を推す理由は、置くべき数値が無いことが実測で分かったから。** [PRD §7][prd] は既に
「**量より“デファクトの兆候”をマイルストーンで**」と書いている。案C はそれを全体の方針に格上げして、
**宙に浮いた「後で数値化する」という約束を消す**だけである。

**案B は明確に誤り。** 唯一の量的チャネルであるダウンロードは**ミラー由来が支配的**で、
実利用者が 1 社から 5 社に増えても数字はほとんど動かない。**ノイズに目標を置けば、
達成・未達のどちらの判定も嘘になる。**

**案A は「後で」を残す。** 発火条件を書けば腐りにくくはなるが、**その保険は ADR の運用が既に持っている** —
将来ほんとうに数値が要るとなれば、新しい ADR を起こして本 ADR を supersede すればよい。
発火条件を別に書くのは二重になる。

**案D は投資に見合わない。** 記録を貯めても、貯まるのはミラーのノイズである。

### 限定 1: 「数値を置かない」の対象は**採用・普及の量**だけ

**自分で測れる先行指標は数値のまま残す。** 利用者がゼロでも測れて、しかも品質を直接動かすため。

| 指標                         | 扱い                                                                                |
| ---------------------------- | ----------------------------------------------------------------------------------- |
| Time-to-first-typed-call     | **数値のまま**（暫定 30 分以内 → **一度も実測していない**ので、実測して確定させる） |
| 評価可能性（契約なしで動く） | **YES/NO のまま**                                                                   |
| ドキュメント自己解決率       | 定性のまま                                                                          |
| 採用数・ダウンロード・star   | **数値目標を置かない**（マイルストーンで見る）                                      |

**Time-to-first-typed-call が 3 か月測られなかったのは、測り方が書いていないから。** 数値を残す以上、
手順まで決める。**契約の有無で別物**なので 2 つに分ける。

|        | 契約なしの経路（**今日測れる**）                                                                                                               | 契約ありの経路（契約待ち）                                                                     |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 手順   | まっさらな Node プロジェクトで `npm i` → [契約なしでテストを書きたい][test-wo]に沿って `createMockTransport` で型付き `search` が 1 本通るまで | `npm i` → [前提][s-prereq] → [認証][s-auth] → [はじめての読み取り][s-read]で実データが返るまで |
| 測る人 | **人が 1 回通しで実行して時計で測る**（読む時間が支配的なので自動化しない）                                                                    | 同じ                                                                                           |
| いつ   | 次のリリース前に 1 回                                                                                                                          | 契約取得後（[ライブ検証][lv]と同じ棚）                                                         |
| 結果   | 実測値で暫定 30 分を置き換える。**超えたら入門の手順を削る**＝指標が改善アクションに直結する                                                   | 同じ                                                                                           |

**「評価可能性」は今日 YES だが、誰も検査していない。** `pnpm sandbox`（[ADR-0024][adr24] の
評価用サンドボックス）は手元で回せば完走する（2026-09-18 実測）が、**CI に入っておらずテストも無い**＝
壊れても利用者が試すまで分からない。**0/1 を機械で出すには CI に `pnpm sandbox` を 1 行足す**。
これは指標の話であると同時に、**fail-open の穴を塞ぐ話**でもある。

### 限定 2: マイルストーンは **0/1 で判定できる形**に書き直す

いまの遅行指標は「実案件 1 件目の採用」「ベンダー言及」など、**誰が何を見たら 1 になるかが書かれていない**。
数値をやめる以上、ここが曖昧だと「デファクトの兆候」が主観になる。各マイルストーンに
**判定の根拠**と**どこを見るか**を与える（右列は 2026-09-18 の実測）。

| 遅行指標     | 何をもって **1** とみなすか                                                   | どこを見るか（現在値）                                                                                                          |
| ------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 実案件採用   | 「実案件で使っている」と分かる連絡が 1 件（Issue / PR / 直接連絡 / 公開事例） | GitHub・問い合わせ（**0 件**）                                                                                                  |
| 流入→試用    | 流入元に**ブログ等の外部ドメイン**が出る                                      | `gh api repos/…/traffic/popular/referrers`（**github.com / npmjs.com / bestpractices.dev のみ**・14 日で 404 view / uniques 6） |
| ベンダー言及 | ポーターズ社の公開物に本ライブラリへの言及が出る                              | 人が確認（**無し**）                                                                                                            |
| 品質シグナル | **外部からの Issue / PR が 1 件**来る（Dependabot を除く）                    | GitHub（**0 件**）                                                                                                              |

> ⚠️ **GitHub の traffic は直近 14 日ぶんしか残らない**（取得には push 権限が要る）。見に行かなければ
> 消えるので、**発火しても気づけない**（fail-open）。対策は、定期レビュー（`project-review`）のときに
> traffic のスナップショットを台帳に控えること。**案D の最小版**だが、貯めるのがミラーのノイズではなく
> **人の訪問**である点が違う。

### Consequences（案C を採る場合）

- Good: **最後の未決が閉じ、V3 の判断待ちが 0 になる**（`1.0.0` の前提が 1 つ進む）。
- Good: ノイズに目標を置かない。**達成・未達の誤判定が起きない。**
- Good: 「後で数値化する」という宙づりの約束が消える。
- Bad: **「どれくらい使われているか」を量で語れない。** 外部に説明するとき（ベンダー・採用候補）に
  数字が出せない場面はある。
- Bad: **遅行指標の判定は人が行う**（0/1 の形に書き直しても、発火に気づくのは人）。自動化されるのは
  先行指標の「評価可能性」だけ（CI の `pnpm sandbox`）。
- Neutral: 将来ほんとうに数値が必要になったら、新しい ADR で本 ADR を supersede すればよい。

## 信じている入力

| 値                          | 出どころ                    | 誰が書けるか    | 守り方                                              | 取れなかったら                                                               | 誤っていたら                                             |
| --------------------------- | --------------------------- | --------------- | --------------------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------- |
| npm のダウンロード数        | npm registry API            | npm（＋ミラー） | **散文のみ**（本 ADR に実測値と日付を残す）         | 取得失敗＝「0 件」と読まない                                                 | 形（publish 日の山）が変わったら読み直す                 |
| GitHub の star / Issue / PR | GitHub API                  | 第三者が書ける  | **散文のみ**（同上）                                | 同上                                                                         | 外部からの Issue が来たら、それ自体がシグナル            |
| GitHub の traffic（流入元） | GitHub API                  | 第三者が書ける  | **散文のみ**（定期レビューで控えを残す）            | **14 日で消える**＝取れなかったのか 0 件なのか区別が付かない。控えで区別する | 流入元は自己申告ではないので、誤りより**取り逃し**が問題 |
| 「実需は数十〜百数十社」    | [PRD §7][prd]（推測と明記） | 本リポジトリ    | **散文のみ**（推測であることを PRD が明示している） | —                                                                            | 市場が大きければ数値目標の意味が出る＝再検討             |

**この決定は「量的シグナルが今後も信頼できない」に賭けている。** 外れる形は 2 つあり、どちらも
**外から見えるので気づける** — ①外部からの Issue / PR が来る、②ダウンロードに publish と無関係な
定常が出る。どちらかが起きたら、本 ADR を見直す合図になる。

## Pros and Cons of the Options

### 案A（発火条件つきで確定）

- Good: 「いつか数値を置く」という意思を残せる。
- Bad: 「後で」が残る。発火条件の保険は ADR の supersede で既に足りている＝二重。

### 案B（いま数値目標を置く）

- Good: 対外的に数字で語れる。
- Bad: **置ける数字がノイズしかない**（実測）。達成・未達の判定が嘘になる。

### 案C（マイルストーンだけ・推奨）

- Good: 実測に合っている。未決が閉じ、誤判定が起きない。
- Bad: 量で語れない。判定は人が行う。

### 案D（計測の土台を先に作る）

- Good: 後から振り返れる記録が残る。
- Bad: 貯まるのはミラーのノイズ。投資に見合わない。

- 実測日: 2026-09-18（npm registry API ／ GitHub API）

  3. `project-review` の手順に **traffic のスナップショットを控える** 1 行を足す
  4. [§8][prd] の当該行を（解決済み）にし、[ロードマップ][rm]の「判断待ち」を 0 件にする

  結果が出てから PRD の暫定値を置き換える。
- 将来: 外部からの Issue / PR が来る、またはダウンロードに publish と無関係な定常が出たら、
  本 ADR を見直す（必要なら新しい ADR で supersede）。
