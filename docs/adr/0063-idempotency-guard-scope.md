# 63. 冪等性ガードを「送信済みで結果が不明」に限定する

- Status: accepted
- Date: 2026-08-31（accepted: 2026-09-03）
- Deciders: jun.shiromoto (Joymerrevent)

> [ADR-0010][adr10] の冪等性ガード（非冪等な `create` を不確定失敗で再送しない）は、実装上
> **`PortersNetworkError` かどうか**だけで判定している。その結果、**リクエストが一度も出ていない失敗**や
> **PORTERS が処理前に拒否した失敗**まで「適用されたかもしれない」扱いになり、自動回復できる場面を落としている。
> 判定基準を決め直す（[findings][findings] **RV-22**）。

## Context and Problem Statement

`requester` のガードはこの 1 行:

```ts
// src/http/requester.ts
if (e instanceof PortersNetworkError && write && !idempotent) throw e;
```

[ADR-0010][adr10] が決めたのは「**応答が返らない失敗（timeout / 切断）では自動再試行しない**」ことで、
理由は**書き込みが適用されたかどうか分からない**から＝二重登録を作らない（フェイルセーフ）。
ところが実装はサブクラスで判定しているため、**適用されていないと分かっている失敗**まで巻き込む。
巻き込まれているのは 2 つ:

1. **HTTP 429**（[ADR-0044][adr44] で `rateLimit` ＝ `PortersNetworkError` にした）。
   429 は「**処理される前に拒否された**」ことが分かっているので、再送しても二重登録は起きない。
   ただし **PORTERS 直結では 429 は観測されない想定**（レート超過は強制切断）で、効くのはプロキシ経由の環境。
   429 が実際に返るか自体が [live-verification][lv] **LV-9** の確認事項。
2. **トークン取得の失敗**（[ADR-0050][adr50] で認証経路も `PortersNetworkError` / `PortersConfigError` を
   投げうるようになった）。`getAccessToken` が落ちた時点で**リクエストは一度も出ていない**。
   ADR-0050 は Consequences にこれを書き、**「ガードの粒度は RV-22 と同じ論点なのでそちらで一緒に見直す」**
   と本 ADR へ送っている。**こちらは契約の有無に関係なく今日起きる**。

つまり問うべきは「どのエラー型か」ではなく「**その write は適用されうるのか**」である。

## Decision Drivers

- **フェイルセーフ** — 二重登録は作らない。**迷ったら再送しない**は維持する。
- **安全側に倒しすぎない** — 「適用されていないと分かっている」場面まで人手に返すのは、回復の機会を捨てている。
- **公開サーフェスを増やさない** — 判定はライブラリの内部事情であり、利用者に新しい語彙を覚えさせない。
- **未確認の仮定を実装に埋めない** — 429 の実挙動は LV-9 待ち。仮定は `VERIFY(live)` として残す。

## Considered Options

- **案A: 「送信したか」を requester 内部の状態で持ち、429 は category で例外にする**
- **案B: エラー側に公開フラグを足す**（例 `applied: "no" | "unknown"`）
- **案C: 429 だけ直す**（認証経路は据え置き）
- **案D: 何もしない**（LV-9 の結果を待つ・wontfix もありうる）

## Decision Outcome

**決定（accepted・2026-09-03）：案A。2 つとも今直す。**

ガードの条件を「**送信済み ＋ 結果が不明**」に限定する。具体的には requester のループで

- **送信直前に「送った」印を立てる**。トークン取得や送信前ガードで落ちた場合は印が立たないので、
  ガードの対象外＝ retryable なら通常のバックオフで再送される。
- **応答由来のエラーは `category` で見る**。`rateLimit`（＝ HTTP 429）は「処理前に拒否された」ので
  ガードの対象外にする。それ以外の `PortersNetworkError`（timeout / 切断 / 5xx）は従来どおり再送しない。

判定はすべて requester の内部に閉じ、**公開型・公開 API は変えない**（案B を採らない理由）。
案C を採らないのは、**契約なしで今日起きているのは認証経路のほう**だからで、
「429 が観測できるか」を待つ理由が認証経路には無い。案D は ADR-0050 が送ってきた宿題を残し続ける。

### Consequences

- Good: **自動回復できる場面が 2 つ増える**。トークン取得の一時失敗で `create` / `createMany` が
  落ちなくなる（リクエストは出ていないので二重登録の余地が無い）。
- Good: ガードの根拠が「エラーのクラス」から「**適用されうるか**」になり、[ADR-0010][adr10] の意図と
  実装の言葉が一致する。将来サブクラスの割り当てが変わっても壊れない。
- Good: 公開サーフェスは不変＝ patch リリースで出せる。
- Bad: **「429 は適用前の拒否」という仮定に依存する**。応答経路で 429 を返す中間装置があれば理屈上は
  二重登録の余地が残る（現実的な構成では起きない）。**`VERIFY(live)` を実装に残し**、
  [LV-9][lv] の結果しだいで見直す。
- Neutral: 429 のときは `create` もバックオフ待ちに入る（従来は即座に表面化していた）。
- Neutral: 再送のたびにスロットルのトークンを取り直す点は従来と同じ。

### 実装の当たり（本 ADR では変更しない）

- `src/http/requester.ts` — ループ内に「送信したか」の状態を持ち、ガードの条件に足す。
- `src/errors/classify.ts` — 変更なし（`rateLimit` の写像は [ADR-0044][adr44] のまま）。
- テスト — ①トークン取得失敗後に `create` が再送される ②429 の後に `create` が再送される
  ③ 送信後の timeout / 切断では**従来どおり再送しない**（回帰の芯）。

## Pros and Cons of the Options

### 案A 送信したかを内部状態で持つ（採用）

- Good: 「適用されうるか」を直接表現する。認証経路と 429 の両方が 1 つの条件で片付く。
- Good: 公開サーフェスが増えない。判定が requester の中に閉じる。
- Bad: requester のループに状態が 1 つ増える（読み手が追う対象が増える）。
- Bad: 429 の解釈という**未確認の仮定**を実装に持ち込む（`VERIFY(live)` で明示する）。

### 案B エラーに公開フラグを足す

- Good: 利用者も「適用されていない」と分かる＝自前のリトライを書ける。
- Bad: **公開サーフェスが増える**。全エラー生成箇所で正しく設定する義務が生まれ、間違えると
  「適用されたのに適用されていない」と言い切る**危険な嘘**になる。フェイルセーフの逆。
- Bad: 利用者向けの必要性がまだ無い（要望が出てから足せる）。

### 案C 429 だけ直す

- Good: 変更が最小。
- Bad: **今日起きている側（認証経路）が残る**。ADR-0050 の宿題も残る。
- Bad: LV-9 の結果しだいでは「効かない直し」だけを入れたことになる。

### 案D 何もしない

- Good: 未確認の仮定を持ち込まない。
- Bad: 認証経路の保守的すぎる失敗が残り続ける。**安全側だが、安全側に倒しすぎている**という
  起票時の評価が変わらないまま放置になる。
