# 77. Attachment の本体は `get` でだけ運ぶ（`search` も本体なしにする）

- Status: accepted
- Date: 2026-09-16
- Deciders: jun.shiromoto (Joymerrevent)

> [ADR-0075][0075] が**未決のフォローアップ**として残した問いの決着。0075 の決定
> （`searchAll` を足し、走査では本体を運ばせない）は変わらない。本 ADR はその線を
> **`search` 単発にも広げる**。
>
> **decider が案A を選択し `accepted`（2026-09-16）。** 実装は別 PR（0075 と同じ PR でよい）。

## Context and Problem Statement

[ADR-0075][0075] は `searchAll` に「本体を運ばせない」線を引いたが、**`search` 単発は
制限しなかった**。その理由として本文にはこう書いた。

> `search` 単発を制限しないのは、**件数を呼び出し側が決めている**ためで、`searchAll` との
> 違いはそこにある。

**この前提が成り立っていない。** 危険の大きさは「件数 × 1 件あたりの大きさ」で決まるが、
**呼び出し側は後者を知らない**。Attachment の項目は出典の一覧で 6 つ（`Id` / `Resource` /
`ResourceId` / `ContentType` / `FileName` / `Content`）しかなく、**ファイルサイズを表す項目が無い**。
つまり「10 件だけだから安全」を事前に判断する材料がライブラリにも呼び出し側にも無い。

0075 で測った値は `searchAll` 固有のものではなく、**`search` 単発にそのまま当てはまる**。

- 1 ファイル **2MB 超 × 200 件**は V8 の文字列上限（536,870,888 文字）を越えて**読めない**
  （`RangeError`）。出典は 1 ファイル **10MB** まで許す。
- 読める大きさでも heap は応答の **2〜3 倍**（実測: 応答 130MB で heapUsed 378MB）。
- 既定の transport タイムアウトは 30 秒。触れた失敗は `retryable` 扱いで**最大 4 回**再送される。

**PORTERS 自身の語彙も二択である。** `requestType` はリクエスト単位のスイッチ（`0` = `<Content>`
あり / `1` = なし）で、レコードごとに選ぶ仕組みは無い。**本体を運ぶかどうかは「その 1 回の Read が
どういう Read か」で決まる**というのが出典の形で、ライブラリ側でそれを**メソッドの違い**に
写せば、公開 API と出典が 1 対 1 で並ぶ。

問い: **`search` からも本体を外し、本体は `get(id)` でだけ運ぶか。**

## Decision Drivers

- **フェイルセーフ**: 読めない応答を**作れないようにする**。ライブラリの外（利用者のプロセス）で
  OOM や `RangeError` を起こさせない。
- **予測可能性**: 1 回の Read が扱う最大量が**メソッドで決まる**こと。
- **出典の語彙との一致**: `requestType` の二択を公開 API にそのまま出す。
- **費用**: 本体を N 件取るのに N リクエストかかること。
- **型で言えること**: 「一覧では本体を取れない」を散文でなく型で示せるか。

## Considered Options

- 案A: **`search` / `searchAll` は本体を運ばない。本体は `get(id)` だけ**
  （`field` の型から `Content` を外し、キャストで渡されたら実行時にも拒否）
- 案B: 現状維持（要求されれば `search` も運ぶ）＋ ドキュメントで警告する
- 案C: 本体を要求したときだけ `count` を小さく強制する（例: 10 件以下）
- 案D: 応答サイズの上限ガードを入れる（一定の大きさを超えたらエラーにする）

## Decision Outcome

採用: **案A**。

理由: 危険の大きさを決める 2 つの要素のうち、**片方（1 件の大きさ）を誰も事前に知れない**以上、
「呼び出し側が加減できる」という前提に立てない。メソッドで分ければ、1 回の Read の上限が
**設計で決まる** — 一覧はメタデータのみ、単件は最大 10MB（Base64 で ~14M 文字・heap 40MB 前後）。
`RangeError` になる組み合わせは**作れなくなる**。

### Consequences

- Good: 1 回の Read が扱う最大量がメソッドで決まる。上限を超える組み合わせを利用者が
  書けなくなる（型で止まり、キャストしても実行時に止まる）。
- Good: PORTERS の `requestType` の二択が公開 API に 1 対 1 で出る（`search` = 本体なし /
  `get` = 本体あり）。[LV-24][lv] がどちらに確定しても、この対応は変わらない。
- Bad: **破壊的変更**。`search({ field: ["Content", …] })` はコンパイルエラーになり、
  実行時にも拒否される。本体を N 件取るコードは `get` を N 回呼ぶ形に書き換えが要る。
- Bad: 本体 N 件 = N リクエスト。1 分あたり Read 2000 の中では小さいが、月次のアクセス数
  （契約条件）は消費する。一覧 1 回で全部の本体が取れていた形は無くなる。
- Neutral: `get` は常に本体を取る。メタデータだけ 1 件欲しいときは
  `search({ condition: { "Id:eq": "…" } })` で取れる。
- Neutral: マトリクスの表 B / 表 C は変わらない（送るパラメータ自体は同じで、`field` の
  中身が変わるだけ）。変わるのは表 D（`searchAll` の追加 — [ADR-0075][0075]）。

## 信じている入力

| 値                                      | 出どころ         | 誰が書けるか     | 守り方                                                | 取れなかったら                     | 誤っていたら                                   |
| --------------------------------------- | ---------------- | ---------------- | ----------------------------------------------------- | ---------------------------------- | ---------------------------------------------- |
| 1 ファイルの大きさ                      | PORTERS の応答   | テナントの利用者 | **仕組み**（本体を運ぶのは単件だけ＝最大 10MB／出典） | —                                  | 単件なら読める大きさに収まる                   |
| `field`（`Content` を含むか）           | 呼び出し側（人） | —                | **仕組み**（型から除外 ＋ 実行時ガード）              | 省略＝メタデータのみ               | キャストで渡されても実行時に止まる             |
| 本体の取り方（`field` / `requestType`） | PORTERS の記事   | PORTERS 社       | 散文（[LV-24][lv]）。確定したら実装の書き方が変わる   | 未確認のまま＝**本体を運ばない側** | 決定（メソッドで分ける）は確定しても変わらない |

**サイズを表す項目が出典に無い**ことがこの決定の芯なので、そこが変わったら（PORTERS が
サイズを返すようになったら）前提を見直す。マトリクスの reference 突合が項目の増減を拾う。

## Pros and Cons of the Options

### 案A（本体は `get` だけ）

- Good: 1 回の Read の上限が設計で決まる。読めない応答を作れない。
- Good: 出典の `requestType` と公開 API が 1 対 1 で並ぶ。
- Bad: 破壊的変更。本体を N 件取るコードは N 回の `get` に書き換えが要る。

### 案B（現状維持 ＋ 警告）

- Good: 何も壊さない。1 回で N 件の本体が取れる速さは残る。
- Bad: **守っているのは散文だけ**。踏んだときの症状（`RangeError` / OOM / 4 回の再送）は
  ライブラリの外で起き、原因がライブラリ側にあると分かりにくい。

### 案C（本体を要求したら件数を絞る）

- Good: 妥協点としては分かりやすい。1 回で数件の本体は取れる。
- Bad: **安全な件数を決められない**。10MB × 10 件は既に読めない（文字列上限）。
  サイズが分からない以上、どんな上限も「たいてい大丈夫」にしかならない。

### 案D（応答サイズの上限ガード）

- Good: 本体以外の巨大応答にも効く一般的な守り。
- Bad: **手遅れになってから止まる** — 上限を測るには応答を文字列にする必要があり、
  その文字列化こそが `RangeError` の発生点。転送も既に終わっている。
- Neutral: 一般的な守りとしては別途検討に値する（本 ADR の対象外）。
