# 75. Attachment に `searchAll` を足し、本体は `get` でだけ運ぶ

- Status: accepted
- Date: 2026-09-16
- Deciders: jun.shiromoto (Joymerrevent)

> [エンドポイント × 機能マトリクス][coverage]（V1）の表 D で見つかった [RV-45][rv45] の決着。
> **Read を持つ 17 エンドポイントのうち、置けるのに `searchAll` が無いのは Attachment だけ**で、
> 置かない判断をした記録も無い。
>
> **decider が案1a ＋ 案2a を選択し `accepted`（2026-09-16）。** 実装は accept 後・別 PR。
> 議論の途中で「本体付きの取得は `search` 単発でも同じ危険」と分かったため、**決定を `search`
> にも広げた**（起票時は `searchAll` だけを対象にしていた）。

## Context and Problem Statement

`searchAll`（オフセット式ページングの自動化）が無い Read エンドポイントは 2 つある。

| エンドポイント   | `start`  | `searchAll` | 無い理由           |
| ---------------- | -------- | ----------- | ------------------ |
| `/v1/option`     | 無し     | 無し        | ページングできない |
| `/v1/attachment` | **有り** | **無し**    | **記録なし**       |

Option は出典に `start` が無く、応答のルートに `Total` / `Count` / `Start` も付かない
（[ADR-0022][0022] 事実5）＝**原理的に置けない**。Attachment は違う。

**PORTERS 側は揃っている**（出典 `Attachment - Read`・取得 2026-06-12）。

```text
GET https://{host}/v1/attachment?partition=&requestType=&resource=&resourceId=&id=&count=&start=
```

- `count` は 1〜200（省略時 10）、`start` は 0 以上（省略時 0）。
- 応答のルート要素は `<Attachment Total="1" Count="1" Start="0">` — 記事のサンプルにもそのまま出る。

**ライブラリ側も揃っている。**

- `attachment.search` は既に `total` / `count` / `start` を返している（`src/resources/attachment.ts`）。
- `paginate` は `(count, start) => Promise<{ items, total }>` を取るだけの汎用品で、
  リソース固有の型に依存しない（`src/resources/read-core.ts`）。

**では、なぜ無いのか。** [ADR-0018][0018]（Attachment の設計）が挙げた公開メソッドは
`create` / `get` / `search` で、`searchAll` に触れていない。当時 `searchAll` は**どのリソースにも
無かった**（オフセット走査は後から汎用 factory に入った）ので、**横展開のときに素通りした**と見ている。
意図して外した記録はどこにも無い。

**PORTERS は複数件でも本体を返す。** 出典の `requestType` は**リクエスト単位のスイッチ**で、
`0` なら `<Content>` に Base64 が付き、`1` なら付かない。`count`（1〜200）とは独立していて、
「本体付きは 1 件だけ」といった制限は書かれていない。つまり `requestType=0&count=200` は
**200 件ぶんの本体**を 1 応答で返す（1 ファイル 10MB まで — Write 記事）。
**できないから塞ぐ、という話ではない。**

### 200 件を本体付きで取ると何が起きるか（実測 2026-09-15）

応答は**丸ごと 1 本の文字列**になってから DOM ごとパースされる（`await res.text()` →
`fast-xml-parser`。ストリーミングは無い）。Node 24 / 64bit で計測した。

| 1 ファイル | 200 件の応答 | パース時間 | heapUsed | rss   |
| ---------- | ------------ | ---------- | -------- | ----- |
| 250KB      | 65MB         | 433ms      | 153MB    | 323MB |
| 500KB      | 130MB        | 802ms      | 378MB    | 521MB |

**山は応答の 2〜3 倍**（生の文字列 ＋ パース後の木）。ここから 4 つ出てくる。

1. **読めない大きさがある。** V8 の文字列上限は `MAX_STRING_LENGTH` = 536,870,888 文字（512MiB）。
   Base64 は元の約 4/3 なので、**1 ファイルが 2MB を超えると 200 件は文字列にできない**
   （`RangeError: Invalid string length`）。出典は 1 ファイル **10MB** まで許すので、
   上限に届く組み合わせは普通に作れる。
2. **メモリ。** 1MB のファイル 200 件（応答 267MB）で heap は 700MB 前後になる。
   1 プロセスで複数テナントを回すサーバーでは、1 回の一覧が他の処理を巻き込む。
3. **時間と既定のタイムアウト。** 既定の transport タイムアウトは 30 秒
   （`createFetchTransport`）。数百 MB を 30 秒で受け切るには 100Mbps 超の実効帯域が要る。
4. **失敗が再送される。** 1 と 3 はどちらも `PortersNetworkError`（`retryable: true`）になり、
   既定の `maxRetries: 3` で**最大 4 回**、毎回数百 MB を取り直してから同じ理由で落ちる。

**いま守りは無い。** 送信側は長さ（約 15000 文字）とアップロード本体（~14M 文字）を見ているが、
**応答側の大きさを見る仕組みはどこにも無い**。

再現方法（`tmp/` に置いて `node --max-old-space-size=3000` で実行）:

```js
import { XMLParser } from "fast-xml-parser";
const b64 = "A".repeat(Math.round((500 * 1024 * 4) / 3)); // 500KB のファイル 1 つ分
const item = `<Item><Id>1</Id><Content>${b64}</Content></Item>`;
const xml = `<Attachment Total="200" Count="200" Start="0"><Code>0</Code>${item.repeat(200)}</Attachment>`;
new XMLParser({ parseTagValue: false }).parse(xml); // 130MB -> ~800ms / heapUsed ~378MB
```

### 危険は `searchAll` 固有ではない — 件数では加減できない

上の実測は `search` 単発にもそのまま当てはまる。`search({ field: [… "Content"], count: 200 })` は
**今日も書ける**。

「件数は呼び出し側が決めているのだから `search` は自己責任でよい」とは言えない。
危険の大きさは **件数 × 1 件あたりの大きさ**で決まるが、**呼び出し側は後者を知らない**。
Attachment の項目は出典の一覧で 6 つ（`Id` / `Resource` / `ResourceId` / `ContentType` /
`FileName` / `Content`）しかなく、**ファイルサイズを表す項目が無い**。
「10 件だけだから安全」を事前に判断する材料が、ライブラリにも呼び出し側にも無い。

**本体の選び方が二択**（全件に付ける / 全件に付けない）なのも効く。「この 3 件だけ本体」は
出典の語彙に無いので、**本体を運ぶかどうかは「その 1 回の Read がどういう Read か」で決まる**。
これはメソッドの違いにそのまま写せる。

なお**ライブラリは今 `requestType` を送っておらず**、`field` に `Content` を並べるかどうかで
決めている（[LV-24][lv]）。どちらが実際に効くかは未確認なので、本 ADR の案は
**語彙に依存しない形**（「本体を運ぶか運ばないか」）で書く。

問い: **`searchAll` を足すか。足すなら、本体はどの経路で運ぶか。**

## Decision Drivers

- **語彙の一貫性**: 17 エンドポイント中 15 が `searchAll` を持つ。使う側が Attachment でだけ
  例外を覚えることの費用。
- **フェイルセーフ**: 読めない応答を**作れないようにする**。利用者のプロセスで OOM や
  `RangeError` を起こさせない。既定の `field` が `Content` を外している（[ADR-0020][0020]）のも、
  `get` の JSDoc が「`Content` を頼むのは `get` のほう」と書いているのも同じ線。
- **予測可能性**: 1 回の Read が扱う最大量が**メソッドで決まる**こと。
- **出典の語彙との一致**: `requestType` の二択が公開 API にそのまま出ること。
- **逃げ道が実際にあるか**: メタデータで走査 → 要る 1 件だけ `get(id)`、が書けること。
- **移行コスト**: 本体を N 件まとめて取っていたコードは書き換えが要る。
- **未確定を抱え込まない**: [LV-24][lv] は契約前に確定しない。確定したときに直す量が増えないこと。

## Considered Options

**軸1: `searchAll` を足すか**

- 案1a: **足す**
- 案1b: 足さない（[ADR-0041][0041] 軸5 と同じ「本体が巨大なので一気に扱わせない」で揃える）

**軸2: 本体をどの経路で運ぶか**

- 案2a: **`get(id)` だけ**（`search` / `searchAll` は本体を運ばない）
- 案2b: `searchAll` だけ禁止（`search` は要求されれば運ぶ）＋ ドキュメントで警告
- 案2c: 本体を要求したときだけ `count` を小さく強制する（例: 10 件以下）
- 案2d: 応答サイズの上限ガードを入れる（一定の大きさを超えたらエラーにする）

## Decision Outcome

採用: **案1a ＋ 案2a**。`searchAll` を足し、**本体は `get(id)` でだけ運ぶ**
（`field` の型から `Content` を外し、キャストで渡されたら実行時にも拒否して `get` へ誘導する）。

理由: PORTERS 側の前提（`start` ／ `Total`）が揃っていて部品（`paginate`）も既にある以上、
`searchAll` は「置けない」ではなく「置いていない」だけで、語彙を 1 つ揃える利得が大きい（軸1）。
そのうえで、危険の大きさを決める 2 つの要素のうち**片方（1 件の大きさ）を誰も事前に知れない**以上、
「呼び出し側が加減できる」という前提には立てない（軸2）。メソッドで分ければ 1 回の Read の上限が
**設計で決まる** — 一覧はメタデータのみ、単件は最大 10MB（Base64 で ~14M 文字・heap 40MB 前後）。
`RangeError` になる組み合わせは**作れなくなる**。

### Consequences

- Good: Attachment が他の 15 エンドポイントと同じ語彙になる。200 件を超える添付を持つテナントで、
  呼び出し側が `start` を自分で回さなくてよくなる。
- Good: 1 回の Read が扱う最大量がメソッドで決まる。上限を超える組み合わせを利用者が
  書けなくなる（型で止まり、キャストしても実行時に止まる）。
- Good: PORTERS の `requestType` の二択が公開 API に 1 対 1 で出る（`search` = 本体なし /
  `get` = 本体あり）。[LV-24][lv] がどちらに確定しても、この対応は変わらない。
- Good: [RV-45][rv45] が閉じ、マトリクスの表 D から「理由の無い空白」が消える。
- Bad: **破壊的変更**。`search({ field: ["Content", …] })` はコンパイルエラーになり、
  実行時にも拒否される。本体を N 件取るコードは `get` を N 回呼ぶ形に書き換えが要る。
- Bad: 本体 N 件 = N リクエスト。1 分あたり Read 2000 の中では小さいが、月次のアクセス数
  （契約条件）は消費する。一覧 1 回で全部の本体が取れていた形は無くなる。
- Bad: 実行時ガードが 1 つ増える（[ADR-0064][0064] の `guardNoImageInBulk` と同じ形）。
- Neutral: `get` は常に本体を取る。メタデータだけ 1 件欲しいときは
  `search({ condition: { "Id:eq": "…" } })` で取れる。
- Neutral: マトリクスの表 B / 表 C は変わらない（送るパラメータ自体は同じで、`field` の
  中身が変わるだけ）。変わるのは表 D（`searchAll` の追加）。

## 信じている入力

`searchAll` はページを跨いで**応答の数値を信じ続ける**ので、その値も併せて洗い出す。

| 値                                      | 出どころ         | 誰が書けるか     | 守り方                                                       | 取れなかったら                             | 誤っていたら                                       |
| --------------------------------------- | ---------------- | ---------------- | ------------------------------------------------------------ | ------------------------------------------ | -------------------------------------------------- |
| ルート属性 `Total`                      | PORTERS の応答   | 第三者は書けない | 仕組み（`parseResourcePage` が数値化。非数値は 0）           | 0 として読む ＝ **1 ページで止まる**       | 空ページで止める既定があるので無限ループにならない |
| 1 ページの `items` 件数                 | PORTERS の応答   | 第三者は書けない | 仕組み（`paginate` は実際に返った件数だけ `start` を進める） | 0 件 ＝ 走査終了                           | 進まない／重複は `start >= total` で止まる         |
| 1 ファイルの大きさ                      | PORTERS の応答   | テナントの利用者 | **仕組み**（本体を運ぶのは単件だけ＝最大 10MB／出典）        | —                                          | 単件なら読める大きさに収まる                       |
| `field`（`Content` を含むか）           | 呼び出し側（人） | —                | **仕組み**（型から除外 ＋ 実行時ガード）                     | 省略 ＝ メタデータのみ（[ADR-0020][0020]） | キャストで渡されても実行時に止まる                 |
| 本体の取り方（`field` / `requestType`） | PORTERS の記事   | PORTERS 社       | 散文（[LV-24][lv]）。確定したら実装の書き方が変わる          | 未確認のまま＝**本体を運ばない側**         | 決定（メソッドで分ける）は確定しても変わらない     |

**「取れなかった」と「0 件」は別**という原則はここでも同じで、`Total` が読めないときに
「全部読み終えた」と解釈する形（＝黙って途中で止まる）は既に `paginate` の既定である。
本 ADR はその既定を変えない。

**サイズを表す項目が出典に無い**ことが軸2 の芯なので、そこが変わったら（PORTERS がサイズを
返すようになったら）前提を見直す。マトリクスの reference 突合が項目の増減を拾う。

## Pros and Cons of the Options

### 案1a（`searchAll` を足す）

- Good: 語彙が揃う。200 件を超える添付で `start` を手で回さなくてよくなる。
- Bad: 公開メソッドが 1 つ増える（テスト・ドキュメントも増える）。

### 案1b（足さない）

- Good: 記録が残り、[RV-45][rv45] は閉じる。実装の変更はゼロ。
- Bad: 「置けるのに置かない」理由が**本体を要求したときにしか成り立たない**。軸2 で本体を
  `get` に寄せるなら、走査は既定でメタデータだけになるので危険が無い。
- Bad: 使う側は結局 `start` を手で回す。ライブラリが引き受けるべき退屈さを押し返している。

### 案2a（本体は `get` だけ）

- Good: 1 回の Read の上限が設計で決まる。読めない応答を**作れない**。
- Good: 出典の `requestType` と公開 API が 1 対 1 で並ぶ。
- Bad: 破壊的変更。本体を N 件取るコードは N 回の `get` に書き換えが要る。

### 案2b（`searchAll` だけ禁止・`search` は運ぶ）

- Good: 何も壊さない。1 回で N 件の本体が取れる速さは残る。
- Bad: **守っているのは散文だけ**。踏んだときの症状（`RangeError` / OOM / 4 回の再送）は
  ライブラリの外で起き、原因がライブラリ側にあると分かりにくい。
- Bad: 「件数は呼び出し側が決められる」という前提が成り立たない（サイズが分からない）。

### 案2c（本体を要求したら件数を絞る）

- Good: 妥協点としては分かりやすい。1 回で数件の本体は取れる。
- Bad: **安全な件数を決められない**。10MB × 10 件は既に読めない（文字列上限）。
  サイズが分からない以上、どんな上限も「たいてい大丈夫」にしかならない。

### 案2d（応答サイズの上限ガード）

- Good: 本体以外の巨大応答にも効く一般的な守り。
- Bad: **手遅れになってから止まる** — 上限を測るには応答を文字列にする必要があり、
  その文字列化こそが `RangeError` の発生点。転送も既に終わっている。
- Neutral: 一般的な守りとしては別途検討に値する（本 ADR の対象外）。
