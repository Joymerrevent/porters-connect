# 92. 構築オプションと `tenant()` のオプションは、定義していないキーをすべて実行時に弾く

- Status: accepted
- Date: 2026-09-24
- Deciders: jun.shiromoto (Joymerrevent)
- Implemented: 0.25.0

> 起票元は stakeholder の指摘（2026-09-24）。API リファレンスの `PortersClientOptions` に、使えないことを示すための
> `auth?: never` と `fields?: never` が普通のオプションと並んで出ている。実行時の検査もこの 2 つの名前だけで、
> ほかの誤ったキーは黙って無視される。
>
> [ADR-0087][adr87]（追記 7: `PortersClientOptions.fields` を `never` で型付け）と [ADR-0091][adr91]
> （論点2 の帰結: `auth?: never`）の、型で弾く部分を**改める**。実行時に弾く考え方（[ADR-0048][adr48] の系列の
> fail-closed）は据え置き、弾く範囲を広げる。
>
> **decider が案1a ＋ 案2a ＋ 案3a ＋ 案4a を選択し `accepted`（2026-09-24）。** 実装は accept 後・別 PR。

## Context and Problem Statement

### いまの形

`src/client.ts` の `PortersClientOptions` は、廃止した 2 つのオプションを `never` の型で持っている。

| キー     | 型      | 実行時                                                            | 由来                     |
| -------- | ------- | ----------------------------------------------------------------- | ------------------------ |
| `fields` | `never` | 構築時に `PortersConfigError`（hint は `tenant(id, { fields })`） | [ADR-0087][adr87] 追記 7 |
| `auth`   | `never` | 構築時に `PortersConfigError`（hint は `tokenProvider`）          | [ADR-0091][adr91]        |
| それ以外 | —       | **黙って無視**                                                    | —                        |

`never` にしたのは、設定オブジェクトを変数に入れてから渡すとき（フレッシュでないオブジェクト）には TypeScript の
余分なプロパティの検査が掛からず、古いキーが型を通ってしまうため。

### 起きていること

1. **API リファレンスに、使えないオプションが並ぶ**。`never` の項目も TypeDoc は普通のプロパティとして出すので、
   `docs/usage/api/type-aliases/PortersClientOptions.md` に `auth?` と `fields?` が説明つきで載る。
   利用者は「このオプションは何か」と読んでしまう。説明は「もう使えない」という過去の版との違いで、
   利用者向けの本文に過去の版を書かない方針とも合わない。
2. **弾く範囲が名前 2 つに限られる**。`hostName`（大文字違い）・`timeout`（存在しない）・`partition`（`tenant()` に
   渡すもの）などは、構築が通って黙って無視される。設定の誤りを実行前に止める（[ADR-0048][adr48]・
   [ADR-0087][adr87] 追記 7 と同じ理由）なら、名前で列挙するより「定義していないキー」で止めるほうが漏れない。
3. **`tenant(id, options)` は何も検査しない**。変数に入れたオプションで `fields` を `feilds` と打ち間違えると、宣言が黙って捨てられ、カスタム項目が
   型にも実行時にも現れないまま動く（[ADR-0087][adr87] が塞いだ「宣言が黙って捨てられる」と同じ形）。

### 問い

オプションに定義していないキーが渡されたとき、型と実行時でどう扱うか。

## Decision Drivers

- **フェイルセーフ**: 設定の誤りは、黙って無視せず、PORTERS へ何かを送る前に止める。
- **利用者が読むものに、使えないものを載せない**: 型は「使えるもの」だけを表す。
- **漏れない仕組み**: 弾く対象を名前で列挙すると、次に廃止するキーや打ち間違いが漏れる。
- **型と実行時の一覧がずれない**: 許可するキーの一覧を手で二重に持たない。

## Considered Options

### 論点1: 型に `auth` / `fields` を `never` で残すか

- **案1a: 型から外す**（その場で書いたオブジェクトは TypeScript の余分なプロパティの検査で、変数から渡したものは実行時に止める）
- 案1b: 残す（いまの形）

### 論点2: 実行時に何を弾くか

- **案2a: 定義していないキーをすべて弾く**（値が `undefined` のキーは未指定と同じに扱う）
- 案2b: 廃止した名前だけを弾く（いまの形）
- 案2c: 弾かずに警告を出す

### 論点3: どのオプションに当てるか

- **案3a: `PortersClientOptions`（構築時）と `TenantOptions`（`tenant()` の呼び出し時）の両方**
- 案3b: `PortersClientOptions` だけ

### 論点4: 廃止した名前（`auth` / `fields`）を特別に案内するか

- **案4a: しない**（ほかの定義していないキーと同じメッセージで、使えるキーの一覧を示す）
- 案4b: この 2 つだけ、移行先を `hint` で示す

## Decision Outcome

採用: **案1a ＋ 案2a ＋ 案3a ＋ 案4a**（decider が 2026-09-24 に選択）。

### 決めること

- **型**: `PortersClientOptions` から `auth?: never` と `fields?: never` を外す。`TenantOptions` の型は変えない。
- **実行時**: `new PortersClient(options)` と `porters.tenant(id, options)` は、`options` の**自分のキー**
  （`Object.keys`）のうち、定義していないものが 1 つでもあれば `PortersConfigError`（`category: "config"`）を投げる。
  - 値が `undefined` のキーは未指定と同じ扱いで通す（設定をスプレッドで組み立てると混ざりやすいため。
    [ADR-0087][adr87] 追記 7 の「`fields: undefined` は未指定と同じ」を一般化する）。
  - メッセージに定義していないキーの名前を、`hint` に使えるキーの一覧を出す。
  - コンストラクタも `tenant()` も `Promise` を返さないので、どちらも同期で throw する
    （[ADR-0046][adr46] の「`Promise` を返さない API は同期 throw が正しい」）。
- **許可するキーの一覧**: 型のキーと過不足が無いことを型で確かめる形で 1 か所に置く
  （例: `{ hostname: true, … } satisfies Record<keyof PortersClientOptions, true>`）。型にオプションを足して
  一覧に足し忘れると、コンパイルが通らない。
- **範囲外**: 値の形の検査（`hostname` の書式、`tokenProvider` に `acquire` があるか、など）は変えない。
  入れ子のオブジェクト（`tokenStore` や `throttle` の中身）のキーは検査しない。

### 論点ごとの理由

- **案1a**: 型の役目は「使えるものを表す」こと。`never` の項目は API リファレンスと IDE の補完に「使えないもの」を
  出してしまう。その場で書いたオブジェクトなら、`never` が無くても TypeScript が余分なプロパティとして弾く。
  変数から渡した場合に型で止まらなくなる分は、案2a の実行時の検査が必ず止める（止まる時点が
  コンパイル時から構築時に移るだけで、PORTERS へ送る前であることは変わらない）。
- **案2a**: 弾く対象を名前で並べる形は、新しい誤り（打ち間違い・存在しないオプション・次に廃止するキー）を
  止められない。「定義していない」で止めれば、一覧を保守しなくても漏れない。案2c の警告は読み飛ばされ、
  誤った設定のまま動く（フェイルセーフに反する）。
- **案3a**: `tenant()` の `fields` の打ち間違いは、宣言が黙って捨てられる形で、[ADR-0087][adr87] が構築オプションの
  側で塞いだものと同じ。片方だけ止めると、同じ誤りが止まる場所と止まらない場所に分かれる。
- **案4a**: 利用者向けのエラーに過去の版の事情を持ち込まない。使えるキーの一覧があれば、`auth` を渡した人は
  `tokenProvider` に、`fields` を渡した人は `tenant()` の引数に辿り着ける。移行の案内は CHANGELOG の役目。

### Consequences

- Good: 打ち間違いや存在しないオプションが、構築時・`tenant()` の呼び出し時に必ず止まる。API リファレンスと IDE の
  補完から `auth` / `fields` が消える。許可するキーの一覧が型とずれない。
- Bad: **破壊的変更**。これまで通っていた「定義していないキーを含む設定オブジェクト」（例: アプリの設定を丸ごと
  `new PortersClient(config)` に渡している）は、構築時にエラーになる。使うキーだけを取り出して渡す必要がある。
- Bad: 変数から渡した `auth` / `fields` は、コンパイル時ではなく構築時に止まる（止まる時点が遅れる）。
- Neutral: 廃止したキーを渡したときのメッセージが、移行先を名指ししなくなる（使えるキーの一覧は示す）。

## 信じている入力

| 値                            | 出どころ       | 誰が書けるか | 守り方                                                      | 誤っていたら                             |
| ----------------------------- | -------------- | ------------ | ----------------------------------------------------------- | ---------------------------------------- |
| 構築オプションのキー          | 利用者のコード | 利用者       | 許可するキーの一覧と突き合わせる（値が `undefined` は除く） | `PortersConfigError`（構築時・同期）     |
| `tenant()` のオプションのキー | 利用者のコード | 利用者       | 同上                                                        | `PortersConfigError`（呼び出し時・同期） |
| 許可するキーの一覧            | このライブラリ | 保守者       | 型のキーと過不足が無いことを `satisfies` で確かめる         | コンパイルが通らない                     |

## Pros and Cons of the Options

- 案1a — Good: 型が使えるものだけを表す。Bad: 変数から渡した古いキーは構築時まで止まらない。
- 案1b — Good: 変数から渡した古いキーもコンパイル時に止まる。Bad: API リファレンスと補完に使えないキーが残る。
  廃止するたびに `never` の項目が増える。
- 案2a — Good: 名前を並べずに漏れなく止まる。Bad: 余分なキーを含む設定オブジェクトを渡していたコードが壊れる。
- 案2b — Good: 影響が小さい。Bad: 打ち間違いが黙って無視される。
- 案2c — Good: 壊さない。Bad: 誤った設定のまま動く。
- 案3a — Good: 同じ誤りが同じように止まる。Bad: `tenant()` にも検査が入る（呼び出しごとのキーの数え上げ。コストは小さい）。
- 案3b — Good: 変更が小さい。Bad: `tenant()` の打ち間違いが黙って捨てられたまま。
- 案4a — Good: エラーに過去の版の事情が入らない。Bad: 移行の案内はエラーからは直接得られない。
- 案4b — Good: 移行が 1 手で分かる。Bad: 廃止したキーの特別扱いがコードに残り続ける。
