# 49. `host` の書式検証で既定ポートを落とさない（[ADR-0048][adr48] 機構2 の改訂）

- Status: proposed
- Date: 2026-08-12
- Deciders: jun.shiromoto (Joymerrevent)

> [findings][findings] **RV-21** の是正案。[ADR-0048][adr48] を実装したところ、機構2 のラウンドトリップが
> **既定ポート付きの `host`（`a.test:443`）を通さない**ことが判明した。ADR-0048 自身の Decision Drivers
> 「**既存の正しい設定を壊さない**」と衝突するため、**判定機構だけを差し替えるか**を決める。
> 結論（案A〜C のどれか）は decider が選ぶ。

## Context and Problem Statement

[ADR-0048][adr48] は `host` の書式検証を **機構2＝`new URL()` ラウンドトリップ**で行うと決めた。
実装（`src/http/access-point.ts` の `validateAccessPoint`）は `https://{host}` をパースし、次の 3 つを要求する。

1. `new URL()` が成功する
2. `url.host` が入力の小文字化と一致する
3. `url.pathname` が `/` である

問題は **WHATWG URL がそのスキームの既定ポートを正規化で落とす**ことにある。
`new URL("https://a.test:443").host` は `a.test` を返すため、条件 2 が成立しない。
結果、**`:443` を書いた `host` だけが弾かれる**。実測（実装した `validateAccessPoint` を通した結果）:

| `scheme` | `host`                   | 結果         |
| -------- | ------------------------ | ------------ |
| （既定） | `xxxxx.example.com`      | OK           |
| （既定） | `xxxxx.example.com:8080` | OK           |
| （既定） | `xxxxx.example.com:80`   | OK           |
| （既定） | `xxxxx.example.com:443`  | **REJECTED** |
| `"http"` | `127.0.0.1:4010`         | OK           |
| `"http"` | `localhost:80`           | OK           |
| `"http"` | `localhost:443`          | **REJECTED** |

問題は 2 つある。

- **既存の設定が壊れる**: 現在正しく動作している `PORTERS_HOST=xxxxx.example.com:443` は、
  0.7.0 で**構築時に `PortersConfigError`** になる。ADR-0048 の driver「現在動いている設定
  （ホスト名・`host:port`）は 1 文字も変えずに通ること」を満たしていない。
- **説明できない形になっている**: 検証は `scheme` の設定に関わらず**常に `https://` でパース**するため、
  弾かれる集合は「**`scheme` を問わず `:443`**」になる。`scheme: "http"` にとって 443 は既定ポートではなく
  **意味のある指定**なのに弾かれる。利用者に説明するには「ポートは書いてよい。ただし 443 だけ書けない」と
  言うほかなく、**仕組みではなく文書で支える契約**になってしまっている（[ADR-0048][adr48] が案D を退けた理由と同じ性質）。

実害の大きさ自体は小さい（https で `:443` は冗長なので、消せば直る・エラーは構築時に hint 付きで出る）。
ただし**この挙動が 0.7.0 に載る**ため、出す前に決めておく価値がある。

問い: **既定ポートを落とさない判定へ改訂するか。改訂するなら、どの機構に置き換えるか。**

## Decision Drivers

- **既存の正しい設定を壊さない**（[ADR-0048][adr48] から引き継ぐ driver）: `host:port` は書き方を変えずに通ること。
- **フェイルセーフ**: 列挙に頼らず、**想定していない壊れ方も落ちる**こと。ADR-0048 が機構1（禁止パターンの列挙）より
  機構2 を採った理由をここでも崩さない。
- **説明可能性**: 契約が「ホスト（＋ポート）だけ」なら、**ポートの値によって可否が変わらない**のが素直。
  例外があるなら、それは文書ではなく仕組みの都合であってはならない。
- **薄さ**: URL の完全な正規化・IDN 変換を抱え込まない。「明らかな誤りを弾く」に留める。
- **タイミング**: 0.7.0 で**初めて**この検証が世に出る。**出す前に直せば「壊してから戻す」ことにならない**。

## Considered Options

- **案A: 現状維持**（`:443` は書かない）
  hint（「既定ポート (443) は省く」）・[エラーハンドリング ガイド][guide]の「既知の制限」で誘導済み。変更ゼロ。
- **案B: 既定ポートだけ特例で許容**
  条件 2 を「`url.host` が一致、**または** `url.port` が空で `url.hostname` ＋ `":443"` が入力と一致」に緩める。
- **案C: 既定ポートを持たないスキームでパースする**（推奨）
  `https://` の代わりに**独自スキーム**（例 `porters-check://`）を付けてパースする。
  WHATWG URL は**特殊スキーム以外の既定ポートを知らない**ため、**どのポートも落とさない**。
- **案D: 検証をやめる**（[ADR-0048][adr48] を revert）
  対称性のために挙げる。RV-17（資格情報が別ホストへ飛ぶ）が戻るため採らない。

## Decision Outcome

採用: **（未決定・議論用）案C を推奨**。

理由: 案C は**機構2 の性質（列挙に頼らないラウンドトリップ）をそのまま保ったまま**、既定ポートという
**パーサ都合の例外だけを消せる**。案B は「443 のときはこう」という**特例を 1 つ抱える**ことになり、
機構1（列挙）に一歩戻る。しかも `scheme: "http"` の `:443` は依然として別扱いが要る。
案A は動くが、「ポートは書いてよい。ただし 443 だけダメ」という**説明を利用者に負わせる**契約が残る。

**案C で通る／弾かれるもの**（`node` で実測。判定式は下記）:

| 通る                                                                                                                                                            | 弾かれる                                                                                                                                                                                                      |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `a.test` ／ `XXXXX.EXAMPLE.COM` ／ `a.test:443` ／ `a.test:80` ／ `a.test:8080` ／ `127.0.0.1:4010` ／ `localhost:4010` ／ `[::1]:4010` ／ `xn--eckwd4c7c.test` | `""` ／ `https://a.test` ／ `http://a.test` ／ `a.test/` ／ `a.test/gw` ／ `user@a.test` ／ `a test` ／ `//a.test` ／ `a.test?x=1` ／ `a.test#f` ／ `a.test\gw` ／ `日本語.test` ／ `a.test:` ／ `a.test:abc` |

案C を採る場合、**判定式は 3 箇所調整が要る**（実装前に合意しておく点）:

1. **比較は両側を小文字化**する。特殊スキームと違い、**非特殊スキームは host を小文字化しない**
   （`porters-check://XXXXX.EXAMPLE.COM` の `url.host` は大文字のまま）。
   現在通っている大文字ホストを落とさないため、`url.host.toLowerCase() === host.toLowerCase()` とする。
2. **空文字を明示的に弾く**。非特殊スキームは**空の authority を許す**（`porters-check://` はパースに成功し
   `url.host === ""`）。`host === ""` は RV-17 の実例（env 未設定を `!` で押し通した場合）なので、
   **1 行の非空チェックを足す**。ここだけは列挙に戻る＝案C の唯一のコスト。
3. **条件 3 は `pathname === "/"` から `pathname === ""` へ**。非特殊スキームでは裸のホストの `pathname` は空文字になる。
   なお [ADR-0048][adr48] の実装時、条件 3 は条件 2 に包含される（equivalent mutant）と分かっていたが、
   **案C では実際に効く**（`//a.test` と `a.test/` を落とすのはこの条件）。

**変わらないもの**: IDN の扱い（非 ASCII は percent-encoding されて往復しないため**引き続き punycode 必須**）、
`scheme` の検証、エラーの形（`PortersConfigError` ＋ hint）、検証の位置（`PortersClient` 構築時に 1 回）。
hint から「既定ポート (443) は省く」の一文が不要になる。

**semver**: **patch**。受け入れ入力を**広げるだけ**で、通っていたものが通らなくなることはない。

**リリースとの関係**: **0.7.0 の前に入れることを推奨**する。0.7.0 で初めてこの検証が公開されるため、
先に入れれば「今まで動いていた `:443` が 0.7.0 で壊れ、次の版で戻る」という**往復**を利用者に見せずに済む。
0.7.0 に間に合わせない判断なら、CHANGELOG の「弾かれる例」に `:443` を明記したまま出し、後続版で広げる
（その場合も破壊的ではない）。

### Consequences

- Good: **ポートの値によって可否が変わらない**。`host:port` は書き方を変えずに通る＝ADR-0048 の driver を満たす。
  「既知の制限」が 1 つ減り、hint とガイドが短くなる。
- Bad: パースに**独自スキーム名という見慣れない道具**を使う（`porters-check://`）。なぜそうするのかを
  コメントで説明する責任が生まれる。空文字チェックが 1 行増える。
- Neutral: 非特殊スキームは WHATWG の**特殊スキームとは別のパース規則**を通る。実測では、
  弾く／通す集合は**案A と `:443` の 1 点だけが違い**、他はすべて一致した
  （`a.test\gw` は案A ではパスとして分離されて弾かれ、案C ではパース自体が失敗して弾かれる＝結論は同じ）。
  馴染みの薄い規則に乗る以上、**テストで全件 pin する**ことが前提になる。

## Pros and Cons of the Options

### 案A: 現状維持

- Good: 変更ゼロ。仕様は単純（`https://` を付けてパースするだけ）。
- Good: `:443` は https では冗長なので、実害は「消せば直る」程度。
- Bad: **現在動いている設定が 0.7.0 で壊れる**（ADR-0048 の driver 違反）。
- Bad: 「ポートは書ける。ただし 443 だけダメ」を**文書で支える**ことになる。`scheme: "http"` の `:443` まで
  巻き添えで弾かれる理由は、利用者からは説明できない（実装の都合が漏れている）。

### 案B: 既定ポートだけ特例で許容

- Good: 差分が小さく、意図も読み取りやすい。
- Bad: **特例を 1 つ抱える**。機構2 を選んだ理由（列挙に頼らない）から一歩戻る。
- Bad: `scheme: "http"` の `:443` を通すには**さらに条件が要る**（http の既定は 80）。
  「どのスキームでパースしたか」に判定が依存し続ける。

### 案C: 既定ポートを持たないスキームでパース

- Good: **例外なくポートが保持される**。機構2 の性質（ラウンドトリップ 1 本）を保てる。
- Good: 判定が `scheme` の設定から独立する（何で組み立てるかと、書式が正しいかを分離できる）。
- Bad: 独自スキーム名がやや技巧的。空文字チェックを明示的に足す必要がある。
- Bad: 非特殊スキームのパース規則は特殊スキームより馴染みが薄く、**テストで固定しないと退行が読めない**。

### 案D: 検証をやめる

- Good: 「壊れる設定」が無くなる。
- Bad: RV-17 が戻る（資格情報が意図しないホストへ飛ぶ／設定ミスが `network` として無限リトライ）。
  [ADR-0048][adr48] の決定を捨てることになり、フェイルセーフに反する。
