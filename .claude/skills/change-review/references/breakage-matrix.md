# 入力 × 壊れ方のマトリクス、およびバグクラス一覧

「その場で気づいたことを書く」レビューは、気づかなかったものを取りこぼす。ここは**気づきに頼らずに当てる表**。§1〜§2 が総当たりの枠、§3〜§4 が過去に実際に出たバグクラスの一覧（そのままチェックリストとして使う）。

---

## 1. 信じている入力の棚卸し

まず「このコードが正しいと信じて受け取っているもの」を全部書き出す。**書き出せていない入力は、検証もされない。**

**1 行 = 1 つの値**に割る。「レポートの機械可読 3 行」のようにまとめて 1 行に数えると、**その中で検証済みの値と未検証の値が混在していることが表に現れない**。下は実例で、3 行目だけが空欄になる:

| # | 値 | 出どころ | 誰が書けるか | 事実と突き合わせているか | 失敗時にコードはどう振る舞う |
| --- | --- | --- | --- | --- | --- |
| 1 | 判定の指紋 | LLM が書いた本文 | Issue を編集できる人 | 済 — gate が渡す `EXPECTED_FINGERPRINT` と比較 | 不一致なら投稿前に落ちる |
| 2 | 取り込み対象の head SHA | LLM が書いた本文 | 同上 | 済 — gate が渡す `EXPECTED_PR_HEADS` と比較 | 不一致なら投稿前に落ちる |
| 3 | 検査時刻 | LLM が書いた本文 | 同上 | **未 — 形式しか見ていない** | 未来の値だと 3 日ルールが無言で永久に効かない |

列の意味:

- **出どころ** — 人が手で書くのか、別ジョブから渡るのか、外部 API か、リポジトリ設定か。
- **誰が書けるか** — public リポジトリなら Issue もタイトルもラベルも第三者が作れる。**「自分たちしか書かない」は前提として弱い。**
- **事実と突き合わせているか** — **形式の検証と、事実との突き合わせは別物**。正規表現を通っただけの値は「読める形をしている」ことしか保証しない。ここに ✅ を書くときは**何と突き合わせているか**まで書く。書けないなら ❌。
  **同じ経路の値が並んだとき、一部だけ ✅ になっていたらそれが指摘**である（上の表がまさにその形で、この列が無かったせいで 1 回目のレビューで 3 行目を取りこぼした）。
- **失敗時にコードはどう振る舞う** — ここが空欄なら、それは**まだ確かめていない**ということ。

種類の目安:

- 人 / LLM が書いた文書の機械可読行（検査時刻・指紋・対象リスト）
- 別ジョブ・別ステップから渡ってくる事実
- 外部コマンドの出力（`gh api` の JSON、`git` の終了ステータス）
- イベントペイロード（コメント本文、Issue 本文、ラベル、作者）
- リポジトリ / 環境の設定（branch protection、`dependabot.yml`、ラベルの存在、環境変数）
- HTTP レスポンス（ステータス、ボディの形）と、そのパース結果
- 利用者が渡す設定・引数・テナント固有のフィールド定義

## 2. 当てる壊れ方

§1 の各行に、下記 7 つを順に当てる。**「当てた」と言えるのは、実行して確かめたときだけ**（[verification-recipes.md][recipes]）。

| 壊れ方 | 問う内容 |
| --- | --- |
| **欠落** | 空だったら？ 取得に失敗したら？ → **空を「問題なし」と読んでいないか**（取得失敗と 0 件を区別できているか） |
| **不正** | 形式が崩れたら？ 大文字 / 全角 / CRLF / 前後の空白は？ |
| **重複** | 2 本あったら？ 読む側が 1 本目しか見ないなら、書く側は 1 本だけを許すべきでは？ |
| **古い** | 前回見た時点と今で変わっていたら？ **その事実は誰がいつ見たものか** |
| **敵対的** | 第三者が同じものを作れるか。作れるとして、何が起きるか |
| **権限** | その主体は本当にそれを**できない状態**か。散文の禁止ではなく、トークンの権限やガードで不可能か |
| **設定変更** | 前提（必須チェック、protection、ラベル、環境変数）が変わったら、**黙って通る**ようにならないか |
| **自己申告** | その値を**事実と突き合わせたか**。形式が正しいことと内容が正しいことは別で、正規表現を通った値は「読める形をしている」ことしか保証しない。**同じ経路の値のうち一部だけ突き合わせている**状態になっていないか |

**「欠落」が最も多く、最も重い。** 空リスト・取得失敗・読めない行を「該当なし＝問題なし」と読む形は、テストが緑のまま本番で保護だけが消える。

## 3. バグクラス — シェル / GitHub Actions

前回のレビューで実際に出たもの。

- **空出力を成功と読む** — `x=$(cmd); [ -z "${x}" ]` を「該当なし」として扱う。取得失敗と区別できているか。「PR は必ず 1 ファイル以上変える」のような**不変条件で殴る**。
- **`$var` の直後に全角文字** — bash が `）` を変数名に吸う。`set -u` で即死し、しかも**異常を報告する行に出やすい**＝報告せずに死ぬ。`${var}` で括る。検査は `.sh` だけでなく**ワークフローの `run:`** も対象（`pnpm check:shell`）。
- **CRLF** — GitHub Web UI 由来のコメント / Issue 本文は CRLF。`head -1` の末尾に `\r` が残り、見た目は正しい数字なのに正規表現が弾く。
- **`grep -m1` と重複** — 読む側が 1 本目しか見ないなら、書く側は**2 本目の存在を検出して落とす**。
- **クォートなしの単語分割** — `for t in ${args}` は glob 展開もされる。`set -f` を検討。
- **`local` 宣言漏れ** — 関数の作業変数が漏れると「前回の値が残る」事故の土台になる。
- **bash 3.2（macOS 既定）** — 連想配列 `declare -A` が無い。ローカル実行を想定するなら並列の添字配列で書く。
- **2 箇所の真実** — ワークフローの `if:` は式なのでシェル定数を参照できない。構造的に消せない重複は、**両側にコメントで相手を指す**。
- **`if:` で落ちた job は無言** — リアクションもコメントも返らず、押した人には沈黙に見える。起動条件を厳しくするときは、この副作用を報告に書く。
- **GitHub の状態語を鵜呑みにする** — `mergeable_state=clean` は**必須チェックだけ**を見る。必須設定が変われば CI ゼロでも clean。**設定に依存しない条件**（全チェックの結論が出ている）を自分で持つ。
- **`gh api --paginate` と `-q`** — フィルタは**ページごとに**適用される。`length` のような集約は壊れる（行単位で出して後でまとめる）。
- **jq のフィールド有無に賭ける** — `select(.author.is_bot)` はフィールドが無いと**常に偽**。外れると「毎回新規作成」のような増殖系の事故になる。代替キーも見る。
- **commitlint / hooks** — 件名の先頭大文字は弾かれる（日本語件名でも `CI:` などは NG）。pre-commit（lint-staged）は**絶対パス**を渡すので markdownlint の `ignores` を迂回する。

## 4. バグクラス — TypeScript / このライブラリ

`docs/reviews/findings.md` に載っている確定済み指摘から、**繰り返し出た型**を抜いたもの。括弧内は実際の指摘 ID（本体は `docs/reviews/rv/`）。

### 4.1 静かに通る（fail-open）

- **HTTP ステータスを見ない** — ボディだけ見て成功と判定する（RV-13・RV-19）。200 以外が「空の結果」に化けていないか。
- **200 ＋ 想定外ボディを「空ページ」として通す** — プロキシやログイン画面の HTML が 0 件の検索結果に化ける（RV-20）。**「PORTERS のレスポンスである」ことを確かめているか。**
- **ルートのエラーコードを読まない** — Write のルート `<Code>` を見ないと、失敗が成功として返る（RV-14）。
- **設定ミスが黙って通る** — `host` の書式を検証せず別ホストへ実リクエストする（RV-17）、`partition` 未設定で無言のうちに `partition=0` を送る（RV-25）。**設定の誤りは、実行前に落ちるのが安全側。**
- **送信前ガードの非対称** — 片方の経路にだけ長さ / 件数 / 範囲の検査がある（RV-5・RV-28）。**同じ制約を守るべき経路が全部通っているか。**
- **空配列 / `undefined` を「該当なし」と読む** — 通信失敗・パース失敗と 0 件を区別しているか（§2 の「欠落」の TypeScript 版）。
- **`catch` で握って既定値を返す** — 失敗が呼び出し側に伝わらない。`?.` の連鎖で `undefined` が下流へ流れるのも同じ形。

### 4.2 API 忠実性 / 型

- **静的カタログの取りこぼし** — 標準項目の欠落は型で気づけない（RV-23）。`docs/reference/` との突合は自動化されているか（RV-29）。
- **要求した情報が途中で捨てられる** — 参照を展開して要求しても ID 以外が落ちる（RV-31）。**要求 → 送信 → パース → 返却**のどこで落ちるかを追う。
- **公開サーフェスの穴** — ジェネリクスの制約型が未 export で、利用者が型を書けない（RV-30）。JSDoc が実装と違うことを言っていないか（RV-10）。
- **XML パーサの揺れ** — 要素が 1 件のとき配列にならない形。単数 / 複数の両方の fixture があるか。
- **日時** — `Z` 無しの文字列を `Date` に食わせるとローカル解釈になる。正規化は `util/datetime.ts` に集約されているか（CLAUDE.md）。

### 4.3 テストの厳密性

- **モックが本番より甘い** — 未モック時に既定 200 を返すような mock は、**本番の壊れ方を再現しない**（RV-6）。
- **fixture が本番と乖離** — 実データを見ずに書いた fixture は、テストが緑でも保証が無い（RV-2）。
- **反復中の状態変更** — クエリを反復中に書き換えると次ページ以降が変わる（RV-32）。イテレータは入力のスナップショットを取っているか。

### 4.4 ドキュメント / プロセス

- **ライブラリの保証を過大に書く** — 内蔵スロットルが月次クォータを守るかのような記述（RV-16）。**守れないものを守ると書かない。**
- **文書が実装より先に進む** — accepted 済み ADR の実装が roadmap に現れない（RV-18）、機能にガイドが無い（RV-24・RV-27）。
- **保護ルールをバイパスする経路** — back-merge が develop の保護を迂回する（RV-33）。**通してよい経路が、通してはいけない経路も開けていないか。**
