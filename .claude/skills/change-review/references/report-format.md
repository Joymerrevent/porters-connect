# 報告フォーマット

レビュー結果は、**読んだ人が同じ判断を再現できる形**で出す。「何を指摘したか」より「**その指摘をどこまで確かめたか**」が伝わることが重要で、ここが曖昧だと誤った断定がそのまま修正へ流れ込む（§3 に実例）。

---

## 1. 出力の構成

```markdown
## レビュー結果 — <ブランチ / PR> （基点: develop）

<1〜3 文。通してよいか、ブロッカーが何件か、何を実行して確かめたか>

### 信じている入力

<breakage-matrix.md §1 の表をそのまま貼る>

### 実行した検証

| # | やったこと | 結果 |
| --- | --- | --- |
| 1 | 偽 gh で issue list を 空 / 1 件 / is_bot 欠落 の 3 通り | 欠落時に毎回新規作成される |

### 指摘

<§2 の書式で、重要度の高い順>

### 収束判定

<§4>

### 未検証の前提

<本番でしか確かめられないものを列挙>

### トレードオフ

<§5。無ければ「なし」と書く>
```

品質ゲート（`typecheck` / `lint` / `test` / `build` など）が落ちているなら、**他のどの指摘よりも先に**書く。

## 2. 指摘 1 件の書式

```markdown
#### 🔴 1. レポート行が読めないと 3 日ルールが無言で無効化される

- 重要度: 🔴 High ／ 観点: フェイルセーフ ／ 証拠: **実行済み**
- 場所: `scripts/dependabot-triage-gate.sh:120`

**失敗シナリオ**: レポートの `- 検査時刻:` 行が壊れる（LLM が書式を変える / CRLF が混じる）と、
`date` が空を返し、比較が偽になって「3 日経過していない」と判定されない。
結果、cooldown を満たしていない PR がそのまま取り込み対象に載る。

**根拠**: 偽の Issue 本文 4 通り（正常 / 行なし / CRLF / 全角コロン）で gate を実行し、
後ろ 3 つで判定が素通りすることを確認した。`docs/adr/0065-...md` は
「熟成期間で守る」と決めているので、決定と実装が食い違っている。

**推奨**: 行が読めなかったときは**取り込み対象を空にして落とす**（安全側）。
挙動変更を伴うので ADR 追記が要るなら明記する。
```

必ず入れるもの:

- **重要度** — 🔴 High（通してはいけない）／ 🟡 Medium（通す前に直したい）／ 🟢 Low（あとでよい）。`docs/reviews/findings.md` の凡例に合わせる。
- **失敗シナリオ** — 「**どんな入力・状態で、何が起きるか**」。抽象的な懸念（「堅牢性が低い」）ではなく、具体的な発火条件を書く。書けないなら、それはまだ指摘になっていない。
- **証拠レベル**（§3）。
- **根拠** — `file:line` と、正典（ADR / `docs/design/` / `docs/reference/`）の該当箇所を**対にして**書く。実行したなら、入力と結果も。

## 3. 証拠レベル（必須）

各指摘に、次のいずれかを明示する。

| レベル | 意味 | 書き方の例 |
| --- | --- | --- |
| **実行済み** | 実際に動かして確認した | 「偽 gh で 7 通り確認」「使い捨て repo で 3 系統確認」 |
| **読んだだけ** | コードを読んでの判断。動かしていない | 「コードを読む限り」 |
| **未検証の前提** | 本番でしか確かめられない | 「本番の初回実行でしか分からない」 |

**なぜ必須か。** 前回のレビューで、`templates/report.md` の `<!-- markdownlint-disable-file MD041 -->` を「不要」と断定して削除した。根拠は手元の実験だったが、その実験は**本番と違う起動の形**（相対パス）で走らせていたため 0 issues になっていた。証拠レベルを「実行済み」と曖昧に扱った結果、**間違った確信がそのまま修正になり、コミットが弾かれた**。

逆に、最後の 2 ラウンドで信頼が戻ったのは、指摘ごとに「これは動かして確かめた / これは読んだだけ」を分けて書いたから。**分けて書けば、読む側が重みを自分で決められる。**

「実行済み」と書くときは、その実行が**本番と同じ起動の形か**を一度確かめる（[verification-recipes.md][recipes] §5）。

## 4. 収束判定

次を**全部**満たしたときだけ、「これ以上はコードから出ない」と言ってよい。

- [ ] 棚卸しした入力**すべて**に、7 つの壊れ方を当てた
- [ ] 当てた結果を**実行で**確かめた（読んだだけの入力が残っていない）
- [ ] **列挙した経路をすべて通した**（ループの 0 / 1 / 2 件以上、打ち切り、上限、dry-run と本番の分岐）
- [ ] **自分が書いた修正にも同じ手順を通した**
- [ ] 残るのは「本番でしか確かめられない前提」だけで、それを列挙した

書き方:

```markdown
### 収束判定

**収束**。信じている入力 6 件すべてに 7 つの壊れ方を当て、うち 5 件は実行で確認した
（残り 1 件は §未検証の前提）。今回入れた修正 3 件にも同じ手順を通し、新規の指摘は出なかった。
```

満たしていないなら、**満たしていないと書く**。

```markdown
### 収束判定

**未収束**。入力 #4（branch protection の設定）に「設定変更」の壊れ方を当てていない。
`gh api` で必須チェックの実体を見れば確かめられるが、今回は未実施。
```

「たぶん大丈夫」で終わらせない。**未了を書く方が、収束を偽るより安い。**

## 5. やりすぎの明示（トレードオフ）

厳格化にはコストがある。前回入れた検証は、崩れたレポートを投稿前に落とすので、**その日のレポートが出なくなる**（自己回復はするが 1 日遅れる）。

**安全側だが利便性を削る**変更は、そのトレードオフを必ず報告に書く。書かずに入れると、後日「なぜ動かないのか」が分からなくなり、**安全装置の方が外される**。

## 6. 台帳（`docs/reviews/`）との関係

このスキルの報告は**その変更に閉じた**もので、既定では会話（または PR コメント）に出す。台帳には**上げない**。

ただし、指摘が「この変更の問題」ではなく**プロダクトの継続的な課題**だと分かった場合は、project-review の台帳へ回す:

- コードで直せる継続課題 → `docs/reviews/findings.md` ＋ `docs/reviews/rv/NNNN-*.md` に起票（**索引に行を足さないと `pnpm check:index` が落ちる**）。
- 契約環境が無いと断定できない PORTERS の挙動 → `docs/live-verification.md` の LV エントリへ。コード側に `VERIFY(live)` コメントを置く。

判断に迷う重さの仕様変更を推奨するときは、**「要 ADR」と明記する**（決定を勝手に確定させない）。
