# 対象: TypeScript（ライブラリ本体）

`src/` と `test/`。このライブラリの存在理由は PORTERS 固有の罠（XML / 独自 OAuth / UTC / 削除 API 無し / リクエスト長 / レート制限 / ホスト非公開）を正しく隠すことなので、**API 忠実性が最重要観点**になる。

## 1. 信じている入力

- HTTP レスポンス（ステータス、ボディの形）と、そのパース結果
- XML の構造（要素が 1 件のときの形、入れ子、属性）
- 利用者が渡す設定・引数（`host`・`partition`・`field`・`count`）
- テナント固有のフィールド定義（`U_` / `A_`）
- `docs/reference` の記述（カタログの正典）
- fixture（テストが信じている「本番の形」）

## 2. バグクラス

`docs/reviews/findings.md` の確定済み指摘から、**繰り返し出た型**を抜いたもの。括弧内は指摘 ID（本体は `docs/reviews/rv/`）。

### 静かに通る（fail-open）

- **HTTP ステータスを見ない** — ボディだけ見て成功と判定する（RV-13・RV-19）。200 以外が「空の結果」に化けていないか。
- **200 ＋ 想定外ボディを「空ページ」として通す** — プロキシやログイン画面の HTML が 0 件の検索結果に化ける（RV-20）。**「PORTERS のレスポンスである」ことを確かめているか。**
- **ルートのエラーコードを読まない** — Write のルート `<Code>` を見ないと、失敗が成功として返る（RV-14）。
- **設定ミスが黙って通る** — `host` の書式を検証せず別ホストへ実リクエストする（RV-17）、`partition` 未設定で無言のうちに `partition=0` を送る（RV-25）。**設定の誤りは実行前に落ちるのが安全側。**
- **送信前ガードの非対称** — 片方の経路にだけ長さ / 件数 / 範囲の検査がある（RV-5・RV-28）。**同じ制約を守るべき経路が全部通っているか。**
- **空配列 / `undefined` を「該当なし」と読む** — 通信失敗・パース失敗と 0 件を区別しているか。
- **`catch` で握って既定値を返す** — 失敗が呼び出し側に伝わらない。`?.` の連鎖で `undefined` が下流へ流れるのも同じ形。

### API 忠実性 / 型

- **静的カタログの取りこぼし** — 標準項目の欠落は型で気づけない（RV-23）。`docs/reference/` との突合は自動化されているか（RV-29）。
- **要求した情報が途中で捨てられる** — 参照を展開して要求しても ID 以外が落ちる（RV-31）。**要求 → 送信 → パース → 返却**のどこで落ちるかを追う。
- **公開サーフェスの穴** — ジェネリクスの制約型が未 export で利用者が型を書けない（RV-30）。JSDoc が実装と違うことを言っていないか（RV-10）。
- **XML パーサの揺れ** — 要素が 1 件のとき配列にならない形。単数 / 複数の両方の fixture があるか。
- **日時** — `Z` 無しの文字列を `Date` に食わせるとローカル解釈になる。正規化は `util/datetime.ts` に集約されているか。

### テストの厳密性

- **モックが本番より甘い** — 未モック時に既定 200 を返すような mock は**本番の壊れ方を再現しない**（RV-6）。
- **fixture が本番と乖離** — 実データを見ずに書いた fixture は、テストが緑でも保証が無い（RV-2）。
- **反復中の状態変更** — クエリを反復中に書き換えると次ページ以降が変わる（RV-32）。イテレータは入力のスナップショットを取っているか。

### ドキュメント / プロセス

- **ライブラリの保証を過大に書く** — 内蔵スロットルが月次クォータを守るかのような記述（RV-16）。**守れないものを守ると書かない。**
- **文書が実装より先に進む** — accepted 済み ADR の実装が roadmap に現れない（RV-18）、機能にガイドが無い（RV-24・RV-27）。
- **保護ルールをバイパスする経路** — back-merge が develop の保護を迂回する（RV-33）。

## 3. 当て方

| 狙い | TypeScript での具体手 |
| --- | --- |
| 1 純粋な部分を総当たり | `it.each` で受理 / 棄却の表を流す。**検証がそのまま回帰テストとして残る**ので、この形が最良 |
| 2 外部を偽物に | mock transport / fixture。**未モックの経路が既定 200 を返さない**ことを確かめる（RV-6） |
| 3 使い捨てのデータ | fixture を実データから起こす。手で書いた fixture は本番と乖離する（RV-2） |
| 4 本物の読み取り専用実行 | `pnpm test:coverage`（per-file 100%・ADR-0014）。**落ちた行ではなく、通っていない行**を見る |
| 5 本番と同じ起動の形 | 公開 API から呼ぶ。内部関数を直接叩くと、既定値の適用や alias の prefix 付与といった**公開サーフェス側の組み立てを飛ばして**通ってしまう |

TypeScript にしかない当て方が 3 つある。

- **型定義まで降りる。** 「型が過剰約束していないか」は実装ではなく型が決める。`ReadRecord<F> = { [K in keyof F]?: … }` のように**全項目が optional**なら、返らない項目があっても型は嘘をついていない。実装だけ読んで「過剰約束だ」と書くと外す（実際に外した）。
- **`as` を数える。** 差分中の型アサーションは 1 つずつ健全性を確かめる。`Object.keys()` を alias の union へ狭める程度なら健全だが、**なぜ必要かを説明できないアサーション**は型検査を黙らせている。
- **正典との突合をテストにする。** `docs/reference` とカタログのズレは実行では出ない（どちらも「正しく」動くから）。突合そのものをテストに書けば、reference を更新したときに落ちる（RV-29）。

**未確認の前提は `docs/live-verification.md` に登録されているかを見る。** 契約環境が無いと確かめられない挙動に依存すること自体は defect ではない。見るべきは「登録されているか」「**外れたときの是正手順が書いてあるか**」で、両方あれば受容済みのリスクとして扱う。

## 4. 道具と落とし穴

- **`pnpm exec vitest run <path>`** — 対象ファイルだけ回す。`--reporter=basic` は vitest 4 で使えない（指定するとエラーになる）。
- **`pnpm test:coverage`** — カバレッジは `src/**/*.ts` のみ対象。`scripts/*.test.mjs` は**既定の include で拾われて実行される**が、カバレッジには入らない。
- **per-file 100% の閾値**（statements / functions / lines、branches は 90%）があるので、**新しい分岐を足したらテストも要る**。緑になった時点でそこは通っている。
- **`pnpm typecheck` は `tsc --noEmit && tsc -p test`** — テスト側の型も見る。
- **`test/fake/serve.ts`（`pnpm fake:serve`）** — 実 HTTP を通した確認に使える。

## 5. まだ当てていないこと

- 使った実績は `feat/d2-master-read-fields`（User マスタの項目追加）の 1 ブランチのみ。**指摘は 0 件**で、これはスキルの力だけでなく対象の質（既定 field の完全一致検証・decode 検証・突合テストがある）を反映している。
- **Write 系・OAuth・スロットリング・エラーモデルの変更には当てていない。**バグクラスは台帳から抜いたので根拠はあるが、レビューで使った結果ではない。
- 上の 5 手のうち、実際に使ったのは 1（テストを読む）・4（coverage）・5（公開 API 経由）と「型定義まで降りる」「`as` を数える」「突合テスト」。**2（mock transport を自分で組む）と 3（fixture を実データから起こす）は未使用。**
