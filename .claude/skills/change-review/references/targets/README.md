# 対象別ファイル

レビュー対象の**種類ごとの知識**をここに置く。汎用の枠（手順・入力と経路の棚卸し・7 つの壊れ方・検証の狙い・報告様式）は上位のファイルが持ち、ここは「その対象では具体的にどう当てるか」だけを持つ。

分けている理由は 2 つ。**対象が増えたときに 1 ファイル足すだけで済む**こと、そして**汎用のつもりで特定対象の前提を書いてしまう事故を防ぐ**こと。実際、分ける前の `verification-recipes.md` は「5 つの汎用パターン」と称しながら中身が全部シェル前提で、TypeScript に当てようとして初めてどれも当てはまらないと分かった。

## 現在ある対象

| ファイル | 対象 |
| --- | --- |
| [shell-ci.md][shell] | シェルスクリプト、GitHub Actions ワークフロー |
| [typescript.md][ts] | TypeScript（このライブラリ本体） |

変更が複数の対象にまたがる PR では、**該当するものを全部開く**。

## 対象を足すときの形

新しいファイルは次の 5 節をこの順で持つ。**節を減らさない。**空なら「まだ無い」と書く — 空欄だと「調べて無かった」のか「調べていない」のか区別できない。

### 1. 信じている入力

その対象で典型的に「正しいと信じて受け取っているもの」の種類。棚卸し表（[breakage-matrix.md][matrix] §1）を埋めるときの目安になる。

### 2. バグクラス

**実際に出たもの**を書く。想像で書かない。出典（指摘 ID・コミット・実例）を添える。並べる順は「静かに通る（fail-open）」を先頭にする — このプロジェクトで最も重い型だから。

### 3. 当て方

[verification-recipes.md][recipes] の 5 つの狙いに対して、この対象での具体手を書く。**5 つ全部に触れる。**当てはまらないものは「当てはまらない」と書く（黙って飛ばすと、次の人が探し直す）。

### 4. 道具と落とし穴

その対象を検証するときに使えるコマンド・ライブラリと、環境差（バージョン・OS・CI との違い）。

### 5. まだ当てていないこと

**この節が一番重要。**その対象で使った実績がどこまでかを正直に書く。1 ブランチでしか使っていないなら、そう書く。ここが空のファイルは「完成した」ではなく「棚卸ししていない」と読む。

## 書かないこと

- **汎用の枠を書き写さない。**7 つの壊れ方や証拠レベルは上位のファイルが正典で、ここに複製すると片方だけ更新されて食い違う。参照する。
- **その対象に固有でないこと。**「テストを書く」「コメントを読む」のような、どの対象でも同じことは上位に属する。
