# 変更レビュー — 収束するまでの手順

## このスキルが解く問題

2026-09-05、`ci/dependabot-triage-automation`（シェル 4 本 ＋ ワークフロー 2 本）を **4 ラウンドかけてレビューし、毎回新しい指摘が出た**。ユーザーの言葉:

> レビューするたびに新しい問題がでるのではレビューの意味がありません。

記録を分析すると、**R2 以降の指摘のほとんどはレビュアー自身が書いた修正から出ていた**。つまり収束しなかった主因は元の実装の質ではなく、**レビューと修正のループ設計**にある。もう一つの相関ははっきりしていて、**実際にコードを動かした回だけ新しい種類の指摘が出た**。読むだけのレビューは、書いてあることの誤りは拾えても、**書いていないこと**（検証していない行、確かめていない事実、区別していない失敗理由）には構造的に届かない。

このスキルは、その 2 つを手順で潰す。

## 4 つの原則

1. **決定的な検証を先に払う。** 安いレビュー（読む）を何度も回さない。実行・実データで確かめる検証を、読むより**先に**やる。往復回数が減り、重い指摘が最初のラウンドで出る。
2. **「静かに通る」を観点として明示的に当てる。** このプロジェクトの哲学はフェイルセーフ（壊れたときに安全側へ倒れる）。**壊れることより、黙って通ることの方が重い**。その場の気づきに任せず、[breakage-matrix.md][matrix] を機械的に当てる。
3. **証拠レベルを必ず添える。** 実行済み / 読んだだけ / 未検証の前提。曖昧な断定は、そのまま誤った修正へ流れ込む（実例は [report-format.md][fmt] §3）。
4. **修正は新しいコード。** 修正したら同じ手順を通し直す。通し直せないなら修正しない（診断だけ返す）。

## 実行フロー

### 1. 接地 — 何を見るのか決める

```sh
git status
git log --oneline develop..HEAD
git diff --stat develop...HEAD
```

- 比較基点は既定で `develop`（このリポジトリの開発本流）。リリース系なら `main`。
- **正典を引く**: 関係する ADR（[docs/adr/index.md][adrindex]）、`docs/design/`、`docs/reference/`、`CLAUDE.md`。判断は記憶や一般論ではなく、ここに接地させる。
- **ADR の決定と実装が食い違っていないかを最初に見る。** 文書やプロンプトが主張している性質（「〜の権限は渡していない」「〜で守られる」）が**事実か**を確かめる。前回のレビューで実際に出た指摘がこの型だった。
- 変更の種類を判定し、当てる観点表を選ぶ（両方混ざる PR なら両方）:
  - シェル / GitHub Actions → [breakage-matrix.md][matrix] §3
  - TypeScript（ライブラリ本体） → [breakage-matrix.md][matrix] §4

### 2. 入力の棚卸し

**このコードが信じている入力**を列挙して表にする（テンプレは [breakage-matrix.md][matrix] §1）。ここを飛ばすと「無いもの」が見えない。

例（シェル / CI の場合）: 人や LLM が書いた文書の機械可読行、別ジョブから渡る事実、外部コマンドの出力、イベントペイロード、リポジトリ設定（branch protection・ラベルの存在）。
例（TypeScript の場合）: HTTP レスポンス（ステータス・ボディ）、XML パース結果、利用者が渡す設定と引数、環境変数、テナント固有のフィールド定義。

作った表はそのまま報告に貼る。**この表が、後で収束を宣言するときの検査対象一覧になる。**

### 3. 決定的な検証を先に払う — 読む前にやる

[verification-recipes.md][recipes] の 5 パターンから、対象に当たるものを**実際に走らせる**。

1. 純粋な部分を切り出して総当たり（正規表現・パーサ・純関数）
2. 外部コマンドを偽物に差し替える（`PATH` 先頭に偽 `gh` を置く）
3. 使い捨てのリポジトリ / データを作る（git の意味論は実物で確かめる）
4. 本物の読み取り専用実行（**冪等性** ＝ 2 回走らせて出力が一致するかもここで取る）
5. **本番と同じ起動の形**で確かめる（引数が絶対パスか相対パスかで結論が反転した実例あり）

あわせて **実データで前提を潰す**。「一般に dependabot は force-push するか」ではなく「**この repo で実際に何回あったか**」を `gh api` で見る。コマンド集は [verification-recipes.md][recipes] §6。

各コミットが単独で緑かは、これで機械的に確かめる:

```sh
bash .claude/skills/change-review/scripts/per-commit-gates.sh
```

### 4. 読む — 実行で出ない種類だけ

実行では出ないのはこの系統。ここに絞って読む。

- **2 箇所にある同じ真実**（片方だけ直すと無言で壊れる）。構造的に消せない重複なら、**両側にコメントで相手を指しているか**。
- **コメント / ドキュメントと実装の乖離**、および ADR の決定との乖離。
- **失敗の理由が事実と違う**（落ちたときに間違った理由が記録される）。
- **権限設計** — 「やらないこと」をプロンプトや散文で禁じているだけか、**トークンの権限や機械的なガード**で不可能にしているか。
- **沈黙する経路** — `if:` で落ちた job、早期 return、握り潰した catch。押した人・呼んだ人に何が見えるか。

### 5. 報告

[report-format.md][fmt] の様式で出す。指摘ごとに **重要度 / 失敗シナリオ / 証拠レベル**、末尾に **収束判定** と **やりすぎのトレードオフ**。

### 6. 修正したら 2〜5 を通し直す

**ここを省いたのが前回の最大の失敗。**

- 既定は**診断まで**（勝手に直さない）。
- 修正を求められた場合、**修正後に同じ手順を通すところまでがワンセット**。「直したばかり」のコードは心理的に甘く見るので、手順で強制する。
- 通し直す対象は修正の diff だが、**修正が触れた入力は §2 の棚卸しからやり直す**（入力が増減していることがある）。
- 再レビューを通す時間が無いなら、**修正しないで診断だけ返す**方が安全。

### 7. 収束判定

次を**全部**満たすまで「これ以上は出ない」と言わない。

- §2 で棚卸しした入力**すべて**に §3 の壊れ方を当て、**実行で**確かめた
- **修正コードにも同じ手順を通した**
- 残っているのは「本番でしか確かめられない前提」だけで、それを**列挙している**

満たしたら明言する。満たさないなら、**何が未了か**を書いて終わる（曖昧に終わらせない）。

## やらないこと

- **勝手に修正しない。** 既定は診断と記録まで。修正するなら §6 まで通す。
- **一般知識で前提を決めない。** API で見られる事実は見る。
- **証拠のない断定をしない。** 実験したなら、その実験が**本番と同じ形か**を確かめてから断定する。
- **安いレビューを何度も回さない。** 決定的な検証を先に払う。
- **PR をマージしない。** マージの判断と操作はユーザーの領分（`CLAUDE.md`）。

## このリポジトリ固有の足場

- **品質ゲート**は project-review と共有:

  ```sh
  bash .claude/skills/project-review/scripts/gates.sh
  ```

  個別には `pnpm typecheck` / `lint` / `format:check` / `test:coverage` / `build`、加えて `check:shell`・`check:index`・`check:release`・`check:publish`。
- **`pnpm check:shell`** は `.sh` と `.github/workflows/*.yml` の「`$var` の直後に非 ASCII」を検出する（`.claude/` 配下の `.sh` も対象）。日本語メッセージ行で起きやすく、**異常を報告する行が報告せずに死ぬ**ので、シェルを触る変更では必ず回す。
- **pre-commit（lint-staged）は絶対パスを渡す**ので、markdownlint の `ignores`（`.claude` を含む）を迂回する。md を触る変更の検証は、この起動の形で再現する（`lint-staged.config.mjs` を読むこと）。
- **bash は macOS 既定の 3.2**。連想配列 `declare -A` は使えない。
- **md のリンクは参照スタイル**（`MD054`）。commitlint は件名の先頭大文字を弾く。
