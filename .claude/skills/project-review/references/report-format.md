# レポート様式（findings register + per-run snapshot）

レビュー結果は 2 種類のファイルに残す。`docs/live-verification.md` と同じ「**エントリは消さず、状態と処置を更新する**」運用を踏襲する。

```text
docs/reviews/
├── README.md            # 運用の説明（初回のみ生成）
├── findings.md          # 指摘台帳の【索引】（全 run 横断・行は消さない）
├── rv/
│   └── NNNN-kebab-title.md   # 指摘 1 件 = 1 ファイル（本体・ID 不変・消さない）
└── YYYY-MM-DD-NN.md     # その run のスナップショット（NN=その日の連番・2 桁ゼロ埋め・同日も追記せず別ファイル）
```

---

## 1. 指摘台帳（索引 `findings.md` ＋ 本体 `rv/*.md`）

全レビューを横断する指摘の単一の正典。**ID は採番したら不変**。**確定してもファイルは削除せず**、
「状態」と「処置」を更新する（`live-verification.md` の LV と同じ思想）。

**1 件 1 ファイル**にしている理由（[ADR-0052][adr52]）: 1 件あたりの記述が厚くなる運用なので、
単一ファイルだと「1 件を読むのに全体を読む」構造になる。分割すれば必要な 1 件だけ開けばよく、
更新の diff も 1 ファイルに閉じる。

### 本体 `docs/reviews/rv/NNNN-kebab-title.md`

`NNNN` は RV-N の **4 桁ゼロ埋め**（ADR と同じ）。**メタは箇条書き・本文は見出し**。

```markdown
# RV-23 🔴 Candidate の静的カタログが標準項目 4 件を欠く

- 重要度: 🔴 ／ 観点: API 忠実性 / 型安全
- 状態: open

## 概要

（1〜2 文で defect を述べる）

## 根拠

`file:line` と正典（`docs/reference/` / ADR / PRD）の該当箇所を**対にして**書く。
実測したなら入力と結果も。

## 影響

**なぜその重要度なのか**。放置すると誰が何に困るか、いつ発火するか（今すぐ / latent）。

## 検出経緯

（任意）どの作業中に・何を突き合わせて気づいたか。

## 推奨

処置の選択肢。挙動変更を伴うなら「要 ADR」と明記する。

## 処置

未着手なら `—`。確定したら何をしたかを書く。

## 検証

（任意・`fixed` なら実質必須）直ったとどう確かめたか。どのテストが何を pin しているか。

<!-- 参照定義は末尾。rv/ は docs/reviews/ より 1 段深いので ../../ 起点 -->

[adr19]: ../../adr/0019-static-resource-types.md
```

**雛形 `docs/reviews/rv/0000-template.md` をコピーして使う**（`0000` は検査の対象外）。

**節の役割**（7 節・うち `検出経緯` と `検証` は任意）:

| 節       | 役割                                                                     |
| -------- | ------------------------------------------------------------------------ |
| 概要     | 何が壊れているか                                                         |
| 根拠     | コードと正典を対にした証拠                                               |
| **影響** | **なぜその重要度なのか**。ここが薄いと後から重要度の妥当性を検証できない |
| 検出経緯 | どう気づいたか（次に同じ穴を探す手がかり）                               |
| 推奨     | 処置の選択肢。要 ADR かどうか                                            |
| 処置     | 何をしたか                                                               |
| **検証** | **「直った」と言い切れる根拠**。`fixed` にするなら必須                   |

**メタ行は機械可読な書式を崩さない**（`- 重要度: 🔴 ／ 観点: …` と `- 状態: …`）。
`pnpm check:index` がこれを読んで索引と突き合わせる。

### 索引 `docs/reviews/findings.md`

一覧テーブルだけを持ち、**状態・重要度・観点は各ファイルの写し**。列は
`ID / 重要度 / 観点 / 状態 / 概要` の順（この並びを検査が前提にしている）。

```markdown
| ID          | 重要度 | 観点       | 状態 | 概要                     |
| ----------- | ------ | ---------- | ---- | ------------------------ |
| [RV-1][rv1] | 🔴     | API 忠実性 | open | 一行で分かる要約         |

[rv1]: rv/0001-read-field-default-missing.md
```

### 採番・更新ルール

- ID は `RV-1` から連番。**新規指摘のみ次番号を採る**。既存指摘の再掲では新 ID を作らない。
- **新規指摘は本体を新設し、索引にも 1 行足す**。索引に行が無い／実ファイルが無いと検査が落ちる。
- 各 run で**既存の open エントリを再評価**する（索引で `open` の行だけ開けばよい）:
  - 解消されていれば `状態` を `fixed` にし、`処置` に「何をしたか」を記入。
  - 仕様として許容と判断したら `wontfix`、契約環境待ち等で保留なら `deferred`（理由を処置欄に）。
  - まだ残っていれば `open` のまま（処置は `—` のまま）。
- **状態を変えたら索引も直す**。`pnpm check:index` を通してから終えること。
- **ファイルは削除しない**。fixed/wontfix も残し、判断の経緯を保つ。
- `live-verification.md` の LV と重なる項目（契約が無いと確定できない仮定）は、台帳に重複させず **LV-N を参照**する（例: 処置欄に「LV-3 参照」）。役割分担: LV=契約待ちの仮定、findings=今この時点の品質指摘。

## 2. `docs/reviews/YYYY-MM-DD-NN.md`（スナップショット）

その run 一回限りの記録。台帳が「現在地」なら、こちらは「その時の写真」。**ファイル名は必ず 2 桁ゼロ埋めの連番付き**（`NN` はその日の run 番号・`01` 始まり）。**同日に複数回 review しても既存ファイルへ追記せず、新しい連番ファイルを切る**（写真は後から書き換えない＝差分・履歴が追える）。同日の前 run があれば相互リンクする。

### 様式

```markdown
# プロジェクトレビュー YYYY-MM-DD

- 対象: @joymerrevent/porters-connect
- ブランチ / HEAD: <branch> @ <short-sha>
- レビュアー: /project-review（Claude Code）

## 品質ゲート

<scripts/gates.sh の出力（表）をそのまま貼る>

## 今回の指摘（サマリ）

ここは**重要度順（問題が先）**に並べる＝優先度ビュー。下の観点別所見は固定順なので、急ぎの判断はこの表で済む。

| ID   | 重要度 | 観点       | 概要 | 状態 |
| ---- | ------ | ---------- | ---- | ---- |
| RV-1 | 🔴     | API 忠実性 | …    | open |

- 新規: RV-3, RV-4
- 状態変化: RV-1 open→fixed（…）

## 観点別所見

固定の 8 観点を**番号順（1→8）で通す**（並べ替えない＝位置が安定し過去回と差分が取りやすい・番号が飛ばない）。優先度は上のサマリ表が示す。**指摘ゼロの観点も記録**する（退行検知）。問題のある見出しには重要度バッジを `— 🔴 RV-N` の形で付ける。

### 1. API 忠実性 — 🔴 RV-1
（root cause、根拠 file:line、docs/reference の該当、推奨を散文で。台帳の要約ではなく「なぜ」を残す）

### 2. アーキテクチャ / ADR 遵守 — 問題なし
…

### 3. コーディング規約（ADR-0013） — 問題なし
### 4. 型安全 / 公開面 — 問題なし
### 5. エラーモデル — 🟡 RV-3
### 6. テスト厳密性 — …
### 7. ドキュメント / DX — …
### 8. リリース準備 — 🟡 RV-4

## 良かった点（strengths）

- 退行監視のため、設計上効いている点も記録する（フェイルセーフの実装箇所など）。

## 次アクション候補

- RV-1 を最優先（実用ブロッカー）。…
```

## 初回 `docs/reviews/README.md`

初回 run でだけ生成する（既にあれば触らない）。

```markdown
# レビュー記録（reviews）

`/project-review` スキルが生成・更新するレビュー成果物です。

- [findings.md][findings] — 指摘台帳の**索引**（ID / 重要度 / 観点 / 状態 / 概要）。
- `rv/NNNN-*.md` — 指摘の**本体**（1 件 1 ファイル・ID 不変・ファイルは消さず処置を更新）。
- `YYYY-MM-DD-NN.md` — 各回のスナップショット。

思想は [docs/live-verification.md][lv] と同じ（処置が追えること＝フェイルセーフ）。
台帳の項目と実コードの対応は `RV-N`（findings）/ `LV-N`（live-verification）で双方向に辿れます。
索引と本体のズレは `pnpm check:index` が検出します（ADR-0052 / ADR-0053）。

[findings]: findings.md
[lv]: ../live-verification.md
```
